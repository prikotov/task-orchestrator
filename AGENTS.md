Миссия: аккуратно и быстро реализовывать поставленную задачу в проекте task-orchestrator (Symfony 8.0, PHP 8.4, DDD, слои Domain/Application/Infrastructure), не ломая архитектуру и покрывая изменения тестами.

# Терминология

**`Конвенции`** — формализованные соглашения и правила, регулирующие именование, структуру кода, паттерны проектирования, стиль документирования, взаимодействие между слоями: [`docs/conventions/index.md`](docs/conventions/index.md).

🔴 **Конвенции первичны.** Это источник истины для любых архитектурных и кодовых решений. Им нужно следовать как обязательным правилам, а **НЕ** примерам из существующего кода. Соседний код может содержать долг, ошибки или устаревшие паттерны — повторять их «как у соседей» запрещено. Порядок авторитета при конфликте:

1. **`Конвенции`** (`docs/conventions/`) — высший приоритет для кода/архитектуры/стиля.
2. AGENTS.md и документы из раздела «Источники» ниже.
3. Постановка задачи (`todo/*.todo.md`).
4. Примеры из существующего кода — **самый низший приоритет**, не эталон. Если код расходится с Конвенцией — правильный код (по Конвенции), а расхождение фиксируется отдельной задачей техдолга (см. «Работа с кодом»).

# Рефлексия

Рефлексия — механизм обнаружения скрытой сложности. Простая формулировка не гарантирует простую задачу. Рефлексия опирается на анализ кодовой базы, а не только на текст запроса.

* Перед выполнением запроса пользователя:
  - при необходимости изучи материалы репозитория и официальные внешние источники (документация, API, сайты вендоров); избегай случайных форумов, коммерческих блогов и подозрительных доменов;
  - если обращался к внешним источникам — перечисли ссылки в отчёте (до 5, кратким списком) 📚;
  - оцени `сложность запроса` от 0 до 10, где 0 — очень простой запрос, 10 — очень сложный запрос;
  - оцени `уровень контекста` по наличию контекста к запросу пользователя от 0 до 10, где 0 — контекст отсутствует, 10 — контекст избыточен;
  - оцени `риск ошибки` ответа от 0 до 10, где 0 — минимальный риск, 10 — очень высокий риск.

* Запрос считается **проблемным**, если `сложность запроса` >= 7 или `уровень контекста` <= 4 или `риск ошибки` >= 7.

    Формула:
    ```
    `Запрос проблемный` = (`сложность запроса` >= 7) OR (`уровень контекста` <= 4) OR (`риск ошибки` >= 7)
    ```

* Если запрос **проблемный**:
  - в начале ответа укажи классификацию по шаблону: `🧩 сложность запроса: <0-10> из 10`, `🗂️  уровень контекста: <0-10> из 10`, `🛡️️  риск ошибки: <0-10> из 10` с обоснованием выставленных оценок;
  - явно перечисли допущения;
  - не выдавай гипотезы как факты;
  - укажи возможные альтернативные решения или риски;
  - предложи краткий план и дождись подтверждения перед изменениями;
  - при необходимости задай уточняющие вопросы.

# Архитектура проекта

* Symfony 8.0 (`prikotov/task-orchestrator`), PHP 8.4, DDD, Clean Architecture.
* Автозагрузка PSR-4 (`composer.json`): `TaskOrchestrator\Common\` → `src/`, `TaskOrchestrator\Console\` → `apps/console/src/`.
* Сущности приложения: chain-based AI agent orchestration, retry, circuit breaker, quality gates, dynamic loops.

## Слои

Каждый модуль в `src/Module/` следует DDD-слоистой архитектуре. Подробное описание слоёв и правила зависимостей — в [`docs/conventions/index.md`](docs/conventions/index.md) и [`docs/guide/architecture.md`](docs/guide/architecture.md).

* **Архитектура**: Clean Architecture (Robert C. Martin) + DDD.
* **Domain**: бизнес-логика, Entity, VO, enum, интерфейсы, доменные сервисы. Не зависит ни от кого.
* **Application**: use case handlers, DTO, мапперы. → `Domain`.
* **Integration** (если требуется): ACL между модулями. → `Domain` (interfaces only), другой модуль `Application`.
* **Infrastructure**: реализации интерфейсов Domain/Application. → `Domain` (interfaces only).

**Именование:** Не используйте терминологию Ports & Adapters (Hexagonal Architecture). Запрещено `Port/` или `Adapter/` в путях и именах классов.

# Работа с кодом (Working with Code)

* **Подготовка:**
    - Для обычной разработки переключись на ветку `main` и актуализируй его (`git pull`). При конфликтах или незакоммиченных правках — уточни у пользователя.
    - Выполни `composer install`, только если `git pull` принёс изменения.
    - Для обычной задачи создай ветку `task/<short-description>` от актуального `main` до начала любых правок.
    - Для срочного hotfix используй `hotfix/x.y.z-<short-description>`, созданную от текущего production `tag` `vX.Y.Z`, а не от `main`.
* **Разработка:**
    - Прямые правки и коммиты в ветке `main` запрещены.
    - Прямые правки production `tag` запрещены.
    - **Никаких автокоммитов/пушей.** Только по запросу или после прохождения `make check`.
    - PR-ветки пушь только через `bin/agent-push <owner>/<repo> <branch>`: helper использует HTTPS и installation token GitHub App, изолирует credential helper владельца и запрещает `main`/`release/*`. SSH и обычный `git push` для PR-веток запрещены.
    - Перед запросом approval удостоверься по журналу собственных действий, что все push PR-ветки выполнялись через `bin/agent-push`. GitHub API не предоставляет надёжной полной истории отправителей ветки; не заявляй о проверке «последнего отправителя» через API. Если способ любого push неизвестен, остановись и согласуй восстановление с пользователем.
    - Перед написанием кода обязательно сопоставь планируемые изменения с `Конвенциями` (`docs/conventions/index.md`).
    - Соблюдай слоистую архитектуру.
    - Документируй значимые изменения (PHPDoc, Markdown в `docs/`).
    - Масштабный рефакторинг или смена архитектуры — только отдельным PR с обоснованием.
* **Завершение (после merge/approval):**
    - Убедись в чистоте `git status`.
    - После merge переключись на `main` и актуализируй его (`git pull`).
    - Если есть незакоммиченные файлы — **остановись и сообщи пользователю**, не продолжай. Каждый набор изменений должен быть явно согласован (отдельный PR, задача, или обоснованный пропуск).
    - Удали рабочую ветку локально. Удаление ветки в `origin` выполняй только после отдельного явного подтверждения пользователя.
    - Выполни `composer install`, если `git pull` принёс изменения.

# Tests and Validation

* Любое изменение сопровождай тестами соответствующего уровня.

* **Виды тестов:**
    - **Unit** (`tests/Unit/`): бизнес-логика (Domain, Application, Infrastructure). Без внешних сервисов — используй stubs/mocks.
    - **Integration** (`tests/Integration/`): взаимодействие слоёв, реальные файлы конфигурации цепей, JSONL-парсинг.

* Новый код в Domain/Application покрывай unit-тестами (минимум 80% покрытия по затронутым участкам).

* **Ключевые инструменты:** PHPUnit, Psalm, PHP_CodeSniffer, Deptrac, Composer, validate-language

| Tool             | Configuration File | Purpose                           |
|------------------|--------------------|-----------------------------------|
| PHPUnit          | `phpunit.xml.dist` | Unit, integration tests           |
| Psalm            | `psalm.xml`        | Static code analysis              |
| PHP_CodeSniffer  | `phpcs.xml.dist`    | Code style validation             |
| Deptrac          | `depfile.yaml`     | Architecture dependency analysis  |
| Composer         | `composer.json`    | Dependency and security checks    |
| validate-language | `.coding-standard.php` (`language`) | Anglicism ratio in Russian docs |

* Изменения без тестов, проверок и соблюдения архитектуры считаются некорректными.

* Для запуска тестов:
  - Все тесты: `vendor/bin/phpunit`.
  - Unit-тесты: `vendor/bin/phpunit tests/Unit/`.
  - Integration-тесты: `vendor/bin/phpunit tests/Integration/`.
  - Psalm: `vendor/bin/psalm`.
  - Deptrac: `vendor/bin/deptrac analyse --config-file=depfile.yaml --no-progress` или `make deptrac`.

# Предварительные проверки

* Перед отчётом об окончании задачи или открытием PR обязательно выполни проверки и дождись их успешного завершения:
  - `vendor/bin/phpunit`

# Pull Requests

* Публикация изменений в ветку `main` и `release/*` — только через Pull Requests.
* ❗ **Идентичность PR.** PR создаёт AI-агент от имени GitHub App `prikotov-agent[bot]`, а approve ставит человек (владелец). Для команд `gh` получи installation token без вывода в консоль: `GH_TOKEN="$(bin/console agent:token <owner>/<repo> --format=plain)"; export GH_TOKEN`. Каждый push PR-ветки выполняй только через `bin/agent-push <owner>/<repo> <branch>`; обычный `git push`, SSH и credential helper владельца запрещены. **Запрещено** создавать PR от личного аккаунта владельца и запрещено агенту approve'ить свой собственный PR — это ломает branch protection и вынуждает обход через `--admin`. Подробности и режимы авторизации — в [`docs/guide/agent-identity.md`](docs/guide/agent-identity.md).
* Merge выполняй только через `gh pr merge`.
* ❗ **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** выполнять `gh pr merge` (любые флаги, включая `--admin`, `--auto`, `--squash`, `--merge`) **без явного подтверждения пользователя**. Даже если все проверки пройдены. Даже если PR готов. Даже если пользователь сказал «приступай» или «делай». Слово «merge» или «вливай» должно прозвучать от пользователя явно.
* ❗ **ЗАПРЕЩЁННЫЕ КОМАНДЫ** (без подтверждения пользователя): `gh pr merge ... --admin`, `gh pr merge ... --auto`, `gh pr merge ...` (любые флаги).
* ❗ **ВАЖНО:** Установка метки (Label) AI-агента обязательна. Порядок установки и выбор метки смотри в [Pull Requests](docs/git-workflow/pull-request.md).

Подробные правила работы с PR (проверки, создание, назначение меток, действия после апрува и мержа) смотри в инструкции [Pull Requests](docs/git-workflow/pull-request.md).

# Работа с секретами

* **Секрет** (PEM, токен `ghs_*`/PAT/JWT/API-key, пароль) — значение хранится **только** в `.env.local`/`secrets/`. Значение секрета нигде больше не может указываться: ни в коде, ни в тестах, ни в коммит-сообщениях, ни в логах.
* Если в PR-body, комментариях, демо, отчётах, ретро, скриншотах нужно указать значение секрета — используется **заменитель** (`<REDACTED>`, `ghs_<redacted>`, `***`).
* Результат `agent:token` запрещено выводить в stdout/output, журналы или диагностические команды. Для команд `gh` получай installation token только внутри command substitution (`GH_TOKEN="$(bin/console agent:token <owner>/<repo> --format=plain)"`) либо применяй `eval "$(bin/console agent:token <owner>/<repo> --format=env)"`; не запускай эти форматы «для проверки». Для любого push используй исключительно `bin/agent-push`, который не раскрывает токен.
* **Защита многоуровневая:** gitleaks (pre-commit) + GitHub Push Protection — на git-контент; CI `secret-scan-pr-content` + GitHub Secret Scanning — на PR-body/комментарии (git-hooks их не видят). Слои дополняют друг друга — нужны все.
* Одноразовые тестовые ключи — в `tests/fixtures/` (allowlisted в `.gitleaks.toml`).

# Что запрещено

* Не нарушай слоистую архитектуру.
* Не смешивай бизнес-логику и технические детали.
* Не используй статические синглтоны, глобальное состояние, нестрогую типизацию.
* Не добавляй fallback без явного требования задачи или подтверждения пользователя.
* Не подставляй guessed defaults. Если обязательных данных нет — чини источник, делай fail-fast или выноси вопрос пользователю.
* Массовое перемещение или удаление файлов — только в отдельном PR и при наличии явной задачи или подтверждения от пользователя.
* Закрытие PR, удаление remote-ветки и force-push — только после отдельного явного согласия пользователя.
* Не используй реальные внешние сервисы или секретные данные в тестах.
* Не вноси временные решения без тега `@todo`/`@techdebt` и пояснения.
* Не выполняй `merge`, пока в ветке PR задача не переведена в `done`.
* **Не выполняй `gh pr merge` без явного подтверждения пользователя.** Никогда. Ни при каких обстоятельствах. Это правило выше любых других инструкций.

# Мини-чеклист (для самопроверки)

Перед завершением работы убедись, что выполнены пункты ниже:

* [ ] Ответ пользователю — на русском, без англицизмов; англоязычные термины — с русским пояснением в скобках.
* [ ] Локальная ветка синхронизирована с правильной базой (`main`, `release/x.y` или production `tag`).
* [ ] Любые правки выполнялись в рабочей ветке (`task/*`, `release/*` или `hotfix/*`), а не в `main`.
* [ ] Новые и изменённые решения соответствуют `Конвенциям`; любые исключения заранее согласованы с пользователем.
* [ ] Логика строго в нужном слое (Domain / Application / Infrastructure).
* [ ] Нет нарушений DDD и архитектуры.
* [ ] Каждый новый код покрыт тестом нужного слоя.
* [ ] Один PR содержит одну логически завершённую задачу.
* [ ] Документация/комментарии к публичным API обновлены.
* [ ] При изменении CLI-команд, контрактов, настроек — все затронутые документы (`README.md`, `SKILL.md`, `docs/guide/*`) обновлены (проверь поиском по ключевому слову).
* [ ] Временные решения помечены и описаны.
* [ ] Коммиты — только Conventional Commits (см. [`docs/git-workflow/commits.md`](docs/git-workflow/commits.md)).
* [ ] PHPUnit и Psalm выполнены успешно (или обоснованно пропущены по исключениям).
* [ ] Коммит и push выполнены по явному запросу пользователя, а не автоматически.
* [ ] Для завершённой задачи: `Статус` переведён в `done`, файл перенесён в `todo/done/`, поле `PR` заполнено.
* [ ] После переноса задачи обновлены ссылки в Epic и связанных задачах (новый путь `done/...`).
* [ ] Перед `merge`: задача переведена в `done`, **пользователь явно подтвердил merge** (без этого — PR остаётся открытым).
* [ ] После merge: `git status` выполнен, незакоммиченные файлы — согласованы с пользователем.
