## 1. Постановка проблемы

**`OQ-3` (дорожная карта):** Политика безопасности (`SecurityPolicy`) — единственный сценарий дорожной карты, где разделение статических и динамических стратегий создаёт архитектурную проблему. Сквозная функциональность зависит от обоих поддоменов. Если они в разных модулях → общее ядро разрастается.

**Триггер G4:** Если `SecurityPolicy` потребует раздельных моделей разрешений для статических и динамических стратегий — это сигнал к физическому разделению, а не к общему интерфейсу.

**Ключевой вопрос:** как модуль политики безопасности (`SecurityPolicy`) взаимодействует со статическими и динамическими стратегиями, не нарушая слоистую архитектуру и не раздувая общее ядро?

## 2. Текущая архитектура: точки входа для политики безопасности

На основе анализа текущей кодовой базы `src/Module/ChainDefinition/` выявлены **6 точек**, где политика безопасности (`SecurityPolicy`) должна вмешиваться в процесс выполнения:

### 2.1. Точка 1: обработчик команды — вход в оркестрацию

```
OrchestrateChainCommandHandler::__invoke()
    → chainLoader->load($chainName)
    → resolveStrategy($chain)
    → strategy->execute($chain, $command)
```

**Что можно проверить:** авторизован ли запуск конкретной цепочки для данного окружения/пользователя.

**Одинаково для статических и динамических стратегий:** да — на уровне `ChainDefinitionVo` (имя цепочки, тип, бюджет).

### 2.2. Точка 2: ExecutionStrategy::execute() — начало выполнения

```
StaticExecutionStrategy::execute()  → ExecuteStaticChainService
DynamicExecutionStrategy::execute() → RunDynamicLoopService
```

**Что можно проверить:** разрешения на уровне стратегии (разрешён ли данный тип выполнения в данном окружении).

**Различие:** статические и динамические стратегии имеют разные профили рисков. Динамическая стратегия (маршрутизация фасилитатора во время выполнения) — выше риск непредсказуемых действий. Статическая стратегия (предопределённые шаги) — ниже риск, но контроль качества выполняет команды оболочки.

### 2.3. Точка 3: Выполнение шага (статический путь)

```
RunStaticChainService::executeStep()
    → runAgentService->run(ChainRunRequestVo)
    → qualityGateRunner->run(QualityGateVo)
```

**Что можно проверить:**
- **Шаг агента:** разрешены ли исполнитель (`$step->getRunner()`), инструменты и модель
- **Шаг контроля качества:** разрешена ли команда оболочки (`$step->getCommand()`) — политика выполнения

**Только для статической стратегии:** да, только статические цепочки имеют шаги с предопределёнными исполнителями и контроль качества.

### 2.4. Точка 4: Запуск агента (Agent run; оба пути)

```
RunAgentServiceInterface::run(ChainRunRequestVo)
```

**Что можно проверить:** политику выполнения для исполнителя, запрещённые команды и ограничения для пути.

**Одинаково для статических и динамических стратегий:** оба пути используют `RunAgentServiceInterface` для вызова исполнителя. Имя исполнителя, инструменты, модель — в `ChainRunRequestVo`.

### 2.5. Точка 5: динамический ход (динамический путь)

```
RunDynamicLoopService::execute()
    → agentRunner->run() для фасилитатора/участника
```

**Что можно проверить:** разрешён ли вызов конкретного runner'а для конкретной роли во время выполнения.

**Только для динамической стратегии:** да, маршрутизация происходит во время выполнения — фасилитатор решает, кто говорит. Политика безопасности может ограничивать допустимых участников.

### 2.6. Точка 6: выполнение команд оболочки контроля качества

```
QualityGateRunnerInterface::run(QualityGateVo)
```

**Что можно проверить:** политику выполнения — запрещённые префиксы, обнаружение безопасных команд, ограничения для пути.

**Только для статической стратегии:** контроль качества выполняет команды оболочки. Динамический путь не имеет контроля качества (использует фасилитатора для оценки).

## 3. Оценка: разные ли модели разрешений для статических и динамических стратегий?

### 3.1. Сравнительная таблица

| Аспект | Статический путь | Динамический путь | Общий? |
|--------|-------------|--------------|--------|
| **Авторизация (Authorization)** (может ли цепочка запускаться) | ✅ Имя цепочки + окружение | ✅ Имя цепочки + окружение | **Да** |
| **Политика выполнения (оболочка)** | ✅ Контроль качества и команды агента | ✅ Команды агента | **Частично** (контроль качества — только для статической стратегии) |
| **Ограничения исполнителя** | ✅ исполнитель на уровне шага в `ChainStepVo` | ✅ исполнитель на уровне роли в `RoleConfigVo` | **Да** |
| **Ограничения инструментов** | ✅ инструменты на уровне шага в `ChainStepVo` | ✅ инструменты на уровне роли в `RoleConfigVo` | **Да** |
| **Ограничения модели** | ✅ модель на уровне шага в `ChainStepVo` | ✅ модель на уровне роли в `RoleConfigVo` | **Да** |
| **Разрешения уровня шага** | ✅ Предопределённые шаги | ❌ Маршрутизация во время выполнения | **Нет** |
| **Разрешения уровня роли** | ❌ Шаги не привязаны к участникам | ✅ Участники и фасилитатор | **Нет** |
| **Лимиты итераций** | ✅ Итерации исправления → повтор шагов | ❌ Максимум раундов вместо итераций | **Нет** |

### 3.2. Вывод по G4

**Модель разрешений едина по сути, но различается детализацией:**

- **Общее ядро:** политика выполнения (фильтр правил), ограничения исполнителя, инструмента и модели. Реализуется через одни и те же интерфейсы.
- **Различие в точках применения:** статическая стратегия проверяет разрешения уровня шага, динамическая — уровня роли и хода. Это не две разные модели разрешений, а **два контекста применения одной модели**.

**Вердикт по G4:** Триггер **НЕ срабатывает**. Статические и динамические стратегии используют **одну и ту же** модель разрешений с разной детализацией применения. Общее ядро не разрастается — достаточно двух интерфейсов (`ChainSecurityPolicyInterface` + `ExecPolicyInterface`), применяемых в разных точках (см. секцию 4.3).

## 4. Рекомендация: Decorator и внедрение интерфейсов (а не ACL)

### 4.1. Почему не ACL

ACL (Anti-Corruption Layer) между `SecurityPolicy` и Orchestrator означает:
- `SecurityPolicy` определяет свои интерфейсы
- Orchestrator создаёт реализации совместимости и сопоставление DTO

Это оправдано при интеграции двух **независимых ограниченных контекстов** с разными едиными языками. Но политика безопасности — это **сквозная функциональность**, а не ограниченный контекст с собственной бизнес-логикой. Он не производит данные — он фильтрует и проверяет. ACL здесь — избыточное усложнение.

### 4.2. Почему Decorator

task-orchestrator уже использует **паттерн Decorator** для сквозной функциональности:
- `RetryingAgentRunner` в роли Decorator для повторных попыток
- `CircuitBreakerAgentRunner` в роли Decorator для circuit breaker
- Проверка бюджета через внедрение сервиса

Политика безопасности (`SecurityPolicy`) естественно использует тот же паттерн:

```
                         ExecutionStrategyInterface
                                  │
                    ┌─────────────┼─────────────┐
                    │             │             │
          StaticExecution    DynamicExec    Conditional...
                    │             │
                    └──────┬──────┘
                           │
              SecurityPolicyExecutionStrategyDecorator
              (проверяет разрешения уровня цепочки)
```

```
                       RunAgentServiceInterface
                                  │
              SecurityPolicyRunAgentDecorator
              (проверяет политику выполнения, исполнителя, инструменты и модель)
                    │
              RetryingAgentRunner (существующий)
                    │
              CircuitBreakerAgentRunner (существующий)
                    │
              Конкретный исполнитель
```

### 4.3. Эскиз интерфейсов

Интерфейсы определяются в **Orchestrator Domain** (как интерфейс интеграции), реализуются в **`SecurityPolicy` Infrastructure**:

```php
// src/Module/ChainDefinition/Domain/Service/Security/

/**
 * Проверка политики безопасности перед выполнением цепочки.
 * Порт в Orchestrator Domain, реализация — в `SecurityPolicy` Infrastructure.
 */
`interface` ChainSecurityPolicyInterface
{
    /**
     * Проверяет, авторизован ли запуск цепочки.
     * @throws SecurityPolicyViolationException если цепочка запрещена
     */
    public function checkChainExecution(string $chainName, ChainTypeEnum $type): void;
}

/**
 * Проверка `exec policy` для команды runner'а.
 * Порт в Orchestrator Domain, реализация — в `SecurityPolicy` Infrastructure.
 */
`interface` ExecPolicyInterface
{
    /**
     * Проверяет, разрешена ли команда runner'а.
     * @throws ExecPolicyViolationException если команда запрещена
     */
    public function checkRunnerCommand(string $runnerName, string $task, ?string $tools = null): void;

    /**
     * Проверяет, разрешена ли shell-команда (quality gates).
     * @throws ExecPolicyViolationException если команда запрещена
     */
    public function checkShellCommand(string $command): void;
}
```

### 4.4. Слой размещения

```
src/Module/
├── Orchestrator/
│   └── Domain/Service/Security/        ← Interfaces (ports)
│       ├── ChainSecurityPolicyInterface.php
│       └── ExecPolicyInterface.php
│   └── Infrastructure/Security/        ← Decorators (если нужно)
│       └── SecurityPolicyRunAgentDecorator.php
│
├── `SecurityPolicy`/                     ← Спринт 9: отдельный модуль
│   └── Domain/
│       ├── Policy/                     ← Rules, Permission models
│       │   ├── ExecRule.php
│       │   └── Permission.php
│       └── Service/
│           └── SecurityPolicyService.php
│   └── Infrastructure/
│       └── Orchestrator/               ← Реализация ports Orchestrator'а
│           ├── Chain`SecurityPolicy`.php   (implements ChainSecurityPolicyInterface)
│           └── ExecPolicyCheck.php       (implements ExecPolicyInterface)
```

**Зависимости:**
- `SecurityPolicy` Infrastructure → `Orchestrator` Domain (только интерфейсы) ✅
- `Orchestrator` Domain не зависит от `SecurityPolicy` ✅
- Инверсия зависимостей через интерфейсы в Orchestrator Domain ✅

## 5. Ответ на `OQ-3` Roadmap

> **`OQ-3`:** Модуль политики безопасности (`SecurityPolicy`) — единственный сценарий дорожной карты, где разделение статических и динамических стратегий создаёт проблему.

**Ответ:** Разделение статических и динамических стратегий **НЕ создаёт проблемы** для политики безопасности по трём причинам:

1. **Модель разрешений едина.** Политика выполнения (фильтр правил) и проверки разрешений работают через одни и те же интерфейсы (`ChainSecurityPolicyInterface`, `ExecPolicyInterface`), независимо от типа цепочки. Различие — только в точках применения (на уровне шага для статической стратегии, на уровне роли и хода для динамической), но это реализационная деталь Decorator.

2. **Общее ядро не разрастается.** Интерфейсы размещаются в `Orchestrator/Domain/Service/Security/` — это доменный слой Orchestrator, а не общее ядро. Общее ядро (по ADR-008: имя, бюджет, роли) остаётся неизменным — `SecurityPolicy` не добавляет в него методы.

3. **Сквозная функциональность реализована через Decorator, а не через общие данные.** `SecurityPolicy` не нуждается в доступе к данным, специфичным для стратегии (шагам, промптам). Ему достаточно идентичности цепочки (имя, тип) и информации об исполнителе (имя исполнителя, инструменты, команда) — всё доступно через существующие VO без расширения контрактов.

## 6. Влияние на Integration-слой при разделении статической стратегии (спринт 7)

Если статическая стратегия физически выделяется в отдельный модуль (`src/Module/StaticExecution/`) в спринте 7:

| Аспект | Влияние | Митигация |
|--------|---------|-----------|
| `ChainSecurityPolicyInterface` | Остается в Orchestrator Domain. Модуль StaticExecution зависит от интерфейсов Orchestrator — это уже так (ExecutionStrategyInterface) | 0 изменений |
| `ExecPolicyInterface` | Может потребоваться в модуле StaticExecution для контроля качества | Определить интерфейс в Orchestrator Domain. StaticExecution Infrastructure его реализует. Либо вынести его в отдельные общие интерфейсы Security |
| Decorator для `RunAgentService` | Интеграционный сервис уже проходит через интерфейс Orchestrator Domain | 0 изменений |

**Вывод:** Разделение статической стратегии не влияет на архитектуру политики безопасности, если интерфейсы остаются в Orchestrator Domain. Это согласуется с Integration-паттерном из ADR-007 (граница ACL для VO).

| Паттерн | Источник | Применимость в task-orchestrator |
|---------|----------|----------------------------------|
| **Политика выполнения (правила)** | Codex (.rules-файлы), Claude Code (списки разрешений/запретов) | ✅ Основной паттерн. Декларативные правила: запрещённые префиксы, обнаружение безопасных команд. Реализуется через `ExecPolicyInterface` |

## 8. Резюме для спринта 9

### Архитектурные решения

1. **`SecurityPolicy` — отдельный модуль** (подтверждено мозговым штурмом #2, все четыре участника).
2. **Интерфейсы в Orchestrator Domain**, реализация в `SecurityPolicy` Infrastructure — инверсия зависимостей.
3. **Паттерн Decorator** для применения проверок безопасности — согласован с повторными попытками и circuit breaker.
4. **Общее ядро не расширяется** — `SecurityPolicy` не добавляет методов в `SharedChainDefinitionVo`.

### Что реализовать в спринте 9

| Приоритет | Компонент | Описание |
|-----------|-----------|----------|
| P0 | `ExecPolicyInterface` + реализация | Фильтрация команд на основе правил: запрещённые префиксы, безопасные команды |
| P0 | `ChainSecurityPolicyInterface` + реализация | Авторизация уровня цепочки: может ли цепочка запускаться |
| P1 | SecurityPolicyRunAgentDecorator | Decorator для `RunAgentServiceInterface` — проверка политики выполнения перед запуском агента |
| P1 | SecurityPolicyExecutionStrategyDecorator | Decorator для `ExecutionStrategyInterface` — проверки уровня цепочки |
| P2 | YAML DSL: блок `permissions:` | Декларативные разрешения уровня цепочки в YAML-конфигурации |
| P2 | Файл политики выполнения | Внешний файл с правилами (аналог Codex .rules) |

### Что НЕ реализовать в спринте 9

- Песочница Docker (Q4 R&D)
- Guardian / LLM-ревьюер безопасности (спринт 10+)
- Движок организационных политик (долгосрочная перспектива)
- Разрешения файловой системы на уровне пути (требуют изоляции контейнера)
