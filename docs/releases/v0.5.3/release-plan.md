# План релиза v0.5.3

## Метаданные

- Тег релиза: `v0.5.3`
- База релиза: `main`
- Последний опубликованный тег: `v0.5.2`
- Ответственный: Бэкендер Тони (pi)
- Плановая дата публикации: 2026-09-03

## Состав

- Обновление dev-зависимости `prikotov/coding-standard` до `^0.32.0` (`composer.json`, `composer.lock`): транзитивно `phpstan/phpdoc-parser` 2.3.3 → 2.3.5 (запрос [#378](https://github.com/prikotov/task-orchestrator/pull/378), merge-коммит `db372c8`).
- Новое в `coding-standard` 0.32.0: правило `ReservedLayerSegment` (phpcs-снифф + deptrac-правило) — зарезервированные имена слоёв (`Domain`, `Application`, `Infrastructure`, `Integration`) запрещены как вложенные сегменты namespace; обновлены эталонные deptrac-коллекторы (сегмент модуля `[^\\]+` вместо `.*`). Проектный `depfile.yaml` импортирует эталонный из вендора — подхвачено автоматически, код проекта не менялся.
- Остальные пакеты `prikotov/*` уже на последних версиях (`git-workflow` 0.3.2, `todo-md` 0.0.12).
- Вне состава: любые изменения после подготовительного запроса релиза; обновление сторонних зависимостей (symfony/*, phpunit 13, deptrac 4 и пр.).

## Риски

- Зависимость только в `require-dev`: runtime-код библиотеки и публичные контракты не меняются; для потребителей Composer-установки пакет ничего не меняет.
- `coding-standard` 0.32.0 добавляет ломающее правило `ReservedLayerSegment`: проекты-потребители с вложенными именами слоёв в namespace получат ошибки phpcs/deptrac при обновлении dev-инструментария. В этом проекте нарушений нет (проверено до обновления).
- Миграции отсутствуют; риск окна несовместимости: низкий.
- Обратная совместимость: код, конфигурация, CLI-команды и PHAR-установка не изменены.

## Порядок публикации

1. Убедиться, что подготовительный запрос с артефактами релиза слит в `main` и его обязательные проверки зелёные.
2. Убедиться, что `main` содержит только согласованный состав релиза: запрос #378 и артефакты `v0.5.3`.
3. Выполнить `make check`, `PHAR_EXPECTED_VERSION=dev make phar-smoke`, `make composer-host-smoke` на вершине `main`.
4. Создать тег `v0.5.3` на вершине `main` и отправить его через GitHub App.
5. Дождаться сценария `Release Phar`: он автоматически создаёт GitHub Release и загружает файл `task-orchestrator.phar`.
6. Проверить автоматически созданный GitHub Release; при необходимости обновить заметки через `gh release edit`.
7. Проверить опубликованный PHAR командой `php task-orchestrator.phar list`.

## Проверки перед публикацией

- [ ] Подготовительный запрос слит в `main`; непрерывная интеграция зелёная.
- [ ] `make check` успешно выполнен на вершине `main`.
- [ ] `PHAR_EXPECTED_VERSION=dev make phar-smoke` и `make composer-host-smoke` успешно выполнены до публикации тега.
- [ ] Тег `v0.5.3` отсутствует до публикации.
- [ ] В `main` присутствуют запись `CHANGELOG.md`, план `v0.5.3` и завершённая задача подготовки release PR.

## Проверки после публикации

- [ ] Выпуск GitHub содержит тег `v0.5.3` и `task-orchestrator.phar`.
- [ ] `git describe --tags` на `main` показывает `v0.5.3`.
- [ ] PHAR запускается: `php task-orchestrator.phar list`.
- [ ] Публичные контракты остаются совместимыми (состав релиза не затрагивает код).

## Действия при проблеме после релиза

- Откат неизменяемого тега не используется.
- Стратегия исправления: срочное исправление от тега `v0.5.3` в ветку `hotfix/0.5.4-<short-description>` с последующим запросом на слияние в `main` и выпуском исправления `v0.5.4`.
- Ответственный инженер: Бэкендер Тони (pi).
- Канал коммуникации и фиксации: `todo/` и запрос GitHub.
