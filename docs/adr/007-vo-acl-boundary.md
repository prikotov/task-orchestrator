# ADR-007: VO ACL между `Orchestrator` и `AgentRunner`

| Поле        | Значение                                             |
|-------------|------------------------------------------------------|
| Статус      | Принято                                              |
| Дата        | 2026-04-29                                           |
| Автор       | Архитектор (Гэндальф)                                |
| Участники   | Гэндальф, Локи, Левша, Шерлок                       |
| Источник    | Сессия идей: декомпозиция модуля `Orchestrator`   |

## Контекст

После декомпозиции модуля на `AgentRunner` и `Orchestrator` (ADR-001) на границе модулей образовались 4 пары VO с идентичной или близкой структурой:

| `Orchestrator` VO            | `AgentRunner` VO          | Назначение              |
|------------------------------|---------------------------|-------------------------|
| `ChainRetryPolicyVo`         | `RetryPolicyVo`           | Политика повторов       |
| `ChainRunRequestVo`          | `AgentRunRequestVo`       | Запуск агента           |
| `ChainRunResultVo`           | `AgentResultVo`           | Результат выполнения    |
| `ChainTurnResultVo`          | `AgentTurnResultVo`       | Результат одного хода   |

Маппинг реализован через `AgentDtoMapper` (82 строки) в Integration-слое `Orchestrator`. Покрытие тестами — 265 строк. VO уже начали расходиться: `ChainRunRequestVo` имеет `runnerName` и `withTruncatedContext()`, которых нет в `AgentRunner`.

## Решение

**ACL (Anti-Corruption Layer) принят как осознанное архитектурное решение.** VO остаются в своих модулях, маппинг — через `AgentDtoMapper`.

### Принципы

1. **Каждый модуль владеет своей моделью данных.** `Orchestrator` VO отражают домен оркестрации цепочек, `AgentRunner` VO — домен запуска агентов.
2. **Дивергенция VO ожидаема и нормальна.** По мере развития модулей их модели данных будут расходиться — это следствие правильных границ ограниченных контекстов.
3. **`AgentDtoMapper` = граница ACL.** Любое изменение полей `AgentRunner` VO требует обновления маппера и его тестов, но НЕ затрагивает `Orchestrator` Domain.
4. **Комментарии в коде:** существующие комментарии «дубликат» заменить на `ACL boundary VO` для явной фиксации архитектурного намерения.

### Порог пересмотра решения

Данный ADR пересматривается при выполнении **одного из условий**:

- >3 общих поля добавляются к VO на границе (не считая текущих);
- Появление типизированного ввода/вывода агентов, требующего формализованного контракта между модулями.

## Обоснование

| Критерий                          | ACL (текущее решение)          | Shared Kernel              |
|-----------------------------------|--------------------------------|----------------------------|
| Область воздействия при изменении VO | 1 модуль + маппер           | 50 файлов (34 исходных + 16 тестов) |
| VO дивергенция                    | Естественная, без ограничений  | Требует согласования       |
| Coupling между модулями           | Только через Integration-слой  | Прямая зависимость от Shared |
| Соответствие DDD                  | ACL — рекомендованный паттерн  | Shared Kernel — только при общей модели |
| Текущий статус                    | Работает, покрыто тестами      | Новый coupling-слой без потребителя |

## Последствия

### Положительные

- Модули развиваются независимо: `Orchestrator` добавляет поля (например, `runnerName`, `withTruncatedContext()`) без координации с `AgentRunner`.
- `AgentRunner` можно переиспользовать в других бандлах без эффекта переноса зависимостей от `Orchestrator` VO.
- Тесты маппера (265 строк) уже существуют и валидируют контракт — нет дополнительных затрат.
- Явная маркировка `ACL boundary VO` в коде предотвращает случайное удаление «дубликатов».

### Отрицательные

- Поддержка 4 пар VO и маппера при изменении полей — ручная синхронизация.
- Дополнительный уровень косвенности при каждом вызове `AgentRunner`.

### Риски

- Разрастание маппера при увеличении числа VO-пар. Митигируется: текущий маппер — 82 строки, рост линейный, не предвидится >6 пар.
- Рассинхронизация полей при небрежном рефакторинге. Митигируется: тесты маппера (265 LOC) падают при рассинхронизации.

## Альтернативы

1. **Shared Kernel (`Common\Shared\ValueObject\`):** выделить общие VO в отдельный namespace. Отвергнуто по результатам brainstorm-сессии:
   - **Область воздействия:** 50 уникальных файлов (Локи, раунд 14) при нулевой выгоде — VO уже разошлись.
   - **Связанность через общую зависимость:** замена связанности через дублирование на связанность через общую зависимость без реального потребителя.
   - **Несоответствие текущей модели:** ограниченный контекст один, но модели данных модулей расходятся. Shared Kernel оправдан при общей модели, которой здесь нет.

2. **Прямое использование `AgentRunner` VO в `Orchestrator` Domain:** устранить маппинг, использовать `AgentRunner` VO напрямую. Отвергнуто — нарушает границу DDD: `Orchestrator` Domain получает зависимость от `AgentRunner` Domain, что противоречит ADR-001 (Integration-слой как единственная точка связи).
