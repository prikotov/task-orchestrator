# ADR-008: Контракт общего ядра (Shared Kernel)

| Поле        | Значение                                             |
|-------------|------------------------------------------------------|
| Статус      | Принято                                              |
| Дата        | 2026-04-29                                           |
| Автор       | Архитектор (Гэндальф)                                |
| Участники   | Гэндальф, Локи, Левша, Шерлок                       |
| Источник    | Сессия мозгового штурма: декомпозиция модуля Orchestrator |

## Контекст

Модуль Orchestrator содержит два де-факто ограниченных контекста (bounded context): цепочки Static и Dynamic. Между ними нет импортов в Domain-слое. `ChainDefinitionVo` (20 параметров, закрытый конструктор, именованные конструкторы) — единая точка входа для обоих контекстов, но при этом:
- Специфичные для Static данные (шаги, конфигурация промптов) и специфичные для Dynamic данные (агент, политика повторов, бюджет) смешаны в одном VO.
- ExecutionStrategy (ADR-006) требует доступа к общим данным (имя, бюджет, роли), но не к данным, специфичным для стратегии.
- Сценарии развития (ветвление по условиям, параллельное выполнение) добавляют новые типы данных, специфичных для цепочки.

Текущий `ChainDefinitionVo` с именованными конструкторами (`createFromSteps()`, `createFromDynamic()`) обеспечивает типобезопасность, но не формализует контракт между ограниченными контекстами.

## Решение

**Общее ядро (Shared Kernel) = идентичность цепочки (имя, бюджет, роли). Специфичные для стратегии данные НЕ входят.**

Формальный контракт определяется через `ChainDefinitionInterface` при реализации P4 (расщепление `ChainDefinitionVo`):

```php
interface ChainDefinitionInterface
{
    public function getName(): string;
    public function getBudget(): BudgetVo;
    public function getRoleConfig(): ?RoleConfigVo;
}
```

### Расширение через дочерние интерфейсы

Новые стратегии добавляют данные через дочерние интерфейсы, не изменяя общее ядро:

```php
interface StaticChainDefinitionInterface extends ChainDefinitionInterface
{
    public function getSteps(): list<ChainStepVo>;
    public function getPromptConfiguration(): PromptConfigurationVo;
}

interface DynamicChainDefinitionInterface extends ChainDefinitionInterface
{
    public function getAgentName(): string;
    public function getRetryPolicy(): ChainRetryPolicyVo;
    public function getMaxTurns(): int;
}

// Будущие стратегии:
// interface ConditionalChainDefinitionInterface extends ChainDefinitionInterface { ... }
// interface ParallelChainDefinitionInterface extends ChainDefinitionInterface { ... }
```

### Принцип OCP для расширения

- **Добавление** новой стратегии = новый дочерний интерфейс + новая реализация `ExecutionStrategy`. Нулевые изменения в существующих интерфейсах.
- **Модификация** общего ядра (добавление метода в `ChainDefinitionInterface`) — только при появлении поля, общего для ВСЕХ стратегий. Это событие требует нового ADR.

### Триггер для P4

P4 (расщепление `ChainDefinitionVo` и формализация общего ядра) реализуется **до** ExecutionStrategy (задачи #7–9 из плана действий сессии мозгового штурма). Это обеспечивает:
1. Типизированный контракт для `ExecutionStrategyInterface::supports(ChainDefinitionVo $chain)`.
2. Явные границы ограниченных контекстов Static и Dynamic.
3. Возможность физического разделения модулей при появлении бизнес-драйвера (решение 9 сессии мозгового штурма).

## Обоснование

| Критерий                            | Текущее состояние                 | После контракта общего ядра          |
|-------------------------------------|-----------------------------------|--------------------------------------|
| Формализация границ контекстов      | Неявная (именованные конструкторы) | Явная (интерфейсы + дочерние интерфейсы) |
| Расширение новой стратегией         | Редактирование ChainDefinitionVo  | Новый sub-интерфейс, 0 изменений    |
| Связанность Static и Dynamic        | Один VO на 20 параметров          | Только 3 общих метода               |
| Типобезопасность в ExecutionStrategy| `instanceof` + `isDynamic()`      | `supports(ChainDefinitionInterface)` |
| Физическое разделение модулей       | Невозможно без VO-рефакторинга    | Возможно: общее ядро = контракт    |

## Последствия

### Положительные

- **Формализованный контракт** между ограниченными контекстами Static и Dynamic — 3 метода вместо 20 параметров.
- **OCP-совместимое расширение:** ветвление по условиям, параллельное выполнение, субагенты добавляются через дочерние интерфейсы без изменения `ChainDefinitionInterface`.
- **Предпосылка физического разделения** модулей: после P4 Static и Dynamic можно переносить в отдельные пространства имён и модули при появлении бизнес-драйвера.
- **Чистая типизация в ExecutionStrategy:** `supports()` работает с `ChainDefinitionInterface`, а не с 20-параметровым VO.

### Отрицательные

- P4 — нетривиальная задача: расщепление `ChainDefinitionVo` затрагивает всех потребителей (оценочно 20+ файлов).
- До реализации P4 контракт остаётся неявным (именованные конструкторы), что не формализует архитектурную дисциплину в коде.

### Риски

- **Чрезмерное дробление:** при проектировании дочерних интерфейсов можно ошибочно отнести общее поле к специфичным для стратегии. Митигируется: в дочерний интерфейс попадают только поля, которые не нужны другим стратегиям.
- **Политика безопасности как сквозная задача:** будущий модуль Security Policy может потребовать доступа к данным обеих стратегий. Общее ядро при этом разрастается. Это открытый вопрос (владелец: Локи, задача #14 из плана действий).

## Альтернативы

1. **Общее ядро = все данные ChainDefinitionVo:** формальный контракт включает все 20 параметров. Отвергнуто: специфичные для стратегии данные (шаги, политика повторов) не являются общими между контекстами и будут загрязнять контракт.

2. **ISP-рефакторинг (Interface Segregation) без общего ядра:** расщепить ChainDefinitionVo на интерфейсы по ISP, но не выделять общий корневой интерфейс. Отвергнуто — при добавлении новой стратегии нет гарантии, что «общие» методы действительно общие; формальный корневой интерфейс обеспечивает дисциплину.

3. **Не формализовать контракт до необходимости:** оставить `ChainDefinitionVo` как есть, не создавать интерфейсы. Отвергнуто — ExecutionStrategy (ADR-006) требует типизированного входа, а сценарии развития добавляют как минимум 2 новых типа цепочек. Без формального контракта `supports()` превращается в обходную проверку типа.
