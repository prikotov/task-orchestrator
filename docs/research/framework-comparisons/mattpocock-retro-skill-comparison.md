## 1. Обзор `/retro`

`/retro` — скилл ретроспективы **кодинг-сессии** из набора Matt Pocock Skills. Ключевая идея: **ретроспектива меняет окружение агента, а не код** («It changes the environment, not the code»). Навык читает запись самой сессии (по умолчанию текущей, либо из логов сессий на диске), находит моменты, где агент буксовал, и выдаёт список кандидатов на исправление по убыванию серьёзности. Ничего не применяет сам — только предложения, пока человек не выберет кандидат.

Вызывается только вручную (фронтма́ттер `disable-model-invocation: true`, команда `/retro`). Документация прямо рекомендует запускать его после «тяжёлой» сессии: агент долго что-то искал, совершил ошибку, которую могла поймать машина, или не имел доступа к нужной информации. «Гладкая сессия нечему учит» — на ровных сессиях навык в основном порождает правила, которые никому не нужны.

### 1.1. Категории находок: симптом → тип фикса

Категория находки сама определяет, куда попадает исправление:

| Симптом в сессии | Фикс |
| --- | --- |
| Агент долго искал файл или факт | **Navigation pointer** (навигационный указатель) из файла, который агент и так читает |
| Ошибку мог поймать инструмент | **Automated check** (автоматическая проверка): lint-правило, тип, тест, pre-commit hook, CI-задача |
| Ревьюер пропустил ошибку уровня «суждения» | Правило в `CODING_STANDARDS.md` для агента-ревьюера |
| `AGENTS.md` / `CLAUDE.md` разросся | Вынести стиринг (управляющие инструкции) в стандарты или проверки |
| Дорогой вызов инструмента | Упростить или заменить инструмент |
| Строки в стиринг-файлах, которые ничего не меняют | Удалить **no-ops** (пустые инструкции) |
| Агенту была недоступна нужная информация | Расширить доступ: tee логов dev-сервера, read-only доступ к сервисам |

### 1.2. Три принципа

1. **Check over prose** («проверка вместо прозы»). Механическое нарушение (запрещённый API, форма импорта, правило расположения файлов) — всегда детерминированная проверка: «проверка может упасть, а предложение в файле стандартов — нет». Проза — только для нарушений, требующих суждения (cross-file consistency, «соответствует окружающему стилю»). Перед созданием новой проверки навык читает собственные check-команды репозитория (`package.json` scripts, CI): **уже существующая, но не подключённая или молча сломанная проверка — сама по себе находка**, а не повод изобретать новую. Отсутствие guardrail вообще (нет pre-commit hook и нет CI-задачи с lint/typecheck/test) — тоже находка.
2. **Стандарты принадлежат ревьюеру, а не исполнителю.** У агента-реализатора максимальное давление на контекст (исследование, код, отладка); ревьюер получает diff и ничего больше. Новое правило кладётся туда, где есть место его применять. Отсюда же ответ на частый вопрос «агент повторяет ошибку — добавить строку в `CLAUDE.md`?»: почти всегда нет; строка в стиринге грузится в каждый контекст, разбавляет остальное и дрейфует вместе с кодом.
3. **Трассировка к моментам сессии.** Каждый кандидат обязан указывать на конкретный момент сессии, а не на дженерик-практику. Это защита от главного риска: «агент забывает боры середины сессии и выдумывает дженерик-советы, чтобы заполнить категории».

### 1.3. Самодокументированные слабые места

Документация навыка честно фиксирует ограничения:

- **Видит одну сессию** — не может понять, что предложенное ранее правило зашумело или пережило свою ошибку; обрезка проверок остаётся на человеке.
- **Не является системой памяти** — не хранит, что произошло, а меняет окружение, чтобы это не повторилось.
- **Порядок серьёзности — черновик**: тихая дорогая ошибка может оказаться ниже громкой дешёвой.

Навык стоит последним в основной цепочке: `grill-with-docs → to-spec → to-tickets → implement → code-review → retro`.

## 2. Обзор нашего `retrospective`

Навык [`retrospective`](../../agents/skills/retrospective/SKILL.md) — организационная ретроспектива **команды ролей** после завершённой работы (задача/эпик/PR). Цикл из 8 шагов: сбор контекста → анализ ролей (плюсы/минусы/предложения) → анализ процесса (5 направлений) → проверка на повторы → до трёх предложений с приоритизацией 🔴🟡🟢 → файл по шаблону в `docs/agents/team-retro/` → обновление реестра [`RETRO-ROADMAP.md`](../../agents/team-retro/RETRO-ROADMAP.md) → отчёт пользователю.

Ключевые особенности: память между ретро (реестр со счётчиками, статусами `watch/escalated/resolved`, порогом эскалации «3 упоминания → задача»), целенаправленный сбор позитивных практик («Что прошло хорошо»: приём → польза → когда повторять), запрет выдуманных улучшений («Без замечаний»/«Без предложений» допустимы), привязка находок к задачам/файлам.

## 3. Сравнение

### 3.1. По осям

| Ось | `/retro` (Matt Pocock) | `retrospective` (наш) |
| --- | --- | --- |
| **Объект анализа** | Сессия (транскрипт: вызовы инструментов, буксования) | Задача/эпик/PR (артефакты работы) |
| **Вызов** | Только вручную (`/retro`) | Автоматически при явной приёмке результата |
| **Когда запускать** | Только после тяжёлой сессии | Всегда после приёмки, даже чистой — собираем хорошие практики |
| **Кто «виноват»** | Окружение («что в репо позволило этому случиться») | Роли и процесс (с оговоркой «где не хватило инструкций») |
| **Что меняет** | Guardrails: проверки, указатели, стандарты ревьюера, обрезка стиринга, доступ к информации | Инструкции: файлы ролей, `AGENTS.md`, конвенции; задачи через эскалацию реестра |
| **Отношение к прозе-правилам** | Последнее средство; механика — всегда проверкой | Штатный путь (пример: запрет стековых PR лёг прозой в `AGENTS.md`) |
| **Память между ретро** | Нет — видит одну сессию | Реестр `RETRO-ROADMAP.md`: счётчики, повторы, пороги, эскалация |
| **Позитивные практики** | Не собирает (только дефекты среды) | Обязательный раздел «Что прошло хорошо» |
| **Применение изменений** | Только предложения; выбор за человеком | Может внедрить сразу (статус «внедрено» этим же PR) |
| **Источник фактов** | Лог сессии; трассировка к конкретным моментам | Артефакты задачи: постановка, PR, результаты проверок |
| **Категории находок** | 7 категорий с таблицей «симптом → тип фикса» | 5 направлений анализа без маппинга на тип фикса |

### 3.2. Философия

`/retro` — инженерия среды: **«вините окружение, а не агента»**. Если ошибка механическая, её должна ловить машина; послушание модели — ненадёжный механизм. Наш `retrospective` — организационное обучение: память о повторах, эскалация в задачи, роли, закрепление практик. Подходы комплементарны: `/retro` оптимизирует **превенцию через детерминированные ограждения**, наш — **накопление и трассируемость командного опыта**.

Сильные стороны зеркальны: слабое место `/retro` (нет памяти между сессиями — признано самим автором) — наша сильная сторона (реестр); наше слабое место (правило-проза там, где могла бы быть проверка) — сильная сторона `/retro`.

## 4. Выводы

### 4.1. Что `/retro` делает лучше — заимствовать

1. **Дисциплина «check over prose»** — классификация нарушения до выбора фикса: механическое → детерминированная проверка (custom-сниффер PHP_CodeSniffer, слой Deptrac, CI-задача, pre-commit), проза — только для суждений. Арсенал уже есть (phpcs, Psalm, Deptrac, gitleaks, `make check`) — нет шага «прежде чем писать правило, проверь, нельзя ли проверку».
2. **Аудит подключённости существующих проверок** — «уже существующая, но не подключённая или молча сломанная проверка — сама находка»; отсутствие guardrail — тоже находка.
3. **Охота на no-ops и разросшийся стиринг** — направление «инструкции, которые не меняют поведение агента»; большой `AGENTS.md` — источник находок.
4. **Сессионный вход** — ниша «агент буксовал прямо сейчас, задача ещё не завершена» у нас не закрыта: полная ретро ради одной сессии тяжеловата.
5. **Трассировка к моментам сессии** — логи сессии и `audit.jsonl` как первоисточник; защита от дрейфа находок в сторону обобщений.

### 4.2. Что наш навык делает лучше — сохранить

1. **Реестр повторов** (`RETRO-ROADMAP.md`) со счётчиками и порогами эскалации — ровно то, что `/retro` признаёт своим слабейшим местом.
2. **Проверка на повторы** как отдельный шаг с приоритизацией 🔴 повторяющихся проблем.
3. **Сбор позитивных практик** («Что прошло хорошо») — у `/retro` ретро чисто дефектная.
4. **Фиксированное место хранения** находок (архив ретро + реестр) — у `/retro` кандидаты живут только в диалоге, пока пользователь не выберет.
5. **Статусы предложений** (`внедрено` / `TODO` / `требует обсуждения`) и связь с задачами.

### 4.3. Синтез

Вердикт: **apply (частично)** — заимствовать пять практик из раздела 4.1 в навык `retrospective`, сохранив реестр, шаблон и цикл как есть. Стратегия та же, что в [сравнении brainstorming-skill](superpowers-brainstorming-comparison.md): **borrow principles, not implementation** — принципы переносятся в наши документы, без копирования чужой структуры файлов (`CODING_STANDARDS.md`, `/retro`-команда). Пилот для закрепления дисциплины №1: перевести одно существующее прозаическое правило (запрет стековых PR из [ретро 2026-09-24](../../agents/team-retro/2026-09-24_10-39-stacked-prs-incident.md)) в падающую CI-проверку.
