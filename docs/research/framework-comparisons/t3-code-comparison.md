## 0. Ограничения исследования

Исследование проведено по README, пользовательской и внутренней документации, лендингу и открытым исходникам на зафиксированном commit. T3 Code не устанавливался и не запускался; заявления о пользовательском поведении не являются результатом собственного испытания.

Продукт помечен авторами как ранний, а desktop-приложение — как Alpha. Маркетинговое утверждение «каждый поток пишет в свою ветку» уточняется пользовательской документацией: отдельные branch (ветка) и worktree (изолированное рабочее дерево Git) создаются при выбранном режиме **New worktree**, тогда как поток может работать и в основном checkout (рабочей копии). Ниже это рассматривается как управляемая изоляция потока, а не как безусловная гарантия.

## 1. Краткий вывод

T3 Code — не новый исполнитель агента, а **мета-оркестратор**: сервер владеет рабочей областью, Git, учётными данными и процессами сторонних агент-харнесов, а web-, desktop- и mobile-клиенты управляют ими через аутентифицированный RPC-контракт (контракт удалённых вызовов). Различия провайдеров скрыты за `ProviderAdapter`; оркестрация работает с нормализованными командами, событиями, разрешениями и возможностями.

**Итоговый вердикт:** выборочный `apply` (применить) для нормализованной границы харнеса и модели использования существующих подписок; `study` (изучить) для изоляции параллельных исполнений, долговечных потоков, переключения исполнителя, удалённого управления и режимов разрешений; `skip` (не переносить) для «одной кнопки PR» как части текущего движка без пользовательского интерфейса.

Главная архитектурная находка — не интерфейс приложения, а разделение:

1. долговечный поток и его история принадлежат оркестратору;
2. провайдерская сессия — заменяемый технический ресурс;
3. намерение сначала фиксируется событием и квитанцией команды, затем reactor (обработчик последствий) выполняет внешний эффект;
4. возможность продолжения или смены модели проверяется явно, а не предполагается.

## 3. Критерий 1 — тезис и решаемая проблема

T3 Code решает четыре связанные проблемы:

1. **Фрагментация харнесов.** Claude Code, Codex и другие инструменты имеют разные протоколы запуска, события, сессии, модели разрешений и способы продолжения диалога.
2. **Привязка исполнения к рабочей машине.** Код, Git и авторизация должны оставаться в окружении, которому принадлежит рабочая область; удалённый клиент не подменяет файловую систему и учётные данные.
3. **Связь разговора с изменениями кода.** Поток должен быть связан с branch/worktree, diff (разницей), контрольными точками и одним или несколькими PR (запросами на слияние).
4. **Долговечность управления.** Выход процесса провайдера, переподключение клиента или независимое обновление клиента и сервера не должны уничтожать историю и состояние намерений.

Для task-orchestrator первый пункт совпадает с задачей `AgentRunner`; третий — с операционным процессом Git, но пока не с доменной моделью; четвёртый частично закрыт только сессиями `DynamicLoop`.

## 4. Критерий 2 — ключевые концепции T3 Code

### 4.1. Нормализованная граница харнеса

`apps/server/src/provider/Services/ProviderAdapter.ts` задаёт единый контракт: старт/остановка сессии, отправка и прерывание хода, ответы на запрос разрешения и структурированный вопрос, чтение и откат потока, поток канонических событий и матрица возможностей. Провайдерские особенности остаются внутри реализаций.

Это шире нашего `AgentRunnerInterface`: task-orchestrator нормализует однократный `run()` и итог `AgentResultVo`, но не жизненный цикл сессии, поток событий, запросы подтверждений, откат и возможности продолжения.

### 4.2. Долговечный поток поверх провайдерской сессии

В терминах T3 Code thread (поток) — долговечная история задачи, сохраняющаяся после завершения процесса провайдера; session (сессия) — подключённый к потоку runtime (исполняемая среда) провайдера. Это позволяет остановить и возобновить процесс, не удаляя продуктовую историю.

Контракт `packages/contracts/src/orchestration.ts` хранит модель, режим разрешений, branch и worktree вместе с потоком. Серверные события являются источником истины, а клиент подписывается только на нужное состояние и не оплачивает передачей всю историю всех потоков.

### 4.3. Фиксация намерения до побочного эффекта

`OrchestrationEngine.ts` сериализует команды. Чистый `decider.ts` формирует события без файловых и провайдерских операций. События, проекция и квитанция принятой команды фиксируются одной транзакцией; затем обработчики последствий выполняют внешние действия и возвращают результат новыми командами.

Подтверждение команды означает «намерение зафиксировано», а не «агент или Git-операция завершены». Квитанции делают повторную отправку команды идемпотентной.

### 4.4. Рабочая область принадлежит серверу

Клиенты управляют окружением через аутентифицированный RPC. Процессы провайдеров, терминалы, Git и файлы остаются на серверной машине. Для удалённой работы доступны прямое сопряжение, T3 Connect, Tailscale HTTPS и управляемый desktop-клиентом SSH.

### 4.5. Контрольные точки без служебных commit

T3 Code хранит checkpoint (контрольную точку) рабочей области в скрытых Git refs (ссылках), не добавляя commit в пользовательскую ветку. Откат координирует файловое состояние и разговор провайдера. Если провайдер не умеет откатывать разговор, операция отклоняется **до** изменения файлов.

## 6. Критерий 4 — обработка сбоев

### 6.1. Что делает T3 Code

| Сбой или риск | Механизм T3 Code |
|---|---|
| Повтор одной команды клиента | Квитанция команды и проверка `commandId`; повтор идемпотентен, конфликт с другим агрегатом отклоняется. |
| Падение между намерением и внешним эффектом | Сначала транзакционно сохраняются событие и проекция, затем обработчик последствий выполняет I/O. |
| Поздняя контрольная точка или diff | Завершение хода отделено от завершения последующих работ; поздний результат не увеличивает длительность хода и не показывает провайдера активным. |
| Несовместимый откат разговора | Возможность декларируется провайдером; откат отклоняется до изменения файлов. |
| Смена несовместимого исполнителя | Смена между разными driver (видами интеграции) в начатом потоке запрещена; смена instance (экземпляра учётной записи) разрешена только при совместимой идентичности продолжения. |
| Провайдер не поддерживает смену модели в сессии | Сессия перезапускается или смена отклоняется, если провайдер требует новый поток. |
| Независимые версии клиента и сервера | Возможности согласуются через descriptor (описатель) окружения; старые поля сохраняются для воспроизведения истории. |
| Истечение удалённых учётных данных | Обновление не разрывает здоровое соединение; ошибка обновления относится к конкретному запросу. |
| Временная недоступность T3 Connect | При старте временные ошибки повторяются до десяти минут; постоянные отказы требуют явного восстановления. |
| Небезопасный автоматический `pull` | Только fast-forward при чистой рабочей копии, без untracked-файлов и локальных commit. |
| Частичный сбой составного PR | Нижние успешно обновлённые слои остаются; сбойный слой исправляется перед повтором. |

### 6.2. Сравнение с task-orchestrator

У нас сильнее проработана устойчивость отдельного запуска:

- [`RetryingAgentRunnerService.php`](../../../src/Module/AgentRunner/Infrastructure/Service/RetryingAgentRunnerService.php) — повтор временных ошибок;
- [`CircuitBreakerAgentRunnerService.php`](../../../src/Module/AgentRunner/Infrastructure/Service/CircuitBreakerAgentRunnerService.php) — автоматический размыкатель;
- [`ResolveChainRunnerService.php`](../../../src/Module/ChainExecution/Infrastructure/Service/Agent/ResolveChainRunnerService.php) — резервный исполнитель;
- [`RunStaticChainService.php`](../../../src/Module/ChainExecution/Domain/Service/Static/RunStaticChainService.php) — остановка по ошибке и бюджету;
- [`ChainSessionWriter.php`](../../../src/Module/DynamicLoop/Infrastructure/Service/ChainSessionWriter.php) — сохранение и возобновление динамической сессии.

У T3 Code сильнее обработка сбоев долгоживущего управляющего процесса: идемпотентные команды, отделение намерения от I/O, совместимость сохранённой истории, явные возможности провайдера и согласование разговора с файловым откатом. Перенос event sourcing (хранения состояния через события) целиком преждевременен; сначала нужен отдельный анализ требований к долгим и удалённым запускам.

## 8. Подробный маппинг на модули task-orchestrator

### 8.1. AgentRunner

Что валидировано:

- `AgentRunnerInterface` уже скрывает Pi и Codex за общим контрактом;
- `AgentRunnerRegistryService` выбирает реализацию по имени;
- `PiJsonlParser` и `CodexJsonlParser` преобразуют разные форматы в общий результат;
- retry и Circuit Breaker оборачивают runner независимо от его реализации.

Что подсветил T3 Code:

- контракт результата недостаточен для интерактивного или удалённого управления;
- возможности нельзя выводить из имени runner: нужны явные признаки поддержки смены модели, продолжения, разрешений, вопросов и отката;
- provider instance (экземпляр провайдера) должен быть отличен от driver kind (вида интеграции), если появятся несколько аккаунтов.

### 8.2. ChainDefinition

[`ChainStepVo.php`](../../../src/Module/ChainDefinition/Domain/ValueObject/ChainStepVo.php) уже позволяет выбирать runner и model на шаге, а [`RoleConfigVo.php`](../../../src/Module/ChainDefinition/Domain/ValueObject/RoleConfigVo.php) хранит команду и fallback. Профиль делегирования в `config/chains.yaml` похож на конфигурацию provider instance, но смешивает:

- вид runner;
- бинарный файл и аргументы запуска;
- провайдера и модель;
- режим автономии через флаги;
- конкретную роль.

Не следует немедленно копировать модель T3 Code. При следующем расширении нескольких аккаунтов или разрешений стоит сначала разделить идентичность интеграции, экземпляр учётной записи, выбор модели и политику запуска на уровне контракта.

### 8.3. ChainExecution

[`RunStaticChainService.php`](../../../src/Module/ChainExecution/Domain/Service/Static/RunStaticChainService.php) централизованно ведёт порядок, контекст, бюджет и остановку, а [`ResolveChainRunnerService.php`](../../../src/Module/ChainExecution/Infrastructure/Service/Agent/ResolveChainRunnerService.php) запускает fallback после ошибки.

Смена runner у нас — новый независимый вызов с текстовым контекстом. У T3 Code продолжение связано с совместимостью provider driver, continuation key (ключа продолжения), resume cursor (указателя продолжения) и capability. Поэтому текущий fallback нельзя считать бесшовной сменой харнеса внутри одной нативной сессии.

Для branch-per-thread отсутствует владелец рабочей области. `workingDir` — параметр, но не инвариант эксклюзивности и не жизненный цикл создания/очистки worktree.

### 8.4. DynamicLoop

[`ChainSessionWriter.php`](../../../src/Module/DynamicLoop/Infrastructure/Service/ChainSessionWriter.php) ближе всего к долговечному потоку T3 Code: сохраняет `session.json`, раунды, контекст, состояние `in_progress/interrupted/completed` и поддерживает resume.

Различия:

- состояние ориентировано на один тип динамической цепочки, а не на общий execution;
- нет идемпотентного `commandId` и транзакции «событие + проекция + квитанция»;
- файловая запись раунда и внешний вызов агента не разделены как durable intent (долговечное намерение) и reactor;
- роль и runner следующего хода известны цепочке, но совместимость нативной сессии между ними не моделируется.

### 8.5. GitIdentity и процесс Git

[`ObtainTokenCommandHandler.php`](../../../src/Module/GitIdentity/Application/UseCase/Command/ObtainToken/ObtainTokenCommandHandler.php) решает безопасное получение и кеширование токена GitHub App с восстановлением устаревшего installation id. Это только identity (идентичность), не управление branch/worktree или PR.

T3 Code подтверждает полезность связи «поток → branch/worktree → PR», но его продуктовая кнопка не должна обходить наши ограничения:

- PR-ветка отправляется только через безопасный HTTPS-рецепт GitHub App;
- commit и push выполняются только по явному запросу;
- merge требует отдельного явного подтверждения человека;
- автоматизация не должна считать commit/push/create-PR одной неделимой внешней транзакцией: каждый этап может завершиться частично.

### 8.6. `run-subagent` и профиль делегирования

[`run-subagent/SKILL.md`](../../agents/skills/run-subagent/SKILL.md), его [`watch-subagent.sh`](../../agents/skills/run-subagent/scripts/watch-subagent.sh) и `config/chains.yaml` уже дают практический мета-харнес:

- роль выбирает профиль runner/provider/model/reasoning;
- CLI и env могут явно переопределять профиль;
- Pi и Codex приводятся к общему наблюдаемому запуску;
- есть soft/hard/stall timeout и журналы;
- рабочий процесс использует локальную авторизацию runner.

Пробелы относительно T3 Code: нет долговечного thread id, переключение runner не проверяет совместимость продолжения, режим разрешений выражен сырыми флагами, а параллельные сабагенты не получают отдельный worktree автоматически.

## 11. T3 Code и налог оркестратора

T3 Code платит тот же налог централизованной оркестрации, который описан в [предыдущем исследовании](../orchestration-articles/orchestrator-tax-research.md): он владеет нормализацией шести харнесов, совместимостью сохранённых событий, несколькими клиентами, reconnect (переподключением), Git и безопасностью.

Как продукт уменьшает налог:

1. провайдерские различия локализованы за `ProviderAdapter`;
2. общий RPC-контракт отделяет независимо обновляемые клиент и сервер;
3. подписка отдаёт клиенту состояние выбранного потока, а не всю историю;
4. `decider` не выполняет I/O, обработчики последствий отделены;
5. capability negotiation (согласование возможностей) заменяет предположение о синхронном обновлении;
6. driver и instance разделены, поэтому несколько аккаунтов не делят изменяемое состояние.

Цена не исчезает: сложность переходит в нормализованный контракт, совместимость replay (воспроизведения), матрицу возможностей и обработчики последствий. Это аргумент не против централизованного оркестратора, а за тонкую и строго ограниченную границу интеграции.

## 12. Что уже делаем правильно, что изучить, что не применять

### Уже делаем правильно

- Изолируем конкретный CLI за `AgentRunnerInterface` и реестром.
- Нормализуем JSONL Pi/Codex в общий результат.
- Декларативно выбираем runner/model через `ChainDefinition` и профиль роли.
- Используем локальную авторизацию и подписки харнесов.
- Имеем retry, Circuit Breaker, fallback, timeout, бюджет и аудит.
- Сохраняем состояние и поддерживаем resume для `DynamicLoop`.
- Отделяем GitHub App identity от бизнес-логики цепочек.

### Изучить детально

1. Контракт возможностей runner: смена модели, native resume, вопросы, разрешения, откат.
2. Явные семантики продолжения: `text_handoff`, `native_resume`, `unsupported`.
3. Worktree-per-concurrent-execution с владением, сборкой результата и очисткой.
4. Общий долговечный execution lifecycle (жизненный цикл исполнения) поверх static/dynamic цепочек.
5. Идемпотентность команд и разделение намерения/эффекта для будущего удалённого режима.
6. Нормализованная политика разрешений с project policy ceiling (верхним пределом политики проекта).
7. Модель угроз и граница окружения для удалённого управления.

### Не применять сейчас

- Web/desktop/mobile-клиенты как часть текущего docs-only эпика.
- Единую кнопку, автоматически объединяющую commit, push, PR и тем более merge.
- Event sourcing целиком без подтверждённых требований к удалённым и восстанавливаемым запускам.
- Предположение, что любой harness может продолжить нативную историю другого harness.
- Безусловное правило «один поток — одна ветка»: изоляция нужна конкурентным писателям и достигается worktree, а не именем branch само по себе.

## 14. Итоговый вердикт

T3 Code подтверждает правильность направления task-orchestrator как центральной контрольной поверхности над независимыми runner. Наш текущий контракт хорошо нормализует **завершённый однократный запуск**, но ещё не нормализует **долговечную работу**: сессию, события, разрешения, вопросы, продолжение и владение рабочей областью.

Наиболее полезный следующий шаг — не копировать интерфейс T3 Code, а сделать явными две границы:

1. **возможности и совместимость runner** — что можно продолжить, переключить или откатить;
2. **владение исполнением и рабочей областью** — какой execution владеет каким worktree и состоянием.
