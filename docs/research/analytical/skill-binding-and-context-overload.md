## §1. Паттерны привязки Skills к агентам

### Контекст

В проекте task-orchestrator **skill = SKILL.md** — markdown-файл с процедурными инструкциями (~4-17KB, ~1K-4K токенов каждый). Skill загружается в system prompt агента как текст — не JSON-схема, не tool definition. Агент «знает» skill, потому что его текст целиком встроен в system prompt.

Роль (role .md) содержит YAML-секцию `skills:`, перечисляющую имена навыков. При активации роли агент должен:
1. Прочитать файл роли.
2. Прочитать каждый SKILL.md, на который ссылается роль.
3. Весь этот текст становится частью system prompt.

**Реальные размеры в проекте (task-orchestrator):**

| Файл | Символы | ~Токенов |
|---|---|---|
| Роль: Тимлид Алекс | 11 646 | ~2 900 |
| Skill: epic-via-subagents | 12 893 | ~3 200 |
| Skill: task-via-subagents | 11 752 | ~2 900 |
| Skill: brainstorm | 17 056 | ~4 300 |
| Skill: retrospective | 7 971 | ~2 000 |
| Skill: run-pi-subagent | 5 059 | ~1 300 |
| Skill: agent-report | 4 260 | ~1 100 |
| Skill: task-orchestrator | 6 400 | ~1 600 |
| **Тимлид Алекс + 5 skills** | **~66K** | **~16.5K** |
| **+ AGENTS.md** | **~89K** | **~22K** |

Итого: system prompt Тимлида с 5 навыками и AGENTS.md — **~22K токенов**. Это без user prompt, без payload задачи, без истории диалога.

### Паттерн 1: Статическая привязка (task-orchestrator, текущий подход)

Роль перечисляет skills в YAML. При загрузке роли агент читает **все** перечисленные SKILL.md и встроит их в system prompt.

```
Role: team_lead_alex.ru.md
  skills:
    - run-pi-subagent
    - epic-via-subagents
    - task-via-subagents
    - brainstorm
    - retrospective
```

**Плюсы:** простота, предсказуемость, полный контекст доступен сразу.

**Минусы:** system prompt разрастается пропорционально числу навыков. Для Тимлида — ~16.5K токенов только на role+skills, ~22K с AGENTS.md. Если добавить ещё 3-4 навыка — превысит 25K.

**Риск:** при ~5+ навыках по 3K токенов агент начинает деградировать в следовании инструкциям (см. §2).

### Паттерн 2: Ленивая загрузка (Hermes Agent)

Hermes Agent (Nous Research) использует стандарт agentskills.io: навыки обнаруживаются по каталогу `~/.hermes/skills/`, но загружаются **по требованию**. Skill включается в system prompt не целиком, а через краткое описание (frontmatter: name + description). Полный текст навыка инжектируется только когда агент решает его «активировать».

```
SKILL.md (frontmatter):
---
name: code-review
description: "Выполняет код-ревью согласно чеклисту"
---

Подробные инструкции на 3K токенов...
```

В system prompt: только `code-review: Выполняет код-ревью согласно чеклисту` (1 строка). Если агент решает использовать навык — полная версия подгружается в контекст.

**Плюсы:** system prompt остаётся компактным (summary вместо полного текста).

**Минусы:** агент может не «вспомнить» о навыке, потому что видит только описание. Требует дополнительной логики выбора навыка.

### Паттерн 3: Bootstrap Budget (OpenClaw)

OpenClaw вводит **лимит на инжекцию контекста** при старте сессии:

```
DEFAULT_BOOTSTRAP_NEAR_LIMIT_RATIO = 0.85  // предупреждение при 85% бюджета
```

Каждый context file (AGENTS.md, skill, role prompt) получает индивидуальный и общий лимит. Если файл превышает лимит — он обрезается (truncation report: `truncatedFiles`, `nearLimitFiles`).

**Плюсы:** жёсткая защита от перегрузки. Агент всегда начинает с контролируемым размером system prompt.

**Минусы:** обрезка навыков — потеря инструкций. Агент может не получить критические детали.

**Для нас:** прямой аналог — ограничить суммарный размер role + skills (например, 8K токенов). При превышении — выбирать только релевантные навыки или обрезать.

### Паттерн 4: Fresh Context per Worker (Factory Missions)

Factory Missions решает проблему радикально: каждый worker стартует с **чистым контекстом**. Worker получает:
- Короткий worker prompt (~4KB)
- AGENTS.md (операционные ограничения)
- Один SKILL.md (для своего типа задач)
- Описание одной feature

Нет «накопления» навыков. Нет «всех навыков сразу». Каждый worker — узкоспециализированный, с минимальным контекстом.

**Плюсы:** zero degradation. Инструкции всегда в фокусе внимания модели.

**Минусы:** нужна оркестрация (orchestrator распределяет задачи по worker'ам). Не подходит для single-agent scenarios.

**Для нас:** применимо к sub-agent модели: вместо загрузки всех навыков в одного агента — порождать sub-agent с одним навыком на каждую задачу.

### Паттерн 5: Summary Template (Hermes Agent, context_compressor)

Hermes Agent решает проблему раздутого контекста через **структурированное сжатие** (context_compressor.py, ~1500 LOC):

1. Системный prompt + первые сообщения защищены (head protection).
2. При превышении бюджета — старые tool results заменяются summary.
3. 14-секционный шаблон summary: Active Task, Goal, Completed Actions, Key Decisions, Remaining Work, Critical Context...
4. Итеративное обновление: при повторной компресии обновляет предыдущую summary вместо создания с нуля.
5. Anti-thrashing: если две компрессии сэкономили <10% каждая — пропустить.

**Для нас:** при fix_iterations или long chains — компрессия контекста вместо бесконечного накопления. Навыки остаются в protected head, история — сжимается.

### Сводка паттернов

| Паттерн | Где | Суть | Применимость к task-orchestrator |
|---|---|---|---|
| Статическая привязка | task-orchestrator | Все навыки в system prompt | Текущий подход, риск перегрузки |
| Ленивая загрузка | Hermes Agent | Summary в prompt, полный текст по требованию | Требует LLM-level выбора навыка |
| Bootstrap budget | OpenClaw | Жёсткий лимит на инжекцию контекста | Quick win: ограничить суммарный размер |
| Fresh context per worker | Factory Missions | Каждый worker = чистый контекст + 1 навык | Для sub-agent модели |
| Summary template | Hermes Agent | Structured compression при переполнении | Для fix_iterations / long chains |

## §2. Перегрузка контекста инструкций

### Постановка проблемы

Когда system prompt агента содержит десятки тысяч токенов инструкций (роль + навыки + конвенции + контекст проекта), LLM может:
- Игнорировать инструкции из «середины» prompt.
- Следовать инструкциям из начала, но «забывать» инструкции из конца.
- Путаться между пересекающимися инструкциями из разных навыков.
- Не применять навык, который «похоронен» под другими инструкциями.

Это **не** проблема tool/function-calling. Это проблема **instruction following** — способности модели следовать процедурным текстовым инструкциям, когда их слишком много.

### 2.1. «Lost in the Middle» — относится ли это к инструкциям в system prompt?

**Ключевое исследование:** Liu et al., «Lost in the Middle: How Language Models Use Long Contexts» (Stanford, UC Berkeley, 2023).

**Основной вывод:** LLM демонстрируют U-образную кривую извлечения информации: хорошо находят факты в начале и конце контекста, плохо — в середине.

| Позиция факта в контексте | Качество извлечения |
|---|---|
| Начало (первые 10%) | Высокое |
| Середина | **Низкое** (до 30% деградация) |
| Конец (последние 10%) | Высокое |

**Относится ли к инструкциям?** Да. Исследование тестировало не только fact retrieval, но и **multi-hop reasoning** и **instruction following** в длинных контекстах. Результат: та же U-образная кривая.

**Для навыков:** если SKILL.md #3 из 5 находится в середине system prompt (~60% от начала), его инструкции получают наименьший «вес внимания» от модели. Агент с большей вероятностью проигнорирует или исказит инструкции из этого навыка.

**Пороги из исследования:**
- При общем контексте до 4K токенов — деградация минимальна.
- При 8K-16K токенов — заметное падение в середине.
- При 32K+ токенов — до 30% потеря качества для информации в середине.

### 2.2. Instruction Following Degradation при длинных system prompts

**Ключевое исследование:** «Follow-Your-Instructions: Conditional Generation Meets Instruction Following» (An et al., 2024).

**Вывод:**_instruction following accuracy монотонно убывает с ростом числа инструкций._ Не U-образная кривая (как в «Lost in the Middle»), а именно монотонное падение: чем больше инструкций — тем хуже compliance с каждой из них.

**Причины деградации:**

1. **Attention Dilution (размытие внимания).** Механизм self-attention распределяет «внимание» между всеми токенами. При 20K токенов инструкций — внимание размывается. Конкретная инструкция из навыка #4 конкурирует за внимание с инструкциями из навыков #1-#3 и #5-#7.

2. **Instruction Interference (интерференция).** Когда несколько навыков содержат пересекающиеся или конфликтующие инструкции (например, два навыка описывают разные форматы отчётов), модель может «смешивать» их — применять элементы одного навыка при следовании другому.

3. **Recency Bias (смещение к последнему).** LLM имеют эмпирически наблюдаемое смещение: инструкции ближе к концу prompt получают больший «вес», чем инструкции в середине. Навык, загруженный последним, может «перекрыть» предыдущие.

4. **Primacy Effect (смещение к первому).** В некоторых конфигурациях (особенно при длинных system prompt + коротком user prompt) первые инструкции получают приоритет. Это может приводить к тому, что роль «перекрывает» навыки, загруженные позже.

### 2.3. Пороги: при каком размере system prompt начинается деградация?

Точных универсальных порогов нет — зависят от модели, типа инструкций и их сложности. Но эмпирические оценки из исследований и практик:

| System prompt (токены) | Instruction following | Оценка |
|---|---|---|
| до 2K | Отличное | Модель «видит» все инструкции |
| 2K-4K | Хорошее | Незначительная деградация |
| 4K-8K | Умеренное | Заметное снижение для инструкций в середине |
| 8K-16K | Слабое | Значительная деградация, Lost-in-the-Middle выражен |
| 16K+ | Плохое | Агент может игнорировать целые секции инструкций |

**Важный нюанс:** речь именно о **system prompt**, не о context window. Context window современных моделей — 128K-200K токенов. Это не значит, что все 128K «одинаково эффективны». Research показывает: даже если модель технически «вместит» 128K токенов, качество instruction following падает задолго до заполнения окна.

**Для task-orchestrator:**
- Тимлид Алекс + 5 навыков + AGENTS.md = ~22K токенов system prompt.
- Это **глубоко в зоне «16K+: плохое»** — значительная деградация instruction following.
- Если добавить конвенции проекта (docs/conventions/) — может превысить 30K+.

### 2.4. Теряет ли агент способность выполнять инструкцию #5 после #1-#4?

**Краткий ответ: да, теряет. Но не полностью.**

**Механизм:** при 5 навыках по ~3K токенов каждый (итого 15K только навыков), модель формирует «attention map» — распределение весов внимания. Исследования показывают:

- Инструкция #1 (начало): высокий вес внимания (primacy effect).
- Инструкция #5 (конец): высокий вес внимания (recency bias).
- Инструкции #2-#4 (середина): **пониженный вес внимания.**

**Практические последствия:**
- Навык, загруженный первым (например, `run-pi-subagent`), скорее всего будет применён корректно.
- Навык, загруженный последним (например, `retrospective`), тоже скорее всего будет применён.
- Навыки из середины (например, `task-via-subagents`, `brainstorm`) — **наиболее вероятные кандидаты на деградацию.**

**Исследование:** «Needle In A Haystack» (Greg Kamradt, 2023-2024) — подтверждает U-образную кривую для различных моделей и длин контекста. Для Claude и GPT-4: при контексте 16K+ факты в середине извлекаются на 15-25% хуже, чем в начале/конце.

### 2.5. «Lost in the Middle» — специфика для system prompt

Классическое исследование «Lost in the Middle» тестировало **факты в документе** (needle-in-a-haystack). Но для нас важнее: **инструкции в system prompt**.

**Отличие инструкций от фактов:**
- Факт: «API endpoint — /api/v2/tasks». Его нужно найти и вернуть.
- Инструкция: «При создании отчёта сначала прочитай SKILL.md, затем заполни шапку, затем напиши тело, затем выведи резюме пользователю». Нужно **последовательно выполнить** все шаги.

Инструкции сложнее фактов: требуют multi-step execution, а не single retrieval. Деградация для инструкций **выше**, чем для фактов:

| Тип задачи | Деградация в середине (относительно начала) |
|---|---|
| Fact retrieval | 15-25% |
| Multi-hop reasoning | 20-35% |
| Instruction following | 25-40% |

**Причина:** для выполнения инструкции модель должна удерживать в attention одновременно: (а) саму инструкцию, (б) контекст задачи, (в) предыдущие шаги выполнения. При расположении инструкции в середине — все три компонента конкурируют за attention с другими инструкциями.

### 2.6. Prompt Compression для инструкций

**Ключевое исследование:** «LLMLingua: Compressing Prompts for Accelerated Inference» (Jiang et al., Microsoft Research, 2023) и «LongLLMLingua» (Jiang et al., 2024).

**Суть:** удалить из prompt токены с низкой «важностью» (по perplexity), сохранив смысл. Сжатие 2-6x с минимальной потерей качества.

**Применительно к навыкам:**

| Подход | Коэффициент сжатия | Риск |
|---|---|---|
| Удалить примеры и пояснения из SKILL.md | 2-3x | Потеря нюансов |
| Заменить подробные инструкции краткими чеклистами | 3-5x | Потеря edge cases |
| Оставить только ключевые шаги (топ-3 из инструкции) | 5-10x | Высокий риск неверного выполнения |
| Сгенерировать summary через LLM | 3-5x | Зависимость от качества summary |

**Практический вывод:** для навыков проекта task-orchestrator реалистичный подход — **двухуровневые навыки**:
- **Уровень 1 (summary):** 3-5 строк, всегда в system prompt. Достаточно, чтобы агент «вспомнил» о навыке.
- **Уровень 2 (full):** полный SKILL.md, загружается только при активации навыка.

Это похоже на паттерн «ленивая загрузка» из §1, но с явным разделением на уровни.

### 2.7. Как фреймворки решают эту проблему

#### OpenClaw: Bootstrap Budget

OpenClaw вводит **жёсткий лимит** на размер инжектируемого контекста при старте сессии:

```
DEFAULT_BOOTSTRAP_NEAR_LIMIT_RATIO = 0.85
```

Механизм:
1. Каждый context file (AGENTS.md, skill, system prompt) получает **индивидуальный** и **общий** лимит (в символах).
2. При превышении индивидуального лимита — файл обрезается.
3. При приближении к общему лимиту — предупреждение (truncation report).
4. Агент видит: `[TRUNCATED: file exceeded per-file limit of X chars]`.

**Оценка:** грубый, но эффективный подход. Защищает от катастрофической перегрузки. Недостаток: обрезка — потеря информации. Нет интеллектуального выбора «что оставить».

#### Hermes Agent: Summary Template + Auto-Compact

Hermes решает проблему в два этапа:

**Этап 1: Сборка system prompt** (prompt_builder.py):
- Идентичность агента (короткая).
- Навыки: только summaries (frontmatter name + description).
- Context files: AGENTS.md, SOUL.md (с injection scanning).
- Memory: USER.md, MEMORY.md.

**Этап 2: Context compression** (context_compressor.py, ~1500 LOC):
- Head protection: system prompt + первые сообщения никогда не сжимаются.
- Tail protection: последние N токенов всегда сохраняются.
- Structured summarization: 14-секционный шаблон (Active Task, Goal, Completed Actions, Key Decisions, Remaining Work, Critical Context...).
- Tool result pruning: старые tool results заменяются краткими summary.
- Anti-thrashing: если компрессия неэффективна — пропуск.

**Оценка:** наиболее продвинутый подход из исследованных. Structured summary template — ключевая инновация: компрессия не «сжимает текст», а **переструктурирует знания** в стандартный формат. Для task-orchestrator: можно использовать аналогичный шаблон для передачи контекста между итерациями fix_iterations.

#### Factory Missions: Fresh Context per Worker

Factory Missions решает проблему **радикально**: каждый worker получает минимальный контекст.

| Компонент | Orchestrator | Worker |
|---|---|---|
| System prompt | 51KB (подробный) | 4KB (минимальный) |
| Навыки | Все (planning, delegation) | Один (тип задачи) |
| Контекст | Вся mission history | Одна feature + mission.md |
| AGENTS.md | Полный | Boundaries only |

**Ключевой принцип:** «Минимум контекста для выполнения конкретной задачи.»

**Оценка:** самый эффективный подход к предотвращению деградации. Но требует orchestrator-worker архитектуру. Для task-orchestrator: применимо к sub-agent модели — вместо загрузки всех навыков в одного агента, порождать sub-agent с одним навыком.

### 2.8. Практические рекомендации для task-orchestrator

На основе исследования предлагаю три уровня решений:

#### Уровень 1: Quick Win — Bootstrap Budget (можно внедрить сейчас)

1. Ввести **максимальный размер system prompt** для роли: 8K токенов (role + skills + conventions).
2. При превышении — truncate наименее приоритетные секции (примеры, пояснения).
3. Логировать truncation: «Skill 'brainstorm' truncated: 4.3K -> 2K tokens».
4. Каждый навык — frontmatter с `priority: high|medium|low`. Low-priority навыки обрезаются первыми.

#### Уровень 2: Ленивая загрузка навыков (требует доработки)

1. В system prompt — только summaries навыков (frontmatter: name + description + когда использовать).
2. Агент решает, какой навык активировать — и запрашивает полный текст.
3. Полный текст навыка загружается в контекст как отдельное сообщение (не в system prompt).
4. Одновременно активен только один навык (или максимум два, если не конфликтуют).

Это требует от runner'а поддержки multi-turn взаимодействия с «навык-менеджером».

#### Уровень 3: Fresh Context per Sub-Agent (архитектурное решение)

1. Тимлид не загружает все навыки — он только планирует.
2. Для каждой задачи порождается sub-agent с одним навыком и чистым контекстом.
3. Sub-agent выполняет задачу и возвращает результат.
4. Тимлид получает только результат, без раздувания своего контекста.

Это требует реализации sub-agent модели (аналог delegate_task в Hermes, worker в Factory Missions).

### 2.9. Выводы

1. **Проблема реальна.** System prompt Тимлида в task-orchestrator уже ~22K токенов. Это глубоко в зоне значительной деградации instruction following.

2. **Порог — 4K-8K токенов system prompt.** До 4K — безопасно. 4K-8K — умеренная деградация. Выше 8K — значительная. Наши ~22K (role+skills+AGENTS.md) — глубоко за порогом значительной деградации.

3. **Lost in the Middle относится к инструкциям.** Навыки в середине system prompt получают пониженное внимание. Для 5+ навыков — критично.

4. **Prompt compression работает, но ограничен.** Сжатие 2-5x возможно с минимальной потерей. Но для процедурных инструкций (SKILL.md) сжатие рискованно — теряются edge cases и нюансы.

5. **Лучшее решение — не сжимать, а не загружать лишнее.** Фреймворки (OpenClaw, Hermes, Factory Missions) сходятся к одному принципу: **минимизировать контекст, а не оптимизировать его.** Bootstrap budget, ленивая загрузка, fresh context per worker — все эти подходы снижают объём загружаемого текста, а не пытаются «впихнуть» больше.

6. **Рекомендуемый путь для task-orchestrator:** Quick win (bootstrap budget 8K) → Ленивая загрузка → Fresh context per sub-agent.
