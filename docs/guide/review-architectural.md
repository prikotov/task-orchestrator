# Архитектурное ревью (RV-A)

Архитектурное ревью отвечает на вопрос «соответствует ли решение проекту?». Ответственность — строка `RV-A` [матрицы RACI](../agents/raci-matrix.md); чек-лист ревьювера — в ролях архитекторов ([Гэндальф](../agents/roles/team/system_architect_gandalf.ru.md), [Локи](../agents/roles/team/system_architect_loki.ru.md)). Правила функционального ревью — [функциональное ревью](review-functional.md).

## Гейтинг

RV-A обязателен при `complexity` C2+ или при любом из признаков по фактическому набору изменений:

1. Новый, удаляемый или перемещаемый модуль; смена владельца бизнес-логики.
2. Новые или изменённые зависимости между слоями и модулями.
3. Изменение контракта другого модуля или внешнего потребителя (обработчик Application, DTO, CLI, конфигурация, событие, сохраняемый формат, семантика ошибки).
4. Изменения `Kernel`, модульной регистрации, `config/`, `depfile.yaml`, архитектурно значимых зависимостей `composer.json`.
5. Новый архитектурный паттерн или отступление от Конвенции/ADR.

Запись «RV-A: да/нет» + основание обязательна в задании ревьюверу; отсутствие записи означает, что гейтинг не выполнен. Гейтинг пересматривается по каждой дельте до приёмки; сомнение — в пользу RV-A. C0–C1 без признаков — одно комбинированное ревью по строке RV-F (`RV-A: нет`).

Ослабления проверок качества (exclude-списки, suppress-метки — `@psalm-suppress`, `@phpstan-ignore*`, `@SuppressWarnings(PHPMD.*)`, оператор `@`, рост baseline, смягчение thresholds) допустимы только с техдолг-задачей. Правила подавлений PHPMD — [подавления PHPMD](../conventions/ops/phpmd-suppressions-guidelines.md).

## Дельта метрик качества

`vendor/bin/coding-standard-metrics-review --base=<target>` формирует дельту (CC/WMC, LCOM4/Ca/Ce, покрытие, churn) в `var/metrics-review/`: подсвечивает, где пахнет код и куда смотреть; замечание — по решению ревьювера. Правила интерпретации — [метрики качества](../conventions/ops/quality-metrics.md).

## Порядок, лимиты и апрувы

- Порядок по умолчанию: RV-F → RV-A; обратный порядок — исключение, фиксируемое тимлидом (основной риск задачи архитектурный).
- Лимит «ревью → доработка» — 3 итерации отдельно на каждый трек и QA-петлю; исчерпание — эскалация пользователю. Счётчики сбрасываются только решением пользователя.
- Доработка отменяет апрув другого трека, если дельта затрагивает его область: поведение, контракт, сценарии, безопасность, тесты — RV-F; границы, контракты, паттерны — RV-A. Сомнение — в пользу повторного ревью затронутых пунктов.
- Перед приёмкой апрувы обязательных треков действительны для итогового набора изменений. Носитель записи апрува — файл задачи или описание PR: «трек, дата, diff».
- Консультанты (ячейка `C` строк ревью) подключаются до решения по этапу ревью.
- QA-петля: доработка по замечаниям QA → повторное RV-F по дельте → RV-A по гейтингу → повторный QA.
