# Правила проведения ревью

Правила проведения код-ревью в task-orchestrator: два трека проверки, гейтинг архитектурного ревью, порядок, лимиты и документирование расхождений. Распределение ответственности по этапам ревью — [матрица RACI](../agents/raci-matrix.md) (строки `RV-F`/`RV-A`); чек-листы ревьюверов — в файлах ролей ([Ревьювер Бэка](../agents/roles/team/code_reviewer_backend_puaro.ru.md), [Гэндальф](../agents/roles/team/system_architect_gandalf.ru.md), [Локи](../agents/roles/team/system_architect_loki.ru.md)); смежные конвенции — [метрики качества](../conventions/ops/quality-metrics.md) и [подавления PHPMD](../conventions/ops/phpmd-suppressions-guidelines.md).

## Два трека

- **RV-F — функциональное ревью**: «делает ли код то, что написано в задаче?». Соответствие постановке, прослеживаемость отклонений, безопасность, качество кода и типизация, именование и код-уровневые конвенции, статическая оценка тестов.
- **RV-A — архитектурное ревью**: «соответствует ли решение проекту?». Конвенции, архитектурные правила, границы слоёв и модулей, DDD, согласованность с ADR, дельта метрик качества.

Порядок по умолчанию: сначала RV-F, после его апрува — RV-A. Обратный порядок — исключение, фиксируемое тимлидом (основной риск задачи архитектурный, например `refactor` или новый модуль). Для `docs`/`research` строки ревью не делятся — проводится одно ревью.

## Гейтинг RV-A

RV-A обязателен при `complexity` C2+ или при любом из признаков по фактическому набору изменений:

1. Новый, удаляемый или перемещаемый модуль; смена владельца бизнес-логики.
2. Новые или изменённые зависимости между слоями и модулями.
3. Изменение контракта другого модуля или внешнего потребителя (обработчик Application, DTO, CLI, конфигурация, событие, сохраняемый формат, семантика ошибки).
4. Изменения `Kernel`, модульной регистрации, `config/`, `depfile.yaml`, архитектурно значимых зависимостей `composer.json`.
5. Новый архитектурный паттерн или отступление от Конвенции/ADR.

Запись «RV-A: да/нет» + основание обязательна в задании ревьюверу; отсутствие записи означает, что гейтинг не выполнен. Гейтинг пересматривается по каждой дельте до приёмки; сомнение — в пользу RV-A. C0–C1 без признаков — одно комбинированное ревью по строке RV-F.

## Ревьюверы

- RV-F — ревьювер функционального ревью по матрице RACI (строка `RV-F`).
- RV-A — архитектор по матрице RACI (строка `RV-A`), не участвовавший в проектировании решения задачи; проектировали оба — эскалация пользователю.
- Консультанты (ячейка `C` в строках ревью) подключаются до решения по этапу ревью, а не до выполнения работы: аналитик — по спорным отклонениям в RV-F.
- Исполнитель не проверяет собственные изменения на этапе ревью: самопроверка — отдельный обязательный этап до ревью.

## Лимиты и апрувы

- Лимит «ревью → доработка» — 3 итерации отдельно на каждый трек и QA-петлю; исчерпание — эскалация пользователю. Счётчики сбрасываются только решением пользователя.
- Доработка отменяет апрув другого трека, если дельта затрагивает его область: поведение, контракт, сценарии, безопасность, тесты — RV-F; границы, контракты, паттерны — RV-A. Сомнение — в пользу повторного ревью.
- Перед приёмкой апрувы обязательных треков действительны для итогового набора изменений. Носитель записи апрува — файл задачи или описание PR: «трек, дата, diff».

## Документирование расхождений

Расхождение с постановкой (несоответствие по поведению, scope, критериям приёмки или контракту) исправляется или оформляется:

- **техдолг** — отдельная задача в `todo/` и тег `@todo`/`@techdebt` в коде со ссылкой на неё;
- **осознанное отступление** — запись в файле задачи с причиной и утверждением тимлида.

Оформленное расхождение — принятое решение, а не отклонение: замечание к нему не выставляется. Выбор способа реализации, не предписанного постановкой, отклонением не считается.

## QA-петля

Доработка по замечаниям QA → повторное RV-F по дельте → RV-A по гейтингу → повторный QA (подтверждение замечаний и обязательные проверки, без полного перезапуска).
