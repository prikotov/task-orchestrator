# Ретроспектива: цикл «апрув → done-коммит → повторный апрув» в каждом PR

**Дата:** 2026-08-21
**Эпик:** нет (процессная ретро по серии PR: #362, #363, #364)
**Что делали:** три PR подряд (docs-правка SKILL.md, релиз v0.3.1, шины Use Case) слиты по единому сценарию; во всех трёх повторился один и тот же штрафной цикл снятия апрува.

## Оценка ролей

- **Тимлид Алекс** (`docs/agents/roles/team/team_lead_alex.ru.md`)
  - **Плюсы:** все отправки веток выполнены безопасным рецептом от GitHub App (журнал push-ей чист, `require_last_push_approval` ни разу не заблокировал из-за идентичности отправителя); merge во всех случаях прошёл без `--admin`; регламент «задача → done до merge» выполнялся буквально.
  - **Минусы:** порядок операций не оптимизирован под защиту ветки: `done`-коммит отправлялся ПОСЛЕ апрува владельца и каждый раз снимал одобрение (`DISMISSED`), вынуждая владельца ставить апрув повторно. В PR #362 цикл прошёл дважды (поле `pr` + done), итого владелец апрувил 4 раза на 3 PR вместо 3.
  - **Предложения для улучшения:** перевести задачу в `done` и запушить финальный коммит ДО запроса апрува (после зелёного CI); апрув запрашивать только когда ветка гарантированно финальна.

## Что прошло хорошо

- Идентичность push-ей ни разу не была причиной снятия апрува — рецепт из ретро [2026-08-05](2026-08-05_00-08-triz-task-merge-last-pusher-repeat.md) работает стабильно.
- Каждый блокированный merge корректно ожидал переапрува; запрещённые обходы (`--admin`, `--auto`) не применялись.
- CI (`test`, smokes) во всех PR зелёный с первого прогона.

## Проблемы

- 🔴 **Структурный конфликт регламента с защитой ветки.** Регламент ([`todo/AGENTS.md`](../../../todo/AGENTS.md) п.4, [`pull-request.md`](../../git-workflow/pull-request.md) «Перед слиянием») требует перевести задачу в `done` коммитом в ветку PR до merge. Защита `require_last_push_approval` снимает апрув при любом новом пуше. Итог: последовательность «апрув → done-коммит → merge» невозможна без повторного апрува — воспроизведено в #362 (дважды: коммит с полем `pr` + done-коммит), #363 и #364. Владелец ставит апрувы на каждый PR сверх необходимого.

## Предложения для улучшения

- [ ] **P0 — изменить порядок: `done` до запроса апрува.** Регламент требует done только «до вызова `gh pr merge`», а не «после апрува» — значит достаточно процессной правки порядка действий агента: после зелёного CI перевести задачу в `done`, запушить финальный коммит и только затем просить апрув; ветка не меняется после одобрения. Внедрение: скорректировать формулировку в `docs/git-workflow/pull-request.md` (раздел «Перед слиянием» — upstream пакета `prikotov/git-workflow`, правка требует решения владельца) и при необходимости — в `todo/AGENTS.md`. Статус: `watch`, задача-кандидат предложена владельцу в реестре.
- [ ] **P1 — доопределить поведение при ревью с замечаниями.** Если после done-коммита ревью требует правок: задача возвращается из `done/` в `todo/` тем же коммитом, что вносит правки, затем снова `done` до следующего апрува. Зафиксировать в том же upstream-документе. Статус: `watch`.

## Важные комментарии

- Это НЕ повтор проблемы из [2026-08-05](2026-08-05_00-08-triz-task-merge-last-pusher-repeat.md): там апрув не засчитывался из-за push-а токеном владельца (ошибка идентичности), здесь идентичность корректна, а апрув снимает сам факт обязательного пост-апрувного коммита.
- Побочный кандидат из этой же серии (не эскалируется): `agent:token` падал с `ClassNotFoundError` после переключения веток с DI-изменениями (`var/cache/prod` скомпилирован под другую ветку) — лечится `rm -rf var/cache`; дважды за сессию. Отдельная запись не заводится (штатное поведение кеша Symfony), но при третьем повторе стоит добавить в `docs/guide/troubleshooting.md`.
