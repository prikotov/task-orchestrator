# Матрица RACI по типам задач

Общие этапы и условия переходов определяет [SDLC — жизненный цикл разработки](workflow/sdlc.md). Матрица распределяет ответственность участников команды task-orchestrator в рамках этого процесса.

Матрица **RACI** (англ. RACI matrix, матрица распределения ответственности) закрепляет, кто из ролей команды что делает на каждом этапе жизненного цикла задачи. Применяется ко всем задачам в `todo/`.

> Источник истины для состава команды — описания ролей в [`roles/team/`](roles/team/). Данный документ задаёт **взаимодействие** ролей по задачам, а не переопределяет сами роли.

|-------|----------------|-------|
| **R** | Исполнитель (Responsible) | Делает работу. Может быть несколько. |
| **A** | Владелец (Accountable) | Несёт финальную ответственность за результат этапа, принимает решение «принято/не принято». **Ровно один на строку.** |

| **—** | — | Этап неприменим для данного типа задачи. |

> Одноимённые роли (два Архитектора, два Бэкендера, два Техписателя) — взаимо­заменяемые слоты в своей колонке. Тимлид назначает конкретного исполнителя (R) на задачу; в матрице указан слот.

## 2. Неизменные правила RACI

1. На каждой строке (этапе) — **ровно один A**. Два «владельца» = ноль владельцев.
2. Каждый выполнимый этап имеет **хотя бы один R**.
3. A и R могут совпадать в одном лице (владелец сам делает).
4. В рамках одной задачи A на разных этапах могут принадлежать разным ролям (это нормально: A на «реализации» — бэкендер, A на «ревью» — ревьювер бэка, A на «приёмке/merge» — тимлид).
5. **Merge в `main`/`release/*` выполняется только тимлидом** и **только после явного подтверждения пользователя** (правило AGENTS.md: `gh pr merge` без подтверждения запрещён).
6. Если для задачи нужен участник вне матрицы (внешний эксперт, заказчик) — он добавляется отдельной строкой-ролью с пометкой, зачем.
7. Участие определяется только по строке матрицы, её легенде (включая условное участие) либо явно согласованному исключению с фиксацией (кто согласовал, что и на каком основании); самоназначение запрещено.
8. Специализированные циклы (раздел 6) — часть матрицы: их строки подчиняются правилам 1–4, не отменяют правило 5, согласование пользователя и обязательные проверки проекта.

## 3. Этапы жизненного цикла задачи

| Код | Этап | Что происходит |
|-----|------|----------------|
| **RF** | Уточнение (Refinement) | Уточнение формулировки, критерии готовости, декомпозиция. |
| **AN** | Анализ требований (Analysis) | Системный анализ, контракты, граничные случаи. |
| **DS** | Проектирование (Design) | Архитектурное решение, границы слоёв/модулей, ADR при необходимости. |
| **IM** | Реализация (Implementation) | Код в нужном слое (Domain/Application/Infrastructure/Presentation). |
| **RV** | Ревью кода (Review) | Code review, статический анализ (Psalm), Deptrac, стиль (PHPCS). |
| **QA** | QA (тестирование) | Unit/Integration-тесты, проверка use cases и тест-плана. |
| **DC** | Документация (Docs) | Обновление `README`, `docs/`, `SKILL.md`, PHPDoc публичных API. |
| **AC** | Приёмка / Merge (Acceptance) | Приёмочные проверки, перевод задачи в `done`, merge PR. |

## 4. Шпаргалка: тип задачи → владелец (Accountable) по умолчанию

Быстрый ориентир «кто владеет результатом задачи целиком» (без чтения полной матрицы). На уровне отдельных этапов A может отличаться — см. раздел 5.

| Тип задачи | Владелец результата (Accountable) | Краткое описание |
|------------|-----------------------------------|------------------|
| `feat`     | **Бэкендер** (под А тимлида на приёмке) | Новая функциональность: полный цикл анализ → дизайн → код → ревью → QA → доки. |
| `fix`      | **Бэкендер** | Исправление бага: короткий цикл, анализ опционален, ревью и QA обязательны. |
| `refactor` | **Бэкендер** (с обязательным **архитектором** на DS) | Изменение структуры без смены поведения: проектирование и ревью критичны. |
| `chore`    | **Бэкендер** | Служебные задачи (зависимости, сборка, регламент): анализа/архитектуры обычно нет. |
| `docs`     | **Технический писатель** | Документация: код не трогается, QA/ревью по необходимости. |
| `build`    | **Бэкендер** | Сборка/релиз-инфраструктура: ревью обязательно, QA обычно не нужно. |
| `research` | **Аналитик** | Исследование/RFC: гипотеза → анализ → отчёт; кода нет, merge — отчёт в `docs/research/`. |
| `epic`     | **Тимлид** | Группа задач: оркестрация, декомпозиция, координация сабагентов. |

> Изменение регламента, оркестрационного навыка или распределения ответственности не сводится к типу `docs` и не назначается по расширению файла: состав участников задаёт специализированный цикл «Проектирование процессов взаимодействия команды» (раздел 6) — автор модели — тимлид, оформитель — технический писатель. Этапы цикла проходят **до** этапа `DC` (документация) соответствующего типа задачи.

## 6. Специализированный цикл: проектирование процессов взаимодействия команды

Цикл применяется по **виду работы**, а не по типу задачи и не по расширению файла: к изменениям регламентов, оркестрационных навыков и распределения ответственности (что закрепляет, кто, что и в каком порядке делает в процессах команды). Это не новый тип `todo-md`: изменения оформляются задачами обычных типов, но этапы цикла проходят **до** этапа `DC` (документация) соответствующего типа — оформление документации не заменяет цикл, а оформляет его принятый результат.

Обязательные проверки проекта сохраняются: прохождение цикла не подменяет проверки, предусмотренные для изменяемого артефакта. `A` этапов цикла не заменяет пользовательского согласования и разрешения на merge (правило 5 раздела 2).

### 6.1. Строки цикла

| Этап | Тимлид | Аналитик | Архитектор | Бэкендер | Ревьювер бэка | Тестировщик бэка | Технический писатель |
|------|:------:|:--------:|:----------:|:--------:|:-------------:|:----------------:|:-------------------:|
| `PM1` — модель процесса | **A**/R | C | C | c | c | c | c |
| `PM2` — проверка модели | C | **A**/R | C | c | c | C | c |
| `PM3` — принятие модели | **A**/R | C | i | i | i | i | i |
| `PM4` — оформление | C | C | — | — | — | — | **A**/R |
| `PM5` — сверка оформления с моделью | **A**/R | C | — | — | — | — | C |

Правила строк:

- **`PM1` — модель процесса.** Тимлид проектирует процесс и фиксирует управленческие решения (этапы, входы/выходы, ответственность, переходы, условия проверки/принятия, остановки/эскалации); аналитик и архитектор — обязательные консультанты. Условные `c` остальных ролей применяются при затронутых обязанностях: тимлид фиксирует состав применимых консультантов и основание в самой модели до начала `PM2`.
- **`PM2` — проверка модели.** Проверяет аналитик: полнота этапов, входов/выходов, переходов; противоречия и пропуски. Тимлид и архитектор — консультанты; тестировщик бэка — обязательный консультант по сценариям отказов. Условные `c` затронутых ролей — по списку из `PM1`.
- **`PM3` — принятие модели.** Решение «принято / не принято» принимает тимлид; аналитик — консультант, затронутые роли уведомляются (`i`). Критические замечания `PM2` нельзя проигнорировать: неразрешённый спор выносится пользователю.
- **`PM4` — оформление.** Принятую модель оформляет технический писатель; вход — только принятая модель; тимлид и аналитик — консультанты. Оформитель не проектирует полномочия, этапы, шлюзы и исключения: пробел возвращается владельцу модели.
- **`PM5` — сверка оформления с моделью.** Тимлид сверяет, что оформление сохраняет управленческие решения модели; технический писатель и аналитик — консультанты. Сверка проверяет сохранность решений модели и не подменяет проверку кода или технического артефакта.

После `PM5` изменения проходят обычные этапы своего типа задачи (`DC`, `AC` и остальные) по строкам разделов 5.1–5.8. Связь цикла с `DC`: `PM4` — оформление принятой модели; последующий этап `DC` соответствующего типа задачи — только публикация оформленного и сопроводительная документация, без повторного проектирования. Нормативные изменения, выявленные после `PM5`, возвращаются на `PM1`–`PM5` в затронутом объёме; редакционные правки без смены смысла не требуют повторного проектирования, но сверка оформления с моделью сохраняется.

## 7. Примечания и исключения

- **Заглушка этапа (`—`).** Если этап неприменим к конкретной задаче (например, QA для `docs`), он пропускается, а не заполняется «для галочки».
- **Несколько кандидатов в слоте.** Если в задаче участвуют оба Бэкендера / Архитектора / Техписателя, один из них назначается **A**/R, остальные — R или C. Два A в одном этапе запрещено.
- **Исключения согласуются с тимлидом.** Любое отклонение от матрицы фиксируется в формулировке задачи (`todo/`) с обоснованием.
- **Связь с AGENTS.md.** RACI не отменяет правил AGENTS.md (слойность, тесты, проверки, запрет `gh pr merge` без подтверждения) — она их дополняет распределением ролей.
