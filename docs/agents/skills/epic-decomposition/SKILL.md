# Декомпозиция эпика на задачи

Навык процесса декомпозиции: превращает принятую концепцию эпика в план атомарных задач с проверками и зависимостями. Не реализует задачи и не пишет концепцию.

## Когда использовать

- Концепция эпика **принята** (решение `A` зафиксировано) — нужно построить план задач в файле эпика и файлы задач.
- Требования эпика нужно разложить по правилу «требование → задача → проверка» с зависимостями без циклов.

Не использовать:

- концепция эпика не принята — сначала навык `epic-definition`;
- постановка одиночной задачи вне эпика — навык `task-definition`;
- реализация задач эпика — `epic-via-subagents`.

## Как использовать

> Общий протокол подготовки постановок: [протокол в материалах навыка task-definition](../task-definition/references/definition-protocol.md) — прочитай до выполнения шагов. Правила постановки одиночной задачи — навык [`task-definition`](../task-definition/SKILL.md). Материалы навыков лежат рядом с их `SKILL.md`, а не в корне принимающего проекта. Навыки `task-definition`, `epic-definition`, `epic-decomposition` устанавливаются совместно с общим протоколом: настоящий навык зависит от `task-definition`; зависимость не установлена — стоп-условие, без протокола не продолжай (протокол, раздел 1).

### **Шаг 0:** Проверка предусловий

1. Файл эпика существует; концепция принята (`A`; статус эпика — из справочника статусов установленного todo-md).
2. Проверь существующий план эпика: задачи, уже созданные и связанные с эпиком, — не создавай повторно; строй карту по их фактическому составу.
3. Концепция не принята или файла нет — стоп: сначала `epic-definition`; в комплексном запросе (концепция + декомпозиция) концепция доводится до принятия навыком `epic-definition` в этом же запросе, затем продолжай здесь.

### **Шаг 1:** Выбор этапов и участников по RACI

1. Сначала назначаются участники **уровня эпика**. Найди в матрице RACI принимающего проекта раздел для эпиков; зафиксируй участников декомпозиции с цитатами строк: автор плана (`R` строки декомпозиции/уточнения), консультанты (`C`), проверяющий плана, принимающий план (`A`). Проверяющий ищется по смыслу артефакта и этапа: применимая строка этапа проверки плана задач и его связей либо легенда, явно закрепляющая проверку за `A` этапа; имена строк различаются между проектами, фиксированных названий нет. Проверка концепции не подменяет проверку плана, ревью кода не подменяет проверку плана (протокол, разделы 3 и 6). Проверяющий однозначно не определён — стоп-условие: согласование с уполномоченным владельцем (`A`) или пользователем, не подстановка; автоматическое назначение `A` декомпозиции проверяющим запрещено.
2. Участники **подзадач назначаются после построения карты** (Шаг 2), когда определён вид работы каждой задачи: каждая задача имеет собственный RACI — её автор, консультанты, проверяющий и принимающий определяются разделом матрицы по виду работы этой задачи (применимый специализированный цикл либо `type` по справочнику принимающего проекта), а не разделом эпика. Автор задачи не выбирает тип сам и не назначает себя: вид работы определяется по правилам принимающего проекта, участие — по строке матрицы с основанием (протокол, раздел 3; самоназначение запрещено). Каждая задача проходит полный цикл подготовки постановки (как в навыке `task-definition`: черновик → консультации → проверка → принятие) и принимается **своим `A` до принятия итогового плана** (Шаг 6); `A` декомпозиции не заменяет `A` задач.
3. Пробелы и конфликты матрицы — стоп-условие: согласование, не угадывание.

### **Шаг 2:** Карта «требование → задача → проверка»

Карту строит назначенный `R` строки декомпозиции — не обязательно оркестратор навыка: если `R` — роль, в которой ты работаешь, строй карту сам; иначе делегируй сабагенту этой роли. Карта строится по требованиям эпика (в первую очередь блокирующим — `Must Have` или эквиваленту по руководству проекта). План (секцию задач) файла эпика обновляет `R` декомпозиции: вносит в план ссылки на созданные задачи; файлы задач пишут `R` этих задач.

| Требование эпика | Задача (`ID`) | Вид работы (цикл / `type`) | Атомарный результат | Проверка задачи | Зависимости |
|---|---|---|---|---|---|
| <требование> | `TASK-...` | <применимый цикл либо `type` по правилам проекта> | <один проверяемый результат> | <способ проверки> | <`ID` задач или «нет»> |

Правила карты:

- **Атомарность**: одна задача — один проверяемый результат; смешение независимых частей системы, механических правок и изменений поведения — сигнал дробления (критерии размера задачи — по руководству принимающего проекта).
- **Покрытие**: каждое блокирующее требование покрыто хотя бы одной задачей; каждая задача ссылается на покрываемое требование или его необходимую предпосылку (фиксируй в карте, чему соответствует задача — прямому требованию или предпосылке).
- **Проверка**: у каждой задачи конкретный способ проверки (критерий приёмки, тест, инспекция) — не «сделать», а «как убедимся, что сделано».
- **Неизвестное** (как реализовать или проверить — не ясно) не прячется в задачу: это либо уточнение у `A`/консультантов, либо отдельная исследовательская задача (тип — по справочнику типов принимающего проекта).
- **Зависимости**: направленный граф без циклов; независимые задачи не связываются — они образуют параллельные ветви (зафиксируй группы параллельных задач в плане).
- **Интеграционные проверки**: сквозные проверки эпика (сборка, основной сценарий, регресс — по правилам проекта) оформляются отдельными задачами или критериями приёмки эпика, а не растворяются в задачах. Сквозные проверки дополняют собственные проверки каждой задачи и не переносят их целиком на конец плана.

Сверка с существующими задачами и назначение участников — после формирования карты:

- **Осиротевшие задачи.** Концепция эпика изменена и в новую карту не вошли задачи, ранее связанные с эпиком, — сравни карту с существующими задачами и вынеси судьбу каждой выпавшей на согласование с уполномоченным `A` (декомпозиции) или пользователем: перепривязка к требованию/эпику, сохранение вне эпика или отмена по правилам принимающего проекта. Самовольное удаление, закрытие и переформулирование выпавших задач запрещены; пока судьба выпавших не решена, карта не объявляется согласованной.
- **Назначение участников задач.** После формирования карты назначь каждой задаче `R`/`A`/`C`/`I` по разделу матрицы её вида работы из карты; для каждого участника зафиксируй основание — цитату строки (формат — как в Шаге 1). Назначение выполняется по матрице, а не автором задачи по его выбору; спорный вид работы — согласование с `A` или пользователем (протокол, раздел 3), не подстановка.

### **Шаг 3:** Согласование объёма плана

1. Согласуй с пользователем или `A`: состав задач карты, параллельные ветви, исследовательские задачи, оценки (если правила проекта их требуют). Состав карты изменился после назначения участников — обнови назначения и основания (Шаг 2).
2. Расширение объёма сверх концепции эпика — только по согласованию; дополнения требований — с обоснованием и способом проверки (протокол, раздел 7).

### **Шаг 4:** Делегирование черновиков задач

Черновик каждой задачи готовит её `R`, назначенный по карте (Шаг 2, «Назначение участников задач»; правило — Шаг 1, пункт 2). Вид работы и участники передаются из карты: автор задачи не выбирает тип сам и не назначает себя. Пример промпта делегирования одного черновика:

```
Подготовь черновик задачи для эпика.

Роль: загрузи из файла <путь к файлу роли из каталога ролей проекта>.
Эпик: <EPIC-ID>, файл <путь>.
Покрываемое требование эпика: <требование из карты>.
Вид работы задачи: <применимый цикл либо type из карты>.
Атомарный результат задачи: <результат из карты>.
Проверка: <способ проверки из карты>.
Зависимости: <список ID задач или «нет»>.
Участники задачи (назначены по матрице; цитаты строк): автор — <роль>;
консультанты — <роли>; проверяющий — <роль и основание>;
принимающий — <роль>.

Материалы: руководство и шаблон задачи <пути>, файл эпика.
Создай файл задачи <TASK-ID>.todo.md; свяжи с эпиком <EPIC-ID>
по правилам руководства. Значения, которых нет в материалах,
не придумывай — вынеси в открытые вопросы.

Входы: карта декомпозиции (фрагмент), участники задачи с обоснованиями,
эпик, руководство, шаблон.
Выходы: путь к файлу задачи; список открытых вопросов.
Стоп-условия: противоречие правилам проекта; дубликат существующей задачи;
требование не покрывается без расширения объёма эпика — остановись и верни
вопрос на согласование.
```

Если `R` задач — роль, в которой ты работаешь, черновики пиши сам.

### **Шаг 5:** Консультации

1. Консультируются участники **уровня эпика** (строки декомпозиции). Момент консультации задают правила принимающего проекта, не навык (протокол, раздел 4): консультация задана до начала этапа — получи вход каждого обязательного `C` **до построения карты** (до Шага 2), затем уточняй по готовой карте; консультация задана по черновику артефакта — запрос по готовой карте; в типичной матрице мнение `C` требуется до завершения этапа и не позже принятия плана. Консультации применимых строк каждой задачи проводятся в её собственном цикле подготовки постановки (Шаг 6). Срок — по правилам принимающего проекта; местных сроков нет — согласуй срок с `A`, не выдумывай (протокол, раздел 4).
2. Ответы вносит в черновики соответствующий `R`. Конфликт разрешает `A` своего уровня: внутри задачи — её `A`; на уровне плана и между задачами — `A` декомпозиции, не отменяя полномочий `A` задач; конфликт, неразрешимый без изменения принятого контракта или объёма (концепции эпика, принятой постановки), выносится владельцу такого решения или пользователю, а затронутое проходит повторное принятие.
3. Просроченный без ответа запрос — зафиксируй и согласуй с `A` (протокол, раздел 4).

### **Шаг 6:** Подготовка постановок задач (каждая задача — до итоговой проверки плана)

До итоговой проверки плана (Шаг 7) каждая задача проходит цикл навыка `task-definition`: проверка содержания и формата, доработка, принятие **своим `A`** (назначен по карте, Шаг 2).

- Не начинай подготовку с нуля и не создавай дубли: передавай уже собранные входы — фрагмент карты (требование, вид работы, атомарный результат, проверка, зависимости), участников с обоснованиями, требования консультантов, материалы эпика.
- Постановку каждой задачи принимает её `A` (раздел матрицы по виду работы задачи); `A` декомпозиции не заменяет это решение.
- Задача, изменённая после принятия, повторно проходит затронутую проверку и повторное принятие её `A`.
- Весь план после этого шага принимает `A` декомпозиции (Шаг 9): приёмка плана не раньше приёмки всех его задач.

### **Шаг 7:** Проверка

1. **Содержание** (проверяющий из Шага 1): карта полная — каждое блокирующее требование покрыто; задачи атомарны; у каждой задачи указана проверка; граф зависимостей без циклов; параллельные ветви обоснованы; интеграционные проверки присутствуют; у каждой задачи зафиксирован её собственный RACI (раздел матрицы по её виду работы) и она принята своим `A` (Шаг 6); открытые вопросы перечислены явно.
2. **Формат**: валидатор пакета todo-md по файлу эпика и каждому файлу задачи (типичная команда: `php vendor/bin/todo-md validate <путь>`; точную команду возьми из правил проекта); ссылки плана эпика ↔ файлы задач корректны.

Замечания есть → Шаг 8. Замечаний нет → Шаг 9.

### **Шаг 8:** Доработка

Доработку выполняют `R` соответствующих артефактов (план эпика — `R` декомпозиции; файлы задач — их `R`) по замечаниям; затем повтор проверки. Лимит итераций — по таблице «Лимиты».

### **Шаг 9:** Принятие плана и отчёт

1. Решение принимает `A` декомпозиции: «принято» или отклонение с замечаниями (→ Шаг 8). План принимается только после того, как каждая задача прошла собственные проверку и принятие её `A` (Шаг 6, полный цикл навыка `task-definition`); `A` декомпозиции не заменяет решения `A` задач.
2. После принятия: статусы эпика и задач — только из справочника статусов установленного todo-md и только его средствами. Готовность плана не означает, что все зависимости выполнены и каждую задачу можно запустить немедленно: порядок запуска задают зависимости и план запуска по правилам принимающего проекта; реализация начинается отдельным процессом. Блокирующие открытые вопросы запрещают объявлять план готовым (протокол, раздел 8).
3. Уведоми `I` применимых строк о результате.
4. Отчитайся пользователю:

```
Эпик: <EPIC-ID> — <название>
План: <количество задач; блокирующие требования покрыты: да/нет>
Карта «требование → задача → проверка»: <таблица или путь к ней>
Параллельные ветви: <группы задач>
Интеграционные проверки: <список задач/критериев>
Участники (раздел матрицы, строка, буква): <план — цитаты; задачи — их разделы>
Консультации: <кто, что дал, что внесено; просроченные ответы>
Проверка: <проверяющий, содержание, валидатор>
Решение принимающего: <принято / отклонено>
Открытые вопросы: <список или «нет»>
Следующий шаг: реализация эпика — отдельным процессом принимающего проекта.
```

## Лимиты

| Лимит | Значение |
|---|---|
| Итерации доработка → проверка | Предел из правил принимающего проекта или согласованного плана запуска; не задан — согласуй с пользователем или `A` до повторных запусков, собственные дефолты не выдумывай |
| Повторные запросы одному консультанту | Предел из правил принимающего проекта или согласованного плана запуска; не задан — согласуй с пользователем или `A` до повторных запусков, собственные дефолты не выдумывай |
| Исчерпание лимитов | Эскалация пользователю |

## Стоп-условия

| Ситуация | Действие |
|---|---|
| Концепция эпика не принята | Остановиться; сначала навык `epic-definition` (в комплексном запросе — концепция доводится до принятия навыком `epic-definition` в этом же запросе) |
| Нет строки RACI для декомпозиции, два `A`, нет `R` или проверяющий плана не определён однозначно | Согласовать состав участников и проверяющего с пользователем или уполномоченным `A`; основание зафиксировать; до решения план проверенным не объявлять |
| Требование не покрывается без расширения объёма эпика | Вопрос на согласование с пользователем или `A` |
| Цикл в зависимостях не устраняется повторной раскладкой | Эскалация к `A` с вариантом разрешения |
| Неизвестное требует исследования больше задачи | Предложить исследовательскую задачу (тип — по справочнику проекта) или эскалацию |
| Механизм запуска сабагентов не установлен | Согласовать способ делегирования с пользователем |
| Навык `task-definition` с общим протоколом не установлен | Остановиться; согласовать с пользователем совместную установку набора навыков |
| Повторный запуск при существующем плане | Работать с существующими задачами; согласованные формулировки не переписывать |
| Задачи, выпавшие из карты при изменении концепции (осиротевшие) | Согласовать судьбу каждой с уполномоченным `A` или пользователем: перепривязка, сохранение вне эпика, отмена по правилам проекта; самовольное удаление/закрытие/переформулирование запрещены; до решения карту согласованной не объявлять |

## Результат

- План эпика заполнен ссылками на задачи; файлы задач созданы, связаны с эпиком и валидны по валидатору.
- У каждой задачи: атомарный результат, проверка, зависимости; собственный RACI зафиксирован с основанием (по виду работы из карты); постановка принята её `A` до принятия плана.
- Статусы — из справочника статусов установленного todo-md; решение `A` по плану зафиксировано.
- Отчёт пользователю: карта, участники с цитатами строк RACI, консультации, проверка, решение, открытые вопросы.
