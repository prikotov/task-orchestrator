# Классификация предложений: симптом → тип фикса

Справочник для Шага 5 навыка [`retrospective`](../SKILL.md). Канон сформулирован в SKILL.md; ниже — таблица, пояснения и примеры.

## Таблица «симптом → тип фикса»

| Симптом | Тип фикса | Куда попадает |
|---|---|---|
| Агент долго искал файл или факт | **Навигационный указатель** | Указатель в файле, который агент и так читает (роль, навык, конвенции) |
| Ошибку мог поймать инструмент | **Автоматическая проверка** | PHP_CodeSniffer, Deptrac, Psalm, gitleaks, тест, CI-задача, pre-commit |
| Ошибку уровня «суждение» пропустил ревьюер | **Правило для ревьюера** | Файл роли ревьюера / чеклист ревью |
| Инструкция не работает или шумит | **Правка стиринга** | Правка или удаление строки в `AGENTS.md`, файле роли, навыке |
| Полезный приём, который стоит закрепить | **Закрепление практики** | Правило или приём в файл роли, навыка или конвенций (род предложений «Что прошло хорошо») |

## Пояснения к правилу «проверка вместо прозы»

- Проверка (check) — детерминированный инструмент, который ловит нарушение без участия человека; проза — правило, исполнение которого зависит от «послушания» модели.
- Прозаические формулировки уместны, когда нарушение требует суждения: оценить уместность, полноту или архитектурное решение. Пример: «слои не перепутаны» ловит Deptrac (проверка), а «согласуй границы пакета до правок» остаётся прозой (суждение).
- Если симптом одинаково подходит и «автоматической проверке», и «правилу для ревьюера» — выбирай автоматическую проверку.

## Связка с аудитом проверок (Шаг 3)

Предложение типа «автоматическая проверка» всегда ссылается на результат аудита подключённости проверок из Шага 3:

- «существующая проверка не подключена — подключить»;
- «проверка отсутствует — создать по регламенту с согласованием».

Не предлагай новую проверку, пока существующая той же цели не подключена. Классификация не создаёт проверку автоматически: предложение получает статус по действующим правилам Шага 5, а создание выполняется по регламенту с согласованием.
