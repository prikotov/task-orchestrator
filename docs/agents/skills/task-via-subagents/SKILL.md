# Обработка одиночной задачи через сабагентов

## Когда использовать

- Нужно провести **одну задачу** от `todo` до `done` через команду ИИ-сабагентов.
- Задача **не входит в эпик** (или эпик не требует общей ветки).
- Ты оркестратор процесса: подготавливаешь задачу, запускаешь сабагента-исполнителя, контролируешь самопроверку и ревью кода, коммитишь, создаёшь PR, выполняешь слияние.

## Рабочий процесс Git

```
main
  └── task/<short-description>    ← создаётся от main
        └── (одна ветка, один PR)
```

Финальный PR: `task/<short-description>` → `main`.

**Hotfix (срочное исправление):** для срочных исправлений используй ветку `hotfix/x.y.z-<short-description>` от производственного тега `vX.Y.Z`, а не от `main`. База PR — `main`. Остальной конвейер тот же.

## Как использовать

### **Шаг 0:** Проверка готовности

1. Прочитай файл задачи (`todo/TASK-*.todo.md`).
2. Убедись, что задача готова к работе (см. [`todo/AGENTS.md`](../../../../todo/AGENTS.md)):
   - Заполнены `type`, `value`, `complexity`, `priority`, `author`, `created`.
   - Есть постановка, контекст, scope, критерии приёмки.
   - `depends_on` — все зависимости выполнены (файлы зависимых задач лежат в `todo/done/`).
3. Если задача не готова — **остановись**, запроси уточнение у пользователя.

### **Шаг 1:** Подготовка задачи

1. Определи **роль исполнителя** исходя из сути задачи.
2. Предложи пользователю: кто, какая роль. Формат:
   > «Предлагаю взять в работу TASK-... — <Роль>. Подтверждаешь?»
3. Получи подтверждение.
4. Обнови заголовок с метаданными задачи: `assignee`, `status: in_progress`.
5. Создай ветку `task/<short-description>` от актуального `main`.
6. Запиши имя ветки в поле `branch`.
7. Закоммить и запушь.

### **Шаг 2:** Реализация

Запусти сабагента-исполнителя через скилл [`run-subagent`](../run-subagent/SKILL.md), передав `--task-id <TASK-ID>`. Тогда командный профиль выбирается по `complexity` задачи; для ручного переопределения используй `--complexity <C0-C5>`. Один из этих параметров обязателен: если не передан ни один, запуск завершается ошибкой.

> `<role-title>` — заголовок роли из поля `title` файла роли (например, `Бэкендер Левша`).

Пример промпта:

```
<role-title>, выполни задачу: todo/<TASK-ID>.todo.md.
Реализуй в текущей ветке task/<short-description>.
Следуй [Конвенциям](../../../../docs/conventions/index.md) проекта.
После реализации запусти проверки: `make check`.
НЕ делай коммит — я сделаю сам.
```

⚠️ **Сабагент НЕ коммитит и НЕ пушит.** Тимлид контролирует git.

### **Шаг 3:** Анализ результата

**Успех** → самопроверка (**Шаг 4**). **Ошибка** → перезапусти с уточнением или эскалируй.

Если агент завершён по таймауту:

1. Проверь `git status` — есть ли незакоммиченные изменения?
2. Оцени прогресс: `git diff --stat`, `vendor/bin/phpunit 2>&1 | tail -5`.
3. Перезапусти с уточняющим промптом. Увеличь таймаут относительно предыдущего запуска (например, ×1.5).
4. Если после 2 перезапусков задача не завершена — эскалируй пользователю.

### **Шаг 4:** Самопроверка

🛑 **Самопроверка обязательна.** Не пропускай этот шаг.

Запусти сабагента-исполнителя для самопроверки:

```
<role-title>, выполни самопроверку своих изменений в текущей ветке task/<short-description>.
Проверь соответствие задаче: todo/<TASK-ID>.todo.md.
Проверь: полноту реализации, соблюдение конвенций, качество тестов, edge cases.
Если есть замечания — сформулируй конкретные запросы на изменения.
Если всё ок — дай подтверждение.
```

- **Замечаний нет** → запускай ревью кода (**Шаг 5**).
- **Есть замечания** → вернись к **Шаг 2** для доработки, передав замечания в промпте:

```
<role-title>, доработай задачу: todo/<TASK-ID>.todo.md по результатам самопроверки:
<суть замечаний>
НЕ делай коммит — я сделаю сам.
```

Затем повтори самопроверку (**Шаг 4**).

### **Шаг 5:** Ревью кода

🛑 **Ревью кода обязательно.** Не пропускай этот шаг. Ревью идёт **двумя треками в порядке 5а → 5б**: сначала **RV-F** (функциональное ревью), после его апрува — **RV-A** (архитектурное ревью, по гейтингу).

Перед началом треков выполни **гейтинг RV-A** (см. Шаг 5б) и зафиксируй запись `RV-A: да/нет` + основание в задании ревьюверу (обязательна для задач 5.1–5.4 и 5.6; для docs/research — решение о консультации архитектора, см. ниже). Для задач типа `docs` и `research` (5.5/5.7) строки ревью **не делятся** на RV-F/RV-A: проводится одно ревью, а решение о консультации архитектора фиксируется в файле задачи (при изменении нормативной архитектуры — ADR, Конвенции, архитектурные контракты — архитектор обязателен как консультант этого ревью).

#### **Шаг 5а:** RV-F — функциональное ревью (Ревьювер Бэка Пуаро)

Вопрос трека: «делает ли код то, что написано в задаче?». Метод — статическое сопоставление diff и постановки; допускается точечный запуск затронутых тестов для проверки спорного поведения (полный прогон — обязательные проверки и QA).

1. Запусти сабагента-ревьювера (Ревьювер Бэка):

```
<reviewer-role-title>, проведи функциональное ревью (RV-F) изменений в ветке task/<short-description>.
Задача: todo/<TASK-ID>.todo.md.
Вопрос трека: делает ли код то, что написано в задаче. Метод — статическое сопоставление diff и постановки; при спорном поведении допускается точечный запуск затронутых тестов (полный прогон и достаточность покрытия — вне твоей зоны: обязательные проверки и QA).
Чек-лист по блокам scope:
- Блок «постановка» — построчное сопоставление «требование или критерий приёмки → файл:строка → выполнено / отклонено (оформлено, ссылка) / не выполнено (замечание)».
  Построчное сопоставление применяется только к блоку «постановка» (требования и критерии приёмки задачи); остальные блоки — короткие проверочные вопросы:
- Безопасность: уязвимости (инъекции, XSS, небезопасная десериализация, утечки), обработка пользовательского ввода, секреты в коде/логах. Уязвимость — всегда блокирующее замечание; по остальным блокам scope серьёзность определяешь ты.
- Качество кода и типизация: строгие типы, readonly там, где положено по Конвенциям, N+1, мёртвый код, магические числа.
- Именование и код-уровневые конвенции: именование по Конвенциям, DTO-структуры, PHPDoc публичных контрактов (архитектурно значимые имена, запрещённые Port/Adapter — зона RV-A, не отмечай их здесь).
- Статическая оценка тестов: тесты соответствуют конвенциям тестирования; ассерты проверяют существенное; тестопригодность изменений.
- Прослеживаемость отклонений: каждое отклонение оформлено допустимым способом (см. ниже).
Определение отклонения: несоответствие реализации постановке задачи по поведению, scope, критериям приёмки или контракту, не оформленное допустимым способом. Выбор способа реализации, не предписанного постановкой (структура кода, внутренние решения), отклонением не считается.
Если правку делать не планируется, расхождение оформляется и перестаёт быть отклонением: техдолг — отдельная задача в todo/ и тег @todo/@techdebt в коде со ссылкой на неё; осознанное отступление — запись в файле задачи с причиной и утверждением тимлида.
Если обнаружен признак гейтинга RV-A или архитектурное наблюдение — сообщи тимлиду сигналом (архитектурное замечание не выноси); тимлид пересматривает запись гейтинга по правилам Шага 5б.
Если есть замечания — сформулируй конкретные запросы на изменения с файлом и строкой.
Если всё в порядке — одобри изменения.
Важно: НЕ исправляй код сам — только укажи замечания.
```

2. **Ревьювер одобрил изменения (апрув RV-F)** → переходи к **Шагу 5б**.
3. **Есть замечания** → вернись к **Шаг 2** для доработки, передав замечания:

```
<role-title>, доработай задачу: todo/<TASK-ID>.todo.md по замечаниям ревьювера RV-F:
<суть замечаний>
НЕ делай коммит — я сделаю сам.
```

Правила замечаний RV-F: замечание снимает ревьювер RV-F после исправления либо оформления расхождения; тимлид единолично замечания RV-F не снимает. Блокирующее замечание «отклонение без оформления» снимается оформлением. Спорные отклонения утверждает тимлид с консультацией владельца постановки (аналитик — по контрактам и критериям приёмки; тимлид — по постановке): тимлид запускает сабагента аналитика с diff, вопросом и выдержкой из постановки; заключение аналитика обязательно к рассмотрению, но не заменяет решение тимлида; несогласие ревьювера RV-F с решением тимлида — эскалация пользователю с приостановкой решения.

Затем повтори ревью кода (**Шаг 5а**).

#### **Шаг 5б:** RV-A — архитектурное ревью (Архитектор Гэндальф или Архитектор Локи)

Вопрос трека: «соответствует ли решение проекту?».

**Гейтинг RV-A (до старта ревью).** Запись `RV-A: да/нет` + основание **обязательна для задач 5.1–5.4 и 5.6** (в задании ревьюверу); отсутствие записи означает, что гейтинг не выполнен; для docs/research — вместо неё решение о консультации архитектора. RV-A обязателен при `complexity` **C2+** или при любом из наблюдаемых признаков по фактическому набору изменений:

1. Создаётся, удаляется или перемещается модуль; меняется владелец бизнес-логики.
2. Добавляется или меняется зависимость между слоями или модулями, включая новый вызов обработчика другого модуля.
3. Меняется контракт, используемый другим модулем или внешним потребителем: обработчик Application, DTO, CLI, конфигурация, событие, сохраняемый формат, семантика ошибки или значения по умолчанию.
4. Меняются `Kernel`, модульная регистрация, `config/` (в т.ч. chains.yaml), `Resource/config/`, `depfile.yaml` или архитектурно значимые зависимости в `composer.json`.
5. Вводится новый архитектурный паттерн либо требуется отступление от Конвенции или ADR.

Правила гейтинга: запись **пересматривается по каждой дельте** (доработка RV-F/RV-A/QA) до приёмки и обновляется; переход `нет → да` делает RV-A обязательным (запуск — после восстановления действительного апрува RV-F); переход `да → нет`: ещё не начатый RV-A не запускается, начатый — решает тимлид (завершить по текущему diff или прекратить, с фиксацией). Не каждый публичный метод — публичное API; изменение только внутренней реализации без смены взаимодействий само по себе RV-A не запускает. Нехватка сведений или сомнение — в пользу RV-A.

Режимы ревью по сложности:

- **C0–C1 без признаков гейтинга:** одно комбинированное ревью — один ревьювер (как в Шаге 5а), scope RV-F, архитектор не привлекается; апрув фиксируется как апрув RV-F, запись гейтинга — `RV-A: нет`.
- **C0–C1 с признаками гейтинга:** два трека в сокращённом объёме — RV-A только по признакам гейтинга; обязательное ядро чек-листа RV-A проверяется полностью, условные блоки — только по затронутым областям.
- **C2+:** оба трека полностью.

**Назначение ревьювера RV-A — по фактическому авторству архитектурного решения** в задаче или эпике (включая консультации и архитектурный контекст эпика): проектировал Гэндальф → ревьюит Локи, и наоборот; архитектурного авторства не было → тимлид назначает любого из слота с фиксацией основания; в проектировании участвовали оба — только эскалация пользователю (внешний эксперт либо согласованное пользователем исключение); единоличное назначение тимлидом авторов проектирования ревьювером RV-A запрещено. Автор проектирования и назначенный ревьюер фиксируются в задании ревьюверу.

1. Запусти сабагента-архитектора:

```
<architect-role-title>, проведи архитектурное ревью (RV-A) изменений в ветке task/<short-description>.
Задача: todo/<TASK-ID>.todo.md.
Запись гейтинга: RV-A: <да/нет> + <основание>.
Вопрос трека: соответствует ли решение проекту. Проверяй по чек-листу RV-A (обязательное ядро + условные блоки при затрагивании области):
- Обязательное ядро: А. Входные данные и источники истины (постановка, принятое проектирование, diff, перечень правок после предыдущего ревью; применимые docs/conventions/, ADR; приоритет: Конвенции → AGENTS.md → проектные документы и ADR → постановка → существующий код; соседний код не оправдание нарушения).
- Б. Границы модулей и слоёв: логика в своём модуле; Domain не зависит от других слоёв/модулей/сторонних библиотек; Application — сценарии использования; Integration — ACL через Application другого модуля; Infrastructure — реализации интерфейсов своего домена; Presentation — только к Application; нет прямого обращения к Domain другого модуля, VO преобразуются на границе, нет скрытых циклов; архитектурно значимые имена: запрещённые Port/Adapter не использованы.
- В. DDD и размещение поведения: инварианты сущностей и VO не вынесены в обработчики или инфраструктуру; семантика команд/запросов сохранена, побочные эффекты не замаскированы под запрос; нет дублирования доменных понятий между модулями без явного преобразования; нет глобального состояния, статических одиночек, скрытых связей через контейнер.
- Г. Контракты и совместимость: семантика входов/результатов, значения по умолчанию, исключения, поведение при ошибках; затронутые внешние контракты (CLI, YAML/JSONL-форматы, события, DTO, файлы сессий и аудита, коды завершения); критические изменения обратной совместимости обозначены явно; контрактная документация и примеры обновлены согласованно.
- Д. Проверяемость результата: учтён результат Deptrac, отдельно проверена семантика границ, которую инструмент не распознаёт; изучена дельта метрик качества (`vendor/bin/coding-standard-metrics-review --base=<target>`, правила — docs/conventions/ops/quality-metrics.md): она подсвечивает, куда смотреть; замечание выставляется по решению ревьювера, сам факт регрессии не блокирует; архитектурные риски подтверждены подходящими контрактными/интеграционными тестами (без повторной ревью качества тестов); каждое замечание содержит: место, нарушенное правило или ADR, последствие, требуемую коррекцию; личное предпочтение не выдаётся за архитектурное нарушение.
- Условные блоки (при затрагивании области): DI и конфигурация (ADR-012, PHAR-безопасные resource/exclude); время выполнения (пути/параметры PHAR не зафиксированы в скомпилированном контейнере, учтены кеширование и два контекста размещения); надёжность (повторы, прерывание при сбоях, бюджеты, конкурентность, транзакции); внешние зависимости (необходимость, допустимый слой, не протекает в доменный контракт); секреты (архитектурные границы не допускают утечки в журналы, тесты, отчёты, доменную модель); ADR (скрытой смены паттерна нет, значимое новое решение имеет ADR с альтернативами и последствиями — особенно ADR-006, ADR-011, ADR-012).
Не входит в RV-A: повторная проверка функциональности, качества тестов, общего именования и код-уровневых конвенций (это зона RV-F).
Если есть замечания — сформулируй конкретные запросы на изменения с файлом и строкой.
Если всё в порядке — одобри изменения.
Важно: НЕ исправляй код сам — только укажи замечания.
```

2. **Архитектор одобрил изменения (апрув RV-A)** → переходи к **Шагу 6**.
3. **Есть замечания** → вернись к **Шаг 2** для доработки, передав замечания:

```
<role-title>, доработай задачу: todo/<TASK-ID>.todo.md по замечаниям ревьювера RV-A:
<суть замечаний>
НЕ делай коммит — я сделаю сам.
```

Правило снятия замечаний RV-A: замечание снимает назначенный архитектор после исправления либо при действующем, заранее согласованном пользователем исключении (тимлид фиксирует отступление, но не утверждает его единолично); постоянное изменение нормы оформляется изменением Конвенции/ADR, а не записью о техдолге.

Затем повтори ревью кода (**Шаг 5б**).

#### Доработки, недействительность апрувов и лимиты треков

- **Недействительность апрувов после доработки.** Доработка по замечаниям любого трека или QA отменяет апрув другого трека, если дельта изменений затрагивает его область: RV-F недействителен, если изменились поведение, публичный контракт, сценарии использования, обработка ошибок/повторы, безопасность, тестовые сценарии или строки, затронутые замечаниями RV-F; RV-A недействителен, если дельта затрагивает границы, контракты или паттерны его области. Решение о затронутости принимает тимлид по дельте diff; сомнение трактуется в пользу повторного ревью затронутых пунктов. Повторное ревью выполняется по изменённому фрагменту и списку последствий, без полного перечитывания неизменённого кода. При недействительности обоих апрувов повторное ревью идёт в порядке RV-F → RV-A по затронутым пунктам, если тимлид не зафиксировал иное.
- **Дельта во время идущего RV-A:** предмет заключения — diff на момент старта ревью; дельта, поступившая во время ревью, обрабатывается как повторное ревью затронутых пунктов.
- **Замечания треков противоречат друг другу** (например, RV-F требует поведения по постановке, RV-A — решения, ему противоречащего, или наоборот): фиксация обоих замечаний → эскалация тимлиду; при неразрешимости — пользователю (компромисс не маскирует спор).
- **Лимит «3 на трек»:** счётчик «3 итерации ревью → доработка» ведётся **отдельно на каждый трек** RV-F и RV-A. Итерация = ревью с содержательными замечаниями → доработка; сбой инструмента без заключения итерацией не считается. Исчерпание лимита = эскалация пользователю с перечнем незакрытых замечаний; замечания не снимаются «молча»; счётчик сбрасывается только решением пользователя. Для комбинированного ревью C0–C1 действует общий лимит 3.
- **Взаимодействие лимитов:** счётчик «реализация → самопроверка → исправление» (см. таблицу «Лимиты») учитывает циклы самопроверки до запуска ревью; лимиты треков — циклы «ревью → доработка» после запуска ревью. Счётчики независимы, двойного учёта нет.
- **Носитель статусов апрувов:** одна запись на трек в формате «трек, дата, ссылка на diff/хеш коммита» — в файле задачи (до создания PR) или в описании PR (после создания); новый апрув заменяет предыдущий; отменённый помечается «недействителен — дата, причина» (в т.ч. при аннулировании всех апрувов по сценарию «дефект постановки»); действителен последний апрув, сопоставленный с итоговым diff.
- **QA-петля:** доработка по замечаниям QA → повторное RV-F по дельте и списку последствий → RV-A по пересмотренному гейтингу, при недействительности апрува, по затронутым пунктам → повторный QA — подтверждение замечаний и обязательные проверки, без полного перезапуска. Счётчики ведёт тимлид при выдаче заданий и фиксирует в файле задачи; счётчик QA-петли тикает на каждом проходе «ревью с замечаниями → доработка» внутри петли; счётчики треков внутри QA-петли не тикают; нестабильный тест — замечание QA с возвратом на доработку (диагностика причины), а не «успешный повторный прогон».

### **Шаг 6:** Коммит, публикация, PR

> **Примечание:** При сабагент-конвейере самопроверка и ревью кода уже пройдены на Шагах 4–5, до создания PR. Статус `review` в заголовке с метаданными можно пропустить — задача переводится сразу в `done`.

🛑 **Контрольная точка перед коммитом:**
- [ ] Шаг 4 (самопроверка) выполнен — замечаний нет.
- [ ] Шаг 5 (ревью кода) выполнен: оба трека пройдены по гейтингу — RV-F (Шаг 5а) и RV-A (Шаг 5б, при записи `RV-A: да`) — апрувы получены.
- [ ] Апрувы действительны именно для итогового набора изменений (см. «Недействительность апрувов после доработки»).
- [ ] `make check` — зелёный.
- Если любой из шагов пропущен — **остановись** и вернись к пропущенному.

1. Закоммить все изменения по Conventional Commits (см. [`docs/git-workflow/commits.md`](../../../../docs/git-workflow/commits.md)).
2. Обнови файл задачи: `status: done`, `pr: '#<NUMBER>'`.
3. Перенеси задачу в `todo/done/`: `git mv todo/<TASK-ID>.todo.md todo/done/<TASK-ID>.todo.md`.
4. Обнови ссылки в Epic и связанных задачах (если есть).
5. Закоммить и запушь.
6. Создай PR через `gh pr create` (см. [`docs/git-workflow/pull-request.md`](../../../../docs/git-workflow/pull-request.md)):
   - `--base main`
   - `--label "pi"` (или другая метка AI-агента)
   - Body: постановка, изменения, ключевые решения, результаты review, проверки.
   - **Перенеси записи апрувов треков (RV-F/RV-A) из файла задачи в описание PR** — записи апрувов хранятся в описании PR после его создания.
7. Отчитайся пользователю: номер PR, краткое саммари.

### **Шаг 7:** Слияние и финализация

1. После подтверждения пользователя выполни слияние PR: `gh pr merge <N> --squash --delete-branch`.
   - Слияние без обхода `--admin`: PR создаётся от GitHub App (идентичность агента), одобрение ставит владелец. Настройка — [Идентичность агента](../../../../docs/guide/agent-identity.md).
2. Переключись на `main`: `git checkout main && git pull origin main`.
3. Проверь: `git status` — working tree должен быть чистым.
4. Удали рабочую ветку (если не удалена автоматически).
5. Отчитайся пользователю об итогах и предложи следующую задачу.

## Уровни сложности

Уровень уже задан в YAML front matter задачи в поле `complexity`. Отдельно определять его перед запуском не нужно: `--task-id` читает значение из файла автоматически. Для ручного переопределения используй `--complexity`. Если не передан ни один из этих параметров, `watch-subagent.sh` завершит запуск ошибкой.

| Уровень | Значение |
| --- | --- |
| `C0` | Тривиальная — простая правка без архитектурных решений |
| `C1` | Низкая — простая задача в одном модуле/слое |
| `C2` | Средняя — задача с несколькими компонентами или интеграциями |
| `C3` | Высокая — сложная архитектурная задача с множеством зависимостей |
| `C4` | Очень высокая — требует глубокой экспертизы или исследования |
| `C5` | Экстремальная — нерешённая проблема, требует R&D |
