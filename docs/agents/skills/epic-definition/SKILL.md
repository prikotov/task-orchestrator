# Подготовка концепции эпика

Навык процесса подготовки концепции эпика — от запроса до принятой концепции в файле эпика. Концепция — это проблема, цель, границы и требования; **не** план задач и **не** реализация.

## Когда использовать

- Пользователь просит подготовить или сформулировать эпик (создать файл `EPIC-*.todo.md`): описать проблему, цель, границы, требования с приоритетами, риски.
- Актуализация концепции существующего эпика: дорабатывай концепцию, не стирая существующий план задач (план — компетенция навыка `epic-decomposition`).
- Запрос сразу на эпик с задачами (концепция + декомпозиция) — комплексный запрос: доведи концепцию до принятия уполномоченным `A` настоящим навыком, затем продолжай декомпозицию навыком `epic-decomposition` в том же запросе (протокол, раздел 1).
- Эпик всегда начинается с концепции: **принятая концепция не означает готовность эпика к исполнению** — план задач строится навыком `epic-decomposition`: в том же запросе, если декомпозиция входила в исходный запрос, иначе отдельным запросом.

Не использовать:

- декомпозиция эпика на задачи — навык `epic-decomposition` (запускай после принятия концепции — в том же запросе, если декомпозиция входила в него);
- реализация эпика — `epic-via-subagents`;
- постановка одиночной задачи вне эпика — навык `task-definition`.

## Как использовать

> Общий протокол подготовки постановок: [протокол в материалах навыка task-definition](../task-definition/references/definition-protocol.md) — прочитай до выполнения шагов. Материалы навыков лежат рядом с их `SKILL.md`, а не в корне принимающего проекта. Навыки `task-definition`, `epic-definition`, `epic-decomposition` устанавливаются совместно с общим протоколом: настоящий навык зависит от `task-definition`; зависимость не установлена — стоп-условие, без протокола не продолжай (протокол, раздел 1).

### **Шаг 1:** Исследование контекста и дублей

1. Найди по `AGENTS.md` принимающего проекта: руководство по созданию эпиков, шаблон эпика, валидатор, матрицу RACI, каталог ролей.
2. Проверь дубликаты: поиск по существующим эпикам (активным, в бэклоге, завершённым) по теме и `ID`.
3. Собери контекст: связанные эпики и задачи, зависимости, документы, действующие ограничения.

Результат шага: источники с путями; дубликат найден или исключён; контекст эпика.

### **Шаг 2:** Выбор этапов и участников по RACI

1. Найди раздел матрицы RACI для эпиков (или раздел, который правила принимающего проекта отводят концепции эпика).
2. Зафиксируй участников с цитатами строк (формат цитат — как в навыке `task-definition`, Шаг 2): автор концепции (`R`), консультанты (`C` применимых строк), проверяющий концепции, принимающий концепцию (`A`). Проверяющий ищется по смыслу артефакта и этапа: применимая строка этапа проверки концепции в разделе матрицы либо легенда, явно закрепляющая проверку за `A` этапа; имена строк различаются между проектами, фиксированных названий нет, строка проверки плана задач концепцию не проверяет (протокол, разделы 3 и 6). Проверяющий однозначно не определён — стоп-условие: согласование с уполномоченным владельцем (`A`) или пользователем, не подстановка; автоматическое назначение `A` уточнения проверяющим запрещено.
3. Пробелы и конфликты матрицы — стоп-условие: согласование, не угадывание (протокол, раздел 3).

### **Шаг 3:** Согласование вопросов и объёма

1. Сформулируй открытые вопросы: проблема, ожидаемый результат, границы (что входит и что не входит), требования и их приоритеты, риски.
2. Вопросы есть — согласуй ответы с пользователем или `A`; нет — переходи к Шагу 4.
3. Дополнения требований сверх исходного запроса — с обоснованием и способом проверки; расширение объёма эпика — по согласованию (протокол, раздел 7).

### **Шаг 4:** Делегирование черновика концепции

Черновик пишет `R` из Шага 2 (сам — если это твоя роль, иначе сабагенту с файлом роли). Пример промпта делегирования:

```
Подготовь черновик концепции эпика.

Роль: загрузи из файла <путь к файлу роли из каталога ролей проекта>.
Запрос пользователя: <текст запроса>.
Материалы: руководство по созданию эпиков <путь>, шаблон эпика <путь>,
контекст: <связанные эпики, задачи, документы>.
Требования консультантов (если уже получены): <список; каждое — с обоснованием
и способом проверки>.

Создай файл эпика <EPIC-ID>.todo.md и заполни секции концепции:
проблема, цель, границы (что входит / что не входит), требования
с приоритетами, риски и зависимости, критерии приёмки эпика.
План реализации задач не создавай и не переписывай — он строится
и актуализируется отдельным процессом (навык epic-decomposition)
после принятия концепции.
Значения, которых нет в материалах, не придумывай — вынеси
в открытые вопросы.

Входы: запрос, материалы, контекст.
Выходы: путь к файлу эпика; список открытых вопросов; список внесённых
дополнений с обоснованием и способом проверки.
Стоп-условия: противоречие правилам проекта; дубликат существующего эпика;
решение не определено на уровне эпика (требует декомпозиции или исследования) —
остановись и верни причину с открытыми вопросами.
```

Эпик уже существует и содержит план задач — дорабатывай только концепцию: план не стирай и не переписывай; актуализация плана — навык `epic-decomposition` по принятой концепции.

### **Шаг 5:** Консультации

1. Момент консультации задают правила принимающего проекта, не навык (протокол, раздел 4). Консультация задана до начала этапа — получи вход каждого обязательного `C` **до черновика концепции** (до Шага 4), затем уточняй по черновику; консультация задана по черновику — запрос по готовому черновику; в типичной матрице мнение `C` требуется до завершения этапа и не позже принятия. Срок — по правилам принимающего проекта; местных сроков нет — согласуй срок с `A`, не выдумывай (протокол, раздел 4).
2. Требования консультантов вносит в черновик `R`; конфликт требований разрешает `A`.
3. Просроченный без ответа запрос — зафиксируй и согласуй с `A` (протокол, раздел 4).

Формат запроса консультанту — как в навыке `task-definition`, Шаг 5; в вопросах укажи границы и приоритеты требований эпика.

### **Шаг 6:** Проверка

1. **Содержание** — проверяет участник, определённый в Шаге 2: цель измерима; границы непротиворечивы; каждое блокирующее требование (`Must Have` или эквивалент по руководству проекта) имеет способ проверки; риски и зависимости учтены; допустимые технические ограничения (технологии, интеграции, среды) зафиксированы как границы концепции, а не как план задач; концепция не содержит плана задач и деталей реализации.
2. **Формат** — валидатор пакета todo-md (типичная команда: `php vendor/bin/todo-md validate <путь к файлу эпика>`; точную команду возьми из правил проекта).

Замечания есть → Шаг 7. Замечаний нет → Шаг 8.

### **Шаг 7:** Доработка

Доработку выполняет `R` по замечаниям (промпт — как в навыке `task-definition`, Шаг 7), затем повтор проверки. Лимит итераций — по таблице «Лимиты».

### **Шаг 8:** Принятие и отчёт

1. Решение принимает `A`: «принято» или отклонение с замечаниями (→ Шаг 7).
2. После принятия: статус эпика — только из справочника статусов установленного todo-md и только его средствами. Принятие концепции — не готовность эпика к исполнению и не основание перевода в `done`: декомпозиция входила в исходный запрос — продолжай навыком `epic-decomposition` в этом же запросе; не входила — предложи декомпозицию следующим шагом (отдельным запросом).
3. Если руководство или валидатор установленного todo-md требуют заполненного плана задач для валидности или готовности файла эпика — не объявляй промежуточную концепцию полностью валидной: зафиксируй ограничение в отчёте (валидация будет завершена после декомпозиции навыком `epic-decomposition`); не ослабляй валидатор и не выдумывай статусы.
4. Уведоми `I` применимых строк о результате.
5. Отчитайся пользователю: файл эпика, участники с цитатами строк RACI, консультации, проверка (содержание; формат — с учётом ограничения пункта 3 этого шага), решение `A`, открытые вопросы, следующий шаг (декомпозиция — навыком `epic-decomposition`: в этом же запросе, если она входила в исходный запрос; иначе — отдельным запросом).

## Лимиты

| Лимит | Значение |
|---|---|
| Итерации доработка → проверка | Предел из правил принимающего проекта или согласованного плана запуска; не задан — согласуй с пользователем или `A` до повторных запусков, собственные дефолты не выдумывай |
| Повторные запросы одному консультанту | Предел из правил принимающего проекта или согласованного плана запуска; не задан — согласуй с пользователем или `A` до повторных запусков, собственные дефолты не выдумывай |
| Исчерпание лимитов | Эскалация пользователю |

## Стоп-условия

| Ситуация | Действие |
|---|---|
| Нет раздела/строки RACI для концепции эпика, два `A`, нет `R` или проверяющий концепции не определён однозначно | Согласовать состав участников и проверяющего с пользователем или уполномоченным `A`; основание зафиксировать; до решения концепцию проверенной не объявлять |
| Навык `task-definition` с общим протоколом не установлен | Остановиться; согласовать с пользователем совместную установку набора навыков |
| Механизм запуска сабагентов не установлен | Согласовать способ делегирования с пользователем |
| Найден дубликат эпика | Согласовать: доработать существующую концепцию или создать новую |
| Требование не формулируется проверяемо на уровне эпика | Вынести в открытые вопросы или предложить исследовательскую задачу (по правилам проекта) |
| Расширение объёма эпика в ходе работы | Согласовать с пользователем или `A` до включения |

## Результат

- Файл эпика `<EPIC-ID>.todo.md` с принятой концепцией: проблема, цель, границы, требования с приоритетами, риски; план реализации задач не заполнен.
- Проверка формата — по правилу Шага 8.3: безусловного «валидатор зелёный» для промежуточной концепции без плана задач нет; если руководство/валидатор установленного todo-md требуют заполненного плана — ограничение зафиксировано в отчёте, а полная проверка формата обязательна до готовности эпика (завершается после декомпозиции навыком `epic-decomposition`). Статус — из справочника статусов установленного todo-md; решение `A` зафиксировано.
- Отчёт пользователю с участниками (цитаты строк RACI), консультациями, проверкой и открытыми вопросами; следующий шаг — декомпозиция навыком `epic-decomposition`: в том же запросе, если она входила в исходный запрос, иначе отдельным запросом.
