# Общий протокол подготовки постановок

Протокол общий для навыков `task-definition`, `epic-definition` и `epic-decomposition`. Каждый навык задаёт свой вид результата (постановка задачи, концепция эпика, план задач эпика); этот документ задаёт единые правила: источники, назначение участников, консультации, проверку, принятие и повторный запуск.

Файл лежит в материалах навыка `task-definition` — в каталоге `references/` рядом с его `SKILL.md`. Пути материалов навыка не совпадают с корнем принимающего проекта: ссылка вида `references/...` внутри навыка читается от каталога этого навыка, а не от корня проекта.

## 1. Границы процесса

- Процесс готовит постановку и **не создаёт реализацию**. После принятия постановки реализация начинается только отдельным запросом или процессом принимающего проекта.
- Запрос пользователя на создание постановки — разрешение на весь процесс: исследование, выбор этапов и участников, согласование, делегирование черновика, консультации, проверку, доработку и принятие. Отдельное подтверждение внутреннего шага не требуется, кроме случаев, когда правила принимающего проекта требуют его явно. Комплексный запрос (например, «подготовь эпик с задачами») разрешает цепочку навыков: концепция эпика навыком `epic-definition` доводится до принятия уполномоченным `A`, затем декомпозиция навыком `epic-decomposition` — без отдельного запроса; декомпозиция, не входившая в исходный запрос, предлагается следующим шагом, а не запускается.
- Навыки `task-definition`, `epic-definition` и `epic-decomposition` — один набор с общим протоколом и устанавливаются совместно: `epic-definition` и `epic-decomposition` зависят от `task-definition`, в материалах которого лежит этот протокол. Отсутствие зависимости (в принимающем проекте нет установленного `task-definition` с материалами протокола) — стоп-условие: остановись и согласуй с пользователем совместную установку набора навыков; без общего протокола не продолжай.
- Оформление файлов задач и эпиков — по руководству, шаблонам и справочникам пакета todo-md принимающего проекта. Навык не дублирует их: используй актуальные версии этих документов и валидатор пакета.

## 2. Источники принимающего проекта

Все источники находи через `AGENTS.md` принимающего проекта — не через документы пакета task-orchestrator. Типичные пути приведены для ориентира; подтверждай их по `AGENTS.md` принимающего проекта:

| Источник | Типичный путь | Назначение |
|---|---|---|
| Правила проекта | `AGENTS.md` | Корневой источник: пути ролей, матрицы, руководств |
| Каталог ролей | `docs/agents/roles/team/` | Файлы ролей для загрузки и делегирования |
| Матрица RACI | `docs/agents/raci-matrix.md` | Назначение участников по виду работы, области и этапу |
| Руководство по постановкам | `docs/todo-md/AGENTS_TASK_WRITING_GUIDE.md` | Формулировки, шаблоны, справочники |
| Валидатор | `php vendor/bin/todo-md validate` | Проверка формата файлов задач и эпиков |

Правила:

- Если типичный путь не подтверждается `AGENTS.md` принимающего проекта — используй путь из `AGENTS.md`, а не типичный.
- Отсутствие источника — стоп-условие: согласуй с пользователем, не подставляй путь пакета task-orchestrator.

## 3. Назначение участников по RACI

Состав участников не фиксирован. Навык не предписывает, кто пишет, проверяет и принимает: это определяет матрица RACI принимающего проекта.

Алгоритм для каждого вида работы:

1. **Вид работы** — не только значение `type` и не расширение файла. Сначала проверь специализированные циклы правил принимающего проекта (например, цикл проектирования процессов взаимодействия команды — для регламентов, оркестрационных навыков и изменений ответственности): участники такого изменения определяются по циклу — по виду работы, области и этапу. Цикл не применим — используй значение `type` по справочнику типов принимающего проекта; для типов без своего раздела матрицы — нормативное сопоставление из правил принимающего проекта (если оно там задано). Назначение автора по расширению файла (например, «`.md` — значит, пишет технический писатель») недопустимо.
2. **Раздел матрицы** — найди раздел или специализированный цикл по виду работы.
3. **Область работ** (`scope`) — строка раздела применяется, когда её область затронута постановкой; неприменимые строки пропускаются, а не заполняются «для галочки».
4. **Этап** — строка раздела для конкретного шага процесса: уточнение, анализ, проверка, принятие.
5. **Легенда матрицы** — трактовка обозначений. Стандартная: `R` — исполнитель (пишет, делает); `A` — владелец результата этапа, принимает решение «принято / не принято», ровно один на строку; `C` — консультант, даёт требования до завершения этапа; `I` — оповещаемый, получает результат; `RA` — одна роль одновременно исполняет этап и владеет его результатом; строчные `raci` — условное участие при затронутой области. Следуй легенде принимающего проекта, а не этой выжимке.

Для каждого участника зафиксируй обоснование — цитату: раздел или цикл матрицы, строка этапа, обозначение в ячейке.

Правила:

- Оркестратор (координатор, назначаемый правилами принимающего проекта) может быть назван явно только как **координатор** процесса: запускает шаги, собирает ответы, ведёт отчёт. Координация не подменяет `A`: решение о принятии принимает тот, кому даёт его строка матрицы.
- **Пробелы и конфликты матрицы** — нет применимой строки, два `A` в строке, нет `R`, неясна применимость строки области — не угадывай. Зафиксируй вопрос и согласуй с пользователем или `A` по правилам принимающего проекта; решение и его основание внеси в постановку или отчёт.
- **Ревью кода не является ревью постановки** без основания: не привлекай ревьювера кода к проверке постановки, концепции или плана, если матрица не назначает его на этап проверки этого артефакта для данного типа работы.
- **Проверяющий содержания** ищется только в матрице и её легенде: применимая строка этапа проверки для артефакта данного вида либо легенда, явно закрепляющая проверку за `A` этапа. Имена строк проверки различаются между проектами — отбирай строку по смыслу артефакта и этапа, без фиксированных названий; проверка концепции эпика и проверка плана задач — разные проверки. Проверяющий однозначно не определён — стоп-условие (раздел 6): согласование с уполномоченным владельцем (`A`) или пользователем, не подстановка.
- Независимый проверяющий сверх RACI не назначается. Проверка артефакта при этом обязательна — см. раздел 6.
- **Основания участия:** строка матрицы, легенда матрицы (включая условное участие при затронутой области) либо явно согласованное исключение с фиксацией (кто согласовал, что и на каком основании). Самоназначение и назначение без этих оснований запрещено.
- **Проектирование предметного решения и его оформление — разные виды работы.** Автора модели (процесса, регламента, решения) назначает принимающий проект — строкой, циклом или легендой матрицы; оформитель принятой модели не наследует полномочия автора и не проектирует содержание самостоятельно — пробел возвращается владельцу решения.
- Навыки переносимы между проектами: фиксированные роли внутри навыков не задаются.

## 4. Консультации и оповещения

- Момент обязательной консультации задаёт принимающий проект (легенда матрицы, правила этапа): в типичной матрице RACI мнение `C` получают **до завершения этапа**, а не только после черновика. Консультация требуется до начала этапа — получи вход консультанта до черновика, затем уточняй по черновику; консультация задана по черновику — запрос по готовому черновику.
- Срок или границу ожидания задаёт механизм запуска или согласованный план принимающего проекта; не навязывай всем проектам согласование календарного срока на каждый вызов. Граница не задана и ожидание существенно — согласуй её с `A` до отправки запроса и укажи согласованную в самом запросе; собственные сроки не выдумывай и бесконечно не жди.
- Истечение срока — не согласие консультанта и не освобождение от обязательной консультации. Ответ не получен — зафиксируй факт; `A` выбирает повтор запроса, блокировку этапа, эскалацию или разрешённое правилами исключение с фиксацией основания. Не принимай результат, нарушив обязательство консультации.
- `I` уведомляются о результате. Уведомление не блокирует принятие, если правила проекта не требуют иного.
- Конфликт требований консультантов разрешает `A`; при отсутствии решения — эскалация по правилам проекта.

## 5. Черновик и доработка

- Черновик пишет `R` этапа. Если `R` — роль, в которой ты работаешь, пиши черновик сам; иначе делегируй сабагенту этой роли.
- **Несколько `R` и один писатель на файл.** Если в применимой строке несколько `R`: распределение вклада между ними и ответственность за итоговую сборку несёт `A` этапа. Файл пишет один участник (один писатель на файл); консультанты возвращают требования автору файла, а не пишут его параллельно.
- Замечания проверки дорабатывает `R`; после доработки проверка повторяется.
- Согласованные формулировки не меняются самовольно: изменение согласованного текста — только новым проходом `R` → проверка → `A` с указанием причины.

## 6. Проверка артефакта

Проверка обязательна и состоит из двух частей:

| Часть | Что проверяется | Чем проверяется |
|---|---|---|
| Содержание | Проблема, результат, границы, критерии; проверяемость критериев; отсутствие противоречий; обоснованность дополнений | Проверяющий по матрице и её легенде: применимая строка этапа проверки либо проверка, закреплённая легендой за `A` этапа |
| Формат | Структура файла, метаданные, ссылки | Руководство пакета todo-md и валидатор |

- Кто проверяет содержание — определяют матрица и её легенда: применимая строка этапа проверки для артефакта данного вида (постановка задачи, концепция эпика, план задач эпика) либо легенда, явно закрепляющая проверку за `A` этапа. Имена строк не фиксированы и различаются между проектами — отбирай строку по смыслу артефакта и этапа; строка проверки плана не проверяет концепцию, ревью кода не проверяет постановку.
- Легенда явно задаёт проверку для `A` — отдельная строка проверки не навязывается; проверяющий сверх матрицы и легенды не добавляется.
- Проверяющий однозначно не определён (нет применимой строки, легенда не закрепляет проверку) — стоп-условие: согласуй назначение с уполномоченным владельцем (`A`) или пользователем по правилам принимающего проекта и зафиксируй основание решения. До решения артефакт проверенным не объявляется. Автоматическая подстановка проверяющего навыком (например, «проверит `A` уточнения», «проверит ревьювер кода») запрещена.
- Валидатор обязателен: постановка не объявляется готовой, пока валидатор не зелёный и решение `A` не получено.

## 7. Дополнения и объём

- Каждое дополнение требований к постановке сверх исходного запроса сопровождай обоснованием (зачем) и способом проверки (как убедимся, что требование выполнено).
- Расширение объёма работ сверх исходного запроса согласуется с пользователем или `A` до включения в постановку.

## 8. Готовность, статусы, повторный запуск

- Готовность постановки = решение `A` + зелёный валидатор + заполненность по руководству пакета todo-md. Незавершённая постановка готовой не объявляется.
- Открытые вопросы делятся на **блокирующие** и **неблокирующие**. Блокирующий запрещает объявлять постановку (концепцию, план) готовой. Неблокирующий фиксируется с владельцем решения и основанием допустимости (почему не блокирует).
- Неизвестный способ реализации сам по себе не блокер постановки, если цель, ограничения и способ проверки ясны — техплан заполнит исполнитель. Существенная неопределённость результата, реализуемости или контракта требует исследовательской задачи (по правилам проекта).
- Статусы и переходы — только средствами установленного todo-md принимающего проекта (справочник статусов и его команды). Навык не вводит собственных состояний.
- Повторный запуск навыка: сначала найди существующий артефакт (файл задачи или эпика по `ID`, план эпика) — не создавай дубликат. Работай с существующим файлом; согласованные ранее формулировки не переписывай.

## 9. Делегирование через роли

- Файл роли исполнителя бери из каталога ролей принимающего проекта; путь каталога — из `AGENTS.md` принимающего проекта.
- Загрузку роли выполняй установленным метанавыком `become-role`; запуск сабагента — установленным навыком запуска (например, `run-subagent`). Обнаруживай их по каталогу навыков принимающего проекта.
- Если механизм запуска сабагентов не установлен — стоп-условие: согласуй способ делегирования с пользователем.
- Промпт делегирования не содержит имён участников: роль передаётся файлом роли, задание — текстом с плейсхолдерами. Обязательные части промпта:
  - **входы** — материалы и их пути (запрос, руководство, шаблон, контекст);
  - **выходы** — артефакт и путь к нему (файл, список открытых вопросов, список внесённых дополнений);
  - **стоп-условия** — когда остановиться и что вернуть (противоречие правилам, дубликат, нехватка данных для обязательных полей, недоступность материала).
