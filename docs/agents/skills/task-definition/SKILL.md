# Подготовка постановки задачи

Навык процесса подготовки постановки одиночной задачи — от запроса до принятого файла задачи. Не оформление файлов (это делает руководство пакета todo-md) и не реализация.

## Когда использовать

- Пользователь просит сформулировать, подготовить или уточнить постановку одиночной задачи (создать файл `TASK-*.todo.md`) до начала реализации.
- Идею, проблему или дефект нужно превратить в проверяемую постановку.

## Как использовать

Сначала прочитай [общий протокол подготовки постановок](references/definition-protocol.md). Он описывает источники, назначение участников, консультации, делегирование, проверку и принятие. Ниже — особенности подготовки отдельной задачи.

### **Шаг 1:** Исследование контекста и дублей

1. Прочитай правила проекта, руководство по созданию задач, справочники (типы, статусы, ценность, сложность, приоритет), шаблон задачи и матрицу ответственности команды (RACI). Ознакомься с доступными ролями и командой проверки формата.
2. Проверь дубликаты: поиск по каталогам задач проекта (активные, отложенные, завершённые) по ключевым словам и `ID`.
3. Собери контекст: проблемная область, затронутые модули, связанные задачи и эпики, документы.

Результат шага: список источников с путями; дубликат найден или исключён; контекст задачи.

### **Шаг 2:** Выбор этапов и участников по RACI

1. Определи вид работы по [разделу 3 «Назначение участников по RACI» общего протокола подготовки постановок](references/definition-protocol.md#3-назначение-участников-по-raci): специальный цикл проекта либо `type` по справочнику типов.
2. По матрице ответственности команды (RACI) определи участников подготовки задачи. Выбери строки по виду работы, области и этапу.
3. Пропусти неприменимые этапы и области участия.
4. Зафиксируй участников с цитатами строк матрицы:

| Участие | Как определяется | Обоснование (формат цитаты) |
|---|---|---|
| Автор черновика (`R`) | Строка этапа уточнения или анализа | «раздел `<тип>`, строка `<этап>`: `<роль-колонка>` — `R`» |
| Консультанты (`C`) | Ячейки `C` применимых строк; условность участия (строчные буквы) — по легенде матрицы | «раздел `<тип>`, строка `<этап>`: `<роль-колонка>` — `C`» |
| Проверяющий содержания | Строка проверки постановки либо легенда матрицы, явно закрепляющая проверку за `A` | «раздел `<тип>`, строка `<этап>`: `<роль-колонка>` — `<буква>`» либо «легенда матрицы: `<цитата правила>`» |
| Принимающий (`A`) | `A` этапа, за которым правила проекта закрепляют принятие | «раздел/цикл `<вид работы>`, строка `<этап>`: `<роль-колонка>` — `A`» |

Если в строке несколько `R`, распределение работы и итоговую сборку определяет `A`. Файл пишет один участник по [разделу 5 «Черновик и доработка» общего протокола подготовки постановок](references/definition-protocol.md#5-черновик-и-доработка).

5. Неоднозначные назначения и конфликты матрицы согласуй с пользователем или уполномоченным `A` и зафиксируй основание решения. До назначения проверяющего не объявляй постановку проверенной.

### **Шаг 3:** Согласование вопросов и объёма

1. Сформулируй открытые вопросы о проблеме, результате, границах, критериях и зависимостях. Раздели их на блокирующие и неблокирующие по [разделу 8 «Готовность, статусы, повторный запуск» общего протокола подготовки постановок](references/definition-protocol.md#8-готовность-статусы-повторный-запуск). Неизвестный способ реализации не блокирует постановку, если результат, ограничения и проверка понятны. Существенную неопределённость вынеси на уточнение либо предложи исследовательскую задачу.
2. Вопросов нет и контекст полный — переходи к Шагу 4. Есть вопросы — согласуй ответы с пользователем или `A`.
3. Дополнения обосновывай, а расширение объёма согласуй по [разделу 7 «Дополнения и объём» общего протокола подготовки постановок](references/definition-protocol.md#7-дополнения-и-объём).

### **Шаг 4:** Делегирование черновика

Черновик пишет `R` из Шага 2. Если это твоя роль, пиши сам; иначе делегируй работу по [разделу 9 «Делегирование через роли» общего протокола подготовки постановок](references/definition-protocol.md#9-делегирование-через-роли).

Пример промпта делегирования (без имён участников; плейсхолдеры замени реальными значениями):

```
Подготовь черновик постановки задачи.

Роль: загрузи из файла <путь к файлу роли из каталога ролей проекта>.
Запрос пользователя: <текст запроса>.
Материалы: руководство по созданию задач <путь>, шаблон задачи <путь>,
справочники типов, ценности, сложности, приоритетов <пути>.
Контекст: <связанные задачи, эпики, документы>.
Требования консультантов (если уже получены): <список; каждое — с обоснованием
и способом проверки>.

Создай файл задачи <TASK-ID>.todo.md по руководству и шаблону проекта.
Значения обязательных полей, которых нет в материалах, не придумывай —
вынеси их в открытые вопросы.

Входы: запрос, материалы, контекст.
Выходы: путь к файлу задачи; список открытых вопросов; список внесённых
дополнений с обоснованием и способом проверки.
Стоп-условия: противоречие правилам проекта; дубликат существующей задачи;
недоступен материал из списка — остановись и верни причину с перечнем
открытых вопросов.
```

### **Шаг 5:** Консультации

1. Передай каждому `C` из Шага 2 запрос по его области. Момент консультации и границу ожидания определяй по [разделу 4 «Консультации и оповещения» общего протокола подготовки постановок](references/definition-protocol.md#4-консультации-и-оповещения). Обязательные консультации до черновика проведи перед Шагом 4.
2. Ответы консультантов вносит в черновик `R`; каждое требование — с обоснованием и способом проверки.
3. Отсутствие ответа и конфликт требований передай `A` по [разделу 4 «Консультации и оповещения» общего протокола подготовки постановок](references/definition-protocol.md#4-консультации-и-оповещения).

Пример запроса консультанту:

```
Прочитай черновик задачи <путь> и дай требования по своей области
до <срок или этап>.

Вопросы для проверки: <список вопросов по черновику>.
Формат ответа: каждое требование — текст, обоснование, способ проверки.
Если область черновика тебя не затрагивает — ответь «не применимо»
с указанием причины.
```

### **Шаг 6:** Проверка

Выполни обе части проверки по [разделу 6 «Проверка артефакта» общего протокола подготовки постановок](references/definition-protocol.md#6-проверка-артефакта):

1. **Содержание** — проверяет участник, назначенный в Шаге 2: проблема и ожидаемый результат сформулированы; критерии проверяемы; границы без противоречий; дополнения обоснованы; открытые вопросы либо закрыты, либо явно перечислены.
2. **Формат** — валидатор установленного todo-md. Команду проверки возьми из правил проекта.

Замечания есть → Шаг 7. Замечаний нет → Шаг 8.

### **Шаг 7:** Доработка

Доработку по замечаниям выполняет `R`. Пример промпта:

```
Доработай постановку задачи <путь> по замечаниям проверки:
<список замечаний>.

Согласованные формулировки (<перечень>) не меняй; если изменение необходимо —
укажи причину в ответе.
Выходы: обновлённый файл; список изменений с обоснованием.
Стоп-условия: замечание противоречит правилам проекта или требует расширения
объёма — остановись и верни вопрос на согласование.
```

После доработки повтори проверку (Шаг 6). Лимит итераций — см. таблицу «Лимиты».

### **Шаг 8:** Принятие и отчёт

1. Решение принимает `A` из Шага 2: «принято» или отклонение с конкретными замечаниями (отклонение → Шаг 7).
2. Зафиксируй решение и обнови статус средствами установленного todo-md по [разделу 8 «Готовность, статусы, повторный запуск» общего протокола подготовки постановок](references/definition-protocol.md#8-готовность-статусы-повторный-запуск).
3. Уведоми `I` применимых строк о результате.
4. Отчитайся пользователю:

```
Задача: <TASK-ID> — <название>
Файл: <путь>
Участники (раздел матрицы, строка, буква): <список с цитатами>
Консультации: <кто, что дал, что внесено; просроченные ответы>
Проверка: <проверяющий, результат содержания, результат валидатора>
Решение принимающего: <принято / отклонено>
Открытые вопросы: <блокирующие / неблокирующие с владельцем решения; или «нет»>
Следующий шаг: реализация — отдельным процессом проекта.
```

## Лимиты

| Лимит | Значение |
|---|---|
| Итерации доработка → проверка | Предел из правил проекта или согласованного плана запуска; если не задан, согласуй с пользователем или `A` до повторных запусков |
| Повторные запросы одному консультанту | Предел из правил проекта или согласованного плана запуска; если не задан, согласуй с пользователем или `A` до повторных запусков |
| Исчерпание лимитов | Эскалация пользователю |

## Стоп-условия

| Ситуация | Действие |
|---|---|
| Неоднозначное назначение или конфликт матрицы | Согласовать участников и зафиксировать основание по [разделу 3 «Назначение участников по RACI» общего протокола подготовки постановок](references/definition-protocol.md#3-назначение-участников-по-raci) |
| Механизм запуска сабагентов не установлен | Согласовать способ делегирования с пользователем |
| Найден дубликат задачи | Согласовать: доработать существующую постановку или создать новую |
| Недостаточно данных для обязательных полей | Вернуть открытые вопросы; значения не придумывать |
| Валидатор не зелёный после исчерпания итераций доработки | Эскалация пользователю |

## Результат

- Файл задачи `<TASK-ID>.todo.md`, соответствующий руководству установленного todo-md и прошедший проверку валидатором.
- Статус постановки — из справочника статусов установленного todo-md; решение `A` получено и зафиксировано.
- Отчёт пользователю: участники с цитатами строк RACI, консультации, проверка, решение, открытые вопросы.
