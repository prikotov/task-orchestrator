# Подготовка постановки задачи

Навык процесса подготовки постановки одиночной задачи — от запроса до принятого файла задачи. Не оформление файлов (это делает руководство пакета todo-md) и не реализация.

## Когда использовать

- Пользователь просит сформулировать, подготовить или уточнить постановку одиночной задачи (создать файл `TASK-*.todo.md`) до начала реализации.
- Идею, проблему или дефект нужно превратить в проверяемую постановку.
- Постановка готовится участниками по RACI принимающего проекта — навык не назначает участников сам.

Не использовать:

- реализация задачи — `task-via-subagents`;
- концепция эпика — навык `epic-definition`;
- декомпозиция эпика на задачи — навык `epic-decomposition`.

## Как использовать

> Общий протокол подготовки постановок: [references/definition-protocol.md](references/definition-protocol.md) — прочитай до выполнения шагов. Файл лежит в материалах этого навыка, а не в корне принимающего проекта. Протокол общий для набора навыков `task-definition`, `epic-definition`, `epic-decomposition` — устанавливай набор совместно; отсутствие зависимости у `epic-*` — стоп-условие (протокол, раздел 1).

### **Шаг 1:** Исследование контекста и дублей

1. Найди по `AGENTS.md` принимающего проекта: руководство по созданию задач, справочники (типы, статусы, ценность, сложность, приоритет), шаблон задачи, валидатор, матрицу RACI, каталог ролей.
2. Проверь дубликаты: поиск по каталогам задач принимающего проекта (активные, бэклог, завершённые) по ключевым словам и `ID`.
3. Собери контекст: проблемная область, затронутые модули, связанные задачи и эпики, документы.

Результат шага: список источников с путями; дубликат найден или исключён; контекст задачи.

### **Шаг 2:** Выбор этапов и участников по RACI

1. Определи вид работы по правилам принимающего проекта: применимый специализированный цикл либо значение `type` по справочнику типов (протокол, раздел 3).
2. Найди раздел матрицы RACI по виду работы (специализированный цикл либо раздел типа); отбор строк — по области работ и этапу (см. протокол, раздел 3).
3. Определи применимые этапы подготовки: не все строки раздела применимы к каждому типу работы — неприменимые пропускаются.
4. Зафиксируй участников с цитатами строк матрицы:

| Участие | Как определяется | Обоснование (формат цитаты) |
|---|---|---|
| Автор черновика (`R`) | Строка этапа уточнения или анализа | «раздел `<тип>`, строка `<этап>`: `<роль-колонка>` — `R`» |
| Консультанты (`C`) | Ячейки `C` применимых строк; условность участия (строчные буквы) — по легенде матрицы | «раздел `<тип>`, строка `<этап>`: `<роль-колонка>` — `C`» |
| Проверяющий содержания | Применимая строка этапа проверки постановки по смыслу либо легенда матрицы, явно закрепляющая проверку за `A` этапа (протокол, разделы 3 и 6); без собственной подстановки | «раздел `<тип>`, строка `<этап>`: `<роль-колонка>` — `<буква>`» либо «легенда матрицы: `<цитата правила>`» |
| Принимающий (`A`) | `A` применимой строки по правилам принимающего проекта — этап не фиксирован (уточнение, проверка или иной этап, за которым правила проекта закрепляют принятие) | «раздел/цикл `<вид работы>`, строка `<этап>`: `<роль-колонка>` — `A`» |

Если в применимой строке несколько `R`: распределение вклада и ответственность за итоговую сборку несёт `A`; файл пишет один участник (один писатель на файл); консультанты возвращают замечания автору без конкурентной записи в файл (протокол, раздел 5).

5. Пробелы и конфликты матрицы (нет строки, два `A`, нет `R`, проверяющий содержания не определён однозначно) — стоп-условие: согласование с пользователем или уполномоченным `A` по правилам принимающего проекта, не угадывание; основание решения зафиксируй, до решения постановка проверенной не объявляется.

### **Шаг 3:** Согласование вопросов и объёма

1. Сформулируй открытые вопросы: что неизвестно для постановки (проблема, ожидаемый результат, границы, критерии, зависимости). Раздели их на блокирующие и неблокирующие (протокол, раздел 8): блокирующие запрещают объявлять постановку готовой; неблокирующие фиксируй с владельцем решения и основанием допустимости. Неизвестный способ реализации сам по себе не блокер, если цель, ограничения и способ проверки ясны (протокол, раздел 8).
2. Вопросов нет и контекст полный — переходи к Шагу 4. Есть вопросы — согласуй ответы с пользователем или `A`.
3. Каждое дополнение требований сверх исходного запроса вноси с обоснованием и способом проверки; расширение объёма работ — только по согласованию (протокол, раздел 7).

### **Шаг 4:** Делегирование черновика

Черновик пишет `R` из Шага 2. Если `R` — роль, в которой ты работаешь, пиши черновик сам; иначе запусти сабагента этой роли через установленный навык запуска, передав файл роли из каталога ролей принимающего проекта (протокол, раздел 9).

Пример промпта делегирования (без имён участников; плейсхолдеры замени реальными значениями):

```
Подготовь черновик постановки задачи.

Роль: загрузи из файла <путь к файлу роли из каталога ролей проекта>.
Запрос пользователя: <текст запроса>.
Материалы: руководство по созданию задач <путь>, шаблон задачи <путь>,
справочники типов, ценности, сложности, приоритетов <пути>.
Контекст: <связанные задачи, эпики, документы>.
Требования консультантов (если уже получены): <список; каждое — с обоснованием
и способом проверки>.

Создай файл задачи <TASK-ID>.todo.md по руководству и шаблону проекта.
Значения обязательных полей, которых нет в материалах, не придумывай —
вынеси их в открытые вопросы.

Входы: запрос, материалы, контекст.
Выходы: путь к файлу задачи; список открытых вопросов; список внесённых
дополнений с обоснованием и способом проверки.
Стоп-условия: противоречие правилам проекта; дубликат существующей задачи;
недоступен материал из списка — остановись и верни причину с перечнем
открытых вопросов.
```

### **Шаг 5:** Консультации

1. Передай каждому `C` из Шага 2 запрос по его области в момент, заданный правилами принимающего проекта: в типичной матрице — до завершения этапа; консультация требуется до начала этапа — получи вход до черновика, затем уточняй по черновику (протокол, раздел 4). Срок или границу ожидания задаёт механизм запуска или согласованный план проекта; их нет и ожидание существенно — согласуй с `A`, не выдумывай.
2. Ответы консультантов вносит в черновик `R`; каждое требование — с обоснованием и способом проверки.
3. Ответ не получен в срок или границу ожидания — истечение срока не согласие и не освобождение от обязательной консультации: зафиксируй факт; `A` выбирает повтор, блокировку, эскалацию или разрешённое правилами исключение с фиксацией (протокол, раздел 4). Конфликт требований консультантов разрешает `A`.

Пример запроса консультанту:

```
Прочитай черновик задачи <путь> и дай требования по своей области
до <срок или этап>.

Вопросы для проверки: <список вопросов по черновику>.
Формат ответа: каждое требование — текст, обоснование, способ проверки.
Если область черновика тебя не затрагивает — ответь «не применимо»
с указанием причины.
```

### **Шаг 6:** Проверка

Обязательны обе части проверки (протокол, раздел 6):

1. **Содержание** — проверяет участник, определённый в Шаге 2 по строке проверки или легенде матрицы: проблема и ожидаемый результат сформулированы; критерии проверяемы; границы без противоречий; дополнения обоснованы; открытые вопросы либо закрыты, либо явно перечислены.
2. **Формат** — валидатор пакета todo-md принимающего проекта (типичная команда: `php vendor/bin/todo-md validate <путь к файлу задачи>`; точную команду возьми из правил проекта).

Замечания есть → Шаг 7. Замечаний нет → Шаг 8.

### **Шаг 7:** Доработка

Доработку по замечаниям выполняет `R`. Пример промпта:

```
Доработай постановку задачи <путь> по замечаниям проверки:
<список замечаний>.

Согласованные формулировки (<перечень>) не меняй; если изменение необходимо —
укажи причину в ответе.
Выходы: обновлённый файл; список изменений с обоснованием.
Стоп-условия: замечание противоречит правилам проекта или требует расширения
объёма — остановись и верни вопрос на согласование.
```

После доработки повтори проверку (Шаг 6). Лимит итераций — см. таблицу «Лимиты».

### **Шаг 8:** Принятие и отчёт

1. Решение принимает `A` из Шага 2: «принято» или отклонение с конкретными замечаниями (отклонение → Шаг 7).
2. После принятия: статус постановки — только из справочника статусов установленного todo-md и только его средствами; незавершённая постановка готовой не объявляется; блокирующие открытые вопросы запрещают объявлять готовность (протокол, раздел 8).
3. Уведоми `I` применимых строк о результате.
4. Отчитайся пользователю:

```
Задача: <TASK-ID> — <название>
Файл: <путь>
Участники (раздел матрицы, строка, буква): <список с цитатами>
Консультации: <кто, что дал, что внесено; просроченные ответы>
Проверка: <проверяющий, результат содержания, результат валидатора>
Решение принимающего: <принято / отклонено>
Открытые вопросы: <блокирующие / неблокирующие с владельцем решения; или «нет»>
Следующий шаг: реализация — отдельным процессом принимающего проекта.
```

## Лимиты

| Лимит | Значение |
|---|---|
| Итерации доработка → проверка | Предел из правил принимающего проекта или согласованного плана запуска; не задан — согласуй с пользователем или `A` до повторных запусков, собственные дефолты не выдумывай |
| Повторные запросы одному консультанту | Предел из правил принимающего проекта или согласованного плана запуска; не задан — согласуй с пользователем или `A` до повторных запусков, собственные дефолты не выдумывай |
| Исчерпание лимитов | Эскалация пользователю |

## Стоп-условия

| Ситуация | Действие |
|---|---|
| Нет применимой строки RACI, два `A`, нет `R` или проверяющий содержания не определён однозначно | Согласовать состав участников и проверяющего с пользователем или уполномоченным `A`; основание зафиксировать; до решения постановку проверенной не объявлять |
| Механизм запуска сабагентов не установлен | Согласовать способ делегирования с пользователем |
| Найден дубликат задачи | Согласовать: доработать существующую постановку или создать новую |
| Недостаточно данных для обязательных полей | Вернуть открытые вопросы; значения не придумывать |
| Ревью кода предлагают вместо проверки постановки | Не подменять: ревью кода не проверяет постановку; проверяющего искать в матрице и её легенде (Шаг 2), при неоднозначности — согласование |
| Валидатор не зелёный после исчерпания итераций доработки | Эскалация пользователю |

## Результат

- Файл задачи `<TASK-ID>.todo.md`, валидный по валидатору и руководству пакета todo-md принимающего проекта.
- Статус постановки — из справочника статусов установленного todo-md; решение `A` получено и зафиксировано.
- Отчёт пользователю: участники с цитатами строк RACI, консультации, проверка, решение, открытые вопросы.
