## 1. Назначение и границы модели

Модель добавляет в навык [`retrospective`](../../skills/retrospective/SKILL.md) **сессионный режим мини-ретроспективы** — сокращённый путь фиксации выводов после тяжёлой сессии, когда задача ещё не завершена и полная ретроспектива не запускается. Принцип — borrow principles, not implementation: ручной вызов Matt Pocock (`disable-model-invocation: true`) не заимствуется; режим запускается запросом пользователя или инициативой агента с подтверждением.

**Меняются:** раздел «Когда использовать» и «Как использовать» `SKILL.md` (новый сокращённый путь как отдельная секция после описания полного пути); `assets/retrospective-template.md` — пометка обязательного минимума разделов для сессии; смежные документы поиском (PM4).

**Не меняются:** полный режим ретроспективы (все 8 шагов — как есть); реестр `RETRO-ROADMAP.md` — пороги, статусы, семантика счётчиков; справочники `assets/evidence-contract.md`, `assets/fix-classification.md`, `assets/process-analysis-reference.md` (переиспользуются как есть); отдельный шаблон для сессий не создаётся.

## 2. Решения по триггеру и запуску

**Решение 2.1 (триггер).** В «Когда использовать» добавляется пункт: тяжёлая сессия без завершённой задачи — по явному запросу пользователя или по инициативе агента при подтверждении пользователя. Критерий «тяжёлой» — наблюдаемыми примерами: заметное буксование (повторные безуспешные попытки), лишние шаги (переделки уже сделанного), многократные исправления по требованию пользователя. Численный порог не вводится; при неоднозначности решение о запуске принимает пользователь.

**Решение 2.2 (антинойс).** Гладкая сессия — без мини-ретро: режим не запускается «на всякий случай», после каждой сессии автоматически — никогда. Прямо формулируется в SKILL.md.

**Решение 2.3 (граница с полной ретро).** Мини-ретро не отменяет и не заменяет полноценную ретроспективу после пользовательской приёмки задачи/эпика: граница фиксируется в сессионной секции (приёмка задачи запускает полный режим) и в триггере «Когда использовать» (Решение 2.1); полный режим структурно не меняется.

## 3. Решения по сокращённому пути

**Решение 3.1 (шаги).** Сессионный режим — сокращённый путь из четырёх шагов (вместо восьми):

1. **Сбор фактов сессии** — первоисточники по типу сессии: каталог запуска сабагента `var/log/watch-subagent/<...>/` (`run.log`, при наличии `events/`) — для сессий сабагентов; журнал интерактивной сессии pi (`~/.pi/agent/sessions/<...>.jsonl`) — для интерактивных сессий; `audit.jsonl` — если включён для цепочки. Применяется [контракт доказательств](../../skills/retrospective/assets/evidence-contract.md) без изменений: трассировка к моментам сессии, «неподтверждено» при отсутствии источника, обезличивание секретов.
2. **Анализ проблемы** — по направлениям справочника [process-analysis-reference.md](../../skills/retrospective/assets/process-analysis-reference.md), но **без оценки ролей** (Шаг 2 полного режима неприменим: сессия может не иметь завершённой задачи и ролевого состава). Находка, сущность которой — работа конкретной роли, фиксируется как проблема без ролевых оценок; оценка ролей — только в полной ретро после приёмки. Повторы проверяются по реестру и прошлым ретро.
3. **Предложения** — до трёх, с классификацией «симптом → тип фикса» по [fix-classification.md](../../skills/retrospective/assets/fix-classification.md) (все пять типов, включая «закрепление практики»); правило check over prose — без изменений; статусы `внедрено / TODO / требует обсуждения` — без изменений.
4. **Запись** — файл в `docs/agents/team-retro/` по обязательному минимуму разделов шаблона (Решение 3.2) + обновление реестра по штатным правилам Шага 7 полного режима.

**Решение 3.2 (обязательный минимум разделов шаблона).** Сессионный отчёт использует существующий шаблон с минимальным набором: **заголовок + метаданные** (обязателен; объект — сессия с устойчивым ключом по Решению 5.1), **проблемы** (обязателен; с доказательствами и направлениями — поля те же, что добавлены задачей переработки), **предложения для улучшения** (обязателен; с типом фикса и доказательством). Раздел **«оценка ролей» в сессионном режиме не заполняется** (пути оценки нет в шагах — Шаг 2 полного режима неприменим без завершённой задачи); раздел «что прошло хорошо» **опционален**: успешные практики фиксируются, только если есть что закрепить — предложением типа «закрепление практики». Раздел «важные комментарии» — опционален, как в полном режиме. Пометки минимума добавляются в шаблон в едином виде — «*(в сессионном режиме: обязательно / опционально / не заполняется)*» (как в Решении 4.2); отдельный файл шаблона не создаётся.

**Решение 3.3 (реестр).** Запись в `RETRO-ROADMAP.md` — по штатным правилам Шага 7 (счётчик +1 за ретро, ссылки, пороги, статусы). Семантика «упоминания в разных ретро» не меняется: сессионное и последующее задачное ретро об одном инциденте — два упоминания в разных файлах ретро (если проблема повторится в задачном ретро); дедупликация между режимами не вводится — расширение границ реестра вынесено за пределы эпика. При отсутствии проблем и предложений запись в реестр не создаётся (действующее правило Шага 7 сохраняется; тогда и файл мини-ретро не создаётся — «гладкая сессия» фактически эквивалентна отсутствию находок). Ограничение: **подтверждённо тяжёлая сессия не может дать нулевой результат** — сам сработавший триггер (буксование, лишние шаги, многократные исправления) наблюдаем; если причина не найдена, фиксируется проблема «тяжесть сессии без установленной причины» со статусом «требует обсуждения».

## 4. Решения по месту в навыке

**Решение 4.1 (структура SKILL.md).** Сессионный режим оформляется отдельной секцией «Сессионный режим (мини-ретроспектива)» **после Шага 8 и до раздела «Результат»**; шаги секции нумеруются с префиксом: **С1–С4** (чтобы перекрёстные ссылки на «Шаг 2/Шаг 7» полного режима оставались однозначными). В конце секции — мини-чеклист самопроверки (4–5 пунктов: задача на момент запуска не завершена и не принята; ключ сессии в метаданных; находки с доказательствами; предложения с типом фикса; повторный запуск проверен на дубликат). Отсылка из «Когда использовать» (Решение 2.1) и обратная отсылка в полный режим (Решение 2.3) обязательны. Раздел «Результат» остаётся общим для обоих режимов. Правило обещаний (абзац «Как использовать» о записи обещаний в ретроспективу) остаётся общим для обоих режимов — сессионная секция не отменяет его (требование комментария 9 задачи). Норма объёма — как в модели переработки: 1–3 предложения на шаг + императивные ссылки на существующие справочники; новых справочников не создаётся, таблицы не дублируются.

**Решение 4.2 (шаблон).** В `assets/retrospective-template.md` к существующим разделам добавляются краткие пометки «*(в сессионном режиме: обязательно/опционально)*» — единообразно с текущим стилем шаблона; полная структура шаблона сохраняется.

## 5. Решения по идентификации сессии и повторным запускам

**Решение 5.1 (ключ сессии).** **Единица мини-ретро — ровно одна тяжёлая сессия**: если буксовала интерактивная работа оркестратора (включая запуски сабагентов из неё) — один мини-ретро на сессию оркестратора; если отдельно буксовал сабагент при гладкой сессии оркестратора — самостоятельный мини-ретро по сабагенту. Один мини-ретро = один ключ; при охвате нескольких источников ключом становится сессия оркестратора, сабагентские каталоги перечисляются в метаданных как охват. Перед самостоятельным мини-ретро по сабагенту — проверка отсутствия уже существующего сессионного отчёта, чей охват в метаданных включает этот каталог (защита от двойного учёта одного инцидента через два разных ключа).

Устойчивый ключ выбирается по приоритету источников: (1) **каталог запуска сабагента** `var/log/watch-subagent/<timestamp>-<runner>-<role>-<pid>/` — его имя; (2) **журнал интерактивной сессии pi** — абсолютный путь без `~` (например, `/home/<user>/.pi/agent/sessions/<...>.jsonl`); (3) **нормализованный временной диапазон** в едином формате ISO 8601: `YYYY-MM-DDTHH:MM±HH:MM/YYYY-MM-DDTHH:MM±HH:MM` (метки начала/окончания берутся из первоисточника; смещение — локальное время машины с явным числовым смещением; свободная запись вроде «19:00–21:30» запрещена). Повторный запуск обязан **реконструировать ключ из тех же первоисточников** тем же приоритетом — только так строка совпадёт. Если ключ неопределим (источники недоступны/отсутствуют) — мини-ретро не выполняется, вопрос выносится пользователю; проводить с неопределимым ключом запрещено (иначе защита от дублей неработоспособна).

Ключ фиксируется в метаданных отчёта (строка `**Сессия:** <ключ>`) и в имени файла: слаг сессионных ретро начинается с `session-` (пример: `2026-10-26_19-45-session-<slug>.md`).

**Решение 5.2 (повторный запуск).** Перед записью — проверка на существующий отчёт с тем же ключом сессии: поиском по `docs/agents/team-retro/*-session-*.md` и строке `**Сессия:** <ключ>`. Строка ключа ищется по всему `docs/agents/team-retro/*.md`; маска имени `*-session-*` — только предфильтр-ускоритель. **Дубликат определяется исключительно совпадением строки ключа** — совпадение имени файла без совпадения ключа дубликатом не считается (например, задачное ретро со слагом `...session-handler...` не мешает; и наоборот — файл с корректной строкой ключа, но без `session-` в имени, всё равно находится).

Ключ проверяется **повторно непосредственно перед записью** (после сбора фактов — защита от гонки двух запусков). При наличии отчёта повторный запуск **не создаёт** новый файл и **не увеличивает счётчики существующих записей реестра** по уже зафиксированным находкам этой сессии: либо отчёт дополняется новыми находками (правка существующего файла с пометкой в метаданных `**Обновлено:** YYYY-MM-DD — дополнено при повторном запуске`; **дополнение — только добавление**: изменение и удаление уже зафиксированных находок запрещено, арбитр — git-история), либо пользователю сообщается «новых находок нет» (в ответе; файл не создаётся, реестр не трогается). **Новая находка повторного запуска** — совпадающая причина или источник момента с существующей находкой этого же отчёта считается дубликатом и счётчик не растит; действительно новая — обрабатывается по штатным правилам Шага 7 (новая запись реестра со счётчиком 1). Если обнаружено более одного файла с одним ключом — стоп, слияние в один по согласованию с пользователем, счётчики не трогаются до слияния. Ожидаемое поведение на примере: одна тяжёлая сессия → сколько бы раз мини-ретро ни запускали — один файл, и каждая затронутая запись реестра получает +1 суммарно не более одного раза от данной сессии.

## 6. Согласование смежных документов

**Решение 6.1.** Поиск по `сессионн|мини-ретро|мини-ретроспектив|session` (исключения — исторические каталоги: `team-retro/`, `reports/`, `research/`, `releases/`) по факту оформления PM4; кандидаты: раздел навыков в роли тимлида, SDLC, README. Устаревших описаний, противоречащих сессионному режиму, в актуальных документах сейчас нет (проверено при декомпозиции); новые упоминания должны быть согласованы с моделью.

## 7. Состав консультантов и проверки модели

Зафиксировано по правилу PM1 (RACI, раздел 6):

- **PM1 (консультации):** аналитик и архитектор — обязательные консультанты (по этой версии). Условные `c` не привлекаются: изменения строго документационные, обязанности кода и тестов не затрагиваются; тестировщик подключается на PM2 (сценарии отказов).
- **PM2 (проверка):** аналитик — A/R; тимлид и архитектор — консультанты; тестировщик бэка — обязательный консультант по сценариям отказов: «сессия без `audit.jsonl`», «мини-ретро вместо полноценной», «повторный запуск по той же сессии», «нулевые проблемы», «ключ сессии неопределим», «сессия сабагента vs интерактивная сессия», «находки требуют оценки ролей», «полное отсутствие первоисточников (нет ни журналов сабагентов, ни журнала pi, ни `audit.jsonl`)».
- **PM3:** тимлид принимает; неразрешённые критические замечания — пользователю.
- **PM4:** технический писатель (Гермиона) оформляет; вход — только эта модель; пробелы возвращаются автору.
- **PM5:** тимлид сверяет сохранность решений; техпис и аналитик — консультанты.

## 8. Критерии принятия модели (PM3)

- [ ] Все Must-требования задачи покрыты решениями разделов 2–6.
- [ ] Ключ сессии воспроизводим (приоритет источников, канонический формат, реконструкция при повторном запуске, отказ при неопределимости); правило обещаний применимо к сессионному режиму.
- [ ] Каждое переиспользуемое правило (контракт доказательств, классификация фиксов, реестр) подключено императивной ссылкой, а не пересказом.
- [ ] Повторный запуск по той же сессии не порождает дубликатов: правило и ожидаемое поведение определены, новые находки — по Шагу 7 без противоречия.
- [ ] Полный режим ретроспективы не сломан: разделение обязательных полей режимов явно.
- [ ] Ни одно решение не меняет реестр, пороги эскалации, семантику счётчиков и human-in-the-loop.
- [ ] Замечания обязательных консультантов PM1 и проверяющего PM2 разрешены или вынесены пользователю.
