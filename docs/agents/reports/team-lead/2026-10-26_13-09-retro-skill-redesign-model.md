## 1. Назначение и границы модели

Модель описывает управленческие решения по переработке навыка [`retrospective`](../../skills/retrospective/SKILL.md) и его шаблона. Принцип заимствования — **borrow principles, not implementation**: переносятся принципы (check over prose, аудит guardrails, no-ops, трассировка), а не структура Matt Pocock Skills (без `CODING_STANDARDS.md`, без команды `/retro`).

**Меняются:** Шаги 1, 3, 5 `SKILL.md`; шаблон `assets/retrospective-template.md`; два новых справочных файла в `assets/`; смежные документы с описанием процесса ретроспектив (поиском, список определяет оформление PM4).

**Не меняются:** Шаги 2, 4, 6, 7, 8 (структурно); реестр `RETRO-ROADMAP.md` — пороги, статусы, формат записей; правило human-in-the-loop (классификация фикса не создаёт проверку автоматически — создание по регламенту с согласованием); сессионный режим мини-ретро (отдельная задача [TASK-docs-retro-session-mode](../../../../todo/TASK-docs-retro-session-mode.todo.md)); исторические ретроспективы и отчёты (свидетельства прошлого, не переписываются).

## 2. Решения по Шагу 1 — первоисточники сессии

**Решение 1.1.** В Шаг 1 добавляется четвёртый пункт: сбор первоисточников сессии рядом с артефактами задачи:

- `var/log/agent_audit.jsonl` — журнал событий цепочки (начало/результат шага, роли, токены, стоимость), если аудит включён. Это **не полный диалог**: сам по себе не доказывает «агент долго искал файл» (см. [`docs/guide/observability.md`](../../../guide/observability.md)).
- Каталоги запусков сабагентов `var/log/watch-subagent/<timestamp>-<runner>-<role>-<pid>/` (`run.log`, при наличии `events/`) — трасса вызовов инструментов, тайминги, финальный ответ.

**Решение 1.2.** Каждая находка обязана трассироваться к конкретному моменту сессии или артефакту: записи журнала (шаг, роль, временная метка), вызову инструмента, коммиту, файлу, задаче, PR. Дженерик-практика без указателя — не находка.

**Решение 1.3.** Матрица достаточности доказательств (контракт) выносится в новый файл `assets/evidence-contract.md`; в Шаге 1 — явная инструкция прочитать его до фиксации находок (одна ссылка не гарантирует применения, поэтому формулировка императивная). Контракт:

| Тип находки | Достаточное доказательство |
|---|---|
| Задержка шага | Временные метки начала/окончания шага из `audit.jsonl` или `run.log` |
| Повторные ошибочные вызовы | Записи журнала сессии (трасса вызовов инструментов) с указателем на момент |
| Отсутствие/сломанность проверки | Файл конфигурации + команда + подтверждённый результат выполнения |
| Долгий поиск файла/факта | Трасса вызовов инструментов из журнала сессии (не `audit.jsonl` в одиночку) |
| Источник отсутствует/неполон | Вывод явно помечается «неподтверждено», не выдаётся за факт и не додумывается |

**Решение 1.4 (секреты).** Доказательство — минимальный указатель (файл + запись/позиция) плюс обезличенная цитата. Копирование чувствительных фрагментов журналов и секретоподобных значений в отчёт ретроспективы запрещено: попадает только безопасный указатель и обезличенное доказательство.

## 3. Решения по Шагу 3 — аудит guardrails и направление «Инструкции»

**Решение 3.1.** Направления анализа процесса расширяются с пяти до семи; новые направления:

- **Проверки (guardrails):** сначала прочитать фактические check-команды проекта — `Makefile` (цели `check`, `test` и производные), `composer.json` (scripts), `.github/workflows/`, pre-commit хуки, `.gitleaks.toml`. Затем: (а) существующая, но не подключённая или молча сломанная проверка — сама находка; (б) отсутствие guardrail для известного механического правила — тоже находка; (в) предложение новой проверки допустимо только после сверки с этим арсеналом — не изобретать новую, когда существующая не подключена.
- **Инструкции:** (а) no-ops — инструкции, которые ничего не меняют в поведении агента (невыполнимые, дублирующие уже enforced проверки, декларативные без адресата); (б) разросшийся стиринг — большой `AGENTS.md`, дублирование правил между файлами ролей и навыками, правила, пережившие свою ошибку.

Существующие направления сохраняются: Процессы, Конвенции, Инструменты, Координация, Повторяющиеся.

**Решение 3.2 (Should — «Инструменты»).** Направление «Инструменты» дополняется анализом дорогих вызовов инструментов и доступа агента к информации (нехватка доступа — находка типа «расширить доступ», дорогой вызов — «упростить или заменить»).

**Решение 3.3 (неразрастание).** Семь направлений перечисляются в `SKILL.md` списком с одной строкой на направление; развёрнутые пояснения и примеры выносятся в новый справочник `assets/process-analysis-reference.md`. В Шаге 3 — явная императивная инструкция прочитать справочник до анализа.

## 4. Решения по Шагу 5 — классификация «симптом → тип фикса»

**Решение 4.1.** После формирования предложения (до трёх, как сейчас) каждое предложение обязательно классифицируется по одному из четырёх типов фикса:

| Симптом | Тип фикса | Куда попадает |
|---|---|---|
| Агент долго искал файл или факт | **Навигационный указатель** | Указатель в файле, который агент и так читает (роль, навык, конвенции) |
| Ошибку мог поймать инструмент | **Автоматическая проверка** | PHP_CodeSniffer, Deptrac, Psalm, gitleaks, тест, CI-задача, pre-commit |
| Ошибку уровня «суждение» пропустил ревьюер | **Правило для ревьюера** | Файл роли ревьюера / чеклист ревью |
| Инструкция не работает или шумит | **Правка стиринга** | Правка/удаление строки в `AGENTS.md`, файле роли, навыке |

**Решение 4.2 (правило check over prose).** Механическое нарушение → детерминированная проверка; проза — только для нарушений, требующих суждения. Формулировка правила попадает в `SKILL.md` дословно как норма.

**Решение 4.3.** Таблица «симптом → тип фикса» выносится в новый файл `assets/fix-classification.md`; в Шаге 5 — явная императивная инструкция прочитать его до классификации. Таблица не дублируется ни в `SKILL.md`, ни в шаблоне (в шаблоне — только пометка типа у предложения).

**Решение 4.4 (связка с Шагом 3).** Предложение типа «автоматическая проверка» обязано ссылаться на результат аудита guardrails (Шаг 3): либо «существующая проверка не подключена — подключить», либо «guardrail отсутствует — создать». Автосоздания проверки не происходит: предложение получает статус «внедрено / TODO / требует обсуждения» по действующим правилам, создание — по регламенту с согласованием.

**Решение 4.5 (шаблон).** В `assets/retrospective-template.md`: (а) раздел «Предложения для улучшения» — каждый пункт помечается типом фикса; (б) раздел «Проблемы» — к описанию добавляется указатель доказательства (по контракту из Решения 1.3). Изменения полей минимальны, полная структура разделов шаблона сохраняется.

## 5. Решения по неразрастанию навыка

**Решение 5.1.** Рост `SKILL.md` ограничен: новые механики в шагах описываются нормой в 1–3 предложения + императивная ссылка на соответствующий файл `assets/`; справочные таблицы (доказательства, классификация, направления анализа) в `SKILL.md` не дублируются.

**Решение 5.2.** Итоговая структура файлов навыка:

| Файл | Статус | Содержание |
|---|---|---|
| `SKILL.md` | изменяется | Шаги 1, 3, 5: нормы + императивные ссылки на справочники |
| `assets/retrospective-template.md` | изменяется | Поля «тип фикса» и «доказательство» в шаблоне |
| `assets/evidence-contract.md` | новый | Матрица достаточности доказательств, правило секретов, границы `audit.jsonl` |
| `assets/fix-classification.md` | новый | Таблица «симптом → тип фикса», правило check over prose, связка с аудитом guardrails |
| `assets/process-analysis-reference.md` | новый | Семь направлений анализа с примерами и списком фактических check-команд проекта |

## 6. Согласование смежных документов

**Решение 6.1.** После PM4 оформление проверяется поиском по ключевым словам `ретроспектив|retrospective|RETRO-ROADMAP` (без каталогов `docs/agents/team-retro/` и `docs/agents/reports/` — исторические свидетельства не переписываются). Кандидаты на обновление: файл роли тимлида (описание навыка), SDLC, RACI (если упоминается процесс ретроспективы), корневой `AGENTS.md`. Список фиксируется по факту поиска; устаревшие описания процесса приводятся к новой модели единообразно.

## 7. Состав консультантов и проверки модели

Зафиксировано по правилу PM1 (RACI, раздел 6):

- **PM1 (консультации):** аналитик и архитектор — обязательные консультанты (по этой версии модели).
- **PM2 (проверка):** аналитик — A/R; тимлид и архитектор — консультанты; тестировщик бэка — обязательный консультант по сценариям отказов: «источник отсутствует/неполон», «журнал не покрывает интерактивную сессию», `audit.jsonl` отключён/неприменим, доказательство содержит секретоподобное значение, существующая проверка не подключена, шаблон неполон для новых полей.
- **PM3:** тимлид принимает решение «принято/не принято»; неразрешённые критические замечания выносятся пользователю.
- **PM4:** технический писатель (Гермиона) оформляет принятую модель; вход — только эта модель; пробелы оформления возвращаются автору модели, не проектируются оформителем.
- **PM5:** тимлид сверяет сохранность управленческих решений; техпис и аналитик — консультанты.

## 8. Критерии принятия модели (PM3)

- [ ] Все Must-требования задачи покрыты решениями разделов 2–6.
- [ ] Каждая вынесенная таблица подключена императивной инструкцией чтения на конкретном шаге.
- [ ] Ни одно решение не меняет реестр, пороги эскалации и human-in-the-loop.
- [ ] Модель не предписывает создание проверок автоматически — только предложения по регламенту.
- [ ] Замечания обязательных консультантов PM1 и проверяющего PM2 разрешены или вынесены пользователю.
