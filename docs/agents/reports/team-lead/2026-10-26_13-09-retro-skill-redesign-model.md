## 1. Назначение и границы модели

Модель описывает управленческие решения по переработке навыка [`retrospective`](../../skills/retrospective/SKILL.md) и его шаблона. Принцип заимствования — **borrow principles, not implementation**: переносятся принципы (check over prose, аудит guardrails, no-ops, трассировка), а не структура Matt Pocock Skills (без `CODING_STANDARDS.md`, без команды `/retro`).

**Меняются:** Шаги 1, 3, 5 `SKILL.md`; шаблон `assets/retrospective-template.md`; три новых справочных файла в `assets/`; смежные документы с описанием процесса ретроспектив (поиском, список определяет оформление PM4).

**Не меняются:** Шаги 2, 4, 6, 7, 8 (структурно); реестр `RETRO-ROADMAP.md` — пороги, статусы, формат записей; правило human-in-the-loop (классификация фикса не создаёт проверку автоматически — создание по регламенту с согласованием); сессионный режим мини-ретро (отдельная задача [TASK-docs-retro-session-mode](../../../../todo/TASK-docs-retro-session-mode.todo.md)); исторические ретроспективы и отчёты (свидетельства прошлого, не переписываются).

## 2. Решения по Шагу 1 — первоисточники сессии

**Решение 1.1.** В Шаг 1 добавляется четвёртый пункт: сбор первоисточников сессии рядом с артефактами задачи:

- `var/log/agent_audit.jsonl` — журнал событий цепочки (начало/результат шага, роли, токены, стоимость), если аудит включён. Это **не полный диалог**: сам по себе не доказывает «агент долго искал файл» (см. [`docs/guide/observability.md`](../../../guide/observability.md)). Путь журнала — по конфигурации из observability.md; в оформлении PM4 абсолютный путь в `SKILL.md` не зашивается, даётся ссылка на документ наблюдаемости. Для объёмных журналов — выборка по шагу/роли/временному окну предмета ретроспективы; неосвоенный журнал не скрывается молча.
- Каталоги запусков сабагентов `var/log/watch-subagent/<timestamp>-<runner>-<role>-<pid>/` (`run.log`, при наличии `events/`) — трасса вызовов инструментов, тайминги, финальный ответ.

**Решение 1.2.** **Находка** — зафиксированная в ретро проблема или предложение (успешные практики — род предложений «закрепление практики», см. Решение 4.1). Каждая находка обязана трассироваться к конкретному моменту сессии или артефакту: записи журнала (шаг, роль, временная метка), вызову инструмента, коммиту, файлу, задаче, PR. Дженерик-практика без указателя — не находка. Если первоисточники отсутствуют или неполны — вывод явно помечается «неподтверждено» прямо в Шаге 1 (не только в справочнике), не выдумывается.

**Решение 1.3.** Матрица достаточности доказательств (контракт) выносится в новый файл `assets/evidence-contract.md`; в Шаге 1 — явная инструкция прочитать его до фиксации находок (одна ссылка не гарантирует применения, поэтому формулировка императивная). Контракт:

| Тип находки | Достаточное доказательство |
|---|---|
| Задержка шага | Временные метки начала/окончания шага из `audit.jsonl` или `run.log` |
| Повторные ошибочные вызовы | Записи журнала сессии (трасса вызовов инструментов) с указателем на момент |
| Проверка не подключена | Статическое чтение связки: команда существует, но не упомянута ни в `make check`/`Makefile`, ни в CI-заданиях, ни в хуках (запуск команды здесь ничего не доказывает) |
| Проверка молча сломана | Файл конфигурации + целевой одноразовый запуск команды (в идеале — на заведомо невалидном образце для «всегда-зелёных» поломок); запуск выполняется в чистом состоянии и не оставляет артефактов в рабочем дереве |
| Противоречие журнала и артефакта (коммит/PR) | Журнал фиксирует попытки, артефакт — результат: для находки о результате приоритет у артефакта, расхождение — наблюдением в отчёт |
| Долгий поиск файла/факта | Трасса вызовов инструментов из журнала сессии (не `audit.jsonl` в одиночку) |
| Дефект уровня «суждение», пропущенный ревьюером | Указатель на коммит/PR/находку ревью, где дефект прошёл, и место, где он проявился или был пойман позже |
| No-op или шумящее правило | Указатель на правило + повторяющееся нарушение при живом правиле либо дублирование уже enforced-проверки (со ссылкой на неё) |
| Успешная практика (кандидат на закрепление) | Указатель на коммит/PR/артефакт, где приём сработал, + подтверждённая польза |
| Расхождение метрик `audit.jsonl` и `run.log` | Приоритет — источник с более полной трассой шага; само расхождение фиксируется наблюдением в отчёте |
| Целевой запуск проверки непомерно дорог/долог | Статус проверки помечается «неподтверждено» с указанием причины; полный прогон не требуется |
| Источник отсутствует/неполон | Вывод явно помечается «неподтверждено», не выдаётся за факт и не додумывается |

**Решение 1.4 (секреты).** Доказательство — минимальный указатель (файл + запись/позиция) плюс обезличенная цитата. Копирование чувствительных фрагментов журналов и секретоподобных значений в отчёт ретроспективы запрещено: попадает только безопасный указатель и обезличенное доказательство. Граница «секретоподобного» — по паттернам регламента «Работа с секретами» `AGENTS.md`: PEM, токены `ghs_*`/PAT/JWT/API-key, пароли, значения `.env*`; при сомнении в нестандартном формате — значение обезличивается (заместитель по регламенту), а не копируется.

## 3. Решения по Шагу 3 — аудит guardrails и направление «Инструкции»

**Решение 3.1.** Направления анализа процесса расширяются с пяти до семи; новые направления:

- **Проверки (guardrails):** сначала прочитать фактические check-команды проекта — `Makefile` (цели `check`, `test` и производные), `composer.json` (scripts), `.github/workflows/`, pre-commit хуки, `.gitleaks.toml`. Затем: (а) существующая, но не подключённая или молча сломанная проверка — сама находка; (б) отсутствие guardrail для известного механического правила — тоже находка; (в) предложение новой проверки допустимо только после сверки с этим арсеналом — не изобретать новую, когда существующая не подключена. Подтверждение статуса «молча сломанная» — целевой одноразовый запуск конкретной команды, а не полный прогон всех проверок.
- **Инструкции:** (а) no-ops — инструкции, которые ничего не меняют в поведении агента (невыполнимые, дублирующие уже enforced проверки, декларативные без адресата); (б) разросшийся стиринг — большой `AGENTS.md`, дублирование правил между файлами ролей и навыками, правила, пережившие свою ошибку.

Существующие направления сохраняются: Процессы, Конвенции, Инструменты, Координация, Повторяющиеся.

**Решение 3.2 (Should — «Инструменты»).** Направление «Инструменты» дополняется анализом дорогих вызовов инструментов и доступа агента к информации (нехватка доступа — находка типа «расширить доступ», дорогой вызов — «упростить или заменить»).

**Решение 3.3 (неразрастание).** Семь направлений перечисляются в `SKILL.md` списком с одной строкой на направление; развёрнутые пояснения и примеры выносятся в новый справочник `assets/process-analysis-reference.md`. В Шаге 3 — явная императивная инструкция прочитать справочник до анализа.

## 4. Решения по Шагу 5 — классификация «симптом → тип фикса»

**Решение 4.1.** После формирования предложения (до трёх, как сейчас) каждое предложение обязательно классифицируется по одному из четырёх типов фикса:

| Симптом | Тип фикса | Куда попадает |
|---|---|---|
| Агент долго искал файл или факт | **Навигационный указатель** | Указатель в файле, который агент и так читает (роль, навык, конвенции) |
| Ошибку мог поймать инструмент | **Автоматическая проверка** | PHP_CodeSniffer, Deptrac, Psalm, gitleaks, тест, CI-задача, pre-commit |
| Ошибку уровня «суждение» пропустил ревьюер | **Правило для ревьюера** | Файл роли ревьюера / чеклист ревью |
| Инструкция не работает или шумит | **Правка стиринга** | Правка/удаление строки в `AGENTS.md`, файле роли, навыке |
| Полезный приём, который стоит закрепить | **Закрепление практики** | Правило/приём в файл роли, навыка или конвенций (род предложений «Что прошло хорошо» из Шага 5) |

**Решение 4.2 (правило check over prose).** Механическое нарушение → детерминированная проверка; проза — только для нарушений, требующих суждения. Каноничная формулировка — одна, в `SKILL.md`; в справочнике `fix-classification.md` — пояснения и примеры без дублирования канона. Тай-брейкер при неоднозначности симптома (подходит и «проверка», и «правило для ревьюера»): выбирается автоматическая проверка.

**Решение 4.3.** Таблица «симптом → тип фикса» выносится в новый файл `assets/fix-classification.md`; в Шаге 5 — явная императивная инструкция прочитать его до классификации. Таблица не дублируется ни в `SKILL.md`, ни в шаблоне (в шаблоне — только пометка типа у предложения).

**Решение 4.4 (связка с Шагом 3).** Предложение типа «автоматическая проверка» обязано ссылаться на результат аудита guardrails (Шаг 3): либо «существующая проверка не подключена — подключить», либо «guardrail отсутствует — создать». Автосоздания проверки не происходит: предложение получает статус «внедрено / TODO / требует обсуждения» по действующим правилам, создание — по регламенту с согласованием. Предложение может опираться и на неподтверждённую находку — тогда оно само помечается «на базе неподтверждённой находки».

**Решение 4.5 (шаблон).** В `assets/retrospective-template.md`: (а) раздел «Предложения для улучшения» — каждый пункт помечается типом фикса (включая «закрепление практики») и указателем доказательства; (б) раздел «Проблемы» — к описанию добавляется указатель доказательства (по контракту из Решения 1.3; при отсутствии источника — пометка «неподтверждено») и пометка направления анализа из Шага 3 (несколько направлений допустимы; находка вне семи направлений фиксируется в «Важных комментариях» без натягивания). Изменения полей минимальны, полная структура разделов шаблона сохраняется.

## 5. Решения по неразрастанию навыка

**Решение 5.1.** Рост `SKILL.md` ограничен: новые механики в шагах описываются нормой в 1–3 предложения + императивная ссылка на соответствующий файл `assets/`; справочные таблицы (доказательства, классификация, направления анализа) в `SKILL.md` не дублируются. Норма объёма справочников: таблица + краткие пояснения, ориентир — один экран; разрастание справочников равнозначно разрастанию навыка.

**Решение 5.2.** Итоговая структура файлов навыка:

| Файл | Статус | Содержание |
|---|---|---|
| `SKILL.md` | изменяется | Шаги 1, 3, 5: нормы + императивные ссылки на справочники |
| `assets/retrospective-template.md` | изменяется | Поля «тип фикса» и «доказательство» в шаблоне |
| `assets/evidence-contract.md` | новый | Матрица достаточности доказательств, правило секретов, границы `audit.jsonl` |
| `assets/fix-classification.md` | новый | Таблица «симптом → тип фикса», пояснения и примеры к правилу check over prose (канон — один, в `SKILL.md`, не дублируется), связка с аудитом guardrails |
| `assets/process-analysis-reference.md` | новый | Семь направлений анализа с примерами; методика аудита guardrails — перечень мест чтения фактических check-команд и признаки «не подключена / сломана»; фактический состав команд всегда читается из первоисточников на каждой ретро, снимок состава в справочнике не хранится |

## 6. Согласование смежных документов

**Решение 6.1.** После PM4 оформление проверяется поиском по ключевым словам `ретроспектив|retrospective|RETRO-ROADMAP` с исключениями исторических каталогов: `docs/agents/team-retro/`, `docs/agents/reports/`, `docs/research/` (снимки с датой анализа), `docs/releases/` (исторические планы релизов) — свидетельства прошлого не переписываются. Фактический поиск при DC выполняется по исключениям модели (rg с глобами `!docs/research/*`, `!docs/releases/*`); команда в разделе «Самопроверка» задачи синхронизируется на DC. Кандидаты на обновление (примеры, не исчерпывающий список — фактический перечень определяется поиском): файл роли тимлида, SDLC, RACI, корневой `AGENTS.md`, `README*.md`, `docs/index.md`, SKILL.md других навыков. Устаревшие описания процесса приводятся к новой модели единообразно; критерий приёмки задачи читается как «поиск вне исключённых каталогов не находит устаревших описаний».

## 7. Состав консультантов и проверки модели

Зафиксировано по правилу PM1 (RACI, раздел 6). Условные консультанты `c` (бэкендер, ревьювер бэка) на PM1–PM2 не привлекаются — основание: изменения строго документационные, обязанности кода не затрагиваются; технический писатель привлекается на PM4 как оформитель (A/R) и ранее — по запросу оформителя о пробелах.

- **PM1 (консультации):** аналитик и архитектор — обязательные консультанты (по этой версии модели).
- **PM2 (проверка):** аналитик — A/R; тимлид и архитектор — консультанты; тестировщик бэка — обязательный консультант по сценариям отказов: «источник отсутствует/неполон», «журнал не покрывает интерактивную сессию», `audit.jsonl` отключён/неприменим, доказательство содержит секретоподобное значение, существующая проверка не подключена, шаблон неполон для новых полей, расхождение метрик `audit.jsonl`/`run.log`, подтверждение статуса проверки требует дорогого/долгого запуска.
- **PM3:** тимлид принимает решение «принято/не принято»; неразрешённые критические замечания выносятся пользователю.
- **PM4:** технический писатель (Гермиона) оформляет принятую модель; вход — только эта модель; пробелы оформления возвращаются автору модели, не проектируются оформителем. Предостережение: формулировки Шага 1 не должны допускать запуск ретроспективы «по ходу живой сессии» — предмет остаётся завершённой работой; лёгкий вход для живой сессии — отдельная задача TASK-docs-retro-session-mode.
- **PM5:** тимлид сверяет сохранность управленческих решений; техпис и аналитик — консультанты.

## 8. Критерии принятия модели (PM3)

- [ ] Все Must-требования задачи покрыты решениями разделов 2–6.

- [ ] Каждая вынесенная таблица подключена императивной инструкцией чтения на конкретном шаге; применение каждой контролируется контрольной точкой в шаблоне или чеклисте самопроверки.
- [ ] Ни одно решение не меняет реестр, пороги эскалации и human-in-the-loop.
- [ ] Модель не предписывает создание проверок автоматически — только предложения по регламенту.
- [ ] Замечания обязательных консультантов PM1 и проверяющего PM2 разрешены или вынесены пользователю.
