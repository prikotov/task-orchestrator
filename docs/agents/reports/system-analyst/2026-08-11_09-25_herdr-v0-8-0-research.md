## Классификация

Herdr — `terminal agent runtime / control surface` (постоянная терминальная среда выполнения и управляющая поверхность для агентов), а не:

- самостоятельный агент программирования;
- LLM SDK (комплект разработки для языковой модели);
- движок YAML-цепочек;
- система повторов, бюджетов или ворот качества.

Herdr держит реальные PTY в фоновом сервере, распознаёт внешние агенты и предоставляет единый CLI/socket API (командный и сокетный интерфейс) для операций `start`, `prompt`, `wait`, `read`, управления разметкой и рабочими деревьями Git.

## Подтверждённые свойства

| Область | Результат |
| --- | --- |
| **Состояния** | `idle`, `working`, `blocked`, `done`, `unknown`; значение сопровождается источником полномочий — интеграцией или экранным манифестом |
| **Координация** | Событийный `agent.wait`, фиксация текущего владельца панели, атомарный `agent.prompt` + wait |
| **Зависание** | `agent_prompt_stalled`, если после отправки из нерабочего состояния за 5 секунд нет перехода |
| **Протокол** | Protocol 19, JSON Schema version 1, 90 методов в схеме `v0.8.0` |
| **Постоянство** | Живой detach/reattach, snapshot разметки, опциональная история, нативное возобновление 16 агентов, экспериментальный live handoff |
| **Git** | `worktree.create/open/remove`, provenance (происхождение) и события; ветка при удалении рабочего дерева сохраняется |
| **Навык** | `SKILL.md` с защитой `HERDR_ENV=1`; `herdr --skill` выдаёт согласованную с выпуском копию |
| **Безопасность** | Unix-сокеты `0600`, SSH через OpenSSH, история панелей выключена по умолчанию; процессы и плагины не изолированы |
| **Расширение** | Исполняемые плагины используют весь CLI; отдельной ограниченной песочницы или SDK нет |

## Сравнение с task-orchestrator

Системы находятся на разных уровнях:

```text
Herdr:              где живут и как наблюдаются интерактивные агенты
task-orchestrator:  в каком порядке они работают и как проверяется результат
```

Herdr сильнее в постоянных терминалах, удалённом подключении, оперативном состоянии, рабочих деревьях и восстановлении интерфейса. `task-orchestrator` сильнее в декларативных цепочках, ролях, JSONL-результате, повторных попытках, автоматическом выключателе, fallback (запасном маршруте), бюджете, воротах качества, условных ветвях и итерациях исправления.

Herdr не заменяет `run-subagent`: его терминальный текст и UI-состояние не равны конечному JSONL-событию конкретного запуска. Кроме того, ожидание состояния не всегда связано с отправленным ходом, если агент уже работал.

## Рекомендации

### Заимствовать

1. `state + authority + evidence` (состояние + источник полномочий + доказательство), включая отдельный `unknown`.
2. Атомарную отправку задания и регистрацию ожидания.
3. Фиксацию владельца/идентификатора запуска до ожидания.
4. Раннюю проверку перехода состояния после отправки промпта.
5. Непрозрачные идентификаторы, явный контекст вызывающего и запрет удаления чужих ресурсов.
6. Жизненный цикл рабочих деревьев с происхождением и событиями.
7. Навык, согласованный с версией установленного бинарного файла.
8. Раздельную семантику непрерывности процесса, восстановления разметки, текста и разговора.

### Не переносить

- экранное распознавание как единственный критерий успеха цепочки;
- бесконечное ожидание по умолчанию;
- терминальный текст вместо DTO/JSONL-контракта;
- плагины с полными правами пользователя без модели доверия;
- Herdr как обязательную зависимость Symfony-приложения.

## Вердикт

- 🟡 **Patterns (паттерны):** заимствовать механизмы состояния, ожидания, владения, рабочих деревьев и восстановления.
- 🔴 **Core dependency (основная зависимость):** не использовать — другой уровень, стек и контракт результата.
- 🟢 **Optional manual runtime (опциональная ручная среда):** допустимо рассмотреть отдельно для долгих интерактивных агентов и удалённого наблюдения.
- ⚪ **Интеграционный эксперимент:** только отдельной задачей с обязательными `correlation id`, таймаутом, структурированным результатом и границей песочницы.
