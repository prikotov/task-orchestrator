### 2.2 Анализ семантической совместимости fallback (§3.3)

Четыре последствия cross-provider fallback (оптимизация промптов, контекстное окно, формат ответа, отсутствие prompt adaptation) — конкретные, проверяемые, не поверхностные.

### 2.3 State management (§3.4)

Четыре характеристики state с отдельным анализом последствий каждой (persistence, schemaless, мутабельность, рост памяти) — системный подход.

Чёткое отделение собственно оркестрации (Core) от вспомогательных возможностей (Supporting) в §5. Это важно для потребителя исследования — понятно, что влияет на flow управления, а что нет.

## 3. Пробелы в §3.9 (отсутствующие паттерны)

### 3.1 🔴 Существенные пропуски

#### 3.1.1 Context Window Management / Auto-compaction

**Что пропущено:** Анализ того, что происходит при переполнении контекстного окна LLM.

**Почему существенно:** При линейном росте state (§3.4 фиксирует: «потребление памяти растёт линейно») неизбежен момент, когда суммарный контекст превысит контекстное окно модели. Это **не memory growth** — это **orchestration failure mode**, специфичный для LLM-оркестрации.

**Что должно быть в §3.9:**

| Паттерн | Назначение | Последствия отсутствия |
|---|---|---|
| **Context window management** | Обработка переполнения контекстного окна (truncate, summarize, compact) | При росте state сверх контекстного окна LLM — вызов завершается ошибкой. Для цепочек 5+ агентов с объёмными ответами (code review, анализ документов) это гарантированный сценарий. Нет auto-truncation, summarization или compaction |

**Контекст:** 6 из 13 фреймворков в нашем исследовании реализуют auto-compaction (Crush, OpenHands SDK, Mastra AI, Claude Code, Codex). В нашем roadmap — Q4 2026.

#### 3.1.2 Timeout Management (per-step и global)

**Что пропущено:** Per-step timeout и global workflow timeout как самостоятельный паттерн.

**Почему существенно:** В §3.2 упоминается «нет общего таймаута» как одно из последствий blanket retry, но timeout — **самостоятельный оркестрационный паттерн**, не сводимый к retry. Retry отвечает на вопрос «что делать при ошибке», timeout — «как долго ждать до признания зависанием».

**Что должно быть в §3.9:**

| Паттерн | Назначение | Последствия отсутствия |
|---|---|---|
| **Timeout (per-step / global)** | Ограничение времени выполнения одного шага и всего workflow | Один «зависший» LLM-вызов (rate limit wait, бесконечный stream) блокирует весь workflow неограниченно долго. `max_delay` в retry ограничивает задержку одной retry-попытки, но не execution time одного LLM-вызова и не суммарное время workflow |

**Контекст:** Per-step timeout — стандарт в production orchestration (Temporal, Prefect, Airflow). В нашем проекте `AgentResultVo` уже имеет `isTimedOut`.

### 3.2 🟡 Умеренные пропуски

#### 3.2.1 Rate Limiting / Throttling

**Что пропущено:** Ограничение частоты запросов к LLM-провайдерам.

**Почему важно:** Отличается от Budget / Token control (который в §3.9 есть). Budget — про стоимость/токены. Rate limiting — про QPS (queries per second) к API. LLM-провайдеры имеют rate limits (OpenAI: RPM/TPM). При parallel или быстром sequential выполнении можно упереться в rate limit → cascade failure.

**Что должно быть в §3.9:**

| Паттерн | Назначение | Последствия отсутствия |
|---|---|---|
| **Rate limiting** | Контроль частоты запросов к LLM API (RPM/TPM limits) | При 5+ агентах с одним провайдером — превышение rate limit → 429 → retry → ещё больше запросов → cascade. Нет throttling между шагами |

#### 3.2.2 Dead Letter / Failed Step Isolation

**Что пропущено:** Механизм обработки окончательно failed-шагов без убийства всего workflow.

**Почему важно:** §3.1 фиксирует: «если вызов завершается ошибкой — весь workflow прерывается». Dead letter — альтернатива: failed шаг изолируется, workflow продолжает или gracefully завершается с partial results. Отличается от checkpointing/resume (которое про возобновление, не про изоляцию).

**Что должно быть в §3.9:**

| Паттерн | Назначение | Последствия отсутствия |
|---|---|---|
| **Dead letter / Error isolation** | Изоляция failed-шагов без прерывания всего workflow | Один failed агент в середине цепочки из 10 убивает всю работу. Нельзя пометить шаг как «skipped/failed» и продолжить с остальными |

#### 3.2.3 Sub-agents / Nested Orchestration

**Что пропущено:** Возможность одного агента породить подзадачу (sub-agent) или вложенный workflow.

**Почему важно:** В нашем roadmap — Q4 2026 (отложено из Q3). Фреймворки Claude Code (Task tool), Codex (spawn/wait), OpenHands SDK (DelegateTool) реализуют этот паттерн.

**Что должно быть в §3.9:**

| Паттерн | Назначение | Последствия отсутствия |
|---|---|---|
| **Sub-agents / Nested orchestration** | Агент может породить подзадачу или вложенный workflow | Один агент не может делегировать часть работы другому агенту в runtime. Все агенты — плоский список, заданный в YAML. Нельзя реализовать «агент-супервайзер → агент-исполнитель» |

#### 3.2.4 Streaming / Partial Results

**Что пропущено:** Обработка потоковых (streaming) ответов LLM.

**Почему важно:** Для long-running LLM-вызовов streaming позволяет начать обработку до полного завершения генерации. В контексте оркестрации это влияет на паттерн «получил начало ответа → начал следующий шаг» (pipeline parallelism).

**Примечание:** Это **наименее критичный** из умеренных пропусков. Для текущего уровня зрелости фреймворка (учебный/прототипный) streaming — не приоритет. Но для полноты исследования стоит упомянуть.

## 4. Пробелы в глубине существующих разделов (§3.1–§3.8)

### 4.1 §3.1 (Sequential Workflow) — не исследован LangGraph potential

Фреймворк использует LangGraph как state manager, но LangGraph **поддерживает** DAG, conditional edges, checkpointing — фреймворк **выбирает не использовать** эти возможности. Это важное различие: не «технически невозможно», а «не реализовано при наличии инструмента».

**Рекомендация:** Добавить в §3.1 или §3.4 примечание:

> LangGraph, используемый для state management, поддерживает conditional edges, branching и checkpointing из коробки. AI-Agents-Orchestrator не задействует эти возможности — ограничение на уровне архитектуры фреймворка, а не библиотеки.

### 4.2 §3.4 (State Management) — не проанализирован context overflow

В §3.4 фиксируется рост памяти, но не анализируется, что происходит при превышении context window. Это не только «рост памяти» — это **крах выполнения** (LLM API вернёт ошибку или обрежет контекст).

**Рекомендация:** Добавить в §3.4 пункт:

> **Context window overflow:** при передаче state в промпт следующего агента суммарный объём ответов может превысить контекстное окно модели. Нет механизма truncation, summarization или selective context passing. Это гарантированный сценарий для цепочек ≥5 агентов с объёмными ответами.

### 4.3 §3.2 (Retry) — idempotency не выделена в отдельный concern

Idempotency упомянута в контексте «timeout с частичным результатом → retry → дублирование», но это шире: **любой** retry без idempotency key создаёт риск side-effect дублирования. Это особенно критично для LLM-оркестрации, где side effect = расход токенов ($).

**Рекомендация:** Расширить §3.2, выделив idempotency как самостоятельный риск:

> **Отсутствие idempotency:** retry без idempotency key означает, что успешно обработанный, но «потерянный» по сети запрос будет повторен — двойной расход токенов. Нет механизма request deduplication.

## 7. Резюме

Исследование AI-Agents-Orchestrator качественно по глубине анализа реализованных возможностей, но содержит **системный пропуск** в перечне отсутствующих паттернов: не учтены **context window management** и **timeout** — два паттерна, критичных для production LLM-оркестрации. Три дополнительных паттерна (rate limiting, dead letter, sub-agents) желательно добавить для полноты.

Итоговый охват после дополнений: **14 паттернов** (9 текущих + 5 новых), что покрывает индустриальный стандарт для comparative analysis multi-agent orchestration frameworks.
