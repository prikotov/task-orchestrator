## 2. Основание: правило и прецедент

Правило (дословно, `AGENTS.md`, раздел «Pull Request», строка 223):

> ❗ **Запрет стековых PR (stacked pull requests — ветка поверх несмерженной ветки другого PR).** PR-ветка создаётся только от актуальной целевой ветки и не содержит коммиты чужих открытых PR. Зависимые правки — один PR или последовательное выполнение.

Прецедент ([ретроспектива 2026-09-24](../../team-retro/2026-09-24_10-39-stacked-prs-incident.md)): пять research-задач оформлены цепочкой PR поверх друг друга; после слияния первого защита `main` пометила аппрувы зависимых PR устаревшими; итог — 4 закрытых PR, переделка ветки, четыре раунда аппрувов.

Машинно проверяемая часть правила — вторая фраза: **«не содержит коммиты чужих открытых PR»**. Требование «создаётся от актуальной целевой ветки» остаётся за штатной механикой GitHub (branch up-to-date) — детектор его не дублирует и не подменяет.

## 3. Модель данных: снимок (Snapshot)

Детектор работает с одиночным снимком состояния на момент `T0`. Схема — одновременно интерфейс чистой функции (раздел 11) и формат фикстур тестов:

```
Snapshot {
  checked_pr: PrInfo            # проверяемый PR P
  target_tip: sha               # актуальная вершина целевой ветки P на T0
  open_prs: list<PrInfo>        # все открытые PR репозитория, кроме P
  commits: map<number, list<sha>>
                                 # для P и каждого PR из open_prs:
                                 # множество неслитых коммитов U (раздел 4)
  truncated: set<number>        # номера PR, чей список достиг лимита 250
                                 # (данные неполны)
}
PrInfo {
  number: int
  head_sha: sha                 # реальная вершина исходной ветки
  source_branch: string | null  # null для PR из форка с несовместимым именем
  target_branch: string
  is_draft: bool
  same_repository: bool         # head-репозиторий совпадает с базовым
}
```

Никаких имён авторов, заголовков и тел PR в модель не входят: признак определяется только графом коммитов и метаданными ветвления.

## 4. Множество неслитых коммитов U(P)

```
U(P) = reachable(head(P)) − reachable(target_tip(P))
```

- `reachable(x)` — достижимость в графе Git (не текстовая похожесть патчей).
- `U(P)` — коммиты, которые PR P принёс бы в свою цель: достижимы из вершины его исходной ветки и ещё не достижимы из **актуальной** вершины его **собственной** цели.
- Источник данных: список коммитов PR из GitHub API (раздел 7). Список и есть U(P) по семантике GitHub; снимок фиксирует его на T0.
- Инвариант: коммиты, уже слитые в цель (в том числе чужая работа, попавшая в цель обычным слиянием), в U не входят — это устраняет главный источник ложных срабатываний (устаревшая обычная ветка).

## 5. Признак нарушения (случай A: общая неслитая история)

**Нарушение для P**, если существует открытый PR Q ≠ P (любая цель, включая форки):

```
U(P) ∩ U(Q) ≠ ∅
```

Свойства признака:

1. **Симметрия.** Пересечение множеств не направленно: факт «общая неслитая история» истинен для обоих PR. Проверка Q найдёт то же пересечение с P. Запрещено автоматически объявлять оба PR «созданными неправильно» или требовать переделки родительского.
2. **Направление — только по доказательству вхождения вершины**, вычисляется относительно проверяемого P:
   - `stacked_on(Q)`: `head(Q) ∈ U(P)` ∧ `head(Q) ≠ head(P)` — вершина Q достижима из ветки P и не в цели: P с высокой достоверностью построен поверх Q. Только этот случай даёт P инструкцию «переделать ветку от целевой».
   - `base_for(Q)`: `head(P) ∈ U(Q)` — над P построен другой PR. К P претензий нет; сообщение информирует.
   - `equal_heads`: `head(P) = head(Q)` — одна вершина в двух PR (возможно, в разные цели). Направление не определено.
   - `partial`: пересечение непусто, но ни одна из вершин в чужое U не входит — типично, когда родитель получил коммиты после ответвления потомка. Направление не определено; это всё равно нарушение (общая неслитая история), но без персональной инструкции.
3. **Частичное пересечение не игнорируется**: оно не хуже полного как свидетельство общей истории — обе ветки несут одни и те же неслитые коммиты, и слияние одной из них обесценит аппрувы другой (механика инцидента #409–#414).

## 6. Случай B: цель PR — исходная ветка другого открытого PR

Факт: `target_branch(P) = source_branch(Q)` для открытого Q из того же репозитория.

**Решение контракта: случай B — НЕ нарушение; детектор выпускает информационную заметку.**

Обоснование:

1. Буква правила. Правило запрещает «коммиты чужих открытых PR» в PR-ветке. PR в чужую ветку Q, ответвлённый от неё, коммитов Q не содержит: они в его базе, U(P) их не включает. Пересечение U пусто.
2. Практика проекта. Ветки эпиков — санкционированный процесс: PR задач мержатся в `task/epic-*`, эпик уходит в `main` одним PR (PR #433 — живой прецедент). Пометка случая B нарушением окрашивает красным всю текущую работу эпика — прямое противоречие с требованием «без ложных срабатываний».
3. Механика вреда. Каскад инцидента возникает при стеке в одну цель (случай A). Слияние PR в интеграционную ветку меняет только её саму; в `main` всё попадает одним слиянием эпика.

При этом случай B **не замалчивается** (требование консультации «отдельно обнаруживать»): в журнале проверки и PR-комментарии появляется заметка — «цель PR — исходная ветка открытого PR #Q; детектор пилота не квалифицирует это как нарушение; убедитесь, что это осознанная интеграционная ветка (например, ветка эпика), а не случайный стек». Заметка не влияет на статус. Это **объявленное ограничение пилота** (раздел 13): «стек через PR в чужую feature-ветку без общих коммитов не блокируется».

Сравнение source-имён выполняется только для PR из того же репозитория (`same_repository = true`): в форке совпадение имён веток случайно.

## 7. Область целей

- Workflow запускается **без фильтра веток**: проверяются PR с любой целью (`main`, `release/*`, `task/epic-*`, прочие рабочие ветки).
- Сравнение ведётся по **всем открытым PR репозитория** без фильтра цели: U каждого вычисляется относительно **своей** цели, поэтому общая слитая история `main` и `release/*` не попадает в U ни одного из них и ложных сигналов не создаёт.
- Штатный перенос исправлений между `main` и `release/*` (cherry-pick, squash-перенос) меняет SHA — пересечение U пусто, переносы не сигналятся. Если перенос выполнен с сохранением SHA и оба PR открыты одновременно, сигнал возникнет — в информирующем пилоте это приемлемо (человек различит), сценарий зафиксирован в матрице (S14).
- Сравнение с **закрытыми** PR не выполняется: правило говорит об открытых PR.

## 8. Три исхода проверки

| Исход | Условие | Заключение job: пилот (inform) | Заключение job: enforce |
|---|---|---|---|
| `violation` | случай A: непустое пересечение U (доказано, в том числе на усечённых данных — раздел 9) | success + PR-комментарий + предупреждение в журнале | failure + PR-комментарий |
| `clean` | пересечений нет **и** снимок полный (без усечений), случай B максимум даёт заметку | success | success |
| `inconclusive` | проверить невозможно: ошибка/недоступность API, неполная пагинация списка PR, усечённые данные без доказанного нарушения, исчерпаны повторы стабилизации снимка | **failure** (не «зелёный») | failure |

Разделение трёх уровней (требование задачи):

1. **Результат детектора** — `violation | clean | inconclusive` + список пересечений и заметок.
2. **Заключение задания GitHub Actions** — отображение результата в статус проверки по таблице выше. Режим задаётся параметром (переменная окружения `DETECTOR_MODE=inform|enforce`, по умолчанию `inform`). Пилот — `inform`: нарушение не красит job, а доносится комментарием и журналом.
3. **Обязательность статуса в защите ветки** (required status check) — настраивается в GitHub отдельно от workflow; решение и действие владельца. Файл workflow сам по себе ничего не блокирует.

Обоснование «inconclusive — не зелёный» (обоих режимов): сбой проверки не должен создавать ложную уверенность «проверено и чисто». Это дешевле владельцу, чем пропущенный стек: red-статус локализует причину (инфраструктура) и переигрывается повторным запуском.

**Повторы и ожидания — ограничены константами контракта:**

- Сбор снимка: до **3 попыток**; пауза между попытками **2 с / 10 с / 30 с**.
- Стабильность снимка: после сбора повторно сверяются контрольные точки — `head(P)`, `target_tip`, пары `(number, head_sha)` всех открытых PR. Любое расхождение с началом сбора → повтор попытки; после третьей — `inconclusive` с причиной «состояние изменилось во время проверки».
- Транзиентные ошибки API (5xx, rate limit) — повтор в пределах тех же 3 попыток; подстановка ожидания rate limit — по заголовкам ответа, но не более суммарных ~90 с.
- Число запросов на прогон ограничено: список PR (1 + пагинация) + коммиты каждого PR (≤ 3 страницы по 100) + вершина цели (1) + контрольные точки. Порядка 2N+6 запросов для N открытых PR.

## 9. Лимит 250 коммитов

GitHub API возвращает не более 250 коммитов PR. Стратегия — **монотонность усечения**:

- Пересечение, найденное на **любом** подмножестве U, уже доказывает нарушение: усечение не может «спрятать» уже найденное. Если на усечённых данных пересечение непусто → `violation` (основание фиксируется в результате: «доказано на первых K коммитах»).
- Если усечён хотя бы один участник сравнения (список достиг 250: `truncated`) и пересечений не найдено → `inconclusive` с явной причиной: «PR #N превышает охват API (250 коммитов); полная проверка невозможна». Молчаливое усечение запрещено.
- Обход лимита (клон с полной историей и `git rev-list`) сознательно не входит в пилот: PR с 250+ неслитыми коммитами противоречит регламенту размера PR проекта (~600 строк diff); при реальном появлении — отдельное решение по задаче.

## 10. Hotfix-допуск: по факту базы, не по имени

В коде детектора **нет ветвления по имени ветки** — ни для `hotfix/*`, ни для каких-либо префиксов. Допуск чистого hotfix и поимка грязного обеспечиваются самой моделью U:

- Чистый hotfix `hotfix/x.y.z-*` от production tag `vX.Y.Z` (цель — новая `release/x.y.z` от того же тега, по регламенту `docs/git-workflow/pull-request.md`): история тега достижима из цели и вычтена; U содержит только собственные коммиты исправления → пересечение пусто → `clean`. То же верно при ошибочной цели в `main`: история `main` после тега вычтена из U через `reachable(main_tip)`.
- Ветка с именем `hotfix/*`, содержащая чужую открытую работу: чужие SHA входят в U → пересечение → `violation`. Иммунитета по имени нет.
- Сценарии S5, S6 матрицы фиксируют оба поведения тестами; «факт базы» воспроизводится в фикстуре вершиной тега при более новой цели.

## 11. Архитектура: чистая функция, сбор, CLI

Три изолированных слоя (требования безопасности и тестируемости):

1. **Pure (чистая функция):** вход — `Snapshot`, выход — `Verdict`. Без сети, файловой системы, времени, окружения. Полная детерминированность: одинаковый снимок → одинаковый вердикт.
2. **Collect (сбор):** единственный слой с доступом к сети (`gh api`); строит `Snapshot`, выполняет пагинацию, повторы, проверку стабильности; помечает `truncated`.
3. **CLI (оркестрация):** разбор аргументов, вызов collect → pure, печать результата, PR-комментарий, код возврата по таблице раздела 8.

Схема `Verdict`:

```
Verdict {
  outcome: violation | clean | inconclusive
  reason: string                       # машиночитаемая причина (для inconclusive)
  matches: list<{                      # случай A, один элемент на Q
    other_number: int
    other_target_branch: string
    common_shas: list<sha>             # общие неслитые коммиты (все или найденные)
    direction: stacked_on | base_for | equal_heads | partial
    proven_on_truncated: bool          # нарушение доказано на усечённых данных
  }>
  notes: list<{                        # информационные заметки (случай B и др.)
    kind: targets_other_open_branch
    other_number: int
    text: string
  }>
}
```

Тесты гоняют слой Pure на синтетических `Snapshot`-ах без сети и секретов; слой Collect в пилотных тестах не выполняет сетевых вызовов (его контрактная оболочка — фикстуры ответов API).

Язык реализации — **Python 3 (только стандартная библиотека)**: workflow обязан работать без установки PHP/Node; из предустановленного на образах остаётся python3/bash, а работа с множествами SHA и вложенными структурами на bash + jq хрупка. Альтернатива «PHP + PHPUnit-тесты чистой функции» отклонена: требует установки PHP в workflow детектора, что запрещено требованиями задачи. Детектор — инструмент репозитория, не бизнес-модуль библиотеки: PHP-конвенции слоёв DDD на него не распространяются, применяется общее правило изоляции логики от IO.

## 12. События запуска workflow

```yaml
on:
  pull_request:
    types: [opened, synchronize, reopened, edited]
```

- `edited` покрывает смену base branch (и, как следствие, заголовка/тела — лишние дешёвые запуски допустимы).
- **Без фильтра `branches`** — все цели (раздел 7).
- `pull_request_target` **запрещён** (исполняет workflow из base с секретами в контексте PR-кода; задача прямо исключает).
- Событие `closed` не подключается: пересчёт чужих PR при закрытии — предмет механизма актуализации (раздел 13), в пилоте отсутствует осознанно.
- Известное ограничение платформы: при конфликте слияния событие `pull_request` может не прийти — статус не обновится; это покрывается маркировкой снимка (раздел 13).

## 13. Актуализация статуса: маркированный снимок (выбор для пилота)

Выбран **явно маркированный снимок**, не централизованный пересчёт.

- Каждый запуск проверяет состояние на T0 и помечает результат временем: «статус — снимок на T0 (UTC), SHA головы и цели); актуализируется при следующих событиях этого PR». Снимок **не выдаётся молча за гарантию** постоянной актуальности — формулировка обязательна в PR-комментарии и summary.
- Причина отказа от централизованного пересчёта в пилоте: он требует записи статусов в чужие PR (права `pull-requests: write` на все проверки, гонки параллельных пересчётов, расписание или реакция на все события чужих PR). Стоимость высока, а информирующий пилот в ней не нуждается.
- Ранняя обратная связь (Should Have задачи): тот же CLI запускается локально до публикации ветки — `bin/stacked-pr-detector --repo <owner>/<repo> --pr <N>` (или `--head <sha> --base <branch>`), сбор через `gh` с учётными данными разработчика. Логика идентична CI.
- Эволюция после пилота (вне этой задачи): пересчёт по расписанию или по событиям чужих PR с публикацией индивидуальных статусов — отдельная задача при переводе в enforce.

**Гонки и их обработка:**

| Гонка | Обработка |
|---|---|
| Снимок неатомарен: между запросами чужой PR закрылся/обновился, цель двинулась | Контрольные точки после сбора; расхождение → повтор (до 3), затем `inconclusive` |
| Успешно проверенный P «загрязнился» позже: открыт Q с общей историей, коммиты P не менялись | Осознанное ограничение снимка; Q при своём открытии получит нарушение, P — нет. Заявлено в сообщении |
| Сигнал на P остался после слияния/закрытия Q | Статус P пересчитается при следующем событии P (push/reopen/edit). До того комментарий хранит время снимка |
| Параллельные запуски на один PR (двойной push) | Независимые прогоны; комментирующий шаг находит свой предыдущий комментарий по маркеру и редактирует его, а не плодит новые |
| Событие не пришло (конфликт слияния, edited без изменений базы) | Ограничение платформы; повторный запуск вручную; заявлено в контракте |

## 14. Безопасность

1. **Исполнение кода из PR исключено.** Workflow на событии `pull_request` берёт версию workflow-файла и (при обычном checkout) код из PR. Поэтому checkout выполняется **только из доверенной базовой ветки**: `actions/checkout` с `ref: ${{ github.event.pull_request.base.ref }}` (для событий не-PR — `github.ref`). Скрипты детектора запускаются из доверенной копии; изменения детектора в самом PR проверяются его же синтетическими тестами в этом же workflow до job детекции. Секреты репозитория не запрашиваются вовсе.
2. **Минимальные права токена:**

```yaml
permissions:
  contents: read          # checkout доверенной ветки
  pull-requests: read     # чтение метаданных PR и коммитов
```

Шаг PR-комментария (только при `violation`) — отдельный job с точечным расширением `pull-requests: write`. Токен не выводится в журнал; никакие секреты (`secrets.*`) детектору не передаются.
3. **Без подстановки данных в оболочку.** Контент PR (заголовки, тела, имена веток) не интерполируется в команды shell ни через `${{ }}`, ни через переменные. Сбор идёт по паттерну действующего `secret-scan-pr-content.yml`: `gh api … > file.json`, чтение файлов — слоем Collect. В shell-окружение передаются только скаляры из контекста события (`PR_NUMBER` — число, `REPO` — `owner/name` из `github.repository`).
4. **Данные PR — недоверенные.** Строки из API не попадают в формируемые shell-команды и в URLs без кодирования; PR-комментарий формируется из шаблонов с подстановкой чисел и SHA (безопасные алфавиты), произвольные строки — только через файловые интерфейсы.
5. **Тесты без GitHub и секретов:** все тесты — чистая функция + фикстуры; сетевых вызовов в тестах нет.

## 15. Сообщения детектора

Принципы: сообщается **общая неслитая история** и перечисляются связанные PR; виновная ветка не назначается без доказательства направления; инструкция «переделать от целевой» — только подтверждённому потомку (`stacked_on`); ссылка на правило `AGENTS.md` обязательна во всех нарушениях.

Шаблоны (подстановки: `#Q` — номер, `K` — количество, SHA укорочены до 7 символов, не более 5 в списке; `{{RULE_LINK}}` — подставляемая CLI ссылка на правило в `AGENTS.md` целевой ветки, раздел «Pull Request», строка запрета стековых PR):

- `violation`, направление `stacked_on` (единственный случай с инструкцией):
  > 🔴 **Детектор стековых PR: нарушение.** Ветка этого PR содержит вершину открытого PR #Q — она построена поверх несмерженной ветки (общих неслитых коммитов: K, например `abc1234`). По правилу AGENTS.md, раздел «Pull Request» ({{RULE_LINK}}), стековые PR запрещены: зависимые правки — один PR или последовательное выполнение. Переделайте ветку от целевой (`target`) или объедините изменения с #Q в один PR. Статус — снимок на T0.
- `violation`, направления `partial` / `equal_heads` / `base_for`:
  > 🔴 **Детектор стековых PR: нарушение.** Обнаружена общая неслитая история с открытым PR #Q (общих коммитов: K, например `abc1234`; направление зависимости автоматически не доказано, виновная ветка не назначается). По правилу AGENTS.md, раздел «Pull Request» ({{RULE_LINK}}), зависимые правки выполняются одним PR или последовательно. Проверьте состав коммитов обеих веток и устраните пересечение (переделка от целевой — для ветки, построенной поверх другой). Статус — снимок на T0.
  - Для `base_for` дополнительно: «Ваша вершина входит в #Q — над этой веткой построен другой PR».
- `clean` с заметкой случая B:
  > ℹ️ **Детектор стековых PR: заметка.** Цель этого PR — исходная ветка открытого PR #Q. Пилот не квалифицирует это как нарушение (коммиты #Q в базе этого PR, пересечения нет). Убедитесь, что это осознанная интеграционная ветка (например, ветка эпика), а не случайный стек. Статус — снимок на T0.
- `inconclusive`:
  > ⚠️ **Детектор стековых PR: проверка не выполнена.** Причина: `<reason>` (ошибка API / неполные данные / состояние изменилось во время проверки / превышен охват 250 коммитов у PR #N). Статус не «зелёный», чтобы не создавать ложную уверенность. Повторите запуск проверки. Статус — снимок на T0.

PR-комментарий помечен маркером `<!-- stacked-pr-detector -->` для повторного редактирования; полное техническое детальное сообщение (JSON-вердикт, время снимка, контрольные точки) — в `GITHUB_STEP_SUMMARY` и журнале задания.

## 17. Матрица синтетических сценариев (тесты)

Каждый сценарий — фикстура `Snapshot` + ожидаемый `Verdict`. Основа — таблица раздела 2.2 консультации; SHA в фикстурах синтетические, инцидент обезличен (номера и названия заменены).

| № | Сценарий | Снимок (суть) | Ожидание | Проверяемое свойство |
|---|---|---|---|---|
| S1 | Независимый PR от старой вершины цели; в цель слился чужой PR | цель продвинулась, U не пересекаются | `clean` | Отставание от цели ≠ стек |
| S2 | Чужие коммиты уже в цели обычным слиянием | слитые SHA вычтены reachable(target) | `clean` | Вычитание цели работает |
| S3 | Другой PR слит со squash (SHA переписаны), остался открытым дубль | нет открытых пересечений | `clean` | Список только открытых PR; эквивалентные патчи не обещаны |
| S4 | Обычный PR в `main` поверх чужого открытого PR в `main` | `head(Q) ∈ U(P)` | `violation`, `stacked_on` | Классический стек, инструкция «переделать» |
| S5 | Чистый hotfix от тега `vX.Y.Z` в новую `release/x.y.z`, цель `main` ушла вперёд | U = только коммиты исправления | `clean` | Допуск по факту базы, не по имени |
| S6 | Ветка с именем `hotfix/*` содержит чужую открытую работу | чужие SHA в U | `violation` | Иммунитета по имени нет |
| S7 | Два PR, одинаковые вершины, разные ветки | `head(P) = head(Q)` | `violation`, `equal_heads` | Пересечение есть, направление не выдумано |
| S8 | Родитель получил коммиты после ответвления потомка | пересечение без вхождения вершин | `violation`, `partial` | Частичный стек не пропущен |
| S9 | Оба порядка открытия одной пары (P↔Q) | одна фикстура, проверка обоих | `violation` у обоих, сообщения симметричны без вины | Симметрия признака |
| S10 | PR с целью в исходную ветку другого открытого PR (ветка эпика), без общих коммитов | `target(P) = source(Q)`, `U ∩ U = ∅` | `clean` + заметка B | Живая практика эпика не красится |
| S11 | Перенос исправления `main` ↔ `release/*` через cherry-pick, оба PR открыты | SHA различны | `clean` | Штатный перенос не сигналит |
| S12 | **Обезличенный инцидент PR #409–#414**: цепочка из пяти открытых PR в одну цель, ветка каждого поверх предыдущей; проверка второго и пятого | `U(k) ⊃ U(k−1)`; у второго `head(1) ∈ U(2)` | `violation` у каждого проверяемого; у второго — `stacked_on`, у пятого — `stacked_on` относительно четвёртого и `partial` относительно первых | Воспроизведение класса инцидента; направление доказывается только для прямой базы |
| S13 | Стек в разные цели: P → `main` содержит неслитые коммиты Q → `release/*` | `U(P) ∩ U(Q) ≠ ∅` при разных целях | `violation` | Область — все цели |
| S14 | Перенос с сохранением SHA, оба PR открыты | одинаковые SHA в двух целях | `violation` (осознанно) | Заявленный компромисс пилота |
| S15 | Список коммитов достиг 250; пересечение найдено в первых | `truncated` + непустое пересечение | `violation` (`proven_on_truncated`) | Монотонность усечения |
| S16 | Список коммитов достиг 250; пересечений не найдено | `truncated` без пересечений | `inconclusive` | Молчаливое усечение запрещено |
| S17 | Ошибка/недоступность API при сборе | collect возвращает отказ | `inconclusive`, job failure | Третий исход не «зелёный» |
| S18 | Состояние изменилось во время сбора (вершина двинулась), повторы исчерпаны | контрольные точки разошлись 3 раза | `inconclusive` | Гонка снимка обработана |
| S19 | PR из форка | `same_repository = false`, сравнение по SHA | по данным (обычно `clean`) | Форк не ломает сбор; случай B для форка не срабатывает |
| S20 | Draft PR с пересечением | как S4, `is_draft = true` | `violation` | Drafts проверяются наравне |

Матрица обязательна для фазы QA; расширение допустимо, сужение — нет.

## 18. Объявленные неподдерживаемые сценарии

Обещание их обнаружения из требований пилота **убирается** (осознанные ограничения, согласованные задачей и консультацией):

1. Эквивалентные патчи после squash/rebase/cherry-pick (Won't Have задачи).
2. Стек, замаскированный PR в чужую feature-ветку без общих коммитов (случай B) — информационная заметка, не блокировка.
3. Постоянная актуальность статуса при изменении чужих PR — маркированный снимок; пересчёт только по событиям самого PR или вручную.
4. PR с более чем 250 неслитыми коммитами без доказанного пересечения — `inconclusive`, обход лимита вне пилота.
5. Обновление статуса, если событие платформы не пришло (конфликт слияния).
6. Закрытые PR и история после переписывания — недоступные исторические факты.
