## 2. Вопрос 1. Реализуемость запрета стековых PR

### 2.1. Признак стека: реализуем, но не как сравнение всей истории

**Замечание высокой важности:** фраза «коммиты входят в другой открытый PR» требует определения множества коммитов и направления зависимости. Общий предок есть у любых обычных веток; отставание от целевой ветки не является доказательством стека. Автор коммита также не определяет принадлежность: один бот может создавать все PR проекта.

Рекомендуемая модель для этапа DS — проектирования:

1. Зафиксировать снимок: номер PR, репозиторий и вершину исходной ветки, целевую ветку и её текущую вершину; список других открытых PR с их вершинами и целями. Текущий PR исключить из сравнения.
2. Для двух PR в одну цель определить `U(P) = reachable(head(P)) − reachable(target)`: коммиты, достижимые из исходной ветки и ещё не достижимые из актуальной целевой. `reachable` здесь — достижимость в графе Git, а не текстовая похожесть изменений.
3. Непустое `U(P) ∩ U(Q)` — свидетельство общей ещё не интегрированной истории. Это симметричный признак: он может отметить оба PR. Нельзя автоматически объявлять оба «ветками, созданными неправильно» или требовать переделки родительского PR.
4. Если вершина `Q` является предком вершины `P`, отличается от неё и не находится в цели, это сильное свидетельство направления `Q → P`. Но проверка только текущей вершины `Q` неполна: родитель мог получить новые коммиты после ответвления потомка. Частичное пересечение тоже необходимо учитывать.
5. Отдельно обнаруживать цель PR, совпадающую с исходной веткой другого открытого PR. При таком стеке список изменений потомка относительно непосредственной базы может **не содержать** коммиты родителя. Ограничение проверки только пересечением списков PR пропустит случай.
6. Для разных целей (`main`, `release/*`) определить область сравнения отдельно. Не считать общую историю основных и релизных веток чужими новыми коммитами; учитывать базы обоих PR и разрешённый процесс переноса исправлений. Не игнорировать все PR с другой целью: это тоже возможный пропуск стека.

Это проектная рекомендация, а не доказанный полный алгоритм. Сравнение идентификаторов коммитов (SHA) выявляет общую историю, но не эквивалентные изменения после копирования коммита или переписывания истории. Добавлять сравнение патчей в пилот не рекомендую: это иная, более дорогая эвристика. Также невозможно восстановить любой исторический факт ответвления, если исходный PR уже закрыт и данные истории изменились. Обещание пилота следует ограничить обнаружением текущих признаков стека.

### 2.2. Ложные срабатывания и обязательные различия

| Сценарий | Ожидаемое решение | Проверка |
|---|---|---|
| Независимый PR от старой вершины `main`; в `main` слился чужой PR | Не считать стеком только из-за отставания | Синтетический граф с продвижением цели и повторным расчётом |
| Изменения другого PR уже попали в цель обычным слиянием | Общие интегрированные коммиты исключить | Проверить вычитание достижимого из текущей цели |
| Другой PR слит со сжатием или переписыванием коммитов | Закрытый PR не должен оставаться причиной сигнала «другой открытый PR»; очистка оставшейся истории — отдельный вопрос | Проверить обновление списка открытых PR; не обещать распознавание эквивалентных патчей |
| Срочное исправление `hotfix/x.y.z-*` от рабочего тега `vX.Y.Z` | Не требовать равенства общего предка вершине `main` | Фикстура с тегом и более новой целевой веткой |
| Ветка названа `hotfix/*`, но содержит чужую открытую работу | Не предоставлять иммунитет по имени | Отрицательный тест с тем же префиксом |
| Два PR имеют одинаковые вершины либо часть общей истории | Сообщить пересечение; не выдумывать направление зависимости | Проверить оба порядка открытия и симметрию результата |
| Родительский PR получил новый коммит после создания потомка | Не пропустить частичный стек | Граф с пересечением без вхождения текущей вершины родителя |
| Исправление переносится между `main` и `release/*` | Решение по согласованной модели целей, не по одному общему SHA | Отдельные фикстуры штатного переноса и настоящей зависимости |

Формулировка раздела рисков задачи CI «признак … этому не подвержен» слишком сильна: она верна лишь при корректно выбранном множестве коммитов, актуальном списке PR и определённой области целей. Предлагаю заменить её проверяемыми условиями на этапе уточнения постановки.

### 2.3. Точка внедрения

Факт: `.github/workflows/ci.yml` запускается для PR в `main` и `release/**` и содержит три задания проверки приложения. Отдельного детектора в нём нет. Простой дополнительный job (задание) дешевле, но наследует фильтр целей и не увидит PR, направленный в чужую рабочую ветку.

**Рекомендация:** отдельный небольшой workflow (рабочий процесс) для проверки метаданных PR, без установки PHP/Node и без зависимости от тестов приложения. Не ограничивать его только `main`/`release/**`, пока отдельно не определено поведение для неправильной цели. Альтернатива — отдельное задание в существующем файле с пересмотром фильтров, но это затронет и запуск тяжёлых проверок.

Стандартный `pull_request` запускается на открытие, обновление исходной ветки и повторное открытие; смену базы следует учитывать через `edited`. Для анализа использовать настоящие `head.sha` и целевую вершину, не искусственный коммит пробного слияния из `GITHUB_SHA`. При конфликте слияния обычный `pull_request` может не запуститься. Это ограничение следует явно принять либо отдельно спроектировать безопасную проверку метаданных через `pull_request_target`, никогда не исполняя в ней код недоверенного PR. [События GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).

Проверка на событии PR выполняется **после** открытия асинхронно. Требование «до/при открытии» следует уточнить: «ранний статус после открытия, до запроса одобрения». Запретить само создание PR таким заданием нельзя.

### 2.4. Главная скрытая сложность — актуальность статуса

Результат зависит не только от собственного коммита, но и от **других PR и состояния цели**. Пример: `P` проверен успешно, затем открыт `Q` с общей историей; коммит `P` не изменился. Обратный пример: сигнал на `P` остался после слияния или закрытия `Q`.

Одного запуска на событие текущего PR недостаточно для гарантии постоянной актуальности. На DS нужно выбрать и испытать механизм повторной оценки затронутых PR при открытии, обновлении, смене базы, закрытии и повторном открытии другого PR, а также изменении цели. Возможны централизованный обход открытых PR и публикация индивидуальных статусов либо ограниченный пилот, прямо маркирующий результат как снимок. Первый вариант требует дополнительных прав на запись статусов и контроля гонок; второй не является полной гарантией блокирования. Не надо молча выдавать его за такую гарантию.

### 2.5. Блокирование и обработка неполных данных

Для цели «машина запрещает» конечное решение — отдельная **обязательная проверка** в защите целевых веток. Красное необязательное задание и предупреждение не равнозначны запрету слияния. Обязательность настраивается в GitHub отдельно от YAML; это зависимость от владельца репозитория. [Обязательные проверки в правилах GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-status-checks-to-pass-before-merging).

До подтверждения алгоритма и актуальности статуса допустим только **явно согласованный** информирующий пилот. Тогда критерий результата — оценка обнаружения, а не автоматическое обеспечение запрета. Это альтернатива для согласования, не предлагаемый обход существующего правила.

Разделить три результата: нарушение, отсутствие обнаруженного нарушения при полном снимке, невозможность проверить. Ошибки API, отсутствие прав, неполные страницы и изменение вершин во время проверки — третий результат, а не зелёный. Для обязательного режима он блокирует завершение проверки с понятным сообщением; количество повторов и срок ожидания должны быть ограничены.

GitHub REST API (программный интерфейс) возвращает не более 250 коммитов через список коммитов PR. Обычной постраничной загрузки недостаточно для превышения этого предела. Нужны проверка полноты и заранее выбранная стратегия для больших историй — например, обход графа через другой интерфейс либо явный неподдерживаемый размер; не молчаливое усечение. [REST API: список коммитов PR](https://docs.github.com/en/rest/pulls/pulls#list-commits-on-a-pull-request).

Минимальные права на чтение метаданных; запись — только если выбран механизм обновления чужих статусов. Не использовать секрет GitHub App для исполнения кода из PR, не подставлять заголовки и имена веток непосредственно в команды оболочки, не выводить токены. Сведения о PR считать данными. Чистую функцию определения пересечений отделить от сетевого сбора; тесты работают без GitHub и секретов.

**Проверка вопроса 1:** таблица сценариев выше плюс пагинация, предел 250, недоступный API, смена базы, PR из внешней копии репозитория, родитель с новыми коммитами, изменения списка PR после успешной проверки. Испытывать производственную функцию и преобразование её результата в код завершения задания; синтетический тест не должен «красить» основной CI в красный при правильном обнаружении нарушения. Проверить включение тестов в `make check` и фактический CI. Требование обязательного статуса проверять по настройкам GitHub, а не только по YAML. Реальные стековые PR не создавать.

## 3. Вопрос 2. Изменения навыка и цикл PM1–PM5

### 3.1. Размер и подключение справочников

Текущий `docs/agents/skills/retrospective/SKILL.md` — 168 строк. Число строк само по себе не критерий качества: важно не повторить правила в нескольких местах.

Рекомендую оставить в основном файле обязательные решения: когда запускать каждый режим, какие доказательства допустимы, порядок анализа, согласование изменений и сохранение результата. Классификацию симптомов и расширенные примеры можно вынести в `assets/`, но добавить **явную инструкцию прочитать конкретный файл на конкретном шаге**. Одна ссылка не гарантирует применения вынесенной таблицы. Шаблон хранит поля результата, справочник — объяснение классификации; таблица не должна дублироваться в обоих местах.

Проверка: пройти сценарий, начиная только с основного файла навыка; убедиться, что справочник прочитан до выбора исправления, ссылки разрешаются, категории совпадают с шаблоном. Не вводить произвольный жёсткий предел строк без основания.

### 3.2. Источники: журнал аудита не равен записи сессии

`docs/guide/observability.md` описывает опциональный журнал событий цепочки. Проверенная реализация `JsonlAuditLoggerService.php` записывает начало/результат шага, роль, запускатель, метрики, статус и ошибку, но не полный диалог и не последовательность вызовов инструментов. Поэтому запись `step_result` не доказывает конкретное «агент долго искал файл».

Обеим задачам нужна матрица достаточности доказательств:

- Для утверждения о задержке шага — временные метки и длительность из журнала.
- Для утверждения о повторных ошибочных вызовах — запись сессии с конкретными событиями.
- Для отсутствующей проверки — конфигурация, команда и подтверждённый результат её выполнения, а не предположение по названию.
- При отсутствии нужного источника — явно отметить неподтверждённость и запросить данные либо остановить соответствующий вывод. Не выдумывать журнал и не подставлять путь `audit.jsonl` как универсальный существующий файл.
- Перед сохранением исключить секреты, персональные данные и чувствительные фрагменты журналов; сохранять минимальное доказательство и указатель на источник, а не копировать всю сессию.

Это скрытая зависимость задачи 1 тоже: там уже вводится трассировка находок. Сценарий отсутствия журнала нельзя отложить целиком до задачи 2. Расширение подсистемы журналирования не входит в этот эпик и не должно возникнуть как незаметное условие приёмки документации.

### 3.3. Согласованность режимов и документов

Сессионный режим намеренно меняет контракт текущего навыка: сейчас оценка ролей и объект «задача/эпик/PR» обязательны. Модель должна явно указать, какие поля обязательны только для полного режима, что является объектом сессионного отчёта, нужен ли раздел успешных практик и как действуют предел трёх предложений и статусы реестра. Это не основание ломать старые полноценные ретроспективы.

Риски, которые следует испытать:

1. Мини-ретро не отменяет полноценную ретроспективу после пользовательской приёмки.
2. Отсутствие проблем не создаёт пустую запись в `RETRO-ROADMAP.md`: сохранить действующее условие шага 7.
3. Повторный запуск по той же сессии не должен случайно порождать ещё один отчёт и счётчик. В то же время действующее правило считает упоминания **в разных ретро**, а не уникальные инциденты. Нельзя молча заменить его дедупликацией между сессионным и итоговым отчётами: это изменение семантики реестра, вынесенной за границы эпика. В PM1 нужно показать ожидаемый счёт на таком примере и принять решение в существующих границах либо отдельно согласовать их расширение.
4. Запись предложения не даёт разрешения внедрить его или менять уже одобренную ветку.

Проверить актуальные указания в `docs/agents/roles/team/team_lead_alex.*.md`, `docs/agents/workflow/sdlc.md`, `docs/agents/raci-matrix.md`, шаблоне, каталогах навыков, `README*.md`, `docs/index.md` и руководствах. Исторические отчёты и ретроспективы — свидетельства прошлого, их не надо переписывать под новую модель. Поиск показывает область проверки, а не разрешение на массовую замену текста.

### 3.4. Применимость PM1–PM5

**Без замечаний к выбору цикла:** обе задачи меняют оркестрационный навык, порядок действий и условия запуска. По разделу 6 RACI цикл определяется видом работы, а не расширением `.md`.

Уточнение планов: архитектор обязателен не только в PM1, но и как консультант PM2; тестировщик в PM2 проверяет сценарии отказов. Краткие планы задач не перечисляют архитектора в PM2 — при назначении участников нельзя прочитать это как исключение из матрицы. Список условных консультантов и причины участия фиксируются до PM2. PM4 оформляет принятую модель; DC публикует, а не повторно проектирует её.

Для CI-пилота DS/IM/QA/RV достаточны, **пока** он только реализует существующее правило. Если проектирование вводит новые исключения, право обхода, новые обязанности перед одобрением или меняет процесс команды, соответствующий нормативный объём также подпадает под PM1–PM5. Нельзя выводить его из цикла одним типом задачи `ci`.

**Проверка вопроса 2:** модель и таблица сценариев для двух режимов; отсутствие/неполнота журнала; секрет в записи; повторный запуск; полный отчёт после мини-ретро; нулевое число проблем; согласование и публикация после одобрения. Проверка ссылок и языка плюс сверка PM5; обычные PHPUnit/Psalm не заменяют проверки поведения инструкции.

## 4. Вопрос 3. Порядок, параллельность и скрытые зависимости

**Без замечаний к основной последовательности:** `TASK-docs-retro-skill-redesign` → слияние по явному разрешению пользователя → новая ветка от актуальной цели → `TASK-docs-retro-session-mode`. Это реальные зависимости по общим файлам, классификации и источникам. Нельзя начинать ветку задачи 2 поверх несмерженной ветки задачи 1.

CI-пилот технически независим от готовности текста навыка: он реализует уже существующее правило. Его проектирование и реализация могут идти параллельно задаче 1 в независимой ветке от целевой. В данной консультации параллельные агенты не запускались.

**Скрытые зависимости и уточнения:**

- **Общий контракт источников.** Задача 1 заранее определяет, чем подтверждается находка без журнала; задача 2 использует этот контракт, не изобретает другой.
- **Общая приёмка эпика.** Реальная ретроспектива по обновлённому навыку зависит от его доступности; независимость реализации CI не означает независимость демонстрации метода на его результатах. Не требуется делать CI зависимым от задачи 1 только ради этой демонстрации.
- **Работа владельца GitHub.** Обязательный статус требует настройки защиты, доступов и согласования режима. Это отдельный пункт приёмки пилота; файл рабочего процесса сам его не закрывает.
- **Общие сопроводительные файлы.** Оба направления могут затронуть руководства и `CHANGELOG.md`; заранее назначить владельца каждого изменения и порядок интеграции, не создавать стек веток ради устранения конфликтов.
- **Подключение тестов.** `make check` запускает PHPUnit и статические проверки, но текущий CI не вызывает `make check` целиком. Скриптовый тест детектора вне PHPUnit автоматически никуда не подключится. Нужен явный запуск и локально, и в CI; оболочка проверки относится к инструментам репозитория, не к бизнес-модулям библиотеки.
- **Фактическая обязательность пилота.** В эпике CI отнесён к Should Have (важно, но не обязательно), однако присутствует в цели и обязательном критерии завершения. Владелец должен выбрать: пилот обязателен для закрытия эпика либо переносим с явным изменением приёмки. Сейчас план допускает разные прочтения.
- **Практическая мини-ретроспектива.** Приёмка задачи 2 зависит от наличия реальной тяжёлой сессии и доступных доказательств. Не следует искусственно создавать ошибки ради неё. Предусмотреть время и выбрать подходящую сессию; если её нет, критерий не объявлять выполненным.

Рекомендуемые контрольные точки: согласование контракта детектора и объёма пилота; принятие модели задачи 1; её публикация и слияние; задача 2 от новой базы; проверка реальных примеров обоих режимов и итоговая приёмка эпика. Условия завершения не сводить к наличию трёх файлов с изменениями.

**Проверка вопроса 3:** схема зависимостей с основаниями, проверка баз веток, перечень общих файлов и ответственных, отдельный пункт настройки обязательного статуса, соответствие обязательных критериев приоритетам эпика.

## 5. Вопрос 4. Более дешёвые альтернативы

### 5.1. Штатные средства GitHub не равнозначны запрету стека

По опубликованному перечню правил GitHub отдельного правила «нет общих неслитых коммитов с другим открытым PR» не найдено. Это вывод из перечня, а не утверждение о проверенных настройках данного репозитория.

- Требование актуальности ветки перед слиянием проверяет её соответствие цели, а не принадлежность коммитов другому PR. Ветка может быть актуальной и содержать чужую неслитую работу.
- Требование линейной истории запрещает коммиты слияния, но стек из обычных последовательных коммитов остаётся линейным.
- Обязательное одобрение и сброс устаревших одобрений защищают качество слияния, но не являются ранним детектором стека. Отключать их ради исчезновения симптома инцидента не следует.

Назначение перечисленных механизмов подтверждается [документацией правил GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).

Очередь слияния проверяет совместимость с актуальной целью и ранее поставленными в очередь изменениями; это не запрет стековых веток и не устранение причины инцидента. Доступность очереди зависит от типа владельца и тарифа, поэтому не предполагается автоматически для этого проекта. Её внедрение не является дешёвой заменой данного пилота. [Описание механизмов слияния GitHub](https://docs.github.com/en/pull-requests/concepts/deploying-code).

### 5.2. Средства проекта и наиболее дешёвый путь

В просмотренных исполняемых средствах не найден готовый детектор стека. `make check`, PHPUnit, Psalm, Deptrac, проверки языка и секретов решают другие задачи; они не получают текущий граф открытых PR. Это ограниченный результат поиска, а не доказательство отсутствия любой подходящей сторонней интеграции.

Наиболее дешёвый путь **без собственной автоматизации** — уже действующий регламент: независимые ветки от цели, последовательное выполнение зависимых задач или один PR для связанных правок; перед одобрением человек проверяет состав коммитов. Это снижает риск, но сохраняет зависимость от дисциплины и потому **не закрывает исходное требование автоматического раннего обнаружения**.

Промежуточный вариант — локальная предварительная проверка перед публикацией, использующая тот же алгоритм. Она даёт раннюю обратную связь, но всё равно является собственной проверкой, требует данных GitHub и может быть пропущена; нет смысла выдавать её за бесплатную штатную замену CI.

**Рекомендация по стоимости:** сначала согласовать точную гарантию. Если нужен именно автоматический запрет текущего пересечения работ, небольшой собственный детектор плюс штатный обязательный статус — оправданная минимальная комбинация. Если нужна лишь дисциплина работы с ветками, достаточно существующего процесса, но это сознательное сокращение результата эпика, которое принимает владелец, а не исполнитель.

**Проверка вопроса 4:** прочитать действующие настройки защиты без изменения; сопоставить каждое включённое правило с матрицей сценариев раздела 2. Ни актуальность, ни линейность не должны считаться доказательством отсутствия стека. Синтетический актуальный линейный стек служит контрпримером, без создания реального PR.

## 6. Что передать владельцу постановок

1. Зафиксировать для CI область целей, точный признак, симметрию пересечения, пределы обнаружения, обновление статуса и поведение при неполных данных. Убрать двусмысленность демонстрации: только синтетический тест.
2. В задаче 1 определить контракт доказательств и подключение справочников; в задаче 2 — различия шаблона и ожидаемый подсчёт повторов без скрытой смены реестра.

4. Согласовать, обязателен ли пилот для завершения эпика. Информирование, блокирование слияния и предотвращение открытия PR — три разных результата.
