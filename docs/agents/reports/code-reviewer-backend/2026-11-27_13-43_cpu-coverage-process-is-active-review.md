## 3. Корректность ассертов (статическая верификация против скрипта)

Тайминги теста: `-s 8` (soft), `-t 30` (stall), `-m 30` (hard), `WATCH_WATCHER_INTERVAL=3`, `processTimeout=30.0`. Номинальная хронология (подтверждена прогоном 9.4 с):

- watcher (`watch-subagent.sh:999–1053`): тик t≈3 с — первый замер `process_is_active` инициализирует базу и **консервативно возвращает active** (`watch-subagent.sh:987`); тик t≈6 с — первая настоящая дельта; тик t≈9 с — вторая дельта, затем `elapsed=9 ≥ soft=8` → `watcher_fired reason=soft_timeout`.
- Основной цикл: `read -r -t 30` (`watch-subagent.sh:1122`) блокирован после единственной строки `agent_start`; in-loop проверки не исполняются; `live=` логирует только watcher-heartbeat. Ложных `live=idle` из основного цикла не бывает.
- `AGENT_PID` (`watch-subagent.sh:1094`) — сам bash-процесс фейкового раннера; busy-loop `while [ "$SECONDS" -lt "$end" ]; do :; done` крутится в нём же, builtin'ы без fork/IO. Стартовое IO (запись capture-файлов, чтение stdin, `printf agent_start`) целиком происходит до первого замера на t≈3 с и попадает в базу `/proc/<pid>/io`. Последующие IO-дельты строго нулевые → `live=active` на тиках 6/9 доказывает именно CPU-ветку (`cpu_now > prev_cpu`, `watch-subagent.sh:989`).

Оценка ассертов (строки 731–752 теста):

| Ассерть | Вердикт |
| :--- | :--- |
| `assertStringContainsString('live=active')` | Корректен, но сам по себе слаб: первый heartbeat всегда active (инициализация базы). Силу придаёт связка со следующим ассертом. |
| `assertStringNotContainsString('live=idle')` | **Главный дискриминатор.** Регрессия CPU-ветки (парсинг `ps -o times`, сравнение дельты) при нулевом IO даёт `live=idle` на тиках 6/9 → тест падает. Ложное покрытие исключено в номинале. |
| `assertStringContainsString('reason=soft_timeout')` | Корректен: watcher обязан дожить до soft, а не убить по stall. |
| `assertStringNotContainsString('reason=stall')` | Тривиально удовлетворяется таймингами (stall=30 > soft=8, `w_stall≈9 < 30` на момент soft) — страховочный, не дискриминирующий. Это осознанный дизайн (комментарий строки 703–704): исключает гонку «голодное окно → stall-килл». Приемлемо: детекция регрессии обеспечена ассертом `live=idle`. |

Квантование: дельта `ps times` (целые CPU-секунды) за 3-секундное окно ≥ 1 гарантирована при потреблении ≥ 1 CPU-сек (floor-разность), т.е. вплоть до ~66% голодания ядра; комментарий заявляет консервативные ~30% — запас честный, прогон под 50% нагрузкой (16/16 burners) зелёный.

Замечание о полноте (не дефект): связка «CPU-active подавляет stall-килл» (gate-путь `watch-subagent.sh:1042`) этим тестом не упражняется — она покрыта IO-тестом `stallDoesNotKillActiveProcessAndWaitsUntilSoftTimeout` (`-t 2 -s 4`). Постановка требует покрытия именно детекции CPU-ветки — требование выполнено.

### N1 — рекомендация (неблокирующая): защита от вырожденного прохода под экстремальной нагрузкой

**Файл:** `tests/Integration/Docs/Agents/Skills/RunSubagent/WatchSubagentScriptTest.php`, строки 731–752.

Теоретическое окно ложного покрытия: если первый тик watcher'а задержится планировщиком до `elapsed ≥ 8` (sleep 3 растянут в ~2.7+ раза), единственный heartbeat будет базовым (всегда `active`), сразу за ним сработает soft — все четыре ассерта пройдут **без единого настоящего CPU-замера**. Вероятность мала (под 16/16 нагрузкой тайминги номинальные), но дёшево закрывается насовсем: добавить ассерт минимального числа heartbeat'ов, например:

```php
self::assertGreaterThanOrEqual(
    2,
    substr_count($log, 'watcher_heartbeat'),
    'at least one non-baseline liveness measurement must happen before soft-timeout',
);
```

Гарантия: второй heartbeat — всегда настоящая дельта. На усмотрение исполнителя; на вердикт не влияет.
