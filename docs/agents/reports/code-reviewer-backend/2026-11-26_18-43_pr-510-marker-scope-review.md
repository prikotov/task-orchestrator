## 1. Блокирующие замечания (Change Request)

### 🔴 CR-1. `Makefile:129` — экранирование `$$$(date …)` ломает маркер: JSON невалиден, пара epoch/utc не пишется

Строка:
```make
@read -r MAKE_CHECK_EPOCH MAKE_CHECK_UTC <<<$$$(date -u '+%s %Y-%m-%d %H:%M:%S') && \
```
Make разворачивает `$$` → литеральный `$`, а оставшееся `$(date -u '…')` интерпретирует как **обращение к make-переменной** с именем `date -u '+%s %Y-%m-%d %H:%M:%S'` — она не определена и раскрывается в пустую строку. Shell получает `<<<$` (литеральный доллар), а не подстановку команды.

**Эмпирическое доказательство** (изолированный Makefile, GNU make):
- `make -n` печатает рецепт: `read -r MAKE_CHECK_EPOCH MAKE_CHECK_UTC <<<$ && …`
- реальный запуск пишет файл: `{"commit":"abc123","epoch":$,"utc":""}` — **невалидный JSON**.

Последствия: нарушение Must Have п. 3.1 («epoch и utc одной парой»); `python3 json.load` в job (ci.yml:118) упадёт с traceback вместо верификации — job красный даже при корректном маркере по SHA.

**Запрос на изменение:** `Makefile:129` — заменить `$$$(date …)` на `$$(date …)` (два `$`, чтобы shell получил `$(date …)`). После фикса проверить `make -n check`: в рецепте должна остаться подстановка `$(date -u '+%s %Y-%m-%d %H:%M:%S')`, а результат — валидный JSON с числовым `epoch` и полным `utc`.

### 🔴 CR-2. `.github/workflows/ci.yml:119` — `HEAD^^` при merge-checkout указывает не на родителя маркерного коммита: позитивный кейс всегда красный

Строка:
```bash
previous_commit="$(git rev-parse "$(git rev-parse HEAD^)^")"   # = HEAD^^
```
`actions/checkout@v4` на событии `pull_request` по умолчанию чекаутит **merge-коммит** `refs/pull/N/merge` (PR head, влитый в base), а не head ветки. У этого merge-коммита **parent1 = base tip, parent2 = PR head**.

**Эмпирическое доказательство на реальном `refs/pull/510/merge`** (`2dfd8b98`, «Merge 92a2d9a6… into 5ace0b0f…»):
- `HEAD^` (parent1) = `5ace0b0f` — tip `main` (PR #509);
- `HEAD^2` (parent2) = `92a2d9a6` — head PR (маркерный коммит по процедуре задачи);
- `HEAD^^` = `6c7b0ffa` — **родитель base tip**, посторонний коммит main (PR #508);
- родитель маркерного коммита = `HEAD^2^` = `1a8f97be`.

То есть job сравнивает `checked_sha` с коммитом, не имеющим отношения к ветке PR. Позитивная проверка (DoD п. 5.2) не пройдёт **никогда**, даже после снятия блокера 0.35.0 и корректного маркера. Дополнительно: сообщение об ошибке (ci.yml:121) назовёт «последним кодовым коммитом ветки» чужой SHA — дезинформация исполнителя.

Отмечу явно: формула `git rev-parse "HEAD^^"`, приведённая в запросе на ревью как ожидаемая, **ошибочна**; намерение «сверить с родителем маркерного коммита» (постановка, Must Have п. 3.2) — верное, реализация ему не соответствует.

**Запрос на изменение:** `.github/workflows/ci.yml:99-101,119` — чекаутить head PR явно и сравнивать с прямым родителем:
```yaml
- uses: actions/checkout@v4
  with:
    ref: ${{ github.event.pull_request.head.sha }}
    fetch-depth: 0
```
```bash
previous_commit="$(git rev-parse HEAD^)"
```
При таком чекауте HEAD = маркерный коммит, `HEAD^` = последний кодовый коммит — буквально постановка. Diff-фильтр `${BASE_SHA}...HEAD` (ci.yml:108) остаётся корректным (three-dot через merge-base). Альтернатива `HEAD^2^` при merge-checkout тоже работает, но хрупкая (ломается при смене ref чекаута) — не рекомендую. После фикса обязательны отложенные негативная/позитивная проверки на CI (план п. 4).

## 2. Важные замечания

### 🟡 CR-3. `Makefile:129` — bash-only here-string `<<<` при дефолтном `SHELL = /bin/sh` у make

Make не задаёт `SHELL` (проверено: в Makefile нет), дефолт — `/bin/sh`. На машине сопровождения `/bin/sh → bash` (проверено), поэтому рецепт работает; на стандартных Debian/Ubuntu `/bin/sh → dash`, где `<<<` — синтаксическая ошибка: `make check` упадёт на строке маркера **после полностью зелёных проверок**, маркер не запишется. Для гейта, рассчитанного на разных исполнителей (агенты, клоны), это мина.

**Запрос на изменение:** либо объявить `SHELL := /bin/bash` в шапке Makefile, либо POSIX-разбор одной строки без here-string (сохраняет «один вызов date»):
```make
@ts=$$(date -u '+%s %Y-%m-%d %H:%M:%S'); \
	printf '{"commit":"%s","epoch":%s,"utc":"%s"}\n' "$$(git rev-parse HEAD)" "$${ts%% *}" "$${ts#* }" > .make-check.json && …
```
Допустимо объединить с CR-1 одним коммитом.

### 🟡 CR-4. `.github/workflows/ci.yml:109` — фильтр кодовых путей не покрывает все конфиги проверок (Must Have п. 3.3)

В регулярке отсутствуют отслеживаемые git конфиги, влияющие на `make check`:
- `.md-links.php` — дефолтный конфиг `validate-md-links` (подтверждено: `vendor/prikotov/coding-standard/bin/validate-md-links`, «Default: .md-links.php in project root»);
- `phpstan.neon.dist` — конфиг PHPStan (цель `phpstan`);
- `phpmd.baseline.xml` — baseline PHPMD (`--baseline-file=phpmd.baseline.xml`, Makefile:33).

PR, правящий только эти файлы (например, ослабление baseline), пройдёт мимо гейта. **Запрос на изменение:** ci.yml:109 — добавить в альтернативу `\.md-links\.php$|phpstan\.neon\.dist$|phpmd\.baseline\.xml$`.

### 🟡 CR-5. `todo/cancelled/TASK-techdebt-track-todo-agents-md.todo.md:8,117-119` — метка отмены рассинхронизирована с локальной зоной; в Change History нет записи об отмене

- Строка 8: `cancelled: 2026-11-26 11:35:29 (1795692929)`. Epoch `1795692929` = `2026-11-26 18:35:29 +0700` (проверено `date -d @…`); именно так это же событие записано в Change History основной задачи (18:35:29). Локальная часть в cancelled-файле написана в UTC. Формально offset +00:00 проходит валидацию DATES.md, но регламент (`docs/todo-md/reference/DATES.md`, «Кто проставляет») требует метку от CLI в локальном времени машины-писателя; расхождение — признак ручной правки и рассинхрон двух файлов об одном событии.

**Запрос на изменение:** строка 8 — `cancelled: 2026-11-26 18:35:29 (1795692929)`; в Change History добавить строку отмены с причиной и ссылкой на решение владельца.
