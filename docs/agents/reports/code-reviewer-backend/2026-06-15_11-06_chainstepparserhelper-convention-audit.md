## 1. SRP / «один узкий контекст»

Нарушено. В классе **минимум две публичные точки входа, обслуживающие разные контексты**:

1. **Парсинг списка шагов** цепочки (`parseSteps` → `buildStep` → `build{Tool,QualityGate,Agent}Step` + `parseWhen` + `parsePostStep`).
2. **Парсинг retry-политики** (`parseRetryPolicy`) — публичный метод, который `YamlChainLoaderService` вызывает **самостоятельно, на уровне цепочки**, а не шага: `src/.../YamlChainLoaderService.php:133` и `:187`. То есть `parseRetryPolicy` — отдельный публичный контракт, не принадлежащий контексту «парсинг шагов» (продукт `ChainRetryPolicyVo`, а не `ChainStepVo`).

Нарушено правило helper.md: **«Один Helper — один узкий контекст (SRP)»** и **«Группирует утилиты одного узкого контекста»**. `parseRetryPolicy` сгруппирован сюда по признаку «тоже из YAML-конфига цепочки», а не по принципу одной утилиты.

Distinct-ответственности внутри класса (даже без учёта публичного `parseRetryPolicy`):
- A. Диспетчеризация по типу шага (`buildStep`, match по `ChainStepTypeEnum`).
- B. Сборка VO каждого из трёх типов (`buildToolStep`, `buildQualityGateStep`, `buildAgentStep`).
- C. Преобразование DSL-строк в `ConditionExpressionVo` и в строку `post_step` (`parseWhen`, `parsePostStep`).
- D. Парсинг retry-политики в `ChainRetryPolicyVo` (`parseRetryPolicy`).

Вывод по п.1: контекст не «один узкий», а **кластер из 4 связанных, но разнородных ответственностей**.

## 2. «Только техпреобразования, бизнес-логика запрещена»

Нарушено. В классе присутствуют **политики значений по умолчанию и правила приоритета** — это не чистые техпреобразования массив→VO, а кодирование DSL-семантики.

Конкретные строки:

- `buildToolStep`, **стр. 118**: `timeoutSeconds: $step['timeout_seconds'] ?? 120,`
- `buildQualityGateStep`, **стр. 153**: `timeoutSeconds: $step['timeout_seconds'] ?? 120,`

  Захардкоженный дефолт `120` — guessed default (политика таймаута). Противоречит и helper.md («Только техпреобразования, бизнес-логика запрещена»; чек-лист «Нет бизнес-логики домена»), и AGENTS.md («Не подставляй guessed defaults»).

- `buildAgentStep`, **стр. 176**: `$stepNoContextFiles = (bool) ($step['no_context_files'] ?? $chainNoContextFiles);`
- `buildAgentStep`, **стр. 185**: `retryPolicy: $stepRetryPolicy ?? $chainRetryPolicy,`

  Здесь реализовано правило **приоритета «шаг перекрывает цепочку»** (`step ?? chain`). Это бизнес-правило мерджа конфигурации DSL, а не техпреобразование «массив → VO».

- `buildAgentStep`, **стр. 182**: `runner: $step['runner'] ?? 'pi',` — guessed default для runner.
- `buildAgentStep`, **стр. 190**: `runnerExplicit: array_key_exists('runner', $step),` — вычисление **семантического флага** «runner задан явно». Это доменное знание о том, что важно отличать «явно задано» от «дефолт».

- Валидация инвариантов в `buildToolStep` / `buildQualityGateStep` / `buildAgentStep` (стр. 104, 110, 139, 145, 179): проверки «обязательный command/label/role» — это **правила корректности DSL**, т.е. инварианты модели. Допустимо для фабрики (factory.md: «централизовать проверку инвариантов»), но **не входит в понятие утилитарного техпреобразования** для helper.

Вывод по п.2: FAIL по пункту конвенции «Только техпреобразования, бизнес-логика запрещена» (стр. 118, 153, 176, 182, 185, 190).

## 3. Скрытая сложность

Присутствует:

- **Скрытая стратегия (dispatch по типу)** — `buildStep`, **стр. 84–87**:
  ```php
  return match (true) {
      $stepType === ChainStepTypeEnum::tool => self::buildToolStep(...),
      $stepType === ChainStepTypeEnum::qualityGate => self::buildQualityGateStep(...),
      default => self::buildAgentStep(...),
  };
  ```
  Это Strategy/Factory-диспетчеризация, спрятанная в статическом «хелпере».

- **Дублирование между методами**: `buildToolStep` (стр. 100–123) и `buildQualityGateStep` (стр. 135–158) почти идентичны — одинаковая валидация `command`/`label`, одинаковый дефолт `timeout_seconds ?? 120`, разница только в вызове `createTool`/`createQualityGate` и наличии `outputKey`. Классическое дублирование, которое конвенция SRP и DRY не одобряет.

- **Тонкие флаги/ambient-параметры**: `?ChainRetryPolicyVo $chainRetryPolicy` и `bool $chainNoContextFiles` протаскиваются сквозь 4 сигнатуры (`parseSteps` → `buildStep` → `buildAgentStep`) как fallback-окружение. Это сигнал, что класс хранит «контекст сборки» в параметрах вместо зависимости — типичный запах, который уходит, если сделать класс фабрикой/сервисом с состоянием запроса.

Вывод по п.3: скрытая сложность есть — type-dispatch, дублирование двух builder-методов, ambient-флаги.

## 4. Маскировка другого паттерна

Класс по поведению — **фабрика**, одетая в `Helper`:

- Возвращает строго типизированные доменные объекты `ChainStepVo` (стр. 32, 123, 158, 178) — factory.md: «Фабрика возвращает объекты (Entity, VO, DTO)».
- Централизует проверку инвариантов и бросает корректные исключения при их нарушении (стр. 104, 110, 139, 145, 179) — factory.md: «централизовать проверку инвариантов», «При некорректных входных данных ... выбрасываются корректные исключения».
- Скрывает сложность сборки: ветвление по типу + разные наборы параметров для `createTool`/`createQualityGate`/`createAgent` — factory.md: «скрыть сложность сборки».
- Аргументы методов в сигнатурах `build{Tool,QualityGate,Agent}Step` — это не «примитив в → примитив out» (как `FileHelper::removeExtension(string): string` из примера helper.md), а сборка VO из структурированного массива с политиками и инвариантами.

Дополнительно: `parseRetryPolicy` (стр. 55) — отдельный парсер, не производящий `ChainStepVo`, что ещё больше подтверждает, что «Helper» здесь используется как контейнер для разнородной логики сборки/парсинга, а не как одна утилитарная операция.

Альтернативный взгляд: частично Strategy (dispatch в `buildStep`). Но доминирующий паттерн — **Factory** (сборка VO с инвариантами).

Вывод по п.4: по фактам поведения это `ChainStepVoFactory` (+ вспомогательный `parseRetryPolicy`), а не helper-утилита. Наименование `Helper` маскирует реальный паттерн.

## ПРЯМОЙ ответ на вопрос «он простой?»

**НЕТ.**

Формально класс проходит «механические» пункты helper.md (final, static, нет DI, нет I/O, pure, правильный постфикс и слой), но **не является простым helper-ом**, потому что:

1. Нарушает helper.md «Один Helper — один узкий контекст (SRP)»: имеет **вторую публичную ответственность** `parseRetryPolicy` (стр. 55), используемую на уровне цепочки вне потока парсинга шагов (`YamlChainLoaderService:133,187`).
2. Нарушает helper.md «Только техпреобразования, бизнес-логика запрещена» и чек-лист «Нет бизнес-логики домена»: содержит guessed-дефолты (`?? 120`, `?? 'pi'`), правило приоритета конфигурации (`step ?? chain`), семантический флаг `runnerExplicit` (стр. 118, 153, 176, 182, 185, 190).
3. По факту поведения — это **фабрика** (`ChainStepVoFactory`): сборка доменных VO с централизованной проверкой инвариантов и ветвлением по типу (factory.md), замаскированная постфиксом `Helper`.

Точная локализация нарушений конвенции:
- helper.md, «Один Helper — один узкий контекст (SRP)» — публичный `parseRetryPolicy` (стр. 55).
- helper.md, «Только техпреобразования, бизнес-логика запрещена» / чек-лист «Нет бизнес-логики домена» — стр. 118, 153, 176, 182, 185, 190.
- helper.md, чек-лист «Unit-тесты обязательны при ветвлениях и логике» — отсутствие прямых unit-тестов для type-dispatch/валидации/fallback.
- factory.md (косвенно): поведение класса соответствует фабрике, но именование/форма — helper.

Где именно «непростота» с точки зрения конвенций (а не личной оценки): в наличии **бизнес-политики (дефолты + правило приоритета)** внутри «чистой утилиты» и во **второй публичной ответственности**, плюс в **маскировке фабрики под helper**.
