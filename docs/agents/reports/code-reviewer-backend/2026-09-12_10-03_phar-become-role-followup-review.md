## Проверенные аспекты

### 1. Kernel cache isolation (QA-1)

**Реализация:** `src/Kernel.php::writableRoot()` — ключ изоляции `hash('xxh64', getProjectRoot() . "\0" . resolvePharPath())`.

- ✅ **Изоляция по паре (host-проект, физический путь PHAR).** Разделитель `"\0"` исключает граничные коллизии конкатенации; xxh64 достаточен для непересекающегося ключа каталога. После перемещения архива (`mv A → B`) контейнер B получает свежий ключ → свежую компиляцию с корректными `package_dir`/`phar_path`. Инвариант «замороженные в кеш параметры всегда соответствуют фактическому расположению» восстановлен без runtime-инфраструктуры (env-процессоры не понадобились — решение соразмерно дефекту).
- ✅ **Source/Composer не затронуты.** Вне PHAR `resolvePharPath() === null` → прежний `getProjectRoot()`; поведение `<host>/var/cache/task-orchestrator/<version>/<env>` сохранено, `APP_CACHE_DIR`/`APP_LOG_DIR` — прежние полные переопределения. Regression-тесты Composer-host зелёные.
- ✅ **Отсутствие утечки пути.** В кеш-каталоге — только хеш; тест проверяет `assertStringNotContainsString('/tools/', $cacheDir)` при сохранении структуры `var/cache/task-orchestrator/<version>/<env>` (версионная изоляция не демонтирована). Диагностики сервиса по-прежнему без `phar://`.
- ✅ **`resolvePharPath()`** — `Phar::running(false)` с guard `class_exists`, без парсинга `phar://`-строки (обоснование в PHPDoc корректно); protected-шов по образцу `renamePath()` у `InstallBecomeRoleService` — законный проверяемый шов, использован regression-тестом через анонимный класс.
- ✅ **Regression-тест** `pharWritableRootIsIsolatedByHostProjectAndPhysicalPharPath` закрывает матрицу: тот же (host, PHAR) → тот же корень; другой PHAR → другой корень; другой host → другой корень; log-корень изолирован тем же ключом; структура пути и отсутствие утечки. Дополнительно `initCommandWiresInstallBecomeRoleService` фиксирует DI-проводку команды (alias интерфейса + автосайринг аргументов).

### 2. Smoke перемещения PHAR A→B без маскировки дефекта

**Реализация:** `bin/phar-smoke::check_phar_move_reinstall()`.

- ✅ **Дефолтный кеш между A/B.** `APP_CACHE_DIR` в сценарии не задаётся — кеш идёт через дефолтный `writableRoot()`. `TMPDIR`-песочница честно прокомментирована как перенос `sys_get_temp_dir()` (чтобы smoke не мусорил в системном `/tmp`), а не как изоляция; заявленная в комментарии невозможность маскировки дефекта подтверждена ниже негативным контролем.

## Замечания (не блокирующие)

### FR-1 — Nit (симметрия источников PHAR-контекста в `Kernel`)

**Файл:** `src/Kernel.php`, `writableRoot()` vs `getProjectDir()`/`is_phar`.
**Обоснование:** `writableRoot()` теперь ветвится по `resolvePharPath() !== null` (`Phar::running`), а `getProjectDir()` и параметр `is_phar` — по `isPhar()` (`__FILE__` с префиксом `phar://`). Для штатного запуска PHAR-стаба условия эквивалентны. Расхождение возможно в экзотическом кейсе прямого подключения классов через `phar://`-include без запуска стаба (`isPhar() === true`, `Phar::running() === ''`): там `writableRoot()` вернёт `getProjectRoot()` = read-only `phar://…`, и запись кеша упадёт, хотя до правки уходила во временный каталог. Публичный контракт не затронут (PHAR-ветка `agent:init` в этом кейсе и так требует непустой `phar_path`), но «два источника истины» — потенциальная ловушка для будущих правок.
**Рекомендация:** при следующем касании файла выровнять условие консервативно, например `if (!$this->isPhar() && $pharPath === null) { return $this->getProjectRoot(); }` — temp-корень при любом PHAR-признаке; либо зафиксировать инвариант «PHAR-режим ≡ `Phar::running(false)` непусто» явным PHPDoc на обоих методах.
