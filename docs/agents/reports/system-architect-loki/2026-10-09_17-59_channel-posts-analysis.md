## Допущения

- Применимость оценена в двух плоскостях: (а) продукт task-orchestrator как оркестратор CLI-агентов, (б) процесс собственной разработки проекта.
- Содержание постов принято как данность; по первоисточнику проверена только статья Cloudflare Code Mode (см. «Источники»).
- Текущее состояние кодовой базы сверено по src/Module/ (AgentRunner, ChainDefinition, ChainExecution, DynamicLoop, GitIdentity) и README.md.

## Сквозные темы постов

1. **Экономика агентов** — виртуальный кошелёк, плата за LLM, баланс эффективности и стоимости (посты 01.10, 05.10).
2. **Progressive disclosure + Code Mode** — вместо кучи инструментов две команды (`start` → SDK, `run` → код на сервере); Cloudflare ужала 1–2 млн токенов описаний 2549 инструментов до ~1000 токенов (посты 08.10, 09.10).
3. **Общая память агента и человека** — «доска», которую агент и человек правят одновременно; версионированный стор с откатом изменений агента (посты 04.10, 08.10).
4. **Методология** — копировать фишки топовых компаний; делегировать агентам инфраструктурные прототипы с доказуемым критерием (посты 01.10, 04.10).

## Что у нас уже есть — не изобретать

| Идея из постов | Что уже есть в проекте |
|---|---|
| Учёт токенов/стоимости | `AgentResultVo` (inputTokens/outputTokens/cost/model/turns), JSONL-аудит каждого шага (`JsonlAuditLoggerService`) |
| Лимиты расходов | `BudgetVo` (`max_cost_total` / `max_cost_per_step` / `per_role`), проверка до/после шага, предупреждение на 80%, прерывание `budget_exceeded` |
| Progressive disclosure | Каталог скиллов в system prompt — только имя+описание+путь (`FormatSkillCatalogService`); участники dynamic-цикла получают список файлов сессии, а не содержимое; static-контекст — только вывод предыдущего шага с обрезкой `maxContextLength` |
| Версионированная память сессии | Файлы dynamic-сессий по раундам + resume (`restoreFromRoundFiles`) |

Вывод: курс проекта в целом совпадает с тем, что канал продаёт как «будущее». Ниже — deltas (разницы), которые реально стоит взять.

## Что взять: рекомендации по приоритету

### 🟢 P1 — дёшево, эффект сразу

**1. Бюджет как ресурс для решений агента, а не только предохранитель.**
Сейчас `CheckDynamicLoopBudgetService` только прерывает цикл по превышению. Перенос идеи «кошелька» из ECOM2: сообщать фасилитатору в промпт **остаток бюджета и накопленную стоимость раундов** (данные уже есть в `AgentResultVo`). Фасилитатор уже решает `next_role`/`done` — пусть решает с учётом денег: свернуть дискуссию раньше, назначить дешёвую модель на простой раунд. Это превращает лимит из «аварийного клапана» в управляемый ресурс, тот самый «баланс эффективности и стоимости».
Метрика: средняя стоимость цепочки на задачу; доля прерываний по `budget_exceeded` (должна падать — цикл стал сворачиваться сам).

**2. Метрика token efficiency в observability.**
Пост 09.10 измеряет выгоду progressive disclosure в разах. У нас входные токены по шагам уже собираются — добавить в отчёт по цепочке разрез: сколько входных токенов ушло на system prompt роли, каталог скиллов, журнал фасилитатора — а сколько на полезный контекст задачи. Это детектор раздутого контекста (аналог проблемы автора поста: «6.5 минут копошения в файле на 70kb»).
Метрика: доля «служебных» входных токенов на шаг/раунд.

### 🟡 P2 — средняя стоимость

**3. Доступ к сессии кодом, а не чтением файлов целиком (аналог Code Mode для dynamic-цикла).**
Прямой аналог боли из поста 08.10: агенты «находят документы быстрее, но дольше копошатся с изменением». Наши участники читают response-файлы сессии через read-tool; с ростом сессии это растёт по токенам и времени. Решение в духе Code Mode: маленький CLI/скрипт (PHP — стек позволяет) с операциями выборки/поиска/диффа по сессии, который агент вызывает вместо чтения файлов. Уточнение по первоисточнику: у Cloudflare это JavaScript в V8-изоляте, а не Python — принцип «дать агенту код против SDK» важнее языка.
Ожидание: сокращение input-токенов и времени раунда; проверить замером до/после.

**4. Точки human-in-the-loop в dynamic-цикле.**
Из поста 04.10 (человек и агент одновременно работают над доской; конфликт ловит агент). У нас есть файлы сессии и resume — «доска» почти собрана, не хватает входа человека: пауза цикла → правка файлов/журнала человеком → продолжение с подхватом изменений. Это меняет режим работы с «запустил и жди» на «работаю параллельно с командой агентов».

**5. Лог побочных эффектов шага + откат при прерывании.**
Из поста 08.10: «можно откатить изменение агента, даже если он поменял тысячу файлов». У нас при `budget_exceeded`/timeout/agent_error побочные эффекты в рабочей копии репозитория остаются висеть. `GitIdentity` уже есть: фиксировать diff по шагу и предлагать откат при прерывании цепочки. Это развитие существующих retry/interrupt, не новая инфраструктура.

### 🔴 P3 — осознанно НЕ брать (или отложить)

**Firecracker VM, COW-снапшоты, suspend/resume.** Не для PHP CLI-библиотеки: собственная инфраструктура уровня хостинг-провайдера. Посты подсвечивают реальную слепую зону — изоляции запусков нет вообще (codex запускается с `--sandbox danger-full-access`, tool-шаги и quality gate — голый `Process::fromShellCommandline`). Но лечить её дешевле: рабочие директории на шаг, отказ от `danger-full-access` где возможно, контейнеры как опция развёртывания. Рекомендую зафиксировать риск отдельной задачей, а не тащить VM в ядро.

**Mesh-экономика p2p: переводы кредитов и свободные сообщения любым агентам.** Противоречит нашей сильной стороне — процессному контролю через координацию (фасилитатор/тимлид). Рынок без иерархии = потеря детерминированности, которую мы продаём. Участие в BitGN ECOM2 как в полигоне (когда откроют песочницу) — полезно для вынесения уроков; перенос модели в ядро — нет.

**Полная замена скиллов «процессами кодом в SDK».** Текстовые скиллы — наша фича (гибкость, кросс-клиентная конвенция `.agents/skills/`). Правильный гибрид уже зафиксирован в README: детерминированное — YAML/скрипты, решения — агенту. Правило переноса из постов: если скилл разрастается и агент начинает путаться в шагах — переносить механику в скрипт/YAML, оставляя агенту только точки принятия решений.

### Методология (посты 01.10, 04.10)

- **«Эталонные прогоны»:** давать собственным цепочкам задачи уровня «прототип с доказуемым критерием» (как в посте: песочница + доказанный suspend/resume) и мерить, справляется ли стек. Формулировка «минимальный прототип + доказательство» — хороший шаблон для постановок в `todo/` и скиллах.
- **Продолжать серию `docs/research/`:** разбор выступлений топовых компаний → конкретные задачи. Практика уже есть — пост 04.10 её подтверждает как главный канал идей.

## Дополнение (по вопросу владельца): «много агентов, каждый в песочнице» — интересно ли нам

Факт: в `docs/releases/ROADMAP-2026-Q2-Q3.md` уже запланированы на Q4 2026:
- **Параллельное выполнение** (Кластер 3: Оркестрация, спринт 1–2): `?array $dependsOn` + `?string $parallelGroup` на `ChainStepVo`, fan-out через DAG (направленный ациклический граф шагов). Прототипы из чужих решений: Archon (DAG layers), Mastra AI (`.parallel()`).
- **Песочница на базе Docker** (Безопасность, спринт 4–5): приоритет повышен — единственный реальный механизм контроля доступа после отмены модуля политики безопасности.
- Модуль политики безопасности ранее отменён именно с формулировкой «контроль доступа — через песочницу ОС».

Выводы:

1. **Посты канала не меняют план, а подтверждают его приоритет.** Автор решает задачу платформы-хостинга (тысячи чужих агентов, мультиарендность, защита от падения серверов) — там Firecracker с COW-снапшотами оправдан как оптимизация плотности памяти. Наш масштаб — единицы-десятки параллельных агентов на одной машине в одном проекте: Docker из ROADMAP — правильный уровень, VM-слой не окупается для PHP-библиотеки.

2. **Песочница — не отдельная фича, а блокер параллельности.** Без изоляции рабочих каталогов параллельные агенты в общей рабочей копии устроят гонки по файлам (два агента правят один файл — правки перетираются). Сегодня `danger-full-access` + общий рабочий каталог — потому параллельности в коде и нет (`grep` подтверждает: запуск процессов только последовательный). Значит порядок работ внутри Q4 важен: изоляция должна идти раньше или вместе с fan-out.

3. **Промежуточный шаг дешевле Docker (можно сделать до спринта 4–5):** изолированные рабочие копии через `git worktree` на шаг/агента. `GitIdentity` уже есть; это снимает взаимные помехи по файлам для параллельных шагов без контейнеров. Docker добавит ограничения shell-команд и сетевую изоляцию поверх.

4. **Уточнения в дизайн параллельности из постов:**
   - При падении одного из N параллельных агентов не нужны VM-снапшоты: достаточно нашей модели сессий (JSONL-лог + resume), которую автор поста фактически переизобретает через suspend/resume.
   - Fan-out умножает расходы на N: бюджет `per_role` частично покрывает, но нужен контроль бюджета на `parallelGroup`.
   - Параллельный JSONL-аудит станет перемешанным (interleaving) — заранее продумать группировку записей по `parallelGroup`, иначе наблюдаемость деградирует (аналог «доски» из поста 04.10 — общая картина для человека).

Обновлённые кандидаты задач: добавить «worktree-изоляция рабочих копий шагов как предпосылка параллельности» перед Docker-песочницей.

## Дополнение 2 (по вопросу владельца): агенты решают кодом, создают SDK и переиспользуют — «самоулучшение экосистемы агентов»

Факты по проекту:
- `SKILL-CREATION.md` уже определяет скилл как «стандарт структурирования опыта» — концептуально это тот же SDK-подход.
- `retrospective/SKILL.md` реализует петлю самоулучшения для **проблем**: реестр, порог «3 упоминания → задача», эскалация. Симметричной петли для **успешных практик** нет — они остаются текстом в отчёте.
- В `SKILL-CREATION.md` (п. 3) видна живая история такой петли: «ретро 2026-08-20», «самоотчёт исполнителя 2026-09-17» → правило переписано в форму команды. Петля работает, но медленно и через текст.

Лестница зрелости переиспользования (все формы у нас есть, нет конвейера продвижения вверх):
1. Решение в сессии — теряется.
2. Отчёт/ретро — пассивный текст.
3. Скилл-инструкция — шаги исполняет агент сам (может забыть/исказить).
4. Скрипт скилла — детерминированный кусок кода.
5. YAML-цепочка / SDK — весь процесс кодом, агенту остаются только решения.

Дельта: нет механизма, который после решения задачи продвигает наработку вверх по лестнице. У автора поста конвейер простой — код агента живёт в SDK, новые сессии подхватывают новые версии. Слепая зона автора: не описан контроль качества растущего SDK.

Рекомендации:
1. 🟢 **Правило дистилляции** (практика): расширить retrospective симметрией для практик — «успешная практика» порождает кандидата (скрипт в скилл / новый скилл / правило конвенций), по аналогии с существующим порогом «3 упоминания → задача» для проблем. Правило второго раза: повторил процедуру второй раз — обязан оформить кодом, не текстом.
2. 🟢 **Правило «кодом или текстом»** (критерий): повторяемая процедура → код (скрипт/YAML); суждение/стиль → текст. Это снимает соблазн кодировать некодируемое.
3. 🟡 **Конвейер с иммунной системой**: агент-кандидат → PR через GitIdentity → quality gate (тесты скрипта) → ревью-роль → каталог. В отличие от поста — с гейтом качества, используя существующий PR-процесс.
4. Оговорки: каталог раздувает промпты ролей (описания скиллов едят контекст) — нужен порог полезности и чистка мёртвых скиллов, как реестр проблем в ретро. Самоулучшение без гейта превращается в свалку.
5. Метрика: доля повторных задач, решённых переиспользованием артефакта против «с нуля»; скорость решения повторяющихся классов задач.
