## Найденные слабые места и внесённые исправления

### 1. §3.1 — Ложная эквивалентность worktrees и Docker (критичное)

**Было:** «Это lighter-weight альтернатива Docker-изоляции» + аналогия с Archon `IIsolationProvider`.
**Проблема:** Git worktrees и Docker containers решают ортогональные задачи. Worktrees — concurrent filesystem branching (несколько параллельных FS-views одного репо). Containers — process/network sandboxing (изоляция выполнения). AgentCraft использует оба одновременно, что подтверждает их ортогональность. Аналог с Archon неточен: Archon `IIsolationProvider` — изоляция execution environment (ближе к containers), прямой аналог worktrees среди исследованных проектов отсутствует.
**Исправлено:** Добавлено «Важно» с пояснением ортогональности, уточнён аналог.

### 2. §3.2 — Отсутствует анализ топологии координации (критичное)

**Было:** Общий текст «координация нескольких AI-агентов с разделением ролей» + аналогия с sub-agent pattern без различения.
**Проблема:** Ключевой архитектурный вопрос — как координируются агенты: иерархически (parent→child, как в sub-agent) или как peers (через GUI-хаб). От топологии зависит: fault isolation, разрешение зависимостей, распространение контекста. В AgentCraft каждый «герой» — независимый агент со своим backend-ом и worktree → вероятна peer-координация.
**Исправлено:** Добавлен блок «Архитектурный вопрос — топология координации» с анализом. Уточнён аналог — различие иерархической (sub-agent) и peer-координации.

### 3. §3.3 — Недокументированная «полнота» изоляции (среднее)

**Было:** «полная network-изоляция» — утверждение без верификации.
**Проблема:** Для закрытого продукта утверждение «полная» — сильное заявление. Документация говорит о network isolation, но не уточняет CPU/memory/filesystem ограничения.
**Исправлено:** «Полная» заменена на «документация заявляет network isolation» с оговоркой о непроверяемости деталей.

### 4. §3.4 — Тавтология + отсутствует анализ open-loop vs closed-loop (среднее)

**Было:** «Cron-like scheduling — триггерное выполнение агентов по расписанию. AgentCraft не оркестирует выполнение внутри агента, но оркестирует запуск агентов (когда и кого запускать). Это trigger-based orchestration layer.» — одна мысль в трёх вариантах.
**Проблема:** Повтор + отсутствие ключевого различения: open-loop (fire-and-forget) vs closed-loop (с обратной связью). Без conditional scheduling, retry, notification — это automation, а не adaptive orchestration.
**Исправлено:** Убрана тавтология. Добавлен блок «Архитектурное ограничение — open-loop vs closed-loop».

### 5. §3.5 — Неточное «расширение capabilities» (среднее)

**Было:** «Механизм расширения capabilities агентов через декларативные описания.»
**Проблема:** Поскольку AgentCraft — обёртка над CLI-агентами, фактические capabilities (tools, model, context window) определяются backend-ом. Свитки вероятнее всего inject инструкции в промпт (prompt augmentation), а не добавляют runtime-инструменты (capability injection). Это разные архитектурные уровни.
**Исправлено:** Заменено «Capability Injection» на «Prompt Augmentation». Добавлено «Архитектурное различие» между prompt augmentation и capability injection.

### 6. §3.6 — Channels описаны одномерно (мелкое)

**Было:** «Форма Human-in-the-loop (HITL) оркестрации... расширяет точку входа оркестрации за пределы GUI.»
**Проблема:** Channels — не только HITL (Side Panel уже реализует HITL), но и transport extension (новый канал ввода/вывода для асинхронных и мобильных сценариев).
**Исправлено:** Добавлена двойная роль: transport extension + HITL-расширение.

### 7. §3.7 — Generic lifecycle без специфики (среднее)

**Было:** 5 стадий lifecycle (spawn→termination) с подробным описанием каждой, аналогичным любому agent-фреймворку.
**Проблема:** Универсальный паттерн без AgentCraft-специфики. Единственное отличие — конфигурируемый spawn (выбор backend + изоляция), но оно утопало в generic-описании. Также отсутствовали gap-анализ: health check, graceful degradation, checkpoint/resume.
**Исправлено:** Condensed generic-описание, выделена специфика (конфигурируемый spawn), добавлены отсутствующие этапы lifecycle.

### 8. §3.8 — Runtime и post-mortem слиты (среднее)

**Было:** Два механизма описаны в одинаковых терминах, без различения архитектурного назначения.
**Проблема:** Fog of War (runtime) и Mission History (post-mortem) служат разным целям и имеют разные требования (latency vs completeness). Также отсутствовал structured logging/tracing (correlation ID).
**Исправлено:** Добавлена таблица с разделением по назначению и характеристикам. Добавлено ограничение: отсутствие correlation ID.

### 9. §3.0 — Отсутствует паттерн «совместное состояние» (критичное)

**Было:** 7 паттернов, но без state management.
**Проблема:** Для мультиагентной координации критичен вопрос обмена контекстом между агентами. AgentCraft не описывает shared state — это значимое отсутствие (absence as a finding).
**Исправлено:** Добавлена строка «Совместное состояние — не обнаружено» в таблицу паттернов. Уточнено в общем описании Facade.

### 10. §5 — Неточные оценки зрелости (мелкое)

**Исправлено:**
- Scheduling: 🟩 → 🟨 (open-loop без conditional/retry/notification — не «хорошая»)
- Agent capabilities: уточнено «prompt augmentation, не runtime capability extension»
- Observability: уточнено «нет structured logging/tracing»
- Добавлена строка State management: ⬛
