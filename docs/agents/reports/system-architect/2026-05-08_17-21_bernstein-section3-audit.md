## Найденные слабые места (7 категорий, 11 правок)

### 1. Фактическая ошибка — §3.1, п.3 (Circuit Breaker)

**Проблема:** Утверждение «Permanent-ошибки не имеет смысла ретраить через circuit breaker» — некорректная атрибуция. Circuit breaker не «ретраит» ошибки; он размыкает цепь. Размыкание при permanent-ошибках _полезно_, т.к. предотвращает дальнейшие вызовы к сбойному сервису. Проблема в другом: отсутствие классификации ошибок не позволяет применять _дифференцированную стратегию восстановления_.

**Правка:** Переформулировано с разделением: учёт всех ошибок для размыкания — оправдан, но отсутствие классификации затрудняет half-open стратегию.

### 2. Некорректная атрибуция — §3.1, п.4 (Fallback)

**Проблема:** Fallback указан как «ограничение реализации circuit breaker». Fallback — самостоятельный паттерн, не входящий в circuit breaker по Nygard. Отсутствие fallback — факт, но не дефект CB.

**Правка:** Добавлено пояснение, что fallback не входит в паттерн CB, но сопутствующий механизм отсутствует.

### 3. Неточная атрибуция Nygard — §3.1 (оценка)

**Проблема:** «Классическая реализация по Nygard» — Nygard описывает listeners, metrics, sliding window, которых в Bernstein нет.

**Правка:** Уточнено — «минимальная реализация», с перечислением отсутствующих компонентов Nygard.

### 4. Субъективные оценки без критериев — §3.2–3.6

**Проблема:** Формулировки «обоснована», «удачный выбор», «минимально необходимая» — субъективные оценки, не подкреплённые критериями.

**Правки:**
- §3.2: «обоснована» → «распространённый подход»
- §3.3: «полезно при» → «что актуально при»
- §3.4: «минимально необходимая функция» → «базовый механизм»
- §3.5: «идея обоснована» → описание без оценки (форма ensemble-подхода)
- §3.6: «удачный выбор» → «распространённый формат», добавлено «без фиксированной схемы»

### 5. Философский оффтопик — §3.5, п.5

**Проблема:** «Проблема рекурсивной верификации» (нужен ли верификатор верификатору?) — общая философская проблема, не специфичная для Bernstein. Не даёт практически полезной информации.

**Правка:** Заменено на конкретное ограничение — «Отсутствует калибровка верификатора» (нет golden set, нет эталонных примеров для оценки качества верификации).

### 6. Недостаток nuance — §3.6, п.1

**Проблема:** Синхронный I/O описан исключительно как ограничение. Append-per-write для audit trail — _может быть_ осознанным выбором для гарантии записи. Без этого nuance оценка однобока.

**Правка:** Добавлен компромисс: append-per-write обеспечивает гарантию записи (надёжность), но при высокой частоте создаёт overhead. Буферизация снижает overhead ценой риска потери записей.

### 7. Подмена понятий — §3.4, п.5

**Проблема:** «Retry не равен iteration» — важное архитектурное наблюдение, но сформулировано как «ограничение реализации». На самом деле это _концептуальное ограничение модели конфигурации_ (`retry_on_failure` не способна выразить направленный цикл), а не дефект кода.

**Правка:** Уточнено: «концептуальное ограничение конфигурации» вместо «реализация не различает».
