## 2. Корректность DS-решения — ✅ обосновано; слепые зоны зафиксированы (AR-5)

**Восстановление vs документирование отсутствия.** Восстановление — единственный вариант, не закрепляющий потерю данных. Механизм потери подтверждён кодом: `DynamicExecutionStrategy::resume()` (`:128`, `:143`) после `resumeSession()` вызывает `setBudget()` → `logInvocation()`, оба переписывают `session.json`; `writeSessionJson()` собирает `rounds[]` **только** из внутреннего `$roundFiles`, поэтому без восстановления `rounds[*].invocation` исчезали в happy-path (не в «аварийном» сценарии — просто при первом же вызове). Альтернатива «обосновать отсутствие» (DS §6) отклонена справедливо: она зафиксировала бы разные фактические формы свежей и восстановленной записи — ровно тот тихий дрейф, который задача устраняет.

**Реализация (сверена построчно с DS §4):** условное копирование `isset($rd['invocation']) && is_string(...)` — симметрично соседним полям (`model`/`provider`/`thinking`); без значения по умолчанию (для старых записей ключ остаётся отсутствующим — закреплено `assertArrayNotHasKey`); пустая строка проходит гейты и восстанавливается как строка (по DS; тестом не закреплено — подтверждаю OBS-3 Пуаро, не блокирует); `@return` пополнился `invocation?: string` последним полем — форма канонична. Обратная совместимость старых сессий зелёная.

**Сценарии повреждённых данных.** Нестроковое `invocation` (ручная правка `session.json`) молча отбрасывается при разборе и нормализуется (удаляется) при следующей записи — поведение согласовано с модельными полями, задокументировано в DS §6; резервный вариант (fallback) не введён — соответствует правилу «не добавляй резервный вариант без явного требования». Явный `null` = отсутствие данных (DS §7) — согласовано с `logRound()` (`null` не пишется, `:121–123`). Идемпотентность цикла «запись → чтение → перезапись» симметрична (18 полей на обеих сторонах разбора/записи), roundtrip-тест закрывает один полный цикл с подтверждённым подлинным покрытием (эксперимент Пуаро §7.1).

**Слепые зоны (вне границ задачи, найдены этим ревью; не блокируют — в AR-5):**

* **BZ-1. Верхнеуровневый `session.json.invocation` (поток `logInvocation()`) не восстанавливается при resume.** `ChainSessionWriter::resumeSession()` (`:168–205`) заполняет `chainName`/`facilitator`/`participants`/`roundFiles`/`budget`/…, но **не** `$this->invocation`. Первая запись после resume (`setBudget()`, `DynamicExecutionStrategy.php:128`) сериализует `'invocation' => []` — прежнее верхнеуровневое значение стирается на диске; фактическое значение появляется только после `logInvocation()` (`:143`). Окно потери при падении процесса между этими вызовами; в happy-path исходное invocation сессии неизбежно перезаписывается invocation текущего запуска (`latest-wins`, с меткой `resumed_from`) — параметры исходного запуска (например, исходный `timeout`) не сохраняются. DS декларативно исключил поток («отдельный поток данных, который данное решение не меняет») — исключение по scope корректно, но **класс потери данных при перезаписи остаётся**, просто для соседнего поля. Симметричное восстановление в `resumeSession()` — 2 строки; либо явно задокументировать семантику `latest-wins`.
* **BZ-2. Перезапись `session.json` «по белому списку» теряет неизвестные ключи.** `parseRoundFiles()` собирает запись из whitelist-полей, `writeSessionJson()` пишет фиксированную структуру: любой неизвестный ключ в `rounds[i]` или на верхнем уровне (например, записанный более новой версией программы) молча удаляется при первой перезаписи после resume. Настоящая правка убирает одну жертву этого класса (`rounds[*].invocation`), но не сам класс; синхронизация doc-форм его не закрывает — тела `parseRoundFiles()`/`writeSessionJson()` являются параллельной структурой данных, которую сейчас сторожат только пофакторные тесты.
