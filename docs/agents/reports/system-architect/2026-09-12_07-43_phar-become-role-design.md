# Архитектурный отчёт: PHAR-установка `become-role`

**Роль:** Архитектор Гэндальф
**Дата:** 2026-09-12
**Объект:** `agent:init`, PHAR-сборка, `become-role.sh`, файловая установка и тестовый контур
**Задача:** [`TASK-feat-phar-full-become-role-install`](../../../../todo/TASK-feat-phar-full-become-role-install.todo.md)

## Решение

Принято минимальное специализированное решение: один Presentation-сервис `InstallBecomeRoleServiceInterface`/`InstallBecomeRoleService` обслуживает только фиксированный ресурс `docs/agents/skills/become-role`. Универсальный установщик ресурсов, новый доменный модуль и fallback `symlink -> copy` не создаются.

`InitCommand` остаётся транспортной границей: читает `--force`, получает блокировку конкурентного запуска, вызывает сервис, отображает результат или ошибку и возвращает код завершения. Файловое сравнение, подготовка и переключение target из команды удаляются. Для интерфейса сервиса требуется явный alias в `config/services.yaml`.

Сервис сохраняет две явные ветки:

1. source/Composer — существующий относительный симлинк без изменения публичного результата;
2. PHAR — управляемая копия в `.agents/skills/become-role`.

## Почему простой copy недостаточен

Текущий `become-role.sh` находит `bin/task-orchestrator` подъёмом от физического каталога скрипта к package root. После копирования в host-проект физический путь уже не принадлежит package tree, поэтому скрипт не может самостоятельно найти исходный PHAR.

PHAR-установка должна добавить внутрь exact target одну служебную runtime-привязку к физическому пути запущенного архива. `become-role.sh` сначала сохраняет штатное разрешение source/Composer, а при его отсутствии читает привязку и запускает `php <physical-phar-path> agent:role-skills ...`. Физический путь должен поступать из явного runtime-параметра, полученного через `Phar::running(false)`, а не вычисляться разбором строки `phar://`.

Следствие контракта: исходный PHAR должен оставаться по зафиксированному пути. После его перемещения пользователь повторяет `agent:init --force` из нового расположения. Копировать весь PHAR внутрь skill не следует: это непропорционально раздувает установку и выходит за пределы минимального решения.

## Ожидаемое дерево и идемпотентность

Ожидаемое PHAR-дерево сначала полностью материализуется в уникальном соседнем staging-каталоге. Оно состоит из:

- всех обычных каталогов и файлов встроенного `docs/agents/skills/become-role`;
- одной сгенерированной runtime-привязки внутри этого же дерева.

Исходное дерево принимается только при наличии `SKILL.md` и `scripts/become-role.sh`. Симлинки и специальные файлы в источнике запрещены. Это исключает неявный выход из PHAR-дерева при копировании.

Эквивалентность target определяется по отсортированному набору относительных путей, типу каждого элемента и хешу содержимого каждого обычного файла. Лишний файл, отсутствующий файл, изменение содержимого, симлинк или специальный файл означает конфликт. `mtime` и executable-bit не входят в сравнение: публичный контракт запуска использует `bash`, а сохранение режима Box отдельно не гарантируется.

Сравнение выполняется с ожидаемым материализованным деревом, а не только с исходником: смена физического пути PHAR корректно требует `--force` для обновления runtime-привязки.

## Безопасная подготовка и замена

До создания staging проверяются существующие `.agents` и `.agents/skills`: симлинк или объект другого типа приводит к отказу. Для target применяется `lstat`-семантика; target-симлинк никогда не разыменовывается. При `--force` перемещается сам объект target.

Последовательность PHAR-ветки:

1. проверить обязательные исходные ресурсы и типы всего source tree;
2. создать уникальный staging рядом с target;
3. скопировать source tree без следования по симлинкам и создать runtime-привязку;
4. повторно проверить полное staging-дерево;
5. если target отсутствует — выполнить native `rename(staging, target)`;
6. если target отличается и задан `--force` — выполнить `rename(target, backup)`, затем `rename(staging, target)`;
7. при ошибке второго rename попытаться вернуть `backup` в `target`;
8. удалить backup только после успешного переключения, а staging — в `finally`.

На commit-фазе нельзя использовать `Symfony Filesystem::rename`: изученная версия Symfony при неудаче native rename для каталога переходит к `mirror()` и `remove()`, что превращает переключение в частичное рекурсивное копирование. Нужен непосредственно проверяемый native `rename` на соседних путях одного файлового раздела.

Переносимой атомарной замены непустого каталога другим каталогом нет. Между двумя rename остаётся короткое окно. Блокировка предотвращает кооперативный параллельный `agent:init`, но не защищает от `SIGKILL`, отключения питания или внешнего процесса. Если откат невозможен, backup следует сохранить и явно сообщить путь восстановления; удалять единственную сохранную копию ради формальной очистки нельзя.

## Границы слоёв

- `InitCommand`: только CLI-ввод/вывод, блокировка и отображение результата.
- `InstallBecomeRoleServiceInterface` и реализация: Presentation, поскольку сценарий настраивает CLI-интеграцию host-проекта и не является доменной операцией task-orchestrator.
- `Kernel`: только публикация физического пути PHAR как runtime-параметра, если выбран явный DI-вариант.
- `Domain`, `Application`, `Infrastructure` существующих бизнес-модулей не затрагиваются.

Размещать файловую установку в Domain или создавать ради неё общий Infrastructure-контракт было бы ложным расширением предметной области. Оставлять её в `InitCommand` также нельзя: это нарушает конвенцию тонкой консольной команды.

## Проверки

Unit-тесты команды должны проверять только разбор `--force`, блокировку, вызов сервиса, отображение результата/ошибки и коды завершения. Файловый алгоритм проверяется integration-тестами на временной файловой системе:

- source/Composer: создание относительного симлинка, повтор, конфликт, `--force`;
- PHAR: первая установка, неизменный повтор, полный конфликт, `--force`;
- лишний/изменённый файл, target-симлинк, внутренний симлинк, симлинк в родителе;
- неполный источник и ошибка копирования до commit без частичного target;
- очистка staging/backup при штатно обработанных исходах.

`bin/phar-smoke` остаётся обязательной проверкой реального архива: состав PHAR, запуск из произвольного CWD, идемпотентность, конфликт, `--force`, отсутствие лишних артефактов и выполнение установленного `become-role.sh` для тестовой роли.

## Отклонённые альтернативы

1. **Копировать только source tree без runtime-привязки.** Скрипт теряет путь к CLI и не выполняет критерий запуска.
2. **Искать `task-orchestrator` только через `PATH`.** Это вводит незаявленное обязательное условие и не работает для обычного `php /path/task-orchestrator.phar agent:init`.
3. **Копировать сам PHAR внутрь skill.** Самодостаточно, но дублирует весь дистрибутив и несоразмерно задаче.
4. **Использовать symlink на `phar://`.** Некорректно для host-файловой системы и прямо запрещено scope.
5. **Создать универсальный managed-copy installer.** Преждевременное обобщение без второго потребителя.
6. **Заявить полную атомарность замены каталога.** Непереносимо без платформенного API уровня `renameat2` либо смены модели target на симлинк, что противоречит критериям.

## Риски

- Перемещение PHAR инвалидирует runtime-привязку до повторного `agent:init --force`.
- Аварийное завершение в коротком окне между rename может оставить backup вместо target; нужна ясная диагностика и тестируемое восстановление для перехваченных ошибок.
- Проверки `lstat` не устраняют гонку с внешним процессом между проверкой и операцией; блокировка действует только между экземплярами команды.
- Полное сравнение дерева линейно по числу файлов и их размеру, но для малого фиксированного skill это приемлемая цена корректной идемпотентности.
- Реальное поведение `phar://` и состав архива нельзя доказать fixture-тестом; требуется собранный PHAR smoke.

## Итог

Архитектурных блокеров для реализации нет. План задачи уточнён: зафиксированы граница Presentation, runtime-привязка, полное сравнение деревьев, запрет следования по симлинкам, двухфазная замена и честное ограничение гарантий при аварии файловой системы.

Внешние источники не использовались; выводы основаны на коде проекта, конвенциях и установленной реализации `vendor/symfony/filesystem/Filesystem.php`.
