## Диагноз оригинала

§3 содержал 6 существенных проблем:

1. **Ссылки на task-orchestrator** — в каждом подразделе (3.1–3.6) присутствовали блоки «Почему нам нужно», «Чем наша реализация отличается», «Задача: TASK-agent-*». Это превращало объективное исследование в проектный документ.
2. **Приоритетные маркеры 🔴** — отражали приоритет для конкретного проекта, а не архитектурную оценку.
3. **Отсутствие критического анализа** — код описывался, но не оценивался. Не было анализа ограничений, рисков, альтернатив.
4. **Нет различения retry vs iteration** — §3.4 не различал retry-on-error и осмысленные итерационные циклы с передачей контекста.
5. **§4 и §5 содержали те же проблемы** — «наш формат цепочек», «Статус в продукте», приоритеты P3.
6. **§2 оценивал Bernstein через призму другого продукта** — строки «DDD-архитектура ❌», «Decorator pattern ❌» бессмысленны без контекста чьих-то требований.

## Внесённые изменения

### §2 (обзорная таблица)
- Добавлена колонка «Архитектурная заметка» с объективными комментариями
- Убраны строки-критерии другого проекта (DDD, decorator pattern, ролевые промпты)
- Заменены на факты: circuit breaker, quality gates, budget control, retry, audit trail — с заметками об ограничениях

### §3 (основной — 6 подразделов)
Каждый подраздел переписан по структуре: **Реализация** → **Архитектурная оценка** → **Ограничения реализации**.

| Подраздел | Ключевые находки |
| --- | --- |
| 3.1 Circuit Breaker | Нет потокобезопасности, нет персистенции, нет различения transient/permanent ошибок, нет fallback, нет observability |
| 3.2 Quality Gates | Нарушение OCP (жёсткий GATE_TYPES), захардкоженные команды инструментов, нет параллельного выполнения, нет зависимостей между gates |
| 3.3 Бюджетный контроль | Только per-stage, нет адаптации, нет событий при приближении к лимиту, нет приоритетного распределения |
| 3.4 Итерационные циклы | Retry ≠ iteration, нет backoff, retry не интегрирован с бюджетом, нет сохранения прогресса |
| 3.5 Кросс-модельная верификация | Захардкоженный промпт, один верификатор, нет confidence score, стоимость не учтена в бюджете, проблема рекурсивной верификации |
| 3.6 Audit Trail | Синхронный I/O на каждое событие, нет ротации, нет обработки ошибок записи, `datetime.utcnow()` deprecated (Python 3.12+), нет correlation ID, нет event schema |

### §4 (прочие возможности)
- Убраны все ссылки на «наш формат» и «у нас»
- Каждый подраздел переписан как объективная оценка возможности

### §5 (сводная таблица)
- Колонка «Статус в продукте» заменена на «Зрелость» с объективными уровнями (Минимальная / Базовая / Средняя / R&D / Прототип)
- Добавлены архитектурные заметки

## Риски и допущения

- Исследование основано на анализе кода репозитория Bernstein на момент 2026-04-05. Если репозиторий обновлялся — данные могут устареть.
- Анализ ограничений основан на коде, а не на roadmap проекта — некоторые ограничения могут быть осознанным MVP-выбором.
