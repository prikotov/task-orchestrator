**Роль:** Архитектор Локи
**Дата:** 2026-05-10
**Объект:** Два архитектурных предложения по развитию оркестратора
**Задача:** Анализ слепых зон и альтернатив

---

## Предложение 1: Оцифровать task/epic workflow как цепочки

### Слепые зоны

1. **`tool`-шаг — Trojan Horse сложности.** Детерминированные шаги (git commit, gh pr merge) — shell-команды с побочными эффектами и ветвящимися исходами. `tool` быстро превратится в mini-shell-engine: обработка кодов возврата, retry при конфликтах, conditional rollback. Дублирование bash. Вопрос: кто управляет стейтом файловой системы и git при падении на середине цепочки?

2. **Стейт между шагами — чёрная дыра.** Цепочка `task-implement`: agent пишет код → quality_gate проверяет → tool делает commit. Где живёт результат agent-шага? Как tool-шаг узнаёт, какие файлы коммитить? Нет контракта на передачу данных между шагами. Без этого цепочки — glorified bash-скрипты в YAML.

3. **git и gh — не idempotent.** `gh pr merge` при повторном запуске — ошибка. `git commit` на пустой diff — ошибка. Цепочка должна уметь возобновляться (resume) с любого шага, а не только с начала. Где хранится состояние цепочки?

4. **Шаблонные цепочки — хрупкие.** `task-implement` и `task-hotfix` — разные пути: hotfix создаётся от тега, требует bump версии, другой review-поток. Две цепочки быстро станут десятью, а исключения (conflict resolution, WIP-PR) не влезут в YAML.

5. **DoR-проверка — не quality_gate.** DoR — проверка полноты задачи, наличия критериев, связей. Классификация с нечёткими критериями. В quality_gate — хрупкий shell-скрипт вместо простого чеклиста.

### Риски

- **Over-engineering**: тимлид уже работает как «человек-оркестратор». Оцифровка workflow в chains.yaml — AI-фреймворк внутри AI-фреймворка. Сложность².
- **YAML-driven development без визуализации**: цепочка из 10+ шагов в YAML нечитаема. Нужен визуализатор или DSL — отдельный проект.

### Альтернатива

Не новый тип шага `tool`, а **команды Symfony Console**, которые тимлид вызывает напрямую. Цепочки — только для AI-оркестрации (agent → agent). Детерминированные шаги — через CLI-команды с нормальной обработкой ошибок. Проще, тестируемее, не раздувает движок цепочек.

## Предложение 2: watch-subagent.sh не трогать

### Слепое пятно

«Если оркестратор сломан» — это не edge case, это нормальное состояние при разработке. Вы разрабатываете оркестратор. Он регулярно бывает сломан. watch-subagent.sh — единственный способ запустить сабагента. Если не параметризовать — при добавлении нового runner/model устареет и молча сломает запуск.

### Дилемма реальна, решение ложное

Дихотомия «параметризовать vs не трогать» — обе стороны плохие:
- **Параметризовать** → скрипт зависит от оркестратора, теряет independence.
- **Не трогать** → скрипт дрейфует, становится источником багов.

### Альтернатива: скрипт как fallback с явным контрактом

watch-subagent.sh должен:
1. Работать **без** оркестратора (standalone, hardcoded defaults для pi/codex).
2. Поддерживать **опциональные** env-переменные (`RUNNER`, `MODEL`, `TIMEOUT`) — не падать без них.
3. В шапке скрипта — **версия контракта** (`# CONTRACT: v1 — runner=pi|codex, model=string, timeout=int`).

Это не «параметризация через оркестратор», а «контракт с разумными defaults». Оркестратор вызывает с env, человек — без. При изменении контракта обновляется версия.

### Дополнительный риск

Если watch-subagent.sh — единственный fallback и его никто не тестирует при изменениях раннеров, он превращается в мёртвый код, который выглядит рабочим. Нужно: либо интеграционный тест, либо признать best effort и задокументировать ограничение.

## Итого

| Предложение | Главная проблема |
|---|---|
| 1. Оцифровка workflow | Нет стейта между шагами, нет idempotency, `tool`-шаг — троянский конь сложности. Разделяй AI-цепочки и CLI-команды. |
| 2. watch-subagent.sh | Дихотомия ложная. Скрипт = fallback с контрактом + defaults, не «параметризация через оркестратор». |
