# Аудит §3: Оркестрационные возможности AgentCraft

**Роль:** Архитектор Локи
**Дата:** 2026-05-08
**Объект:** `docs/research/framework-comparisons/agentcraft-comparison.md`, §3 (строки ~107–310)
**Задача:** Критический анализ §3, исправление слабых мест

---

## Найденные слабые места и исправления

### 1. §3.0 — Таблица классификации паттернов

**Проблема:** «Совместное состояние» внесено как паттерн, хотя это констатация отсутствия. Строка дезинформировала классификацию. Также отсутствовала строка «Обработка ошибок» — критичный паттерн, даже когда он делегирован.

**Исправление:** Добавлена строка «Обработка ошибок | Delegation» с описанием делегирования fault tolerance на обёрнутый агент. Строка «Совместное состояние» дополнена ссылкой на §3.2.

### 2. §3.1 — Технические ограничения git worktrees

**Проблема:** Worktrees описаны без упоминания технических ограничений. Это создавало ложное впечатление о полноте механизма.

**Исправление:** Добавлен блок «Технические ограничения git worktrees»: один worktree на ветку, линейный рост disk usage, отсутствие cleanup при termination, отсутствие runtime-изоляции (процессы видят друг друга).

### 3. §3.2 — Топология координации

**Проблема:** Предположение о «peer-to-peer или hub-координации» подано слишком уверенно для анализа закрытого кода. Альтернативные топологии координации мультиагентных систем (blackboard, pipeline, event-driven) не рассмотрены.

**Исправление:**
- Добавлена таблица «Известные топологии координации» (5 топологий: иерархия, hub, peer-to-peer, blackboard, pipeline).
- Предположение переформулировано: «вероятнее hub-топология» с обоснованием (Side Panel как supervisor, нет подтверждённого inter-agent communication).
- Усилено разграничение факт/предположение.

### 4. §3.2 — Внутреннее противоречие (hub vs peer)

**Проблема:** В «Предположении» указана hub-топология, а в «Аналоге» осталось «peer-координация через GUI-хаб». Hub (централизованная координация) и peer (децентрализованная) — разные топологии. «GUI-хаб» по сути — это hub.

**Исправление:** Заменено «peer-координация» на «hub-координация через Side Panel» в §3.2 и §5 (сводка).

### 5. §3.3 — Docker vs Apple Containers

**Проблема:** Docker и Apple Containers описаны как единый механизм «контейнерной изоляции». Это принципиально разные технологии с разными гарантиями безопасности (shared kernel vs separate kernel).

**Исправление:** Добавлена сравнительная таблица технологий (Docker: namespace-based, shared kernel; Apple Containers: OS-level виртуализация, separate kernel). Отмечено влияние на security model: macOS получает stronger sandboxing, чем Linux.

### 6. §3.7 — Неполный lifecycle

**Проблема:** Пропущены timeout handling и cleanup/resource deallocation — без них lifecycle неполон и ресурсоёмок при множественных spawn/terminate циклах.

**Исправление:** Добавлены: timeout handling (зависший агент бесконечно потребляет ресурсы), cleanup (освобождение контейнера, worktree, портов), transition rules (допустимые переходы между состояниями).

### 7. §3.8 — Observability-анализ

**Проблема:** Tracing/correlation ID упомянут вскользь в «Ограничениях», но не проанализирован как архитектурный паттерн. Metrics/telemetry отсутствует. Technical mechanism Fog of War не раскрыт.

**Исправление:** Добавлена таблица «Три столпа observability» (Logging, Tracing, Metrics) с оценкой реализации в AgentCraft. Добавлен анализ следствия для Agent Teams (без tracing и metrics координация непрослеживаема). Добавлено замечание о техническом механизме Fog of War.
