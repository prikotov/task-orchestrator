# TASK-fix-phar-runtime-layout-cache: Устранить заморозку runtime layout (QA-3)

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)

После первого запуска PHAR приложение запоминает, где искать роли и другие ресурсы host-проекта. Если пользователь добавляет эти ресурсы позже, приложение продолжает использовать встроенные ресурсы PHAR и не видит новые файлы до ручной очистки кеша.

### Варианты или путь решения (Solution Sketch)

Отделить runtime layout (выбор host- или package-путей во время выполнения) от параметров, безопасно фиксируемых в скомпилированном Symfony-контейнере. По ревью архитектора Локи: чистый резолвер без Symfony-зависимостей в `src/Component/Layout/` плюс тонкий env-процессор; при отсутствии И host-, И package-ресурса резолвер обязан бросать явное исключение, а не возвращать несуществующий путь; аргументы env-процессора — только plain-параметры (env-плейсхолдер в аргументах запрещён — риск рекурсии `getEnv()`). Жизненный цикл устаревших PHAR-кешей — отдельная задача, в эту не входит.

### Ожидаемый результат (Expected Result)

Новые роли, skills (навыки) и конфигурация цепочек host-проекта становятся доступны уже при следующем запуске PHAR без ручной очистки кеша. Изоляция кеша при перемещении PHAR сохраняется без возврата QA-1; накопление и очистка устаревших кеш-корней — вне объёма этой задачи.

## 1. Концепция и Цель (Concept and Goal)

### История (Job Story)

> Когда я добавляю ресурсы в host-проект после первого запуска PHAR, я хочу, чтобы приложение на следующем запуске использовало актуальный layout, чтобы мне не приходилось вручную удалять кеш-каталог PHAR ради появления новых файлов.

### Цель по SMART (Goal)

В отдельной итерации после `TASK-feat-phar-full-become-role-install` устранить зависимость runtime layout-путей (`roles_dir`, `skills_dir`, `chains_yaml`) от ранее скомпилированного PHAR-контейнера так, чтобы выбор host/package выполнялся заново на каждом запуске. Результат подтверждается integration-тестами (интеграционными тестами) ядра — переход package → host → package на повторном boot с персистентным кешем — и smoke-тестом (сквозной быстрой проверкой) реально собранного PHAR: ресурсы, созданные после первого запуска, обнаруживаются без ручной очистки.

## 2. Контекст и Границы (Context and Scope)

- **Где делаем:**
  - `src/Component/Layout/` — чистый резолвер host/package-ресурсов без Symfony-зависимостей и тонкий env-процессор (размещение зафиксировано ревью архитектора Локи);
  - `src/Kernel.php` — вычисление layout-параметров `task_orchestrator.roles_dir`, `task_orchestrator.skills_dir`, `task_orchestrator.chains_yaml` во время выполнения вместо фиксации в скомпилированном контейнере согласно [конвенции Symfony-конфигурации](../../docs/conventions/configuration/configuration.md);
  - конфигурация и потребители layout-параметров в `src/Module/*/Resource/config/services.yaml` — только если runtime-разрешение требует правки потребителей;
  - `tests/Integration/DependencyInjection/KernelIntegrationTest.php` и целевые integration-тесты согласно [конвенции тестирования](../../docs/conventions/testing/index.md) — существующий тест дополняется, а не переписывается;
  - `bin/phar-smoke` — воспроизведение смены host-layout на реально собранном PHAR;
  - пользовательская и архитектурная документация о PHAR-кеше и разрешении host-ресурсов.
- **Текущее поведение:** `Kernel::getKernelParameters()` во время первой компиляции контейнера выбирает host-путь только при наличии соответствующего ресурса, иначе фиксирует fallback (резервный путь) внутри PHAR. Последующее создание host-ресурса не меняет сохранённые `roles_dir`, `skills_dir` или `chains_yaml`. Изоляция `writableRoot()` по паре `(host project, physical PHAR path)` (исправление QA-1) сохраняется без изменений и не пересматривается.
- **Scope:** инвентаризировать layout-зависимые параметры; устранить заморозку выбора host/package для ролей, skills и файла цепочек; добавить integration- и PHAR-проверки перехода package → host → package с персистентным кешем; синхронизировать документацию.
- **Границы (Out of Scope):** не изменять установку `become-role`, `.phar-binding`, контракты `agent:init` и выполненные критерии `TASK-feat-phar-full-become-role-install`; не менять source/Composer layout без выявленной общей ошибки; не выполнять общий рефакторинг `Kernel`; не добавлять новые зависимости, self-update (самообновление) или общесистемный сборщик мусора; жизненный цикл и очистка устаревших PHAR-кеш-корней (FR-4) — вынесены в [`TASK-fix-phar-cache-root-lifecycle`](TASK-fix-phar-cache-root-lifecycle.todo.md).

## 3. Требования, MoSCoW (Requirements)

### 🔴 Обязательно (Must Have)

- [ ] Инвентаризация параметров `task_orchestrator.*` отделяет неизменные параметры сборки от layout-путей, зависящих от появления ресурсов в host-проекте; решение явно охватывает `roles_dir`, `skills_dir` и `chains_yaml` либо документированно доказывает неприменимость для конкретного параметра.
- [ ] После первичного запуска PHAR без host-ролей создание валидной роли в `docs/agents/roles/team/` того же host-проекта делает её доступной на следующем запуске без удаления кеша и без изменения физического пути PHAR.
- [ ] Аналогичное переключение после появления host-каталога skills и host-файла `config/chains.yaml` не требует ручной очистки кеша; fallback на упакованные ресурсы сохраняется, когда host-ресурс отсутствует.
- [ ] Резолвер обязан при отсутствии И host-, И package-ресурса бросать явное исключение и прерывать запуск; возврат несуществующего или предполагаемого пути запрещён (обязательная правка ревью Локи №1).
- [ ] Аргументы env-процессора — только plain-параметры контейнера; передача env-плейсхолдера (`%env(...)%` — плейсхолдер окружения) в аргументах процессора запрещена во избежание рекурсии `getEnv()`; правило зафиксировано и покрыто тестом (обязательная правка ревью Локи №2).
- [ ] Тесты дополняют `KernelIntegrationTest` (не переписывают): переход package → host → package на повторном boot с персистентным между boot кешем (суть дефекта QA-3; `getParameter()` в Symfony 8 резолвит плейсхолдер динамически) и негативный тест битой сборки — отсутствие обоих ресурсов завершается явным исключением (обязательная правка ревью Локи №3).
- [ ] Integration- и PHAR smoke-тесты воспроизводят исходный QA-3: первый запуск до создания host-роли, создание роли, второй запуск без очистки кеша, успешное разрешение роли.
- [ ] Изоляция `writableRoot()` (корня записываемых данных) по паре `(host project, physical PHAR path)` не изменяется: исправление не возвращает QA-1 и не ломает рабочий smoke-сценарий перемещения A → B.
- [ ] Документация описывает актуальное разрешение runtime layout и расположение PHAR-кеша; политика очистки кеш-корней — вне объёма документирования этой задачи.

## 7. Риски и зависимости (Risks and Dependencies)

- Решение о декомпозиции: ревью архитектора Локи от 2026-10-28 — вердикт «одобрено с замечаниями» (обязательные правки №1–№3 включены в Must Have, №4 — размещение `Component/Layout` — в контекст); решение аналитика Шерлока от 2026-10-28 (подтверждено пользователем) — декомпозиция вариантом А: этот файл — TASK-A (runtime layout), жизненный цикл PHAR-кеш-корней выделен в [`TASK-fix-phar-cache-root-lifecycle`](TASK-fix-phar-cache-root-lifecycle.todo.md).
- Зависимость: [`TASK-feat-phar-full-become-role-install`](TASK-feat-phar-full-become-role-install.todo.md) вводит текущую cache isolation (изоляцию кеша) по паре `(host project, physical PHAR path)` и подтверждает наблюдения QA-3/FR-4. Эта задача является отдельным follow-up (последующей работой) и не расширяет scope зависимости.
- Runtime env placeholder (динамический плейсхолдер окружения) Symfony подходит для строковых значений, но выбор первого существующего host/package ресурса требует явной модели; механическое перенесение текущей проверки существования в env processor (обработчик переменной окружения) может смешать конфигурацию и файловую политику — поэтому резолвер выносится в чистый `Component/Layout`, а env-процессор остаётся тонким.
- Изоляция по физическому пути PHAR устраняет замороженные `package_dir`/`phar_path` после перемещения; новая реализация не должна вернуть QA-1 или нарушить рабочий smoke-сценарий A → B.
- Удаление host-ресурса после компиляции — обратный пограничный сценарий: при существующем package-ресурсе система возвращается к fallback, при отсутствии обоих ресурсов — завершается явным исключением, но никогда не использует несуществующий замороженный путь.
- Значения `V2` и `C2` обоснованы так: дефект снижает надёжность существующей PHAR-функции, но не блокирует основной канал дистрибуции; после декомпозиции объём ограничен резолвером путей и env-процессором (средняя ценность, умеренная сложность), а высокорисковый жизненный цикл кеш-корней (конкурентность, владение, удаление) перенесён в TASK-B со сложностью `C3`.
