# TASK-techdebt-writer-round-shape-drift: Синхронизировать форму записи раунда Writer с канонической формой контракта

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)
- Описание записи раунда дискуссии продублировано в коде в нескольких местах и уже разошлось: путь восстановления сессии из файла описывает запись чуть уже, чем канонический контракт чтения (введён в PR #523), — в описании отсутствует поле `invocation` (информация о вызове агента). Формально это допустимо: анализаторы типов на такое расхождение не ругаются, поэтому дрейф незаметен. Это мешает сопровождающим и ревьюерам: при расширении формы записи расхождения будут копиться молча, а обещание «полная форма записи» в контракте станет неточным. Практическое следствие уже есть: поле `invocation` сохраняется при записи сессии, но не восстанавливается при возобновлении (resume) — данные, которые вроде бы есть, после перезапуска пропадают.

### Варианты или путь решения (Solution Sketch)
- Синхронизировать фактическую форму записи Writer с канонической: добавить недостающее поле в форму и восстановление либо явно обосновать его отсутствие в контракте Reader.
- Вопрос с `invocation` (не восстанавливается при resume) проанализировать и зафиксировать решение.
- Отдельного подавления аналитиков типов (Psalm/PHPStan) для маскировки расхождения не вводить.

### Ожидаемый результат (Expected Result)
- Все описания формы записи согласованы с канонической 18-полевой формой контракта либо расхождения явно обоснованы в самом контракте.
- По полю `invocation` зафиксировано и реализовано решение: после resume поле восстанавливается либо его отсутствие обосновано.
- Статические анализаторы и тесты зелёные без новых подавлений; при следующем расширении формы записи расхождение будет видно проверяющим, а не пройдёт молча.

## 1. Концепция и Цель (Concept and Goal)

### История (User Story)
> Как сопровождающий проекта, я хочу, чтобы форма записи раунда была описана одинаково во всех местах кода, чтобы расхождения ловились при сопровождении явно, а не накапливались молча.

### Цель по SMART (Goal)
- **S — конкретно:** привести форму `@return` метода `ChainSessionWriter::parseRoundFiles()` (17 полей, без `invocation?`) в соответствие с канонической 18-полевой формой `DynamicLoopSessionReaderInterface::getRoundFiles()` либо явно обосновать отсутствие поля в контракте Reader; закрыть вопрос восстановления `invocation` при resume.
- **M — измеримо:** все объявления формы записи сверены с канонической (байт-в-байт либо документированное обоснованное расхождение); `vendor/bin/psalm` и `vendor/bin/phpstan analyse --no-progress` — 0 ошибок без новых подавлений; целевые тесты (включая resume-сценарии) зелёные.
- **A — достижимо:** изменения ограничены одним модулем `DynamicLoop` (Writer и контракт чтения); правки преимущественно в PHPDoc и в логике восстановления одной записи; прецеденты синхронизации форм есть в задаче-источнике.
- **R — релевантно:** закрывает находку Л-4 архитектурного ревью PR #523 и наблюдение OBS-1 функционального ревью; снижает риск тихого дрейфа форм записи.

- Форма записи Writer фактически охватывает два потока данных: свежая запись (`logRound()`) и восстановление из файла (`parseRoundFiles()`); «полная форма» контракта — объединение обоих потоков (вывод OBS-1/Л-4).

- **DS, шаг 1 — анализ OBS-1 (2026-11-28, Архитектор Гэндальф):** единственный прод-потребитель публичного `getRoundFiles()` — `RunDynamicLoopService::initExecution()`; он передаёт записи в `restoreFromRoundFiles()`, который `invocation` не читает. Метрики, счётчики, `step`-ключирование и response-пути от поля не зависят. Однако после `resumeSession()` ближайшие `setBudget()`/`logInvocation()` повторно вызывают `writeSessionJson()`, и невосстановленное поле удаляется из ранее сохранённых `rounds[*].invocation`. Таким образом, отсутствие поля — подтверждённая потеря persisted state (сохранённого состояния), а не только неиспользуемые данные. Восстановление в записи Writer/Reader не переносит поле в `DynamicRoundResultVo`: `restoreFromRoundFiles()` остаётся неизменным по границам задачи.
- **DS, шаг 2 — решение (2026-11-28, владелец этапа A = Архитектор Гэндальф, RACI 5.3):** восстанавливать `rounds[*].invocation` в `ChainSessionWriter::parseRoundFiles()` условным копированием существующего строкового значения и добавить `invocation?: string` в его `@return`. Значение по умолчанию не вводить: для старых записей без поля ключ остаётся отсутствующим. `DynamicLoopSessionReaderInterface` и каноническая 18-полевая форма не меняются; альтернатива «обосновать отсутствие» отклонена, поскольку закрепляла бы потерю данных при повторной записи. Проектная инструкция и тест roundtrip (запись → resume → повторная запись) зафиксированы в [отчёте DS](../../docs/agents/reports/system-architect-gandalf/2026-11-28_15-23_writer-round-invocation-resume-design.md).
