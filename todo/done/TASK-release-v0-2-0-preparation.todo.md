# TASK-release-v0-2-0-preparation: Подготовить и выпустить релиз v0.2.0

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)

Изменения для `v0.2.0` приняты, но без итогового changelog (журнала изменений), release plan
(плана релиза), финальных проверок и контролируемого перехода в release branch (релизную ветку)
состав публикуемой версии нельзя считать зафиксированным и воспроизводимым.

### Варианты или путь решения (Solution Sketch)

Ограничить подготовку двумя релизными документами и проверками, открыть PR
`task/release-v0-2-0` → `release/0.2`, а публикацию тега выполнить отдельной операцией только
после явного разрешения пользователя.

### Ожидаемый результат (Expected Result)

Ветка `release/0.2` содержит проверенные релизные метаданные, а тег `v0.2.0` создаётся с её
проверенной вершины только после отдельного разрешения; release workflow (процесс выпуска)
успешно публикует GitHub Release и PHAR-артефакт.

## 1. Concept and Goal (Концепция и Цель)

### Story (Job Story)

> Когда изменения для `v0.2.0` приняты и проверены, я хочу зафиксировать состав релиза,
> провести финальные проверки и подготовить релизную ветку, чтобы опубликовать воспроизводимый
> релиз только после отдельного явного разрешения пользователя.

### Goal (Цель по SMART)

В рамках текущего релизного цикла актуализировать `CHANGELOG.md` и
`docs/releases/v0.2.0/release-plan.md`, подтвердить готовность проверками, создать PR
`task/release-v0-2-0` → `release/0.2`, а после его принятия и отдельного явного разрешения
пользователя опубликовать тег `v0.2.0` с проверенной вершины `release/0.2`.

## 2. Context and Scope (Контекст и Границы)

* **Где делаем:** `CHANGELOG.md`, `docs/releases/v0.2.0/release-plan.md`,
  `todo/done/TASK-release-v0-2-0-preparation.todo.md`; GitHub PR и тег как отдельные операции.
* **Текущее состояние:** релизные изменения уже находятся в `main`; пользователь явно одобрил
  начало выпуска `v0.2.0`; тег `v0.2.0` ещё не опубликован.
* **Границы (Out of Scope):**
  * не менять production-код, тесты, зависимости, сборочные сценарии и CI/CD;
  * не добавлять новый tooling (инструментарий) и не проводить переработку документации;
  * не включать и не выполнять backlog-задачи;
  * не создавать и не отправлять тег до отдельного явного разрешения пользователя на публикацию.

## 3. Requirements (Требования, MoSCoW)

### 🔴 Must Have (Обязательно)

- [x] `CHANGELOG.md` содержит итоговый раздел `0.2.0` без нерелизных изменений.
- [x] `docs/releases/v0.2.0/release-plan.md` фиксирует состав, риски, проверки и порядок выпуска.
- [x] Финальные проверки проекта завершены успешно и их результат отражён в release plan
  (плане релиза).
- [x] Создан PR `task/release-v0-2-0` → `release/0.2`; задача переведена в `review`, поле `pr`
  заполнено.
- [x] После approval (одобрения), до merge (слияния), задача переведена в `done` и перенесена
  в `todo/done/`.
- [ ] PR слит только после явной команды пользователя на merge.
- [ ] Тег `v0.2.0` создан и отправлен только после отдельного явного разрешения пользователя
  на публикацию релиза.
- [ ] После публикации проверены успешный workflow (процесс GitHub Actions) `Release Phar`
  и наличие артефакта релиза.

### 🟡 Should Have (Желательно)

- [ ] Release notes (примечания к релизу) согласованы с `CHANGELOG.md`.

### ⚫ Won't Have (Не будем делать)

- [ ] Новые функциональные изменения, исправления или рефакторинг.
- [ ] Изменение release tooling (инструментария выпуска), CI/CD или форматов дистрибуции.
- [ ] Реализация либо включение задач из `todo/backlog/`.
- [ ] Общая переработка README, guide (руководств) или skills (навыков агентов).

## 7. Risks and Dependencies (Риски и зависимости)

- Публикация тега запускает внешний release workflow (процесс выпуска) и потому требует
  отдельного явного разрешения пользователя.
- Тег должен указывать на проверенную вершину `release/0.2`; иначе состав релиза не совпадёт
  с release plan (планом релиза).
- Backlog-задачи не блокируют выпуск и не входят в его scope (границы).
