# TASK-fix-watch-subagent-timeout: Починить само-терминирование watch-subagent.sh по таймаутам

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)
- `docs/agents/skills/run-subagent/scripts/watch-subagent.sh` (обёртка запуска сабагентов) **не завершается сам** в рамках своих же таймаутов (`--soft-timeout` / `--hard-timeout` / `--stall-timeout`). Запуск кончается только внешним `SIGKILL` от harness'а (по bash `timeout`), теряя cleanup, run-summary, архив `events/` и захваченный ответ агента.
- Это блокирует мандатные шаги сабагент-конвейера (`task-via-subagents`, `epic-via-subagents`): **self-review и code review** сейчас нельзя провести надёжно — ответ ревьюера теряется, цикл сжигает полный бюджет wall-clock + токенов.

### Варианты или путь решения (Solution Sketch)
- **Investigation-first:** сначала воспроизвести с захватом улик (`WATCH_KEEP_TMP=1`, длинный промпт на медленном провайдере), собрать `events.ndjson` / `gaps.tsv` / `runner.stderr` и подтвердить корневую причину.
- **Гипотеза (не подтверждена):** проверки `soft`/`hard`/`stall` живут внутри тела цикла `while IFS= read -r -t "$STALL_TIMEOUT" line; do … done < "$PIPE"` и срабатывают **только когда из пайпа пришла целая строка (до `\n`)**. Если провайдер стримит большой блок без перевода строки (длинный thinking / tool-output одной логической строкой), `read -t` **не таймаутится** (байты постоянно сбрасывают таймер) и **не возвращает строку** → тело цикла и все проверки замирают.
- **Fix:** вынести enforcement таймаутов из тела цикла в **фоновой watcher-процесс** (или внешний `timeout`, посылающий `SIGTERM` → grace → `SIGKILL`), чтобы таймаут срабатывал по часам; гарантировать `cleanup()` на любом пути завершения.

### Ожидаемый результат (Expected Result)
- `watch-subagent.sh` само-терминируется на `soft`/`hard`/`stall` независимо от характера потока событий.
- В любом сценарии завершения (включая kill) отрабатывает `cleanup()`: пишется `=== RUN SUMMARY === ended=... reason=...` и архив `events/` при неуспехе.
- Захваченный ответ ревью/self-review агента (`-o text,files`) не теряется.
- Цикл сабагент-ревью (`task-via-subagents` Шаги 4–5) снова работает штатно.

### Story (Job Story)

## 7. Risks and Dependencies (Рisks и зависимости)
- **`SIGKILL` обходит `trap EXIT`:** гарантировать полный cleanup при внешнем `SIGKILL` невозможно средствами bash — фиксируется через фоновый watcher, который сам пишет summary перед убийством родителя. Учесть в дизайне.
- **Регрессия таймаутов:** вынос проверок из цикла может сломать «мягкий» soft-warn режим (`WATCH_SOFT_WARN_ONLY=1`) — сохранить существующее поведение env-переключателей.
- **`read -t` поведение зависит от bash version:** проверить на целевой версии bash проекта/CI.
- **Эмуляция «стрима без `\n`» в тесте:** может потребовать помощник на Python/`stdbuf`, т.к. чисто bash-эмуляция сложна.
- Зависимость от поведения провайдеров (стриминг большими блоками) — воспроизведение может быть флапающим; фиксировать на нескольких провайдерах.

**Вывод из фактов:** `cleanup()` безусловно пишет `RUN SUMMARY` и архивирует `events/` при любой неуспешной причине (включая `external_signal`). В обоих логах этого нет → `cleanup()` **ни разу не отработал** → обёртку убил **внешний `SIGKILL`** (единственный сигнал, обходящий `trap EXIT`), причём **до** срабатывания собственных soft/hard (1500/1800 и 700/900 соответственно, иначе была бы причина `soft_timeout`/`hard_timeout` в логе). Паттерн стабилен на двух провайдерах и двух конфигах.

### Гипотеза (требует подтверждения)
Проверки `soft`/`hard`/`stall` находятся внутри тела `while IFS= read -r -t "$STALL_TIMEOUT" line; do … done < "$PIPE"` и исполняются только при возврате из `read` целой строкой (до `\n`). Если провайдер стримит большой блок без перевода строки, `read -t` не таймаутится (байты сбрасывают таймер) и не возвращает строку → тело цикла замирает → запускается только внешний SIGKILL. Это объясняет, почему даже stall (240с) не сработал.

### Исполнитель
Среди текущих ролей нет bash-специалиста (роли заточены под PHP/DDD). Кандидатура исполнителя и срочность — на усмотрение Тимлида/пользователя. Задача заведена по итогам блокировки конвейера ревью в работе над PR #272 (TASK-research-swarm-forge).

## 10. Result (Результат)

**Ветка:** `fix/watch-subagent-timeout`. **Проверки:** phpunit 1082/1082 OK, psalm — без ошибок, md-links OK, validate-todo OK.

### Что подтверждено
- **Версия pi НЕ причина:** pi 0.79.6 установлен 2026-06-17 11:50, зависания — 2026-06-18 09:12/09:47 (уже на 0.79.6). Вывод отменённой `TASK-fix-watch-subagent-logical-stall` («исправлено в 0.79.6») тем самым опровергнут.
- **Структурный дефект подтверждён (чтение кода, строки ~700–810):** проверки soft/hard/stall живут внутри тела `while IFS= read -r -t "$STALL_TIMEOUT" line; do … done` и исполняются только когда `read` вернул строку. Если `read` не отдаёт управление — проверки и `cleanup()` (trap EXIT отложен до возврата `read`) замирают. Это объясняет отсутствие `RUN SUMMARY`/архива в обоих логах зависаний.
- **Гипотеза «поток без `\n` не даёт `read -t` таймаутиться» — ОПРОВЕРГНута** валидным микро-тестом (писатель держит pipe открытым, капает байты без `\n`): `read -t` выходит ровно по таймауту.

### Что НЕ удалось (честно)
- **Детерминированно воспроизвести зависание real-pi не удалось** — как и в отменённой соседней задаче (4 теста). Зависание флапает и зависит от поведения провайдера. Воспроизведён **структурный эквивалент** (заблокированный `read` через фейковый pi + большой `-t`), покрывающий тот же класс «основной цикл не отдаёт управление».

### Решение
Введён **фоновый watcher по wall-clock** (`start_watcher` / `watcher_force_exit`) отдельным подпроцессом:
- не блокирован в `read` → терминирует запуск по soft/hard/stall по часам, даже если основной цикл завис;
- при срабатывании **сам** пишет `=== RUN SUMMARY ===` (с `source=watcher`) и архивирует `events/` (trap EXIT основного процесса не сработает, пока `read` блокирован, поэтому watcher делает работу сам), затем убивает дерево агента и основной процесс (SIGTERM → grace → SIGKILL);
- каждые `WATCH_WATCHER_INTERVAL` (default 5с, env) пишет в `run.log` `watcher_heartbeat elapsed=… stall_gap=… agent_alive=…` — **диагностическая улика зависания** (растущий `stall_gap` при живом агенте); на следующем естественном зависании это окончательно покажет триггер.

Helpers `emit_run_summary` / `archive_events` вынесены из `cleanup()` и защищены маркер-файлами от двойной записи (race между in-loop cleanup и watcher). `cleanup()` останавливает watcher на нормальных путях. Существующие env-переключатели (`WATCH_SOFT_WARN_ONLY`, `WATCH_KEEP_TMP`) сохранены.

### Тесты
- `tests/Integration/Docs/Agents/Skills/RunSubagent/WatchSubagentScriptTest.php`: + `watcherTerminatesStuckRunLoopWithSummaryAndArchive` (фейковый pi hang + большой `-t` → watcher терминирует за soft, `source=watcher`, архив `events/`). Существующие 13 тестов зелёные.
- Локальный bash-харнесс (`/tmp/wstest`, вне репо): 3 сценария (success / stuck-read / drip) — 14/14 PASS.

### Известные ограничения
- Внешний `SIGKILL`, убивающий сам watcher (и основной процесс одновременно), обходит trap — полный cleanup невозможен средствами bash (зафиксировано в рисках задачи). Все мягкие сигналы (TERM/INT и собственные soft/hard/stall) обрабатываются.
