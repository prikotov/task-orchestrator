# TASK-feat-runner-provider-fallback: Fallback раннера сабагента на резервного провайдера при недоступности основного

## 1. Concept and Goal (Концепция и Цель)
### Story (Job Story)
Когда основной раннер/провайдер роли сабагента недоступен (исчерпаны лимиты, прокси-несовместимость, 5xx, таймаут), я хочу автоматически или по простой процедуре переключиться на резервного провайдера, чтобы конвейер «реализация → review → PR» не останавливался и Тимлид не блокировал пользователя ручным выбором fallback.

### Goal (Цель по SMART)
Обеспечить устойчивый путь запуска сабагентов: при отказе основного раннера (`codex`/`gpt-5.5`) переключение на резерв (`pi`/`zai`/`glm-5.x`) происходит без потери качества и без ручного вмешательства пользователя в каждое падение. Должны быть зафиксированы: механизм/процедура fallback и качество-компенсация (т.к. резервная модель слабее).

## 2. Context and Scope (Контекст и Границы)
*   **Где делаем:**
    *   `docs/agents/skills/run-subagent/scripts/watch-subagent.sh` — механизм retry/fallback при запуске.
    *   `config/chains.yaml` — профили ролей (`roles.<role>.command`), уже содержат закомментированные альтернативные `command`.
    *   `docs/agents/skills/run-subagent/SKILL.md` — документация fallback-поведения.
*   **Текущее поведение:** профиль роли содержит единственный активный `command` (например, Локи/Гэндальф → `codex`/`gpt-5.5`). При отказе раннера `watch-subagent.sh` падает с `runner_failed_event`, Тимлид вручную подбирает override (`--runner pi --provider zai --model ...`) и валидирует результат.
*   **Инцидент-триггер (2026-06-17):** `codex`/`gpt-5.5` упал (`Proxy URL scheme not supported` для `wss://chatgpt.com`), плюс исчерпаны лимиты codex. Fallback выполнен вручную на `pi`/`zai`/`glm-5.2` для задачи `TASK-fix-fixiterations-config-error-dx`.
*   **Границы (Out of Scope):**
    *   Автоматический выбор модели «по цене/качеству» (out — это балансировка, отдельная тема).
    *   Cross-model verification (кросс-модельная верификация шага) — отдельный механизм в `config/chains.yaml`.

## 3. Requirements (Требования, MoSCoW)
### 🔴 Must Have (Обязательно)
- [ ] В профиле роли (`chains.yaml`) можно указать упорядоченный список раннеров/провайдеров: primary → fallback1 → fallback2.
- [ ] `watch-subagent.sh` при отказе primary (exit≠0 по причине недоступности раннера) автоматически пытается запустить следующий вариант из списка.
- [ ] Классификация ошибок: различать «раннер/провайдер недоступен» (→ fallback) и «сабагент завершился с бизнес-ошибкой» (→ НЕ fallback, эскалация). Иначе ретрируем вхолостую.
- [ ] Лог: в `var/log/watch-subagent/.../run.log` фиксируется, какой fallback сработал и почему primary отказал.
- [ ] Документация в `docs/agents/skills/run-subagent/SKILL.md`: как объявлять fallback, как он выбирается.

### 🟡 Should Have (Желательно)
- [ ] Качество-компенсация: при fallback на более слабую модель Тимлиду выводится явное предупреждение «модель ослаблена, требуется личная валидация артефакта».
- [ ] Env-override всей цепочки (`FALLBACK_CHAIN=...`) для разовых ситуаций без правки `chains.yaml`.

### 🟢 Could Have (Опционально)
- [ ] Health-check провайдеров перед стартом (быстрая проверка коннективности) вместо ожидания отказа в процессе.

### ⚫ Won't Have (Не будем делать)
- [ ] Балансировка нагрузки между провайдерами (round-robin) — это не fallback.
- [ ] Динамический подбор оптимальной модели по метрикам.
