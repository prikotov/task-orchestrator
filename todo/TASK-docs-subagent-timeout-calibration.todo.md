## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)

Сабагенты — рабочие агенты, которых тимлид запускает на подзадачи (реализация, ревью, анализ) — работают с жёстким ограничением времени: «стартовый таймаут» (soft-timeout, `-s`), по которому запланировано завершение работы агента. Текущая таблица этого лимита в скилле оркестрации задач (`docs/agents/skills/task-via-subagents/SKILL.md`, раздел «Таймауты сабагентов») назначает секунды только по уровню сложности задачи и совершенно не учитывает, **какую долю времени внутри задачи занимают тяжёлые финальные или аналитические работы** — финальный полный барьер проверок (`make check`, долго) или, наоборот, объёмное чтение материалов (архив ретро, журналов). Из-за этого типовой сценарий «реализация, а в конце — полный `make check`» и «прочитать большой архив и проанализировать» не влезает в лимит, назначенный по сложности: агент уже выполнил содержательную работу, но срубается на «хвосте» (проверки или чтение). Это мешает процессу повторно — порог реестра ретроспектив достигнут: 6 подтверждённых случаев в разных ретро 2026-08-20, 2026-09-13, 2026-11-02, 2026-11-06, 2026-11-23 (дважды). Каждое срабатывание — потеря 10+ минут на убитый запуск, обязательный перезапуск с корректировкой и ручной контроль инициатора.

### Варианты или путь решения (Solution Sketch)

Предлагается 2 правки текстов инструкций (скиллов), без изменения скриптов:

1. **Калибровка по весу работы** — дополнить раздел «Таймауты сабагентов» скилла `task-via-subagents/SKILL.md` правилами выбора стартового `-s` не только от сложности, но и от «веса» работы внутри задачи. Ядро правила — уже подтверждённые ретроспективами коэффициенты: реализации с финальным `make check` — стартовать с ≥900 сек (то есть ×1.5 к базовой 600 для C0–C2); документные/аналитические этапы — ≥900; контекстоёмкие ретро — 1800 + режим чтения «выборкой» в промпте. При перезапуске после soft-timeout — увеличить ×1.5 (правило уже есть — оставить, переформулировать).
2. **Форматированная сводка лимитов** — в том же разделе дать компактную сводку-шпаргалку «стартовый soft → перезапуск», с формулой вычисления hard (`hard = max(soft×2, 1800)`), чтобы инициаторам не приходилось удерживать это в голове.

Решение не требует изменения скрипта `watch-subagent.sh`: механика hard-timeout уже безопасна (`hard = max(soft×2, 1800)`), проверено по исходнику (`watch-subagent.sh:1097–1105`).

### Ожидаемый результат (Expected Result)

После правки скиллов инициатор, запуская сабагента на типовой сценарий «реализация + финальный `make check`» (или документный/аналитический прогон), сразу берёт стартовый `-s` с учётом веса работы, а не базовый 600 сек по сложности. Это даёт: меньше убитых по soft-timeout запусков (цель — ноль повторов в следующих ретро на реализационных задачах с финальным `make check`), меньше потерянных минут на перезапуски, меньше ручного контроля инициатора. Скилл `task-via-subagents` становится полнее: правило выбора таймаута учитывает не только сложность, но и профиль работы. Ближайшая мера (стартовый `-s ≥900` для реализационных с `make check`) перестаёт зависеть от того, помнит ли инициатор недавние ретро.

## 1. Концепция и Цель (Concept and Goal)
### История (User Story или Job Story)

> **User Story:** Как тимлид, оркестрирующий задачи через сабагентов, я хочу, чтобы стартовый таймаут сабагента подбирался по весу работы внутри задачи (финальный `make check`, документные этапы, объёмное чтение), а не только по сложности, чтобы сабагенты не убивались soft-timeout'ом на финальных проверках или чтении и не терялось время на перезапуски.

### Цель по SMART (Goal)

Дополнить раздел «Таймауты сабагентов» скилла `docs/agents/skills/task-via-subagents/SKILL.md` правилами калибровки стартового soft-timeout по весу работы (реализация + финальный `make check` — старт ≥900; документные/аналитические этапы — ≥900; контекстоёмкие ретро — 1800 + чтение выборкой; перезапуск — ×1.5) и добавить компактную сводку «стартовый soft → перезапуск» с формулой `hard = max(soft×2, 1800)`. Критерий готовности: правило однозначно определяет стартовый `-s` для всех шести подтверждённых повторов из реестра ретроспектив; правки опубликованы в `main` через PR.

## 2. Контекст и Границы (Context and Scope)

*   **Где делаем:** `docs/agents/skills/task-via-subagents/SKILL.md` — раздел «Таймауты сабагентов» (таблица C0–C2 → 600 сек, C3 → 1800, C4 → 2400, C5 → 3600) и примечание «После перезапуска по таймауту увеличивай значение (примерно ×1.5), а не повторяй прежнее». Опционально — синхронное примечание в `docs/agents/skills/run-subagent/SKILL.md` (раздел параметров `-s`), если при правке обнаружится расхождение формулировок.
*   **Текущее поведение:** таблица назначает секунды **только** по уровню сложности задачи (C0–C2 → 600); фактор «веса работы» (финальный полный барьер проверок, объёмное чтение архива/журналов) не отражён, поэтому типовые профили (реализация с финальным `make check`; документные этапы; контекстоёмкие ретро) хронически не влезают в лимит.
*   **Прецеденты для переиспользования:** реестр ретроспектив `docs/agents/team-retro/RETRO-ROADMAP.md` — запись «Таблица таймаутов `task-via-subagents` не учитывает вес проверок и документной работы» (счётчик 6, статусы повторов с конкретными секундами и результатами перезапусков — это готовая фактура для формулировок); ретро `2026-11-23_21-30-task-refactor-overlength-services.md` (мера «стартовый `-s 900`…» для реализационных C1–C2) и `2026-11-23_08-56-runfacilitator-vo-task-retro.md` (повтор №6, предложение 1).
*   **Критичные конвенции:** стиль документации скиллов — по соседним разделам `task-via-subagents/SKILL.md` и `run-subagent/SKILL.md` (таблицы, краткие правила, ссылки на скрипты); доля англицизмов — под контролем валидатора `validate-language` (`.coding-standard.php`).
*   **Границы (Out of Scope):** изменение скриптов (`watch-subagent.sh`, любых сценариев `docs/agents/`), изменение механики таймаутов или дефолтов в коде; правки ролей агентов (`docs/agents/roles/`); изменение самой таблицы сложности (C0–C5); заведение новых задач из этого процесса; реализация в коде защит от таймаутов; переработка других разделов скиллов.
