# TASK-feat-complexity-based-role-commands: Выбирать команду запуска роли по сложности задачи

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)
- Сейчас роль связана с одной `command`, поэтому простые и сложные задачи запускают одну и ту же модель с одинаковым уровнем размышления.
- Нужно выбирать команду по сложности конкретной `TASK-*`, не создавая отдельную роль для каждой модели.

### Варианты или путь решения (Solution Sketch)
- `watch-subagent.sh` принимает `--task-id TASK-*` и детерминированно читает `complexity` из её front matter; `--complexity` является явным override.
- Для роли можно задать набор команд по уровням сложности. Полный набор `C0–C5` не обязателен.
- Для запрошенного уровня выбирается ближайшая настроенная команда того же или более высокого уровня; если выше команды нет — ближайшая команда ниже.
- Если `complexity` отсутствует, используется `C3`.

### Ожидаемый результат (Expected Result)
- Пара `роль + complexity` детерминированно выбирает целую `command`, включая CLI, provider, model, thinking и остальные аргументы.
- `prompt_file`, `system_prompt_file` и остальные настройки роли не зависят от выбранной сложности.

## 1. Концепция и Цель (Concept and Goal)

### История (User Story)
> Как владелец оркестратора, я хочу назначать роли разные команды запуска в зависимости от сложности задачи, чтобы не расходовать сильные модели на простые задачи и не ослаблять выполнение сложных.

### Цель по SMART (Goal)
- Реализовать выбор команды роли по `complexity` из `TASK-*` с ближайшим доступным уровнем и значением по умолчанию `C3`, сохранив совместимость с одиночной `command`.

## 2. Контекст и Границы (Context and Scope)

- Источник сложности: YAML front matter файла `todo/**/TASK-*.todo.md`, поле `complexity` (`C0–C5`).
- Выбор выполняется до запуска каждого agent-шага и применяется одинаково ко всем ролям цепочки для текущей задачи.
- Меняется вся `command`; отдельного сопоставления provider/model/thinking не существует.
- Scope: конфигурация ролей, `watch-subagent.sh`, чтение сложности задачи, документация skills и интеграционные тесты.
- Out of scope: автоматическая оценка сложности агентом, изменение сложности между шагами, выбор `prompt_file` по сложности.

## 3. Требования, MoSCoW (Requirements)

### 🔴 Обязательно (Must Have)

- [x] `TASK-*` передаётся отдельным `--task-id`; файл задачи однозначно находится и парсится без извлечения ID из текста промпта.
- [x] Отсутствующее поле `complexity` трактуется как `C3`.
- [x] Отсутствующий файл задачи, неоднозначное имя или недопустимое значение `complexity` завершают запуск с понятной ошибкой; значения не угадываются.
- [x] Конфигурация роли поддерживает частичный набор отклонений по уровням `C0–C5`; именованные `command_profiles` устраняют дублирование команд.
- [x] Базовая `command` или `command_profile` считается уровнем `C3`.
- [x] Для запрошенного уровня `Cn` алгоритм выбирает настроенный уровень с минимальным `k >= n`; если такого нет — максимальный настроенный `k < n`.
- [x] При наличии точного уровня выбирается он.
- [x] Выбранная `command` используется целиком, включая основной и fallback-запуск по правилам существующей конфигурации.
- [x] Существующая одиночная `command` остаётся поддерживаемой и используется для всех уровней, если вариативные команды не заданы.
- [x] `prompt_file`, системный промпт, таймауты, бюджеты и политики повторов не дублируются по уровням сложности.

### Пример выбора

Для настроенных уровней `C1`, `C3`, `C4`:

| Сложность задачи | Выбранная команда |
| --- | --- |
| `C0` | `C1` |
| `C1` | `C1` |
| `C2` | `C3` |
| `C3` | `C3` |
| `C4` | `C4` |
| `C5` | `C4` |

Если настроена только `C1`, она выбирается для всех уровней `C0–C5`.

### ⚫ Won't Have (Не будем делать)

- Автоматическое определение или пересмотр сложности задачи.
- Отдельные роли вида `role_easy` / `role_hard`.
- Выбор отдельных полей provider/model/thinking вместо целой `command`.
- Обязательная настройка команд для каждой роли и каждого уровня.

## 7. Риски и зависимости (Risks and Dependencies)

- Явные `--runner`, `--provider`, `--model` и `--reasoning` должны сохранять приоритет над выбранным профилем.
- Fallback должен быть связан с выбранным уровнем либо однозначно наследовать существующие правила роли; неявного выбора другой модели быть не должно.
- Изменение YAML-контракта требует синхронного обновления валидатора конфигурации и документации.
- PR #457 меняет разделение системного и ролевого промптов; при параллельной реализации потребуется разрешить пересечения в конфигурации ролей без смешивания задач в одном PR.
