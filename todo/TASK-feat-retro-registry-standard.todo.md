# TASK-feat-retro-registry-standard: Реестр ретро с порогом эскалации и стандарт проведения ретроспектив

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)
Ретроспективы заканчиваются списком «Предложений для улучшения», но эти пункты живут только внутри текста ретро-файлов. Команда (включая тимлида) не видит их между сессиями: одни и те же проблемы повторяются по 3–4 раза, решения теряются, а чтобы понять «что уже сделано по ретро», нужно перечитывать весь архив из 16+ файлов руками. Владелец вынужден сам напоминать, что ретро-уроки надо фиксировать и выполнять. Ретро превращаются в кладбище хороших идей.

### Варианты или путь решения (Solution Sketch)
- Ввести **реестр-агрегатор** (роадмап команды): один живой файл, где каждая проблема копится со счётчиком упоминаний и ссылками на ретро, а после решения остаётся история (чем решено, где).
- **Порог эскалации:** задача создаётся только при 3 упоминаниях в разных ретро либо для критичной проблемы (блокер). Защитный механизм от мелочёвки: разовые замечания остаются в статусе наблюдения.
- Задачи, порождённые реестром, после решения **удаляются**; история решений остаётся в реестре.
- Оформить как стандарт: доработать SKILL `retrospective` (обновление реестра — обязательный шаг каждой ретро).

### Ожидаемый результат (Expected Result)
После любой ретро состояние «что мы делали по ретро» видно одним взглядом в реестр: у каждой проблемы — счётчик упоминаний, ссылки на ретро, статус (наблюдение / задача / решено) и история решения. Повторяющаяся 3-й раз проблема автоматически становится задачей; критичная — сразу. Ретро-уроки больше не теряются и не требуют ручного перечитывания архива.

## 1. Concept and Goal (Концепция и Цель)
### Story (Job Story)
> **Job Story:** Когда ретроспектива завершена и в ней появились предложения по улучшению, я хочу, чтобы они автоматически попадали в единый реестр со счётчиком упоминаний, чтобы проблема, повторившаяся трижды или ставшая критичной, превращалась в задачу — а решённые пункты оставляли в реестре историю решений вместо мёртвого текста в архиве ретро.

### Goal (Цель по SMART)
Создать реестр ретро `docs/agents/team-retro/RETRO-ROADMAP.md` с правилами эскалации (3 упоминания в разных ретро ИЛИ критичность), доработать SKILL `retrospective` (обязательное обновление реестра + проверка порогов после каждой ретро), наполнить реестр пилотно из 16 существующих ретро и эскалировать проблемы, достигшие порога. ## 2. Context and Scope (Контекст и Границы)
*   **Где делаем:**
    *   `docs/agents/team-retro/RETRO-ROADMAP.md` — новый файл реестра (каталог отслеживается git; НЕ генерируемые `docs/conventions/`, `docs/todo-md/`).
    *   `docs/agents/skills/retrospective/SKILL.md` — стандарт проведения ретро (шаг «Обновить реестр»).
    *   `todo/` — задачи, порождаемые эскалацией (по правилам реестра).
*   **Решение владельца (2026-08-18, зафиксировано в ретро 2026-08-18):** накапливать проблемы; задачи — только после 3 упоминаний в разных ретро или при критичности (без решения нельзя двигаться дальше); задачи потом удаляются, реестр остаётся агрегатором/счётчиком/историей решений.
*   **Пилотное наполнение (данные из разбора архива тимлидом, 2026-08-16):**
    *   «Тимлид делает сам вместо делегирования» — 5 упоминаний (04-19, 04-24, 05-13, 06-30, 07-24) → решено (закреплено в роли) — resolved.
    *   «Неполные метаданные задач после сабагента» — 4 (04-22, 04-27, 06-15, 06-20) → решено (контрольная точка в task-via-subagents) — resolved.
    *   «Action items ретро не трекаются» — 4 (06-30, 07-01, 08-05, 08-18) → эскалация: закрывается настоящей задачей.
    *   «Сначала данные, потом гипотезы / нарратив вместо фактов» — 3 (06-30, 07-01, 08-18) → **эскалация: отдельная задача-кандидат** (правило в роль Тимлида).
    *   «Ранние таймауты убийства агентов» — решено PR #352 — resolved.
    *   «Секреты в stdout/PR» — 3, решено правилами AGENTS.md — resolved.
    *   N-2 (поведенческий stall-тест), N-4 (флаки liveness-тест) — по 1 упоминанию — watch.
    *   Прочие из архива — по факту разбора (исполнитель сверяется с файлами `docs/agents/team-retro/*.md`).
*   **Границы (Out of Scope):**
    *   Автоматизация/CLI для парсинга ретро и ведения реестра — ручной Markdown-процесс.
    *   Переписывание существующих ретро-файлов — реестр строится поверх архива, архив не меняется.
    *   Изменение правил хранения задач вне ретро-порождённых (done хранится бессрочно — отклонение ТОЛЬКО для задач из реестра, см. Risks).
    *   Пересмотр самих ролей/конвейера — только механизм учёта.

## 7. Risks and Dependencies (Риски и зависимости)
- **Отклонение от todo/AGENTS.md («done хранится бессрочно»):** для задач, порождённых реестром, вводится удаление после решения. Зафиксировать это исключение явно (в реестре и/или todo/AGENTS.md), чтобы не ломать регламент молча.
- **Субъективность счётчиков:** одно упоминание = одна ретро (не один абзац); спорные случаи помечать, решение за тимлидом.
- **Реестр не ведётся на практике** (главный риск): митигируется обязательным шагом в SKILL + чек-пунктом в мини-чеклисте тимлида (проверить при ревью).
- **Разрастание реестра:** записи `resolved` не удаляются, но пишутся компактно (1–2 строки истории).
