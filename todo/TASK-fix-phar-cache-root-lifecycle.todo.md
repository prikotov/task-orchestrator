# TASK-fix-phar-cache-root-lifecycle: Жизненный цикл и очистка устаревших PHAR-кеш-корней (FR-4)

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)

Каждое перемещение или копирование PHAR в новое расположение материализует новый изолированный кеш-корень `<sys_tmp>/task-orchestrator/<hash>` (изоляция по паре «host-проект + физический путь PHAR» из выполненной задачи). Старые корни при этом не удаляются автоматически и накапливаются в системном временном каталоге до ручной чистки: пользователь вынужден сам находить и удалять служебные каталоги task-orchestrator.

### Варианты или путь решения (Solution Sketch)

Определить доказуемое владение корнем и ограниченную очистку: boot-time захват эксклюзивного `flock(LOCK_EX|LOCK_NB)` на свой корень до `parent::boot()` с удержанием до завершения процесса; маркер владения с self-hash, связанным с именем каталога; диспетчер очистки на `lstat` (без обхода симлинков) с проверкой владельца; очистка выполняется только в PHAR-режиме, ошибка очистки — warning (предупреждение), не меняющее результат команды.

### Ожидаемый результат (Expected Result)

После перемещения PHAR из пути A в путь B устаревший корень A удаляется автоматически при следующем запуске; текущий корень B, активный корень другого процесса, каталог без маркера и симлинк не затрагиваются; повторная очистка идемпотентна; сбой очистки не меняет exit code команды.

## 1. Концепция и Цель (Concept and Goal)

### История (Job Story)

> Когда я перемещаю или обновляю PHAR, я хочу, чтобы устаревшие кеш-корни task-orchestrator очищались автоматически и безопасно, чтобы системный временный каталог не засорялся каталогами прежних расположений.

### Цель по SMART (Goal)

Реализовать автоматическую очистку (только в PHAR-режиме), которая при запуске PHAR из нового расположения B удаляет устаревший корень A, подтверждённый маркером владения (self-hash ↔ имя каталога) при свободном flock, и сохраняет текущий, активный (заблокированный flock), неизвестный (без маркера) и симлинковый узлы. Поведение подтверждается матрицей integration-тестов и smoke-сценарием A → B на реально собранном PHAR; сбой очистки не меняет exit code команды.

## 2. Контекст и Границы (Context and Scope)

- **Где делаем:**
  - `src/Kernel.php` — boot-time flock на собственный кеш-корень до `parent::boot()`; порядок создания корня `mkdir` → `flock` → маркер; права `0700`;
  - чистая логика владения и очистки (без Symfony-зависимостей) — в `src/Component/` (точное размещение исполнитель фиксирует в плане реализации согласно [конвенции](../docs/conventions/index.md)); интеграция очистки — в `Kernel`;
  - `tests/Integration/` и целевые integration-тесты согласно [конвенции тестирования](../docs/conventions/testing/index.md);
  - `bin/phar-smoke` — сценарий перемещения A → B на реально собранном PHAR;
  - пользовательская и архитектурная документация: политика очистки, ограничения NFS/Windows, поведение при аварийном завершении.
- **Текущее поведение:** изоляция `writableRoot()` по паре `(host project, physical PHAR path)` исправляет переиспользование контейнера после перемещения PHAR (закрытие QA-1), но каждый новый физический путь создаёт отдельный корень без автоматического удаления предыдущего; признака владения (маркера) у корней нет.
- **Scope:** маркер владения с self-hash, flock-арбитр активности, ограниченный GC (сборка мусора) только в PHAR-режиме, матрица тестов, warning-семантика ошибки очистки, документирование ограничений.
- **Границы (Out of Scope):** не трогать runtime layout-параметры (`roles_dir`, `skills_dir`, `chains_yaml`) и резолвер `Component/Layout` — это [`TASK-fix-phar-runtime-layout-cache`](done/TASK-fix-phar-runtime-layout-cache.todo.md); не менять контракты `become-role`/`agent:init`; не менять source/Composer layout и не рефакторить `Kernel` целиком; не добавлять новые зависимости, self-update (самообновление) или общесистемный сборщик мусора.

## 3. Требования, MoSCoW (Requirements)

### 🔴 Обязательно (Must Have)

- [ ] Boot-time захват эксклюзивного `flock(LOCK_EX|LOCK_NB)` на собственный кеш-корень ДО `parent::boot()` с удержанием дескриптора до завершения процесса; неудачный захват трактуется как признак активного чужого корня.
- [ ] Порядок создания корня: `mkdir` → `flock` → маркер владения; корень без маркера считается незавершённым или чужим и не очищается.
- [ ] Диспетчер очистки проверяет узлы через `lstat` (без перехода внутрь по симлинку): симлинк удаляется через `unlink` самого узла; traverse (обход по симлинку) запрещён.
- [ ] Владение подтверждается только при совпадении `fileowner` каталога с `posix_getuid()` (POSIX); ограничение Windows (отсутствие POSIX-функций) задокументировано.
- [ ] Маркер владения содержит self-hash, связанный с именем каталога; расхождение маркера и имени трактуется как чужой или неизвестный корень и сохраняется.
- [ ] Права `0700` на `<sys_tmp>/task-orchestrator`; невозможность установить права — задокументированное безопасное поведение (очистка не выполняется).
- [ ] Очистка выполняется только в PHAR-режиме; вне PHAR — no-op (операция-пустышка).
- [ ] Очистка идемпотентна при параллельных запусках: гонки обрабатываются через flock/`lstat`, повторный запуск не падает и не удаляет лишнего.
- [ ] Warning-семантика ошибки очистки зафиксирована до реализации (fail-fast отклонён: немедленное завершение с ошибкой маскирует результат команды): сбой очистки не меняет exit code основной команды и выдаёт безопасную диагностику без раскрытия содержимого кеша; тест «сбой очистки не меняет exit code» обязателен.
- [ ] Legacy-корни без маркера (созданные до введения маркера) сохраняются; их судьба задокументирована.
- [ ] Документированы ограничения: flock на NFS ненадёжен (очистка может не выполняться — неоднозначный каталог сохраняется), Windows (POSIX-функции недоступны), аварийное завершение процесса (lock освобождается ОС).
- [ ] Матрица тестов: текущий корень (свой маркер) / активный корень (чужой flock) / устаревший корень (маркер прежнего расположения, flock свободен) / неизвестный каталог (без маркера) / симлинковый узел / идемпотентный повтор очистки.

## 7. Риски и зависимости (Risks and Dependencies)

- Гонки параллельных запусков старого и нового PHAR: без flock-арбитра возможна попытка удаления активного корня; flock может быть ненадёжен на NFS — ограничение документируется, неоднозначный каталог сохраняется.
- Враждебный системный temp: злоумышленник или другой процесс может создать совпадающий путь, симлинк или каталог чужого владельца; обязательны `lstat`, проверка `fileowner` и прав `0700`; без полного набора признаков владения удаление запрещено.
- Legacy-корни без маркера не идентифицируются и сохраняются — осознанная цена совместимости; накопление ограничивается ротацией системного temp.
- Аварийное завершение процесса: lock освобождается ОС; корень с маркером прежнего расположения удаляется при следующем GC, незавершённый корень без маркера сохраняется.
- Зависимости: [`TASK-feat-phar-full-become-role-install`](done/TASK-feat-phar-full-become-role-install.todo.md) вводит изоляцию корней по паре (основание FR-4); [`TASK-fix-phar-runtime-layout-cache`](done/TASK-fix-phar-runtime-layout-cache.todo.md) правит runtime layout — реализация не должна конфликтовать с его изменениями `Kernel`.
- Значения `V2` и `C3` обоснованы так: накопление корней — осознанная цена изоляции, вред ограничен размером temp, но устранение требует конкурентного flock-арбитра, POSIX-зависимостей, безопасного удаления в потенциально враждебном каталоге и реальных PHAR-проверок — высокая техническая сложность при средней ценности.
