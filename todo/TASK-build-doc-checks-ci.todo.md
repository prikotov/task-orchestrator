# TASK-build-doc-checks-ci: Doc-проверки в CI для docs-only изменений

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)

`make check` включает документные проверки (`md-links`, `validate-language`, `validate-todo` — только активные), но CI-задания GitHub Actions (`test`, `phar-smoke`, `composer-host-smoke`, `scan-pr-content`) — не включают. Вся серия PR #500–#504 (docs-only) прошла CI без doc-проверок; компенсация — ручные прогоны тимлидом перед каждым PR. Это третье упоминание в реестре `RETRO-ROADMAP.md` («Docs-only PR проходит CI без md-links/validate-language/validate-todo») — порог эскалации достигнут, владелец решил оформить задачу.

Учитывать при реализации: решение владельца 2026-11-03 «в CI только критичное» (отклонение тяжёлого `phar-e2e`) — решение должно быть лёгким и быстрым, не раздувать CI.

### Варианты или путь решения (Solution Sketch)

Отдельное быстрое CI-задание (например, `doc-checks`): `make md-links`, `validate-language`, `validate-todo` (активные задачи). Условие запуска — по фильтру путей (docs/**, README*, todo/**, Makefile, конфиги проверок) либо безусловный запуск (проверки быстрые, секунды — допустимо всегда). Конкретный вариант выбирает исполнитель по итогам обсуждения в реализации (см. Риск 2).

### Ожидаемый результат (Expected Result)

Docs-only PR гоняют doc-проверки в CI автоматически; битые ссылки и англицизмы ловятся ботом CI до ручного прогона. Критерий: job в `.github/workflows/`, на docs-only PR задание выполняется и зелёное на актуальном `main`.

## 1. Концепция и Цель (Concept and Goal)

### История (User Story)

> Как владелец репозитория, я хочу, чтобы doc-проверки выполнялись в CI на docs-only изменениях, чтобы битые ссылки и доля англицизмов проверялись машиной, а не памятью тимлида.

### Цель по SMART (Goal)

В GitHub Actions добавлено задание doc-проверок, покрывающее `md-links`, `validate-language`, `validate-todo` для docs-only изменений; критерий: job зелёный на `main`, на тестовом PR с намеренно битой ссылкой задание краснеет, время выполнения — секунды.

## 2. Контекст и Границы (Context and Scope)

*   **Где делаем:** `.github/workflows/ci.yml` (или отдельный workflow-файл, по решению исполнителя), возможно `Makefile` (переиспользование целей `md-links`/`validate-todo`).
*   **Текущее поведение:** doc-проверки существуют только локально (`make check`, `Makefile:121–124`); CI их не содержит.
*   **Прецеденты:** существующие CI-задания (`test` ~3 мин, `phar-smoke`, `composer-host-smoke`, `scan-pr-content` ~11с); решение владельца 2026-11-03 «в CI только критичное».
*   **Критичные конвенции:** состав CI не раздувать; проверки должны быть детерминированными (не зависеть от сети сверх необходимого `md-links` — внешние ссылки уже обрабатываются текущей целью).
*   **Границы (Out of Scope):** правки `make check` (локальный барьер остаётся полным), правки doc-команд themselves, миграция исторических todo-файлов (смежная тема — отдельное решение владельца), добавление иных проверок в CI.

## 7. Риски и зависимости (Risks and Dependencies)

- Риск 1: `md-links` может быть сетезависимым (внешние ссылки) — проверить поведение существующей локальной цели в CI-окружении; при внешних ложных срабатываниях — использовать существующий режим цели (только внутренние ссылки), зафиксировать выбор в реализации.
- Риск 2: обсуждаемый вариант фильтра путей — если задать слишком узко, doc-правки вне фильтра уйдут мимо проверки; если без фильтра — job на каждом code-PR. По умолчанию: безусловный запуск (быстро), фильтр — как Should.
- Зависимостей нет; выполняется после серии PR #500–#504 (слито).
