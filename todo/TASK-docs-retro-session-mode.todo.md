# TASK-docs-retro-session-mode: Сессионный режим мини-ретроспективы: лёгкий вход после тяжёлой сессии без завершённой задачи

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)
Если агент заметно буксовал в сессии — делал лишние шаги, и его приходилось несколько раз исправлять — а задача ещё не завершена, зафиксировать выводы некуда: полная ретроспектива привязана к завершённой задаче/эпику и тяжеловата ради одной сессии. Выводы остаются в диалоге и теряются к следующей сессии, хотя навык прямо предупреждает: «обещание в ответе не сохраняет вывод для следующей сессии».

### Варианты или путь решения (Solution Sketch)
Добавить в навык `retrospective` лёгкий сессионный режим: сокращённый путь для «тяжёлой сессии» — сбор фактов из лога сессии и `audit.jsonl`, классификация фиксов по таблице из задачи переработки, файл ретроспективы по обязательному минимуму разделов и запись в реестр по штатным правилам.

### Ожидаемый результат (Expected Result)
После тяжёлой сессии можно запустить мини-ретро одной командой-запросом и получить файл в `docs/agents/team-retro/` с привязкой находок к моментам сессии и запись в реестре; гладкие сессии мини-ретро не порождают.

## 1. Концепция и Цель (Concept and Goal)

### История (User Story)
> **User Story:** Как владелец проекта, я хочу быстро фиксировать выводы тяжёлой сессии (буксования, лишние шаги, повторные исправления) без завершённой задачи, чтобы окружение агента исправлялось сразу, а не откладывалось до ретроспективы следующей завершённой задачи.

### Цель по SMART (Goal)
Добавить в `docs/agents/skills/retrospective/SKILL.md` сессионный режим мини-ретроспективы: (1) триггер в «Когда использовать» — тяжёлая сессия (заметное буксование, лишние шаги, многократные исправления) без завершённой задачи; (2) сокращённый путь: первоисточники — лог сессии и `audit.jsonl`, анализ по направлениям без оценки ролей, классификация фиксов по таблице из [TASK-docs-retro-skill-redesign](TASK-docs-retro-skill-redesign.todo.md); (3) выход — файл ретро по обязательному минимуму разделов шаблона и запись в реестр по штатным правилам; (4) явное ограничение: гладкая сессия — без мини-ретро. Изменения проходят цикл PM1–PM5 до этапа `DC`.

## 2. Контекст и Границы (Context and Scope)
*   **Где делаем:** `docs/agents/skills/retrospective/SKILL.md` (раздел «Когда использовать», новый сокращённый путь), при необходимости `assets/retrospective-template.md` (минимум обязательных разделов для сессии)
*   **Текущее поведение:** ретроспектива запускается после завершённой задачи/эпика/PR или по явной просьбе пользователя; лёгкого входа для «сессии без задачи» нет
*   **Границы (Out of Scope):** автозапуск после каждой сессии; изменение полного шаблона ретроспективы; изменение реестра и порогов; оценка ролей в сессионном режиме

## 3. Требования, MoSCoW (Requirements)
### 🔴 Обязательно (Must Have)
- [ ] Триггер сессионного режима в «Когда использовать»: тяжёлая сессия без завершённой задачи — по явному запросу пользователя или инициативе агента при подтверждении
- [ ] Сокращённый путь: сбор фактов из лога сессии и `audit.jsonl`; анализ проблемы и предложения без оценки ролей (сессия может не иметь завершённой задачи)
- [ ] Повторный запуск по той же сессии не порождает дубликат отчёта и лишнего счётчика; семантика реестра («упоминания в разных ретро») не меняется молча — расширение границ согласуется отдельно
- [ ] Устойчивый ключ сессии (идентификатор запуска, путь журнала или временной диапазон — выбор в PM1) фиксируется в метаданных отчёта; сценарий повторного запуска по той же сессии проверяется с ожидаемым числом файлов и значением счётчика
- [ ] Критерий «тяжёлой» сессии описан наблюдаемыми примерами (заметное буксование, лишние шаги, многократные исправления по требованию пользователя); при неоднозначности решение о запуске принимает пользователь — искусственный числовой порог не вводится
- [ ] Классификация фиксов по таблице «симптом → тип фикса» из задачи переработки навыка; общий контракт доказательств используется, а не изобретается заново
- [ ] Модель явно разделяет обязательные поля полного и сессионного режимов: объект сессионного отчёта (сессия/запуск), нужен ли раздел успешных практик, действие предела трёх предложений и статусов реестра — полноценные ретроспективы не ломаются
- [ ] Мини-ретро не отменяет полноценную ретроспективу после пользовательской приёмки задачи — граница прописана явно
- [ ] Выход: файл ретро в `docs/agents/team-retro/` по обязательному минимуму разделов + запись в реестре `RETRO-ROADMAP.md` по штатным правилам; при отсутствии проблем пустая запись реестра не создаётся (действующее правило шага 7 сохраняется)
- [ ] Явное ограничение шума: гладкая сессия — без мини-ретро
- [ ] Цикл PM1–PM5 до этапа `DC` ([RACI, раздел 6](../docs/agents/raci-matrix.md#6-специализированный-цикл-проектирование-процессов-взаимодействия-команды))
### 🟡 Желательно (Should Have)
- [ ] Именование файлов сессионных ретро отличает их от задачных (слаг с `session-`)
- [ ] Ссылка на сессию/запуск (ключ сессии) в метаданных файла ретро
### ⚫ Не будем делать (Won't Have)
- [ ] Автозапуск мини-ретро после каждой сессии (антинойс-правило из исследования: «гладкая сессия нечему учит»)
- [ ] Изменение порогов эскалации реестра
- [ ] Отдельный шаблон файла для сессий — используется существующий с минимальным набором разделов

## 7. Риски и зависимости (Risks and Dependencies)
- **Зависимость:** [TASK-docs-retro-skill-redesign](TASK-docs-retro-skill-redesign.todo.md) — режим строится на новой модели; запуск до её слияния создаст двойную переработку
- **Шум:** если режим дёшев, агенты будут запускать его после каждой сессии — обязательное правило «гладкая сессия — без мини-ретро» и подтверждение пользователя
- **Нехватка первоисточников:** лог сессии или `audit.jsonl` могут отсутствовать/быть неполными — сценарий отказа фиксируется в модели (PM2)
- **Путаница с полноценной ретро:** сессионный режим не подменяет ретро завершённой задачи — граница прописывается явно
- **Дублирование при повторном запуске:** та же сессия не должна порождать второй отчёт и второй счётчик; ожидаемый счёт на таком примере показывается в модели (PM1) — см. консультацию архитектора, раздел 3.3
