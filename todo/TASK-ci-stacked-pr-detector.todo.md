# TASK-ci-stacked-pr-detector: Пилот «проверка вместо прозы»: автоматическая CI-проверка запрета стековых PR

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)
После инцидента [PR #409–#414](https://github.com/prikotov/task-orchestrator/pull/414) запрет стековых PR существует только как абзац в `AGENTS.md`. Правило полагается на «послушание» модели: нарушение обнаруживается лишь постфактум защитой ветки — каскадом устаревших апрувов, что в инциденте стоило четырёх раундов аппрувов и закрытия трёх PR. Машина могла бы поймать нарушение раньше и дешевле.

### Варианты или путь решения (Solution Sketch)
Отдельный CI-workflow (рабочий процесс GitHub Actions), детектирующий стековость PR: пересечение множества неслитых коммитов текущей PR-ветки с другим открытым PR в ту же цель. Точный признак, механизм актуализации статуса и режим (информирующий → блокирующий) — по проектным рекомендациям [консультации архитектора](../docs/agents/reports/system-architect-gandalf/2026-09-29_21-07_retro-epic-decomposition-consultation.md).

### Ожидаемый результат (Expected Result)
Стековый сценарий отклоняется автоматической проверкой с понятным сообщением и ссылкой на правило `AGENTS.md`; обычные PR (включая не перебазированные после чужого мержа) и hotfix-ветки от production tag проходят без ложных срабатываний. Штатные механики GitHub (актуальность ветки, линейная история, очередь слияния) проверкой не подменяются — они не эквивалентны запрету стека.

## 1. Концепция и Цель (Concept and Goal)

### История (User Story)
> **User Story:** Как владелец проекта, я хочу, чтобы запрет стековых PR enforced автоматической проверкой, а не только текстом правила, чтобы нарушение ловилось до аппрува и не приводило к каскадам устаревших аппрувов и переделкам веток.

### Цель по SMART (Goal)
Внедрить проверку запрета стековых PR: (1) признак стека — пересечение множества неслитых коммитов `reachable(head(PR)) − reachable(target)` с другим открытым PR в ту же цель, с учётом симметрии пересечения, PR с целью в исходную ветку другого PR и области сравнения для разных целей (`main` / `release/*`) — точный контракт фиксируется на проектировании по [консультации архитектора](../docs/agents/reports/system-architect-gandalf/2026-09-29_21-07_retro-epic-decomposition-consultation.md); (2) три исхода: нарушение / отсутствие нарушения при полном снимке / невозможно проверить (ошибки API, лимиты, гонки) — третий исход не «зелёный»; (3) допуск hotfix-веток от production tag по `AGENTS.md` без иммунитета по имени ветки; (4) логика покрыта автоматическими тестами на синтетических сценариях без обращения к GitHub; (5) пилот запускается в информирующем режиме — перевод в блокирующий (required status check в защите ветки) отдельное решение и настройка владельца. Реальные стековые PR не создаются.

## 2. Контекст и Границы (Context and Scope)
*   **Где делаем:** `.github/workflows/` (отдельный workflow без установки PHP/Node); при необходимости чистая функция определения пересечений и скрипт сбора метаданных в `bin/` или `scripts/`; тесты в `tests/`
*   **Текущее поведение:** правило существует только в `AGENTS.md` (раздел «Pull Request»); нарушение обнаруживает постфактум защита ветки через устаревание апрувов. В `bin/`, `.github/`, `Makefile` и `composer.json` готового детектора нет (проверено консультацией архитектора)
*   **Границы (Out of Scope):** изменение текста правила в `AGENTS.md`; автоматическая переделка/закрытие веток; обход защиты (`--admin`); распознавание эквивалентных патчей после squash/переписывания истории; перевод других правил в проверки

## 3. Требования, MoSCoW (Requirements)
### 🔴 Обязательно (Must Have)
- [ ] Контракт детектора зафиксирован до реализации: множество коммитов, направление зависимости (симметрия пересечения — не выдумывать направление), случай PR с целью в исходную ветку другого PR, область сравнения для разных целей, поведение при частичном пересечении (родитель получил коммиты после ответвления потомка). Охват целевых веток фиксируется в контракте: либо все цели, либо осознанное ограничение с явным объявлением неподдерживаемых сценариев — тогда обещание их обнаружения из требований убирается
- [ ] Три исхода проверки: нарушение / отсутствие нарушения при полном снимке / невозможно проверить (ошибки API, неполные страницы, гонки) — третий исход не «зелёный»; повторы и ожидание ограничены
- [ ] Допуск hotfix-веток от production tag (`hotfix/x.y.z-*` от `vX.Y.Z`) — по факту базы, не по имени: ветка с именем `hotfix/*`, содержащая чужую открытую работу, нарушением считается
- [ ] Актуальность статуса: механизм пересчёта при изменении других открытых PR (открытие/обновление/смена базы/закрытие) выбран на проектировании — централизованный пересчёт либо явно маркированный снимок; снимок не выдаётся молча за гарантию блокирования
- [ ] Ограничение GitHub API (список коммитов PR — не более 250 записей): стратегия для больших историй выбрана на проектировании; молчаливое усечение недопустимо
- [ ] Безопасность: минимальные права токена; код из PR не исполняется; данные PR не подставляются в команды оболочки; чистая функция определения пересечений отделена от сетевого сбора; тесты работают без GitHub и секретов
- [ ] Сообщение сообщает об общей неслитой истории и перечисляет связанные PR, не назначая виновную ветку без доказательства направления; инструкция «переделать ветку от целевой» — только для подтверждённого потомка; ссылка на правило `AGENTS.md` обязательна
- [ ] Логика определения стека покрыта автоматическим тестом на синтетических сценариях (заглушки API / фикстура с обезличенными метаданными инцидента PR #409–#414): стек отклоняется; обычная ветка, устаревшая обычная ветка и hotfix-ветка от production tag — пропускаются; создание реального стекового PR запрещено правилом и не используется
- [ ] Тесты детектора явно подключены к локальным проверкам и CI (текущий CI не вызывает `make check` целиком — подключение не произойдёт автоматически)
- [ ] Режим пилота — информирующий до подтверждения алгоритма и механизма актуализации; разделены три уровня: результат детектора, заключение задания GitHub Actions, обязательность статуса в защите ветки (required status check настраивается в GitHub отдельно от workflow). Решение о блокирующем статусе принимает владелец и фиксируется в задаче
### 🟡 Желательно (Should Have)
- [ ] Отдельный workflow без установки PHP/Node, не ограниченный только целями `main`/`release/**` — либо осознанное ограничение области целей, зафиксированное на проектировании
- [ ] Локальная предварительная проверка той же логикой перед публикацией ветки — ранняя обратная связь
- [ ] Заметка в `CHANGELOG.md`, если проверка меняет поведение contributors-пайплайна
### ⚫ Не будем делать (Won't Have)
- [ ] Изменение правила в `AGENTS.md`
- [ ] Автоматическое закрытие стековых PR или принудительный push
- [ ] Распознавание эквивалентных патчей после squash/переписывания истории (более дорогая эвристика — вне пилота)
- [ ] Перевод других прозаических правил в проверки (только один пилот)

6. [ ] Приёмка (`AC`): прогон тестов; решение владельца о режиме (информирующий/блокирующий) зафиксировано

## 7. Риски и зависимости (Risks and Dependencies)
- **Ложные срабатывания** — главный риск: обычный PR, не перебазированный после чужого мержа, не должен считаться стеком; надёжность признака зависит от точного множества коммитов, актуального списка открытых PR и определённой области целей — полная матрица сценариев в [консультации архитектора](../docs/agents/reports/system-architect-gandalf/2026-09-29_21-07_retro-epic-decomposition-consultation.md), раздел 2
- **Актуальность статуса** — скрытая сложность: результат зависит от других PR и состояния цели; сигнал может остаться после слияния/закрытия базового PR либо появиться у проверенного ранее PR без изменения его коммитов
- **События GitHub**: `pull_request` не запускается при конфликте слияния; смена базы отслеживается событием `edited`; `pull_request_target` опасен исполнением кода из PR
- **Обязательность статуса**: required status check настраивается в защите ветки GitHub отдельно от workflow — файл workflow сам по себе не блокирует merge; настройка — решение и действие владельца
- **Подключение тестов**: текущий CI не вызывает `make check` целиком — тесты детектора подключаются явно и локально, и в CI
