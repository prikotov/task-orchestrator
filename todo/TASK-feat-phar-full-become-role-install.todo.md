# TASK-feat-phar-full-become-role-install: Полная поддержка `agent:init`/`become-role` в PHAR

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)

Пользователь PHAR-дистрибутива не может установить общий навык `become-role` командой `agent:init`: команда намеренно завершается с ошибкой до любых изменений. Из-за этого для полной настройки ролей и навыков приходится переходить на Composer-дистрибутив, хотя остальные необходимые команды доступны непосредственно из PHAR.

### Варианты или путь решения (Solution Sketch)

Добавить в PHAR ресурсы `become-role` и безопасно устанавливать их в host-проект как управляемую копию вместо недопустимого симлинка на `phar://`. Существующее source/Composer-поведение с симлинком сохранить без изменений. Повторный запуск должен быть идемпотентным, а замена отличающегося целевого каталога должна выполняться только с `--force`.

### Ожидаемый результат (Expected Result)

Пользователь PHAR запускает `agent:init` тем же способом, что и пользователь Composer-дистрибутива, получает рабочий `become-role` в `.agents/skills/` и может безопасно повторить установку или явно обновить её через `--force`.

## 1. Концепция и Цель (Concept and Goal)

### История (Job Story)

> Когда я использую `task-orchestrator.phar`, я хочу запускать `agent:init` и получать рабочий `become-role`, чтобы настраивать роли и навыки без перехода на Composer-дистрибутив.

### Цель по SMART (Goal)

В рамках следующего релиза после `v0.2.0` обеспечить для PHAR функционально полный контракт `agent:init`: обычный запуск создаёт или подтверждает актуальную установку `.agents/skills/become-role`, запуск с `--force` безопасно заменяет отличающийся целевой объект, установленный скрипт разрешает тестовую роль, а source/Composer-сценарии остаются без регрессий. Полная поддержка относится к функции `agent:init`/`become-role` и не меняет общий статус PHAR как secondary/best-effort канала дистрибуции без отдельного архитектурного решения.

### Текущее поведение

- После выполнения зависимости `TASK-fix-v0-2-0-phar-become-role-distribution` `agent:init` в PHAR fail-fast завершается с кодом `1`, рекомендует Composer и не пишет в host-файловую систему.

- `box.json.dist` включает `docs/agents/roles`, но не включает `docs/agents/skills/become-role`.
- `bin/phar-smoke` защищает текущий негативный no-write контракт PHAR; в этой задаче он должен быть заменён позитивной проверкой установки.

### Границы (Out of Scope)

- Не менять source/Composer-механизм установки через относительный симлинк и его публичное поведение.
- Не менять контракты `agent:role-skills`, `agent:token`, `agent:run` и `validate:connectivity`.
- Не создавать универсальный managed-copy installer для произвольных skills или ресурсов; копирование ограничено встроенным каталогом `become-role`.
- Не добавлять fallback `symlink -> copy` для source/Composer.
- Не добавлять новые зависимости, self-update PHAR, подпись PHAR, Windows CI или иные общие гарантии PHAR-канала.
- Не изменять ограничения уже выпущенного `v0.2.0`; новый контракт документируется только для релиза, содержащего эту задачу.
- Не выполнять несвязанный рефакторинг файловой логики и соседних команд.

## 7. Риски и зависимости (Risks and Dependencies)

- Выполненная зависимость: `TASK-fix-v0-2-0-phar-become-role-distribution` зафиксировала безопасный fail-fast контракт `v0.2.0`, который эта задача заменяет только в следующем релизе.
- `phar://` поддерживает чтение, но не является обычным каталогом host-файловой системы; рекурсивное копирование, сравнение файлов и обработка прав доступа должны проверяться на реально собранном PHAR, а не только на fixture.
- Неатомарная замена непустого target может уничтожить пользовательские изменения или оставить частичную установку. Реализация должна сначала подготовить и проверить новую копию и иметь контролируемое восстановление при ошибке замены.
- Обычные файловые системы не дают переносимой атомарной замены одного непустого каталога другим. Между `target -> backup` и `staging -> target` остаётся короткое окно; блокировка защищает от кооперативного параллельного `agent:init`, но не от `SIGKILL`, отключения питания и внешнего изменения файлов. При невозможности отката backup должен сохраняться для ручного восстановления, а не удаляться ради формальной очистки.
- Сравнение только наличия `SKILL.md` даёт ложную идемпотентность для устаревшей или повреждённой копии; проверка должна учитывать весь упакованный каталог `become-role` и типы файлов.
- Враждебный или случайный симлинк в target создаёт риск записи вне host-проекта; операции не должны следовать по target-симлинку.
- Скопированный `become-role.sh` больше не находится внутри package tree и сам не способен обнаружить PHAR. Служебная runtime-привязка к физическому пути архива обязательна; перемещение PHAR делает установку устаревшей до повторного `agent:init --force`.
- Box может не сохранить ожидаемые права файла; запуск через `bash` обязателен в smoke-тесте, а необходимость прямого executable-bit должна быть явно проверена до обещания такого контракта.
- Изменение документации не должно противоречить действующему RFC: full support относится только к `agent:init`/`become-role`, PHAR в целом остаётся secondary/best-effort.
- Полный PHAR smoke зависит от доступности Box в локальном или CI-окружении.
- Follow-up (последующая работа): заморозка `roles_dir`/других runtime layout-путей в скомпилированном контейнере и накопление кеш-корней после перемещения PHAR вынесены в отдельную backlog-задачу [`TASK-fix-phar-runtime-layout-cache`](backlog/TASK-fix-phar-runtime-layout-cache.todo.md). Эти наблюдения не изменяют выполненные критерии и scope текущей задачи.
- Follow-up (последующая работа): ложный внешний код `141` и оборванная сводка после успешных запусков сабагентов, наблюдавшиеся при выполнении этой задачи, вынесены в [`TASK-fix-watch-subagent-sigpipe-exit-141`](backlog/TASK-fix-watch-subagent-sigpipe-exit-141.todo.md). ## 9. Комментарии (Comments)

Архитектурное ограничение задачи: управляемая копия допустима только как специализированный PHAR-механизм установки встроенного `become-role`. Обобщение этого механизма на другие ресурсы требует отдельного решения и отдельной задачи. Ожидаемое дерево PHAR-установки состоит из полного встроенного дерева skill и одной служебной runtime-привязки внутри exact target; никаких файлов рядом с target или в других каталогах host-проекта установщик не создаёт.

QA-3 и FR-2/FR-4 отслеживаются отдельно в [`TASK-fix-phar-runtime-layout-cache`](backlog/TASK-fix-phar-runtime-layout-cache.todo.md): новая задача отвечает за актуализацию runtime layout и жизненный цикл устаревших PHAR-кешей, не расширяя текущую реализацию `agent:init`/`become-role`.
